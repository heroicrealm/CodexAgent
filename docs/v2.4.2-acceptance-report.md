# Акт приёмки V2.4.2 — Recovery reconciliation after db restore

**Репозиторий:** `heroicrealm/CodexAgent`  
**Рабочая ветка:** `V2_4_2_RECOVERY_RECONCILIATION`  
**Дата приёмки:** 2026-11-13  
**Решение заказчика:** **ЭТАП V2.4.2 ПРИНЯТ**  
**Статус публикации:** отчёт подготовлен в рабочей ветке; PR и merge не выполнялись.

## 1. Предмет приёмки

Проверена процедура восстановления после `db restore`: глобальная блокировка
`recovery_required`, консервативная внешняя сверка GitHub/Git/SQLite,
автоматическое применение доказанных состояний, индивидуальный карантин
неопределённых Issues и административные решения `accept`, `retry`, `cancel`
в согласованных границах. В рамках этапа также реализованы миграция схемы
1→2 через `db upgrade`, наблюдаемость recovery, Rich CLI и `--json`,
диагностика Git worktree и исправление операций SQLite backup/restore.

Архитектурные решения A2, A2.1, R1, T2 сохранены: независимые Issues
после безопасной сверки не блокируются глобально; карантин нельзя
снять автоматически; изменяющие административные действия требуют
остановленного диспетчера; после retry нужен новый `dispatcher:approve`.

фиксируют сообщённое заказчиком ручное тестирование, а не автоматические
тесты агента.

## 3. Исправление выявленных замечаний

### 3.1. Отложенная синхронизация GitHub-меток

Решено **не изменять** поведение: recovery обновляет SQLite, а после
обычного запуска диспетчер приводит GitHub-метки к соответствующему статусу.
Проверку результата recovery до запуска выполняют через CLI `status`.
Отсутствие немедленной метки `dispatcher:done` не означает отказа
`recover` или `accept`.

### 3.2. WAL/SHM у рабочей SQLite после backup

Причина подтверждена синтетическим воспроизведением: source-соединение
`mode=ro` в WAL-режиме может оставлять WAL/SHM даже после явного
`sqlite3.Connection.close()`. Рабочая БД теперь открывается через
`mode=rw`; SQLite сама выполняет безопасную очистку после последнего
клиента. При работающем диспетчере online backup допускает сохранение
используемых другими подключениями sidecar.

### 3.3. WAL/SHM у входной резервной копии после restore

Restore теперь читает `main+WAL` через приватную временную копию, без
непосредственного открытия пользовательского backup в SQLite. Убрано
ручное удаление рабочего WAL/SHM; после создания `before-restore-*`
повторяется `quiescent()`. Сохранены запреты при неопределённой
остановке, точная схема, identity, защита архива и atomic replace.

Подробные доказательства и тесты:
[v2.4.2-wal-shm-fix-report.md](v2.4.2-wal-shm-fix-report.md).

По отчёту Codex-агента после **последней** корректировки WAL/SHM:

- профильный прогон `tests/test_db_guard.py tests/test_storage.py tests/test_recovery.py`:
  **145 passed in 20.47s**;
- полный `python -m pytest -q`: **391 passed in 56.36s**;
- `git diff --check`: **PASS**.

До исправления новые регрессионные тесты воспроизводили проблему
(`2 failed, 33 deselected` на исходном `db_guard.py`).
Тесты использовали временные синтетические SQLite/Git, а не

отдельный запуск тестов при подготовке данного акта не выполнялся.

## 5. Ограничения и безопасность

- Восстановление не возвращает необнародованные результаты Codex, не
  откатывает GitHub и не реконструирует неизвестные попытки исполнения.
- При конфликтах сохраняется fail-closed и карантин; независимые задания
  могут выполняться после снятия общего барьера.
- `retry` уничтожает только подтверждённо принадлежащие локальные артефакты
  и требует явного согласия и нового подтверждения.
- Online backup не гарантирует отсутствия WAL/SHM при живых подключениях;
  исходная БД должна позволять открытие `mode=rw`.
- Restore не должен использоваться одновременно с произвольным сторонним
  процессом, игнорирующим протокол блокировки.
- GitHub-метки синхронизируются после запуска диспетчера, не обязательно
  сразу после `db recover`/`accept`.

## 6. Заключение

**Этап V2.4.2 принят 2026-11-13.** Основные положительные сценарии
восстановления, карантина, `accept`, `retry` и исправление WAL/SHM
подтверждены ручным испытанием заказчика. Регрессионный набор, по отчёту
агента, прошёл полностью. Оставшееся известное эксплуатационное ограничение
о задержанной синхронизации меток признано допустимым и документировано.

`V2_4_2_RECOVERY_RECONCILIATION` для CI GitHub и последующего слияния
после отдельного подтверждения. Настоящий акт сам по себе не подтверждает
прохождение будущего CI и не фиксирует merge.
