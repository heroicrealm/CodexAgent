**Статус: ПРИНЯТО пользователем 2026-11-07.**

Рабочая ветка: `V2_3_IMPLEMENTATION`. Реализован только каркас и Storage.
Подэтапы B/C, работа с GitHub/Git/Codex и PR не выполнялись.

## Файлы и компоненты

- `pyproject.toml`: независимый пакет V2, Python >=3.11, PyYAML, pytest,
  включение SQL в пакет и отдельный каталог тестов.
- `src/dispatcher/schema.sql`: нормативные 8 прикладных таблиц и 11 явных
  индексов с уточнениями групп/корректировок и четырьмя полями INPUT/OUTPUT. Внутренние sqlite_sequence и
  автоматические индексы SQLite в эти числа не входят.
- `src/dispatcher/storage.py`: атомарное создание schema version 1, проверка
  версии, точного DDL, целостности и FK; отказ от несовместимых БД без миграции;
  соединения FK/WAL/5000 ms; UTC ISO 8601; регистрация и материализация,
  виртуальный родитель со связью, CAS с историей, BEGIN IMMEDIATE резервирование,
  однократный маркер запуска, PR и ошибки, закрепление веток на корне группы;
  `commit_approval` атомарно фиксирует постановку, ID/текст INPUT, исходный YAML,
  hash/время, состояние и историю; `record_confirmed_output` сохраняет ID/текст
  только подтверждённой публикации OUTPUT. Повторный approve снимок не меняет.
  Проверяются полнота INPUT и синтаксис YAML/mapping; прикладная схема параметров,
  полнота внешнего чтения и решение о готовности остаются обязанностью StateService B.
  Publisher B должен вызывать запись OUTPUT только после подтверждения GitHub;
  Storage не выполняет публикацию и не может самостоятельно проверить её факт.
- `src/dispatcher/models.py`: канонические состояния V2.1, типы наблюдений,
  утверждённого снимка (включая ID/текст INPUT) и результатов. Резервирование: pending → preparing,
  статус execution при этом reserved. awaiting_children не вводится.
- `src/dispatcher/contracts.py`: Protocol для всех десяти компонентов V2.2.
  Прикладные сервисы не имеют исполняемой реализации. Storage CAS — примитив,
  а не StateService: разрешённость бизнес-перехода и approve проверяются в B.
- `src/dispatcher/config.py`, `config/config.example.yaml`: отдельные пути V2,
  загрузка YAML, глобальная карта меток с точечными переопределениями проекта,
  проверки ключей/коллизий, разные running/manual-running, preparing без метки.
  Значение off поддерживается также при YAML-разборе его как False.
- `src/dispatcher/diagnostics.py`: off/api/verbose, poll_id, безопасные поля,
  retention 7 дней, очистка при создании logger и максимум раз в сутки на экземпляр
  (в том числе при сбоях), best-effort. Свободные сообщения ошибок/выводы команд
  не записываются: result/component/operation — короткие технические коды,
  endpoint — шаблон маршрута без URL/query; лишние context-поля отбрасываются.
  Вызывающий код обязан передавать именно технические коды, не секреты.
- `src/dispatcher/__init__.py`: граница независимого пакета.
- `tests/test_storage.py`, `tests/test_config_diagnostics.py`, `tests/test_comments.py`: проверки A.
- `.gitignore`: исключены новые runtime-v2/workspace-v2.

## Вопросы перед B

1. V2.1 §5 фиксирует учитываемых детей при preparing и сохраняет исторические
   связи; V2.2 DDL хранит только пары parent/child без признака учитываемости,
   а T14 предусматривает удаление связи. Требуется определить, как сохранить
   замороженный состав и что делать при удалении связи. Схема A не расширялась.
2. Вопрос хранения INPUT/OUTPUT закрыт утверждённым уточнением и реализован в A.
   Для ожидающей очистки ресурсов V2.1 по-прежнему требует хранение, но DDL
   не содержит отдельного представления; перед B нужно согласовать его либо
   восстановление из существующих данных.
3. Условие регистрации корректировки в уточнении требует разрешённой группы,
   тогда как V2.1 привязывает need-fix прежде всего к approve. В A регистрация
   корректировки требует наличия need-fix в незавершённой группе (источник может
   быть любой предыдущей Issue). Следует подтвердить, допустима ли более ранняя
   регистрация discovered до need-fix с запретом только утверждения.
4. Проверка структуры намеренно строгая: сравнивается нормативный DDL, поэтому
   даже семантически эквивалентная вручную пересозданная схема отклоняется.
   Автоматического исправления/миграции нет.

Конфигурация предотвращает пути внутри каталога V1 данного репозитория, но
не распознаёт произвольно размещённые внешние workspace V1. Отдельность таких
путей задаётся оператором. Неподходящая схема БД всё равно отклоняется.

PR не создан; V2.3.A принят, общий PR планируется после завершения V2.3.

## Итог приёмки V2.3.A — 2026-11-07

**Решение пользователя: подэтап V2.3.A принят.** Реализованы независимый каркас V2, начальная схема SQLite (8 таблиц, 11 явных индексов, schema version 1), Storage с транзакциями, контракты компонентов, двухуровневая конфигурация GitHub-меток, диагностический журнал и хранение INPUT/OUTPUT. По отчёту агента: **46 passed**, `compileall` и `git diff --check` успешны. Ревизия кода проведена через GitHub; независимого локального запуска тестов при этой приёмке не было. Интеграция с реальным GitHub, Git и Codex CLI не проверялась и относится к следующим подэтапам.

**Обязательства для V2.3.B:**
1. Не использовать постоянные счётчики Sub-issues (решение V2.2). Новые связи, появившиеся после перехода родителя в `preparing`, не учитывать; поздние связи не должны блокировать продолжение уже начатой работы.
2. Корректирующая Issue без существующего разрешения `need-fix` не регистрируется; обычная Issue с `codex-ready` не требует этого разрешения.
3. Разобрать восстановление незавершённой очистки ресурсов из существующих данных и при необходимости согласовать минимальное дополнение SQLite **до** разработки соответствующих процедур.
4. Реализовать бизнес-валидацию StateService и Publisher поверх Storage: INPUT берётся при approve, OUTPUT фиксируется после подтверждённой публикации.
5. Устаревшие формулировки раздела «Вопросы перед B» выше отражают первоначальный отчёт агента; решения по регистрации корректировок и поздним детям подтверждены пользователем, вопрос очистки остаётся открытым.
