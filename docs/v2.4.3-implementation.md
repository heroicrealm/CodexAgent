# V2.4.3: реализация CLI и блокировка purge

Статус: **реализация неполная; полная приёмка V2.4.3 заблокирована purge**.
Рабочая ветка `V2_4_3_CLI_MONITORING`. PR и merge не выполняются.

## Изменения и организация

- `config.py`: единый resolver, обязательный абсолютный YAML root_path, относительные пути от root_path; прямое создание Config в unit fixtures сохраняется.
- `__main__.py`: парсинг status/queue/show/project, ожидаемые ошибки и exit codes, JSON/Rich маршрутизация без Runtime для мониторинга.
- `monitoring.py`: read-only query-layer на приватном main+WAL snapshot через существующий DB Guard inspection; schema/integrity/FK/UUID/marker checks, query_only. Проверки и чтение выполняются над одним snapshot. Исходные SQLite/WAL/SHM не изменяются, Recovery barrier не снимается.
- `monitoring_output.py`: Rich таблицы/панели, буквальный Text без исполнения Rich markup из пользовательских строк; JSON без ANSI. Полный финальный ответ переносится, длинные ячейки таблиц обрезаются.
- `runtime.py`: только публикация локальных оперативных метаданных; планирование и исполнение не менялись. Ошибка записи метаданных не останавливает runtime.
- `services.py`: существующие проверки дочерних зависимостей вынесены в общий helper `child_reasons_db`; evaluate и список Blocking Children используют одинаковые правила. Переходы состояний не менялись.
- `projects.py`: atomic YAML editor, локальная валидация, remote read-only admission, list/show/add/enable/disable/remove.
- `purge.py`: только read-only inventory и явная блокировка разрушительного режима.
- `tools/worktree_cleanup.py`: общий config resolver, диагностика config ошибок.
- `config/config.example.yaml`, README: пути, установка, команды, ограничения Recovery/purge.
- `tests/test_monitoring_projects.py`: новые локальные тесты. YAML fixtures существующих тестов адаптированы к root_path в test_db_guard, test_execution_cleanup, test_recovery, test_worktree_diagnostics.

Схема данных, триггеры, InstanceLock, UUID, механизм backup/restore, admission
Recovery, штатные GitHub API вызовы poll и архитектура единственного исполнителя
не менялись.

## Команды и вывод

Реализованы `status [--json]`, `queue [--project ID] [--state STATE] [--all]
[--json]`, `show ID NUMBER [-v|--verbose] [--json]`, `project list/show/add/
enable/disable/remove`; `remove --purge --dry-run` — inventory с блокировками,
`remove --purge` — отказ без изменений.

Содержание Rich status (рамки формируются Rich):

```text
CODEX DISPATCHER · STATUS
Daemon: STOPPED
Database: OK · Recovery: READY
Last poll: N/A
Next poll: N/A
Executing: IDLE
№  Project             Open  Disc.  Appr.  Review  Reject  Error
1  Playground             3      1      1       1       0      0
2  Other (disabled)       0      0      0       0       0      0
   TOTAL                  3      1      1       1       0      0
```

Цифры в примере условные. status считает все открытые реальные Issue, включая
терминальные с последним github_state=open; queue по умолчанию дополнительно
исключает done/cancelled. Порядок проектов конфигурационный. Состояния очереди
от error до discovered, архив в конце; preparing/running имеют равный приоритет,
возраст сравнивается по timestamp, при равенстве — номер Issue. Missing history
даёт N/A. JSON не удаляет поля project/state при фильтрации.

## Достоверность показателей

- RUNNING: обе блокировки заняты, настоящий UNIX socket, свежая `.monitor.json`
  (менее 10 секунд), UUID и Linux PID/starttime совпадают. STOPPED: обе свободны,
  socket отсутствует. Иначе UNKNOWN. Блокировки проверяются без создания файлов.
- Метаданные пишутся атомарно, с mode 0600, примерно раз в секунду в coordinator
  loop. Last poll означает завершённый проход проектов (включая проход с ошибкой);
  Next poll публикуется по существующему интервалу. Во время долгого poll heartbeat
  может протухнуть: UNKNOWN безопаснее ложного RUNNING. После остановки Last/Next
  не выдаются за актуальные сведения живого daemon.
- Executing берётся из preparing/running, elapsed — executions.started_at
  (резервирование). При недоказанном daemon показывается unverified. manual-running
  не считается автоматическим слотом.
- Age: последний фактический переход state_history, совпадающий с текущим state;
  повторные наблюдения и issues.updated_at не влияют.
- Blocking Children: только зарегистрированные реальные issue_relations и тот же
  helper GroupService, включая unfinished, quarantined, неверную базу merged PR и
  удалённую ready при открытом PR. Самостоятельных правил готовности в renderer нет.
- stdout ProcessRunner сохраняется Executor в results/execution_id.txt. Plain
  stdout показывается без перефразирования; известный Codex exec JSONL разбирается
  до последнего завершённого agent_message. Произвольный JSON финального ответа
  сохраняется как текст. Прежний output_body и файл предыдущей попытки не берутся.
  Проверены сохранение в существующем Executor и синтетические stdout/JSONL fixtures;
  live запуск установленного Codex CLI не выполнялся.
- Timeline включает только сохранённые state_history/recovery_events и известные
  даты executions/PR. JSON сохраняет полные значения выбранных полей; human вывод
  ошибок исключает вложенные stdout/stderr/traceback из diagnostic JSON.

## Project add и сохранение YAML

Перед API проверяются синтаксис, дубли ID/repository и retained SQLite history
(issues/debug_operations). Затем `gh api GET /repos/owner/repo`: доступность,
идентичность repo, отсутствие archived/disabled и has_issues=false, доступные
permissions.pull/push. Явный false запрещает add; API ошибки, включая 403/404,
сетевые и неопределённые ошибки запрещают add. Затем SSH `git ls-remote` с
BatchMode, без интерактивного запроса пароля: тот же transport, что runtime clone.
API и SSH — разные учётные данные. Вся проверка read-only, без тестовых GitHub writes.

Repository push permission не доказывает token-specific Issues/PR/labels writes.
Неполные свидетельства дают явный WARN, а не утверждение о доказанных правах.
Вызовы не добавлены в штатный poll.

CLI writers сериализуются flock на соседнем `.lock`. Под блокировкой читается
актуальный YAML; сохраняются неизвестные пользовательские ключи. Сформированный
YAML проверяется через load_config, временный файл 0600 fsync, atomic replace,
fsync родителя. При обнаруженном внешнем редакторе — отказ без перезаписи его
изменений. Форматирование и комментарии PyYAML не сохраняет. После изменений всегда
`Restart dispatcher to apply changes`; работающий daemon не перечитывает YAML.

## Purge: конкретный блокер и сохранность

Существующие `recovery_events_no_update` / `recovery_events_no_delete` намеренно
делают события append-only. `recovery_events.issue_id` и `.operation_id` имеют FK
на удаляемые issues/recovery_operations. Полное удаление истории репозитория с
такими событиями невозможно обычным DELETE с сохранением этих гарантий. Удаление
триггеров, отключение FK, ручной SQL или скрытая подмена DB не реализованы.

Требуется согласовать, как сочетаются полное удаление локальной истории и
неудаляемый Recovery audit: отдельная одобренная политика архивации и отвязки FK
либо явно разрешённое удаление аудита при контролируемом purge. Это затрагивает
защиты/схему V2.4.2 и выходит за разрешённый объём. Никакой миграции не выполнено.

Согласно исключению в фазе D задания безопасный упрощённый destructive purge
**не выдаётся за готовую функцию**. Для любых проектов destructive режим пока
отказывает. Нет confirmation prompt, backup, удаления Git/files/SQLite/YAML или
журнала удаления: выполнение не доходит до разрушительных фаз. Поэтому тесты
backup/resume/interrupted destructive purge и повторного add после purge отсутствуют;
они остаются обязательными для следующей реализации после согласования.

Dry-run показывает реальные количества project-scoped issues/relations/history/
executions/PR/errors/debug/recovery, известные пути результатов/worktree и рабочие
ветки из SQLite, checkout и каталог worktree. Это **inventory кандидатов**, не полная
проверка принадлежности Git refs, orphan worktree и архивных файлов. `executable:
false` и blockers печатаются явно. Нет Git, GitHub, изменения данных или lock files.

Сохраняются вся SQLite, Recovery audit, исходные результаты и checkout, shared
workspace, данные чужих проектов, YAML и все объекты GitHub. Повторный запуск
заблокированного purge снова безопасно отказывает. Обычный remove удаляет только
проект из конфигурации; повторный add repo с историей запрещён.

Будущий согласованный destructive алгоритм обязан включать: полный проверенный
план и exact-ID TTY confirmation; InstanceLock/отсутствие socket/опасных sidecars;
DB Guard/Recovery admission; доказательство собственности и отсутствия shared
ресурсов; проверенный Backup API snapshot; устойчивый журнал фаз; безопасные Git
worktree/ref операции; FK-correct SQLite transaction и YAML только после успешной
очистки. Ни одна из этих гарантий не заменяется текущим inventory.
