# Codex Dispatcher как пользовательская служба Ubuntu Server

## Установка и авторизация

Используйте отдельную учётную запись Ubuntu с доступом к тестовому проекту,
workspace, SQLite и Git checkout. Установите Standalone с поддержкой V2.5.3.
Для приёмки до публикации можно установить собранный wheel в отдельный venv
на выделенной учётной записи с незанятым путём CLI:

```sh
python3 -m venv "$HOME/codex-dispatcher-candidate"
"$HOME/codex-dispatcher-candidate/bin/pip" install /absolute/path/to/candidate.whl
mkdir -p "$HOME/.local/bin"
ln -s "$HOME/codex-dispatcher-candidate/bin/codex-dispatcher" "$HOME/.local/bin/codex-dispatcher"
export PATH="$HOME/.local/bin:$PATH"
```

Штатная поставка использует тот же путь CLI через переключаемую `.venv`.
Для проверки обновления пакета S13 нужна именно Standalone-установка и второй
совместимый bundle. Для непубликованного bundle используйте изолированную подмену Release API,
описанную в [регламенте выпуска](releasing.md) и `scripts/smoke-install.py`.

Под пользователем службы один раз выполните `gh auth login`, `gh auth setup-git`
и `codex login`. Проверьте `gh auth status` и `codex login status`. Unit задаёт
`HOME`, рабочий каталог домашнего пользователя и PATH из `~/.local/bin` и
системных каталогов. Если Codex установлен через менеджер версий, обеспечьте
доступный из этого PATH CLI или настройте абсолютный `dispatcher.codex_command`.
При установке сохраняются заданные абсолютные XDG-пути для приложений.
Держите credentials в штатных пользовательских хранилищах.

Настройте конфиг и проверьте `codex-dispatcher db check`. Для новой тестовой БД
явно выполните `codex-dispatcher db bootstrap`, затем `codex-dispatcher init-labels`.
При нестандартном конфиге ставьте `--config /absolute/test.yaml` перед подкомандой.

```sh
codex-dispatcher service install
# Выполнить администратору, подставив имя пользователя службы.
loginctl enable-linger USER
codex-dispatcher service start
codex-dispatcher service status
codex-dispatcher service logs -n 50 -f
```

Установка регистрирует и включает unit. Старт выполняется отдельно. Если
`systemctl --user` сообщает о D-Bus, проверьте вход под нужным пользователем через
SSH с PAM, `loginctl show-user USER -p Linger -p RuntimePath` и
`systemctl --user status`. Если manager использует нестандартные пути поиска,
проверьте `systemd-analyze --user unit-paths` и наличие
`~/.config/systemd/user` в списке. Для диагностики ошибок запуска проверьте
`service status`, `service logs`, версию CLI, путь конфига, `db check` и
`db recovery status`. После устранения причины `start-limit-hit` выполните
`systemctl --user reset-failed codex-dispatcher.service` и `service start`.

## Остановка, обновление и удаление

```sh
codex-dispatcher service stop
codex-dispatcher service status
codex-dispatcher status --json
codex-dispatcher-install
codex-dispatcher --version
codex-dispatcher service start
```

Используйте тот же глобальный `--config` в команде runtime `status`, если он
был указан при регистрации. Продолжайте обновление после `ActiveState=inactive`,
`MainPID=0` и `daemon.state=STOPPED`. При `UNKNOWN` разберите состояние
процессов и locks. Installer дополнительно проверяет остановку и удерживает
блокировку поколения при переключении. При несовпадении SHA обновите installer
вручную по [инструкции Standalone](standalone.md). Старт после обновления
выполняйте только после проверки версии и конфигурации.

Управляйте службой через `service stop` или
`systemctl --user stop codex-dispatcher.service`. Stop ждёт завершения задачи и
публикации. `service restart` выполняет stop и последующий start одним заданием
systemd. Внутренний `stop [--force]` управляет foreground runtime через сокет.

Для удаления выполните `codex-dispatcher service uninstall`, затем при
необходимости `codex-dispatcher-uninstall`. Service uninstall останавливает
службу, отключает автозапуск и удаляет управляемый unit. Данные, журналы и linger
сохраняются.

## Ручная приёмка S01–S19

Проведите на Ubuntu Server с отдельным пользователем и тестовым GitHub-репозиторием.
Зафиксируйте SHA сборки, версии Ubuntu/systemd/Codex, дату, результаты, номера
Issue и PR. Для сбоев S10, S11, S15 и S17 используйте тестовые данные.
Все сценарии ожидают прогона. WSL2 и CI не заменяют эту проверку.

```sh
unit=codex-dispatcher.service
unit_file="$HOME/.config/systemd/user/$unit"
```

| Код | Действие и ожидаемый результат |
| --- | --- |
| S01 | Выполните `codex-dispatcher service install` и `systemd-analyze --user verify "$unit_file"`. Проверьте `systemctl --user is-enabled "$unit"` и `service status`. Unit валиден, включён, состояние inactive. |
| S02 | Запишите `stat -c '%i %a' "$unit_file"` и `sha256sum "$unit_file"`, повторите install и сравните. Inode, права и содержимое совпадают. |
| S03 | Выполните `codex-dispatcher service start` и `codex-dispatcher service status`. Ожидаются active и ненулевой MainPID. |
| S04 | При `Linger=yes` закройте все SSH-сессии пользователя. С отдельной административной учётной записи проверьте сохранение PID и отсутствие его SSH-сессий через `loginctl list-sessions`. |
| S05 | Перезагрузите сервер. До входа пользователя службы проверьте с административной учётной записи `systemctl status "user@UID.service"` и наличие процесса диспетчера. Сверьте время старта службы с временем будущего входа. |
| S06 | На изолированном пользователе остановите службу и сделайте тестовый конфиг без включённых проектов. Для проверки запуска с недоступным GitHub используйте временный loopback-прокси с закрытым портом, как в команде ниже. Ожидаются предупреждение об обновлениях и exit 0. |
| S07 | Создайте тестовую Issue, добавьте `dispatcher:codex-ready`, затем `dispatcher:approve`. Проверьте `codex-dispatcher show PROJECT NUMBER -v`, коммит в удалённой ветке и PR в тестовом репозитории. |
| S08 | Пока Codex обрабатывает новую длительную Issue, вызовите `codex-dispatcher service stop`. Дождитесь возврата команды, проверьте публикацию, inactive и MainPID=0. |
| S09 | Во время активной Issue сохраните MainPID, пошлите два `kill -TERM "$main_pid"` с небольшим интервалом. Убедитесь, что дочерний Codex завершил задачу, публикация прошла и служба осталась остановленной. Запустите её вручную для следующих сценариев. |
| S10 | На бездействующей тестовой службе пошлите `kill -KILL "$main_pid"` и проверьте журнал, новый MainPID и `systemctl --user show "$unit" -p NRestarts`. Ожидается рестарт по политике. |
| S11 | На копии установки с отсутствующей БД либо подготовленным Recovery barrier выполните `service start`. Журнал показывает отказ. Новая БД и новые executions не появляются. Проверьте `db check` и `db recovery status`. |
| S12 | При активной службе выполните `codex-dispatcher run --once` с тем же конфигом. Ожидаются ненулевой exit и один runtime. |
| S13 | Выполните последовательность обновления выше. Сравните `readlink "$HOME/codex-dispatcher/.venv"`, версию CLI и хеш unit до и после. Убедитесь, что unit остался inactive до ручного старта. |
| S14 | После остальных сценариев сохраните хеши остановленной SQLite, конфига и маркера UUID. Выполните `service uninstall`. Unit и enable-ссылка исчезают, хеши совпадают. Для повторного прогона выполните install и start. |
| S15 | В отдельной тестовой учётной записи без авторизации запустите службу и инициируйте тестовую работу. Проверьте диагностику poll или запуска Codex без ожидания ввода. Затем настройте авторизацию вручную. |
| S16 | Выполните `codex-dispatcher service logs -n 20` и `journalctl --user -u "$unit" -b`. Сравните записи. Проверьте `service logs -f` при новом запуске. |
| S17 | При отсутствующем конфиге в изолированной установке дождитесь как минимум 60 секунд после старта. Проверьте `systemctl --user show "$unit" -p Result -p NRestarts` и журнал. Ожидается `start-limit-hit`. Верните конфиг и выполните `reset-failed`. |
| S18 | Пока Codex и его потомки живы, запишите дерево через `systemd-cgls --user-unit "$unit"`. Остановите службу из второго терминала. Проверьте, что Codex жив в начале deactivating, затем штатно завершает работу, а после stop cgroup освобождена. |
| S19 | Выполните отдельный сценарий ниже после выхода из SSH и повторно после reboot. |

Для S06 используйте абсолютный путь тестового конфига с заранее созданной SQLite.
Временная служба не занимает рабочую БД:

```sh
systemd-run --user --wait --pipe --unit=codex-release-offline \
  --setenv=HTTPS_PROXY=http://127.0.0.1:1 --setenv=NO_PROXY= \
  "$HOME/.local/bin/codex-dispatcher" --config /absolute/offline.yaml run --once </dev/null
```

### S19. Настоящий Codex после выхода и перезагрузки

1. На Ubuntu установите и запустите службу с linger. Подтвердите `Linger=yes`,
   active и стабильный MainPID. На административной учётной записи приготовьте
   наблюдение за cgroup и журналом. Из сессии пользователя службы получите
   путь через `systemctl --user show "$unit" -p ControlGroup --value` и сохраните
   его как `cgroup` в административной сессии. Там просматривайте дерево через
   `systemd-cgls "$cgroup"` и журнал через
   `journalctl _UID=UID _SYSTEMD_USER_UNIT=codex-dispatcher.service -b`,
   подставив числовой UID. Закройте все SSH-сессии пользователя службы.
2. С другой машины создайте новую Issue в тестовом репозитории и разрешите её
   выполнение установленными метками. При работающей задаче с административной
   учётной записи найдите PID Codex в cgroup службы. Проверьте
   `ps -o pid,ppid,sid,tty,comm -p "$codex_pid"`,
   `readlink "/proc/$codex_pid/exe"` и `readlink "/proc/$codex_pid/fd/0"` с
   правами на чтение. Сверьте аргумент `exec`, TTY=`?`, stdin в виде pipe с
   промптом, отсутствие tmux/screen и отсутствие интерактивных запросов.
3. Подтвердите push, PR и завершение Codex. Снова проверьте cgroup, журнал и
   состояние Issue. Приложите ссылки на Issue и PR к протоколу.
4. Перезагрузите Ubuntu. До входа под пользователем службы подтвердите автостарт
   и повторите шаги 2–3 с новой Issue. При отказе проверьте stderr/stdout,
   HOME/XDG/PATH, credentials и версию Codex CLI.
