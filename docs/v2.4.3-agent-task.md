# Задание Codex-агенту: реализация V2.4.3 — CLI Monitoring & Project Management

**Репозиторий:** `heroicrealm/CodexAgent`  
**Рабочая ветка:** `V2_4_3_CLI_MONITORING` (создана; выполнять работу ТОЛЬКО в ней)  
**Целевая ветка будущего PR:** `CODEXAGENT_V2`  
**Обязательное утверждённое ТЗ:** [docs/v2.4.3-spec.md](v2.4.3-spec.md)  
**Статус:** задание на реализацию. Приёмку и создание PR выполняем отдельно, после ручных проверок.

## 1. Цель

Реализуй утверждённое ТЗ V2.4.3 целиком, не изменяя принципы работы диспетчера V2.4.2. Результат: удобный человекочитаемый CLI для мониторинга, управление конфигурацией и проектами, безопасное локальное удаление проекта. ТЗ имеет приоритет над этим заданием при расхождении деталей; не сокращай функциональные требования.

Сначала ознакомься с `docs/v2.4.3-spec.md`, затем проверь существующие модули и тесты. Рекомендуемые точки входа: `src/dispatcher/__main__.py`, `config.py`, `storage.py`, `runtime.py`, `services.py`, `execution.py`, `db_guard.py`, `recovery_output.py`, `cleanup.py`, `models.py`, `schema.sql`, `src/dispatcher/tools/worktree_cleanup.py`, `config/config.example.yaml`, `README.md`.

**Не делай предварительно PR и не сливай ветку.** По окончании оставь изменения в рабочей ветке и представь отчёт, команды тестов, ограничения и пошаговую инструкцию ручной проверки.

## 2. Порядок работы

### Фаза A — конфигурация

1. Реализуй общий resolver конфигурации для основного CLI и `worktree-cleanup`: явный `--config` > абсолютный `$XDG_CONFIG_HOME/codex-dispatcher/config.yaml` > `~/.config/codex-dispatcher/config.yaml`.
2. Введи обязательный для новой конфигурации `dispatcher.root_path` (абсолютный путь). Разрешай относительные `database`, `workspace` и `project.checkout` относительно него; абсолютные пути оставь как есть.
3. Не меняй условия идентичности SQLite/workspace. Никакой скрытой миграции прежних файлов и тестовых экземпляров. Адаптируй тестовые фикстуры, пример конфигурации и документацию. Не привязывай путь к CWD или расположению Python entrypoint.
4. Ошибка отсутствия/некорректности конфигурации — понятное сообщение и ненулевой exit code, без Python traceback для ожидаемых ошибок.

### Фаза B — слой чтения и Rich-вывод

1. Сделай общий *read-only* query-layer мониторинга и renderers, не смешивая SQL с форматированием таблиц. Не используй изменяющие методы `Storage.connection()` для обхода Recovery; реализуй безопасное чтение с проверками schema/instance/identity и без side effects.
2. `status`: верхний блок daemon/DB/recovery/last poll/next poll/executing, нижняя таблица именно `№ | Project | Open | Disc. | Appr. | Review | Reject | Error`, строка TOTAL. Значения по открытым реальным отслеживаемым Issue и конфигурационному порядку. Appr. = SQLite `pending`, не временная GitHub-метка approve.
3. Состояние daemon определяй по достоверным локальным признакам. Остаточные `preparing/running` в SQLite после crash не объявляй живым процессом. Механизм публикации last/next poll должен быть минимальным, локальным, устойчивым к stale данным. Не создавай новый daemon/API-server.
4. `queue`: группировка проектами, фильтры `--project`, `--state`, `--all`; скрывай фиксированную колонку State и выноси в заголовок, освобождай место под Title; учитывай `manual-running` и `need-fix`. Сортировка по таблице приоритетов в ТЗ. Возраст состояния вычисляй из `state_history`, НЕ из `issues.updated_at`.
5. `show PROJECT ISSUE`: краткая карточка, `-v/--verbose` с Timeline и диагностикой. Текущий текстовый ответ агента бери из файла результата соответствующего исполнения, не из старого OUTPUT; проверь формат реального stdout. Для `awaiting-children` показывай только фактически блокирующие Issue по существующим правилам `GroupService`, без дублирования бизнес-логики.
6. Rich в стандартном human output, корректность на 80 столбцах, NO_COLOR, stdout pipe. Для `status/queue/show --json` один структурированный документ, без ANSI и потерь значений. Мониторинг не вызывает GitHub API, Git и poll, включая при recovery_required.

### Фаза C — управление проектами

1. `project list`, `show`, `add`, `disable`, `enable`, `remove`, `remove --purge [--dry-run]` по ТЗ.
2. `project add ID REPOSITORY`: сначала локальная валидация ID/repository, конфигурационных дублей и коллизий с локальной SQLite-историей; затем **авторизованные read-only** проверки репозитория на GitHub (существует и доступен), Git-доступности (`git ls-remote`) и доступных сведений о правах записи/Issues/PR. Явно недостаточные права или недоступность/неизвестность из-за ошибки — **FAIL** без изменения YAML; непроверяемые без записи права — **WARN**, разрешить add при успешных обязательных проверках. Не создавать на GitHub тестовые Issue, PR, labels, branches и комментарии. Минимизировать разовые API-запросы.
3. Раздельно учитывай аутентификацию GitHub API и git remote; не утверждай, что права доказаны, если соответствующего API-свидетельства нет.
4. `disable/enable/remove` — изменения только локального YAML. `remove` без purge сохраняет локальную историю, а `add` того же репозитория не должен незаметно повторно подключить старую историю. Переименование `project.id` не реализуй. Изменения вступают в силу только после **restart**; об этом явно сообщай.
5. Изменение YAML атомарное и защищённое от конкурентной записи, с сохранением прочих настроек; права файлов/каталогов безопасные. В случае ошибки YAML остаётся неизменным.

### Фаза D — безопасный `--purge`

**Это наиболее критичная часть задачи. Приоритет — сохранение данных, а не успешное удаление любой ценой.**

1. Реализуй сначала полный *read-only* план очистки: перечень SQLite-строк с FK-зависимостями, результатов Codex, managed worktree, рабочих refs, каталогов. `--dry-run` строго без побочных эффектов и без GitHub.
2. Реальное удаление только при доказанной остановке daemon/Executor и под существующими защитными блокировками, проверках DB Guard/identity, отсутствии глобального recovery barrier, активных блокирующих recovery operations и конфликтующих/shared ресурсов. Не удалять пользовательский внешний checkout. Нельзя автоматически удалять неизвестные каталоги или чужие ветки.
3. Обязательно сохранять проверенную резервную копию SQLite перед разрушительными действиями; предусмотреть прерывание на разных фазах и безопасное повторное завершение без ручного SQL. Если для корректной повторяемости нужен небольшой локальный журнал операции, опиши его в отчёте. Не обходи механизмы безопасности и не добавляй `--force`.
4. Перед выполнением предъявить пользователю реальный план, запросить точный `project.id`. Неинтерактивный запуск без подтверждения — отказ. Не удалять запись в YAML до доказанного успеха очистки.
5. Удаление касается ТОЛЬКО локальных данных. **Никаких GitHub API/remote mutations, включая `git push --delete`.** После purge допускается add прежнего репозитория с новым project.id; старые открытые GitHub Issue с codex-ready могут быть обнаружены снова.

Если в процессе выяснится, что выполнение полного purge требует недоказуемых предпосылок или опасного изменения модели V2.4.2, **не реализуй небезопасный упрощённый вариант**. Реализуй остальные части и явно вынеси конкретную блокирующую проблему для согласования; не выдавай неполный purge за завершённую функциональность.

### Фаза E — тесты и документы

1. Добавь unit/integration tests на все группы из раздела 11 ТЗ. Особенно: ложный running после crash, read-only Recovery, Age из history, блокирующие дочерние Issue, `project add` с отсутствующим repo/403/404/непроверенными правами, конкурентное редактирование YAML, purge без касания GitHub и чужих проектов, отказ при конфликте и прерванный purge.
2. Для сетевых проверок `project add` использовать mocks/stubs, не выполнять настоящие GitHub-записи в тестах.
3. Прогони полный существующий `python -m pytest -q`, исправь регрессии. Дополнительно проверь `--help`, JSON и Rich-представления на терминале 80/120 символов.
4. Обнови README, пример конфига, описание CLI, installation и recovery-ограничений. Явно опиши перезапуск после изменений проектов, различие обычного remove/purge, правила удаления локальных ресурсов и отсутствие изменений GitHub.
5. Не начинай systemd/autostart, перенос WSL2→Linux, горячую перезагрузку, переименование project.id, новые lifecycle-переходы или миграцию V1. Не расширяй схему SQLite без отдельного технического обоснования и указания необходимости согласования.

## 3. Обязательные критерии готовности

- Весь UX `status`, `queue`, `show` по утверждённым колонкам, сортировкам и режимам.
- Человекочитаемый Rich по умолчанию, `--json` машинный; no-color/pipe.
- Мониторинг остаётся локальным и работает при Recovery barrier.
- Отсутствие неожиданных GitHub API вызовов штатных команд просмотра/poll.
- Config resolver и root_path не зависят от текущего каталога.
- `project add` блокирует недоступный repo и явно недостаточные права, WARN если запись не может быть проверена без изменений GitHub.
- `project remove --purge` удаляет только доказанно свои локальные данные, с backup, lock, dry-run, confirmation и устойчивостью к прерыванию.
- Все регрессионные тесты и дополнительные проверки проходят.
- Никаких PR/merge до ручной приёмки.
