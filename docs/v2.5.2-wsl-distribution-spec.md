# ТЗ V2.5.2 — поставка Codex Dispatcher Standalone

Статус: согласованное ТЗ для реализации  
Репозиторий: `heroicrealm/CodexAgent`  
Базовая ветка: `V2_5_1_INFRASTRUCTURE`  
Ветка этапа: `V2_5_2_WSL_DISTRIBUTION`  
Дата: 2026-11-16

## 1. Цель и границы

Поставить диспетчер в режиме Standalone для запуска вручную в Ubuntu под WSL2 и Ubuntu native (без systemd): установка без клонирования исходников, изолированный Python, короткая команда CLI, конфигурация в пользовательском каталоге, безопасное обновление из GitHub Releases, контроль совместимости конфигурации, проверка обновлений и доступности GitHub перед `run`, руководство пользователя.

Не реализуются автозапуск WSL/Windows, служба systemd (вариант Service), Docker (вариант Docker), миграция SQLite, изменение жизненного цикла Issue/PR, обработка сетевого отказа во время выполнения, защита pending/push, автоматическая миграция YAML и обновление самим диспетчером.

Работа в Standalone: пользователь открывает терминал Linux (в WSL2 предварительно запускает WSL), выполняет `codex-dispatcher run`, затем штатно останавливает работу через `codex-dispatcher stop` (либо соответствующий сигнал для foreground). Команды `start` нет и добавлять её не требуется. `run --once` сохраняет текущую семантику. Запуск остаётся в существующем режиме; установщик не превращает его в новую службу.

### Классификация поставок

- **Standalone (V2.5.2):** ручной запуск в Linux-терминале; поддерживаются WSL2 и Ubuntu native; без фоновой службы systemd.
- **Service (следующий этап):** установка и управление постоянно работающей службой systemd на Ubuntu/Linux; переиспользует базовую поставку.
- **Docker (отдельный этап):** контейнерная поставка.

Выбор варианта определяется способом эксплуатации, а не названием ОС. Название ранее созданной рабочей ветки сохранено ради совместимости с текущим процессом, но не определяет область продукта.

## 2. Подтверждённая исходная реализация

Проверено в `V2_5_1_INFRASTRUCTURE`:
- `pyproject.toml`: дистрибутив `codex-dispatcher-v2`, версия `2.3.0a0`, Python >=3.11, entrypoint `codex-dispatcher = dispatcher.__main__:main`, зависимости PyYAML и rich.
- CLI: `run`, `run --once`, `stop`, `stop --force`, `queue`, `status`, `show`, `project`, `db` и др.; нет `start`.
- Сначала необязательный глобальный аргумент `--config /absolute/path`, затем подкоманда.
- Без `--config` используется `$XDG_CONFIG_HOME/codex-dispatcher/config.yaml` при установленной переменной, иначе `~/.config/codex-dispatcher/config.yaml`.
- Существующий шаблон `config/config.example.yaml` содержит вложенное поле `dispatcher.root_path` (не `root_path` на верхнем уровне), а также `projects`.

Реализация должна сохранять эти контракты. Не копировать старую структуру из `main`, не переименовывать пакет.

## 3. Размещение и запуск

Стандартная установка текущего пользователя:
- Конфигурация: `~/.config/codex-dispatcher/config.yaml` (или каталог по уже существующему `XDG_CONFIG_HOME`).
- Исполняемая команда: `~/.local/bin/codex-dispatcher`.
- `venv`: `~/codex-dispatcher/.venv` в стандартном сценарии.
- Значение `dispatcher.root_path`: абсолютный путь, по умолчанию `$HOME/codex-dispatcher`.

Внутри `root_path` могут существовать БД, worktree, репозитории, результаты. При установке/обновлении/удалении их нельзя стирать или перезаписывать. Изменённый пользователем `root_path` в существующем конфиге сохраняется. Не требовать обязательной активации `venv`. Настроить короткий доступ через ссылку/обёртку на установленный entrypoint. Корректно обработать повторный запуск, конфликт существующего `~/.local/bin/codex-dispatcher`, отсутствие каталога в PATH и новое окно shell.

## 4. Пакет, версия и формат конфигурации

Версия фактически установленного ПО определяется из метаданных установленного в выбранном `venv` пакета `codex-dispatcher-v2` через `importlib.metadata.version`. До обновления сравнивается с версией кандидата из релиза; сравнение — семантическое в терминах PEP 440 (например, `packaging.version` или эквивалент). Установщик не понижает версию, не сравнивает строки лексикографически. Метаданные установленного пакета — источник истины, а не YAML.

В конфиг добавляются **два верхнеуровневых служебных поля** (структура остального файла сохраняется):
```yaml
dispatcher_version: "2.5.2"
config_schema_version: 1

dispatcher:
  root_path: /home/example/codex-dispatcher
  # остальные существующие настройки

projects: []
```

`dispatcher_version` — исключительно информативная версия, под которую подготовлен YAML; меняется установщиком при совместимом обновлении. `config_schema_version` — целое число, задающее формат YAML. Поддерживаемая версия схемы определена кодом релиза (начальная — 1). Схема меняется только при несовместимом изменении требований к конфигу, а не при каждой версии пакета.

На **новой установке** шаблон создаётся в том формате, который реально ожидает приложение; `~` разворачивается **установщиком** в абсолютный `dispatcher.root_path`. Никакой новой логики раскрытия `~` в коде диспетчера не требуется.

При **совпадающей схеме** сохранить остальные значения, комментарии и порядок YAML; изменить только `dispatcher_version`. Не пересериализовать конфиг полностью через PyYAML ради одной метки. При **различающейся, отсутствующей или неразбираемой схеме** старый `config.yaml` сохранить без изменений, сформировать `config.new.yaml` по шаблону новой версии, вывести предупреждение о ручном переносе настроек. Уже существующий `config.new.yaml` не перезаписывать без явного согласия. Не выдумывать миграцию и не переносить автоматически неизвестные поля. После ручного согласования пользователь заменяет основной файл; начальный шаблон не содержит пользовательских секретов.

Проверка совместимости в **самом диспетчере** сопоставляет `config_schema_version` с поддерживаемой версией; при несовпадении не допускает `run` и другие изменяющие рабочее состояние операции до создания runtime/SQLite/lock/poll. Диагностика должна показывать имеющуюся и ожидаемую версии. Не блокировать `--help` и безопасные способы остановить уже работающий процесс; минимизировать побочные эффекты при отказе. Версия `dispatcher_version` на допуск не влияет. Старые конфиги без поля схемы не считаются совместимыми автоматически.

**Важно для смены схемы:** после обновления установленный пакет может быть новее, чем `dispatcher_version` сохранённого старого файла. Это допустимо; при повторном запуске установщика ориентироваться на версию пакета, а не старый YAML.

## 5. Установка и обновление через GitHub

**Вариант A (утверждён):** единый `install-standalone.sh`, который пользователь скачивает один раз и может повторно запускать. Сам получает сведения о релизах и пакеты; дополнительную `codex-dispatcher update` не вводить.

Источник: `heroicrealm/CodexAgent`, последний **стабильный** GitHub Release (`/repos/heroicrealm/CodexAgent/releases/latest`). Предварительные релизы и drafts не предлагаются. Установщик проверяет prerequisites (Python нужной версии, pip/venv, git, gh, codex, shell/системные средства). Отсутствие авторизации gh/Codex должно сопровождаться понятной подсказкой о самостоятельной настройке; учётные данные не модифицировать.

До установки выяснить текущую версию пакета и версию предлагаемого релиза. При отсутствующем пакете предложить первичную установку; при равной версии сообщить об актуальности; при более новой предложить обновление; при более старой в релизе отказаться от downgrade. Не заменять пакет при работающем диспетчере: проверять текущие штатные признаки runtime, не ориентироваться только на PID. Не прерывать выполняющиеся Issue.

Скачать релизный `wheel` (готовая универсальная Python-сборка) из **конкретного стабильного релиза**, проверить его целостность по опубликованному SHA-256/контрольной сумме из доверенных метаданных релиза, установить в `venv` обычным `pip install` (не `-e`). Не смешивать файлы от разных релизов. После установки подтвердить версию из установленного пакета, привести конфиг по правилам §4, настроить CLI. При сбое сети/проверки/установки сохранять пользовательские данные и не объявлять успех; по возможности поддерживать рабочую прежнюю установку (включить испытания сбоя обновления).

При проверке/обновлении не требуется клонировать исходный репозиторий. Существующий пользовательский конфиг не перезаписывать без описанных правил. Проверять `XDG_CONFIG_HOME` согласно существующему resolver.

**Доставка самого установщика:** файл размещается среди артефактов релиза; в руководстве дать воспроизводимую команду его получения с GitHub. При будущих изменениях установщика должна быть документирована возможность получить новый установщик того же релиза; не предполагать, что однажды скачанный файл всегда знает новые форматы артефактов.

## 6. Проверка GitHub и обновления перед `run`

При `codex-dispatcher run` (включая `run --once`) **последовательно**, до существующего runtime:
1. Определить установленную версию по метаданным `codex-dispatcher-v2`.
2. Проверить доступность **основного GitHub API**, затем последнего стабильного Release.
3. Если релиз новее — вывести версию, ссылку и указание остановить диспетчер и запустить `install-standalone.sh`.
4. Если версия актуальна — без лишнего вывода продолжить.
5. Если основной GitHub API недоступен — вывести `WARNING: GitHub is unavailable. Start dispatcher anyway? [y/N]:`. При `y` продолжить **без дополнительной защиты**; при `n`, Enter и Ctrl+C — завершить без запуска. В неинтерактивном режиме — завершить с ненулевым кодом без ожидания ввода.
6. Если основной API работает, но Releases не ответил — сообщить, что обновления проверить не удалось, и продолжить.
7. Использовать ограниченный сетевой тайм-аут, исходно 3 секунды, без бесконечных ожиданий.

Эта проверка не выполняется при каждом poll/Issue, не меняет scheduler, SQLite, состояния задач и не производит установку. Не перехватывать исключения, скрывая ошибки конфигурации/БД/авторизации основного приложения. Проверку совместимости YAML выполнить до допуска к runtime.

## 7. Удаление

Предусмотреть `uninstall-standalone.sh`. Удалять только принадлежащие установщику компоненты установленной программы и короткой команды, после проверки, что диспетчер остановлен. Конфиг, SQLite, workspace, worktrees, репозитории и пользовательские credentials сохранять по умолчанию. Не удалять весь `~/codex-dispatcher` рекурсивно. При конфликте/неясной принадлежности файлов сообщить, не удалять постороннее.

## 8. Публикация релизов на GitHub

Подготовить регламент и поддерживающий GitHub Actions workflow (с учётом уже существующего CI):
1. После реализации, прохождения CI и ручной приёмки синхронизировать версию `pyproject.toml`, тег `vX.Y.Z` и сведения релиза; для этапа целевая `2.5.2`.
2. Собрать `codex-dispatcher-v2` wheel и проверить его установку в чистое окружение.
3. Приложить `install-standalone.sh`, шаблон `config.example.yaml`, wheel, контрольные суммы/sha256 и release notes.
4. Публиковать **стабильный** Release только после завершения приемки (подготовка workflow в рамках задачи не означает преждевременный выпуск).
5. Установщик и диспетчер используют именно стабильный Release, не ветку `main`, не HEAD исходников.
6. Не требуется PyPI.

Версионирование и публикацию разработать так, чтобы в дальнейшем Ubuntu native могла переиспользовать ядро установки/проверки обновлений.

## 9. Руководство пользователя

Подготовить руководство Standalone на русском с разделами для WSL2 и Ubuntu native: требования и подготовка Ubuntu/WSL2; получение установщика; установка; `gh auth login`, `gh auth setup-git`, авторизация Codex; конфиг, абсолютный `dispatcher.root_path`, проекты; `run`/`run --once`/`stop`/`status`/`queue`; повторная установка; обновление YAML через `config.new.yaml`; диагностика и удаление. Примеры должны соответствовать **реальному CLI**. Не писать `codex-dispatcher start`.

## 10. Автоматические тесты

Испытать без реального сетевого доступа в CI (mock GitHub и временные HOME/XDG, окружения/файлы, subprocess):
- чистая и повторная установка; отсутствие активации `venv`; конфигурация с правильной вложенностью `dispatcher.root_path`;
- сравнение версий PEP 440, запрет downgrade, определение версии из метаданных, не из YAML;
- совместимый апдейт: изменение только `dispatcher_version`, сохранность остальных параметров и комментариев;
- новая/отсутствующая/некорректная схема: сохранение основного файла, создание нового шаблона, отказ runtime; существующий `config.new.yaml`;
- `run`: новое обновление, нет обновления, ошибка Releases, основной API недоступен + ответы y/n/Enter, отсутствие TTY, тайм-аут;
- проверка, что `run` при ответе y передаёт управление прежней логике без новых блокировок;
- обнаружение работающего диспетчера, запрет обновления; неудачная загрузка/проверка/установка; сохранность пользовательских данных;
- удаление установщиком только своих компонентов;
- регрессия существующих CLI, DB guard, recovery и пользовательского пути `--config`.

## 11. Ручная приёмка

На реальном WSL2 (обязательная ручная приёмка) и по возможности Ubuntu native (отдельная проверка платформенной совместимости):
1. Чистая установка из опубликованного проверочного релизного артефакта; `pip show codex-dispatcher-v2`; команда доступна из любого каталога и нового терминала без `source .venv/bin/activate`.
2. Проверка конфигурации по стандартному пути и с `--config`; запуск `run --once`, затем `run`, штатная остановка.
3. Проверка рабочих `status`, `queue`; реальная тестовая Issue с публикацией PR.
4. Повторная установка, сравнение версии; совместимое обновление без потери комментариев/проектов.
5. Смоделированное изменение схемы, создание `config.new.yaml`, блокировка и ручное восстановление.
6. Недоступность GitHub: ответы y/n/Enter, отсутствие TTY; уведомление о более новой версии.
7. Проверка запрета обновления при работающем диспетчере, сохранности БД/worktree, удаления только программы.

## 12. Результаты и критерии завершения

Результат: установщик, удалитель, проверка версий/схемы, уведомление при `run`, GitHub Actions/регламент Release, пользовательская документация, тесты и отчёт об испытаниях.

Этап принят, если пакет устанавливается из стабильного GitHub Release без клонирования исходников, команда работает без активации venv, путь XDG/шаблон совпадает с действующей моделью, совместимые обновления сохраняют настройки, несовместимая схема блокирует запуск с понятной диагностикой, недоступный GitHub порождает только согласованный вопрос y/N, а существующая обработка Issue/PR и CI не регрессируют.

**Область V2.5.2 ограничена вариантом Standalone (WSL2 и Ubuntu native без службы) и проверками при запуске.** Сбой push из-за потери связи во время работы рассматривается отдельно.
