# Диспетчер задач для агента Codex. Версия 2.0

Целью проекта является разработка диспетчера задач для управления агентом Codex через постановку задач на Github Issues.
Для постановки задачи, пользователь подготавливает ветку TaskBranch(имя может быть произвольным), в эту ветку могут быть помещены документы спецификации, программный код и другие релевантные для задачи материалы.
В теле Github Issue пользователь помещает текст задачи агенту.
Для регистрации задачи, пользователь помещает на нее метку codex-ready.
Далее он может продолжать работу над текстом задачи. 
Как только постановка задачи будет окончательно сформулирована, пользователь ставит метку approve.
Получив в результате периодического опроса меток что статус перешел в approve диспетчер ставит метку pending означающую что задача перешла в режим ожидании запуска.
В рабочем цикле диспетчера, диспетчер берет следующую задачу в списке pending и переводит ее в режим preparing, беря в работу.
На этапе preparing:
Он создает временную ветку с названием codex/task-XXXXX от указанной пользователем ветки, подготавливает git-worktree.
подготовив все к запуску codex диспетчер переводит задачу в статус running и запускает агент codex на текущем git-worktree передав ему задачу из issue.
По завершении работы агента, диспетчер делает пуш ветки на гитхаб и PR на слияние в ветку TaskBranch.
При этом он переводит issue в режим review.
В первом комментарии он пишет:
1) имя ветки которую он создал
2) последнее сообщение агента о том что он сделал
3) время начала и завершения работы агента а так же длительность работы
4) возникшие ошибки

Пользователь увидев что issue перешло в статус review производит приемку issue.
Если его устраивает результат:
1)он сливает PR в TaskBranch или какую-либо еще по своему усмотрению
2) диспетчер увидев что PR слит, удаляет рабочую ветку codex/task-XXXX а так же удаляет git-worktree на рабочей станции диспетчера
3)отмечает Issue как закрытую ( close as completed) и вешает метку done
Если пользователя не устраивает результат:
1) он закрывает PR без слияния
2) диспетчер  увидев что PR закрыт без слияния отмечает issue как rejected

Далее у пользователя есть два пути:
1) отказаться от доработки.
  В этом случае он ставит метку cancelled
  Диспетчер прочитав, что установлена метка cancelled, удаляет рабочую ветку codex/task-XXXX а так же удаляет git-worktree на рабочей станции диспетчера
  и отмечает Issue как отмененную ( close as not planned) и оставляя метку cancelled
2) отправить задачу на доработку
   В этом случае он ставить метку need-fix
   Диспетчер пока никак на это не реагирует, данная метка большее нужна пользователю, чтобы понимать что эта задача отправлена на доработку. 
   Для диспетчера она эквивалентна review
   
Отправка на доработку:
Для сохранения истории постановок задач, для исправления работы пользователь создает новую issue
но указывает в ней, что она является продолжением предыдущей.
когда на эту диспетчер возьмет ее в работу, на этапе prepare он должен взять ветку и worktree предыдущей issue указанной в параметрах, а не создавать новую, тем самым агент будет дорабатывать то что он недоделал в рамках первой issue
по завершении, issue так же переходит в review.
Если PR слит со слиянием, то обе issue ( оригинальная и корректирующая) получают метку done и закрываются как close as complted ветка и worktree удалятся
Если PR закрыт без слияния то ветка помечается rejected.
Далее пользователь может отметить ее как cancelled, ветка удаляется, worktree удаляется issue и предыдущая issue закрываются как not planned.
Пользователь так же может сделать третью корректирующую issue. Количество корректировок не ограничено.

Контейнерная issue.
  Если у issue есть sub-issue отмеченные как codex-ready она считается контейнерной.
  при переводе такой issue в статус approve она переходит в статус awaiting-children до тех пор пока все ее дочерние issue не перейду в состояние done или cancelled.
  диспетчер не запускает их, а просто ждет
  после этого она обрабатывается как обычная issue.

Ручная issue
 если у issue установлен флаг run_codex :false то issue считается ручной, исполнять ее должен человек а не агент. диспечер готовит ветку manual/task-XXX и перерводит ее в состояние review. git-worktree на компьютере диспетчера не нужен,
 так как человек сделает fetch/checkout  на своем компьютере затем сделает push в гитхаб.

 Ввод вывод:
 Операции ввода/вывода параметров и текстов ошибок предлагаю осуществлять через первый комментарий.
 В начале комментария идет fenced yaml блок с вводными параметрами для диспетчера такими как:
 1) имя базовой ветки
 2) номер корректируемой issue в случае доработки
 3) метка run_codex
 4) другие по необходимости

 под YAML блоком будет вывод диспетчера:
 по завершении стадии prepared в комментарий добавится имя рабочей ветки
 по завершении работы агента информация о работе агента.

 Надо предусмотреть формат вывода так, чтобы корректирующая issue смогла прочитать имя рабочей ветки, возможно имеет смысл закинуть его еще и в fenced yaml блок
