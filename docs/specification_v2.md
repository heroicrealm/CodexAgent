# Codex Task Dispatcher V2 — концептуальное ТЗ и модель состояний (V2.1)

**Репозиторий:** `heroicrealm/CodexAgent`  
**Статус:** согласованная концептуальная спецификация V2.1  
**Назначение:** нормативная основа для проектирования модели данных, CLI, реализации и приёмочных испытаний V2.

## 1. Цель и принципы

Диспетчер выполняет задачи Codex, поставленные через GitHub Issues. Пользователь управляет регистрацией, утверждением, приёмкой, доработкой и отменой посредством меток, Pull Requests и комментария INPUT. SQLite хранит состояние исполнения и связи.

Основные принципы:

1. **Одна Issue — одна утверждённая постановка и не более одной попытки исполнения.** Возобновление выполнения той же Issue после ошибки или отклонения PR не предусмотрено: создаётся корректирующая Issue.
2. **Любая Issue — потенциальный родитель.** Нет отдельного типа «контейнер» и YAML-флага контейнера. У каждой записи есть `children_total` и `children_completed`, по умолчанию 0/0.
3. **Подтверждение отдельно от готовности детей.** Запуск возможен только после обработки `approve` и завершения всех учитываемых детей.
4. **Событийные зависимости.** Дочерние Issue при регистрации и завершении меняют счётчики родителя. Родитель не опрашивает своих детей постоянно.
5. **Группа исполнения объединяет доработки одной рабочей веткой.** Ссылки корректировок могут образовывать дерево; фактическое исполнение внутри группы последовательно.
6. **GitHub и SQLite имеют разные роли.** GitHub хранит постановки, метки, PR, ветки и действия пользователя; SQLite — снимок утверждённой задачи, локальный жизненный цикл, группы, связи и техническую информацию.
7. **Минимум защит от нестандартных действий пользователя.** Диспетчер не пытается запрещать изменения структуры Sub-issues, закрытие Issue вручную, изменение целевой ветки PR или изменение текста после утверждения.
8. **Идемпотентность.** Повторный poll и восстановление после рестарта не должны повторно запускать задачу или дважды учитывать ребёнка.

## 2. Основные сущности и идентификаторы

### 2.1 Issue

Внутренний ключ — глобальный GitHub Issue ID. Отображаемый номер Issue (`#NNN`) уникален только внутри репозитория. В INPUT пользователь указывает **номер Issue своего репозитория**, а диспетчер разрешает его в глобальный ID; в SQLite хранится соответствие с репозиторием.

Для Issue хранятся как минимум: GitHub ID, репозиторий и номер, признак виртуальности, жизненный статус, утверждённый снимок постановки и INPUT, идентификатор группы исполнения, связь с родителем, счётчики детей и признаки однократного учёта, технические ссылки на ветку/PR и историю ошибок. Детальная схема таблиц — предмет следующего этапа.

### 2.2 Виртуальная Issue

Если зарегистрирован ребёнок с `codex-ready`, а запись его родителя отсутствует, создаётся **виртуальная запись родителя** (признак `is_virtual=true`), содержащая GitHub ID, репозиторий, номер и счётчики. Это *не* состояние жизненного цикла и такая запись не участвует в очереди.

У виртуального родителя могут накапливаться как количество детей, так и количество завершённых детей. Достижение равенства счётчиков не запускает его. При появлении `codex-ready` у самого родителя та же запись становится реальной (`is_virtual=false`, статус `discovered`), сохраняя накопленные данные.

Порядок обнаружения родительской и дочерней Issue в одном poll значения не имеет; ребёнок может исполняться, пока родитель виртуальный или не утверждён.

### 2.3 Группа исполнения

Группа — общий жизненный контекст одной исходной Issue и всех её корректирующих Issue. Группа имеет единственную рабочую ветку и итоговое состояние; любая Issue группы ссылается на `execution_group_id`.

Корректирующая Issue указывает номер **любой** предыдущей Issue незавершённой группы (`correction_of`). Непосредственная ссылка сохраняется для истории, но ветка берётся текущая общая, с учётом всех предыдущих доработок и ручных изменений. Откат истории ветки пользователь выполняет самостоятельно. В одной группе может быть только одна активная Issue.

Идентификатор группы служит основой уникального имени ветки, например `codex/task-XXXXX` или `manual/task-XXXXX`. Имя первоначальной рабочей ветки и первоначальная базовая ветка закрепляются за группой. Если первая попытка завершилась до создания ветки, корректирующая Issue создаёт ветку **с исходным именем группы от исходной базовой ветки**.

### 2.4 Связи Sub-issues и корректировок

GitHub Parent/Sub-issue и связь `correction_of` независимы. Корректирующая Issue **не наследует автоматически** родителя первоначальной Issue. Если пользователь вручную добавил её в Sub-issues, это допустимо: контейнер учитывает обе Issue по отдельности, даже если они принадлежат одной группе.

При завершении группы статусы `done`/`cancelled` распространяются на каждую её Issue. Каждая зарегистрированная как учитываемый ребёнок Issue однократно влияет на счётчик собственного родителя. Родителю не нужно знать структуру группы корректировок.

## 3. Интерфейс GitHub

### 3.1 Метки и команды

- `codex-ready` — **однократный признак первоначальной регистрации**. После появления записи в SQLite удаление или повторное добавление метки игнорируется; автоматически восстанавливать метку не требуется.
- `approve` — команда утверждения. Диспетчер делает снимок текста Issue и INPUT в SQLite; затем переводит задачу в `pending` или `awaiting-children`. Изменение текста и INPUT после этого игнорируется.
- `need-fix` — явное решение пользователя продолжать работу после `rejected` либо `error`. Только тогда открывается возможность утвердить корректирующую Issue.
- `cancelled` — команда отмены в допустимых состояниях и терминальное состояние группы.
- `done` — терминальное состояние группы после успешного merge PR либо ручного разрешения `error` пользователем.
- Остальные названия состояний представлены статусными метками для отображения жизненного цикла; схема их настройки конфигурируема.

`approve` и `codex-ready` могут быть выставлены до одного poll: регистрация и утверждение допускаются в одном проходе. После утверждения единственным источником текста задания является сохранённый снимок SQLite.

### 3.2 INPUT и OUTPUT

У Issue используются **два отдельных комментария** с устойчивыми уникальными маркерами:

- **INPUT** — пользовательский комментарий с fenced YAML-блоком параметров. Минимально предусматриваются `base_branch`, `correction_of` (номер Issue данного репозитория), `run_codex` (по умолчанию `true`) и необходимые настройки выполнения. Точные имена ключей и формат маркера закрепляются при проектировании контракта данных.
- **OUTPUT** — комментарий, которым управляет диспетчер. Содержит рабочую ветку, информацию о подготовке, последнее сообщение Codex, время начала/завершения, длительность, ссылки на PR и описание ошибок. При необходимости — машиночитаемые поля.

Идентификаторы комментариев хранятся в SQLite; поиск по маркеру позволяет восстановить связь. Поля OUTPUT информативны: источником внутренних связей остаётся SQLite.

### 3.3 Open/closed

Обычный `poll` получает **открытые GitHub Issues**. После регистрации Issue остаётся в SQLite даже при закрытии на GitHub. Закрытая Issue не участвует в очередном опросе её меток; повторное открытие возвращает её в poll.

Закрытие **не** отменяет зарегистрированную Issue, не выключает scheduler и не препятствует внутреннему исполнению, обработке PR, завершению группы либо переходам родителя по событиям детей. Диспетчер не реализует дополнительных блокировок для преждевременно закрытых вручную Issue.

При итоговом `done` диспетчер старается установить для всех Issue группы GitHub `closed as completed`, при `cancelled` — `closed as not planned`, включая уже закрытые Issue. Неудача синхронизации причины закрытия не отменяет терминальный статус SQLite.

## 4. Состояния и единая модель переходов

### 4.1 Реестр

| Состояние | Значение |
|---|---|
| `discovered` | Зарегистрирована, ожидает утверждения |
| `awaiting-children` | Утверждена, но имеются незавершённые учтённые дети |
| `pending` | Утверждена и готова к исполнению; в очереди |
| `preparing` | Начата единая фаза исполнения: подготовка ветки и окружения |
| `running` | Codex исполняет задачу / выполняется публикация результата |
| `manual-running` | Ручная задача передана человеку; ожидается PR |
| `review` | PR доступен для приёмки |
| `rejected` | PR закрыт без merge; ожидается решение пользователя |
| `need-fix` | Пользователь разрешил следующую корректирующую Issue |
| `error` | Попытка исполнения или публикации не завершилась штатно |
| `done` | Терминальный успех группы |
| `cancelled` | Терминальная отмена группы |

`is_virtual` — отдельный признак, а не статус. `approve` — команда, не состояние. `preparing` и `running` имеют **одинаковые бизнес-ограничения**, являясь техническими подэтапами исполнения.

### 4.2 Переходы

| Исходное состояние | Событие / условие | Результат |
|---|---|---|
| Отсутствует / виртуальная запись | Poll обнаружил `codex-ready` | `discovered` (виртуальная запись становится реальной) |
| `discovered` | `approve`, `children_total = children_completed` | Снимок постановки; `pending` |
| `discovered` | `approve`, `children_total > children_completed` | Снимок постановки; `awaiting-children` |
| `discovered` или виртуальная | Дети завершились до `approve` | Только обновить счётчики; не запускать |
| `awaiting-children` | Последний учитываемый ребёнок завершён | `pending` |
| `pending` | До начала исполнения добавлен незавершённый учитываемый ребёнок | `awaiting-children` |
| `pending` | Scheduler атомарно захватил задачу | `preparing` |
| `preparing` | Codex-окружение готово | `running` |
| `preparing` | Ручная ветка опубликована | `manual-running` |
| `running` | Результат опубликован, PR создан/найден | `review` |
| `manual-running` | Обнаружен PR из закреплённой ветки группы в том же репозитории | `review` |
| `review` | PR успешно слит в **любую** целевую ветку | Вся группа → `done` |
| `review` | PR закрыт без merge | `rejected` |
| `rejected` или `error` | Пользователь поставил `need-fix` | `need-fix`; разрешить новую корректирующую Issue |
| `error` | Пользователь поставил `done` (разрешил вне диспетчера) | Вся группа → `done` |
| `discovered`, `awaiting-children`, `pending`, `rejected`, `need-fix`, `error` | Пользователь поставил `cancelled` | Вся группа → `cancelled` |
| `preparing` или `running` | Ошибка подготовки, исполнения или публикации | `error` |
| `need-fix` | Новая корректирующая Issue утверждена | Старая остаётся `need-fix`; новая получает `pending`/`awaiting-children` |
| `need-fix`, `rejected` и иные предшествующие статусы группы | Любая Issue группы терминально завершила группу | Все Issue группы получают `done` либо `cancelled` |

Успешный запуск Codex без изменений, когда PR создать невозможно, трактуется как `error` (без отдельного `no-changes`).

### 4.3 Ограничения

- В группе **не более одной активной Issue**. Активными для проверки нового `approve` являются `pending`, `awaiting-children`, `preparing`, `running`, `manual-running`, `review`. `rejected` и `error` ещё **не** разрешают новую корректировку: требуется `need-fix`.
- При недопустимом `approve` диспетчер снимает метку `approve`, публикует причину в OUTPUT и не утверждает постановку.
- Новая корректирующая Issue допускается лишь для открытой группы, получившей разрешение на доработку; для завершённых групп запрещена.
- `done`/`cancelled` всей группы **не допускаются при текущем исполнении** (`preparing`, `running`, `manual-running`). Принудительное прерывание для отмены не предусматривается. После штатного исполнения пользователь принимает решение на `review`/`rejected`, а после сбоя — на `error`.
- `preparing` и `running` — одна семантическая фаза: одинаковы правила новых детей, группового завершения и обработки ошибок.
- Одновременные противоречивые команды (`need-fix` и `cancelled` и т.п.) не интерпретируются произвольно: фиксируется ошибка команд и требуется исправление меток.

## 5. Подсчёт детей и допуск к запуску

Каждая Issue имеет `children_total=0` и `children_completed=0` по умолчанию. Обычная Issue — вырожденный родитель с 0/0. Специального YAML-флага контейнера нет.

### 5.1 Регистрация

При первом обнаружении новой Issue с `codex-ready` диспетчер получает её GitHub parent (если есть) и регистрирует отношение в SQLite. Если родитель отсутствует, создаётся виртуальная запись.

Если родитель **ещё не начал исполнение** (виртуальный, `discovered`, `awaiting-children`, `pending`), ребёнок однократно увеличивает `children_total`. При родителе `pending` и новом незавершённом ребёнке родитель возвращается в `awaiting-children`.

Если родитель уже достиг `preparing` либо любой более поздней стадии, связь нового ребёнка может сохраняться как справочная, **но он не входит в учитываемый набор** и не меняет счётчики даже после своего завершения. Фактический прогресс GitHub Sub-issues может расходиться со счётчиками SQLite; это допустимо.

Sub-issues **без** `codex-ready` не регистрируются как управляемые дети и не влияют на счётчики. Их последующая регистрация с этой меткой обрабатывается обычным порядком. Удаление уже зарегистрированной связи пользователем не поддерживается как операция пересчёта.

### 5.2 Завершение

При первом терминальном переходе учтённого ребёнка в `done` или `cancelled` он однократно увеличивает `children_completed` родителя. Если родитель сейчас `awaiting-children` и счётчики равны, родитель переходит в `pending`. Если родитель виртуальный или `discovered`, его статус не меняется даже при равенстве счётчиков.

Отмена ребёнка означает, что его результат не принимается, но зависимость считается завершённой. Если одновременно завершаются несколько детей из одной группы корректировок, **каждый** зарегистрированный ребёнок учитывается ровно один раз.

Все изменения дочерней связи, счётчика и признака `completion_counted` выполняются атомарно в SQLite. Счётчики не должны зависеть от числа повторных опросов. Данные о фактически учтённых детях сохраняются для диагностики и восстановления счётчиков при необходимости.

### 5.3 Два необходимых условия

Переход в `pending` возможен только после **обработанного `approve`** и при `children_total = children_completed`. Равенство счётчиков до утверждения **никогда** не запускает Issue.

При входе родителя в `preparing` учитываемый состав детей фиксируется. Позднее добавление Sub-issues на GitHub не блокирует review или закрытие родителя.

## 6. Исполнение Codex и ручных Issue

### 6.1 Первая Issue группы

Пользователь заранее создаёт базовую ветку (`TaskBranch`) с материалами. В `preparing` диспетчер создаёт рабочую ветку `codex/task-XXXXX` от утверждённой базовой ветки и временный Git worktree, затем запускает Codex с **зафиксированным текстом SQLite**.

После завершения агентской работы диспетчер коммитит имеющиеся изменения, выполняет push в рабочую ветку группы и создаёт PR в базовую ветку. Переход в `review` происходит при успешном создании/обнаружении PR. OUTPUT содержит результат агента и технические сведения.

Временный worktree удаляется **после сохранения результатов на GitHub**, а не удерживается между корректировками.

### 6.2 Корректирующая Issue

Корректирующая Issue пользуется той же веткой группы и создаёт **новый PR**; предыдущие отклонённые PR остаются закрытыми.

При старте делается fetch актуальной рабочей ветки с GitHub; в новом временном worktree продолжается её **текущее** состояние, включая изменения пользователя. Старый worktree не требуется.

Если рабочая ветка ещё не существует вследствие ранней ошибки, её создают под закреплённым за группой именем от **исходной** базовой ветки. Ссылку на любую предыдущую Issue группы разрешают в саму группу, а не в старый снимок коммитов.

Одновременно выполнять две Issue группы запрещено; проверка и захват производятся атомарно.

### 6.3 Ручная Issue

При `run_codex: false` диспетчер в `preparing` создаёт и публикует `manual/task-XXXXX`, **не** создаёт локальный worktree для Codex и переводит Issue в `manual-running`. Человек самостоятельно выполняет checkout, изменения и push.

При обнаружении PR, у которого совпадают **репозиторий и исходная ветка группы**, задача переходит в `review`. Дальнейшая приёмка и завершение группы общие. Отдельного требования указывать номер Issue в PR нет.

### 6.4 Решение пользователя по PR

- PR **merged** в любую целевую ветку → вся группа `done`; ветка группы и остаточные worktree очищаются.
- PR **closed без merge** → текущая Issue `rejected`; ветка остаётся.
- В `rejected` пользователь ставит `need-fix` для новой корректировки либо `cancelled` для отмены всей группы.
- В `error` пользователь выбирает `need-fix`, `cancelled` или `done` (если исправил всё самостоятельно).
- При `cancelled` очищается рабочая ветка и результаты группы, все её Issue закрываются `not planned`. Уже слитые в другие ветки внешние коммиты диспетчер не откатывает.

## 7. Poll, scheduler и порядок обработки

### 7.1 Poll

В назначенное время `poll` получает открытые Issues и их метки, регистрирует новые `codex-ready` Issue, определяет родителей, обновляет виртуальные записи, обрабатывает `approve` и другие допустимые команды. Отдельно синхронизируются PR, которые диспетчер отслеживает по SQLite, включая закрытие/слияние PR независимо от того, открыта ли связанная GitHub Issue.

Предлагаемый порядок одного прохода:

1. Получить необходимые сведения GitHub.
2. Зарегистрировать все новые Issue и родительские связи.
3. Применить изменения команд, PR и терминальных переходов; обновить счётчики.
4. Зафиксировать SQLite.
5. Только затем разрешать scheduler выбирать задачи из `pending`.

В частности, новый ребёнок, зарегистрированный до начала `preparing`, должен успеть вернуть родителя из `pending` в `awaiting-children` до захвата scheduler.

### 7.2 Scheduler и процессы

Scheduler работает **по SQLite**, не проверяя GitHub open/closed перед началом уже утверждённой задачи. Poll продолжает выполняться во время длительного запуска Codex: управляющий цикл не блокируется ожиданием агента, Codex исполняется отдельным процессом.

Для начальной реализации достаточно одного одновременно исполняемого процесса Codex; расширение параллелизма возможно позднее без изменения логики единственной активной Issue в группе.

Повторный poll не должен повторять уже начатую операцию. Состояние SQLite и выбор следующей задачи обновляются атомарно. Операции GitHub (push, PR, метки, комментарии) по возможности выполняются идемпотентно.

### 7.3 Остановка

Обычный `stop` прекращает приём новой работы и ожидает штатного завершения уже запущенной задачи. Принудительный `stop --force` прерывает исполнение; последующий запуск обрабатывает прерванную работу как восстановление после сбоя. Оба режима сохраняют согласованное требование не запускать новую задачу во время остановки.

## 8. Ошибки и восстановление

### 8.1 Ошибка исполнения или публикации

Ошибка подготовки, Codex, push, PR или отсутствие diff для необходимого PR приводит к `error`. По возможности диспетчер сохраняет текущие изменения коммитом и push, записывает описание ошибки в OUTPUT и лог, сохраняет доступный локальный результат, если публикация не удалась.

Push выполняется **без force push**; конкурирующие изменения рабочей ветки пользователем во время исполнения вызывают ошибку, а не автоматический rebase. После `error` та же Issue повторно не запускается: пользователь выбирает `need-fix` с новой корректирующей Issue, `cancelled` или `done` при самостоятельном успешном разрешении.

### 8.2 Восстановление при запуске

После инициализации, но **до** основного poll/scheduler, диспетчер ищет задачи SQLite, оставшиеся в `preparing` или `running`. При условии отсутствия продолжающего работать старого процесса он:

1. Проверяет локальные ветки/worktree и фактическую публикацию на GitHub.
2. Если PR уже существует и результат публикации завершён, восстанавливает `review` без повторного Codex и без повторного PR.
3. В остальных случаях пытается сохранить оставшийся результат (commit/push, если возможно), помечает Issue `error` с причиной «прерванное исполнение», сообщает о степени сохранности данных.
4. Не удаляет единственную локальную копию неопубликованного результата.

Это восстановление **не является возобновлением Codex**. Для предотвращения конфликтов требуется исключить одновременный запуск двух экземпляров диспетчера над одной рабочей SQLite/workspace.

### 8.3 Согласование внешних эффектов

Сначала фиксируется надёжное локальное состояние; недостающие комментарии, метки, закрытия Issue или очистка ресурсов могут повторяться идемпотентно. Ошибка удаления worktree, удалённой ветки или приведения причины закрытия GitHub Issue к `completed`/`not planned` не отменяет уже состоявшееся `done`/`cancelled`. Такие сбои должны быть видны в логе и доступны для повторной очистки.

## 9. Минимальные требования к SQLite и целостности

Нужно предусмотреть модель данных для:

- зарегистрированных Issue, включая виртуальные записи и снимки утверждённой постановки;
- связи GitHub repository + Issue number ↔ глобальный Issue ID;
- групп исполнения (закреплённые базовая/рабочая ветки, терминальный статус, текущая активная Issue);
- непосредственных связей исправлений `correction_of`;
- зарегистрированных дочерних связей и признаков `counted`/`completion_counted`;
- PR отдельных попыток, ссылок INPUT/OUTPUT и состояния публикации;
- ошибок и ожидающих операций очистки/синхронизации.

Критические атомарные операции: первичная регистрация ребёнка с увеличением счётчика; однократный учёт его завершения; разрешение `approve` и захват активной Issue группы; выбор scheduler `pending → preparing`; локальное групповое терминальное завершение с обновлением всех входящих Issue и родительских счётчиков.

Нельзя допускать повторного увеличения счётчиков при повторном poll, сбое между операциями или изменениях статуса группы. Пересчёт счётчиков из сохранённых дочерних связей допускается как диагностическая/восстановительная операция, не как постоянный мониторинг.

## 10. Требования к наблюдаемости

CLI должен показывать фактическое состояние из SQLite, включая виртуальность, группу исполнения, ветку, привязанные PR, счётчики детей и последнюю ошибку. Виртуальные записи не должны отображаться как обычные готовые задания в очереди `queue`.

OUTPUT сообщает об этапах, публикации и ошибках так, чтобы пользователь мог решить, объединять PR, отправлять корректировку либо отменять группу. Ошибки GitHub и Git должны сопровождаться понятным сообщением и сохранением диагностических подробностей в логе.

## 11. Критерии приёмки концепции при реализации

1. Обычная Issue с 0/0 после `approve` идёт прямо в `pending`.
2. Подтверждённая Issue с незавершёнными детьми ждёт в `awaiting-children`; достижение равенства до `approve` не запускает её.
3. Виртуальный родитель накапливает детей и их завершения; после своей регистрации сохраняет счётчики.
4. Добавление ребёнка в `pending` может вернуть родителя в `awaiting-children`; добавление после `preparing` не учитывается.
5. Отмена учтённого ребёнка освобождает зависимость; одновременное групповое завершение нескольких детей учитывает каждого ровно раз.
6. Повторный poll не дублирует регистрации, PR, исполнение и счётчики.
7. После `approve` изменение текста Issue/INPUT не меняет исполнение.
8. Удаление `codex-ready` после регистрации не отменяет работу и не восстанавливается автоматически.
9. Доработки образуют группу и используют актуальную общую ветку GitHub с новым PR на каждую попытку.
10. `approve` второй активной корректирующей Issue отклоняется со снятием метки и сообщением.
11. Merge в любую целевую ветку завершает всю группу как `done`; `cancelled` завершает всю группу и очищает её ресурсы.
12. Ручная Issue переходит в `manual-running` и далее в `review` после появления PR из её ветки.
13. Закрытие GitHub Issue исключает её из poll, но не мешает scheduler, наблюдению за PR и внутренним завершениям; reopen возвращает её в poll.
14. Ошибка подготовки, исполнения, отсутствия diff или публикации приводит в `error`, с сохранением результата по возможности и выбором `need-fix`/`done`/`cancelled`.
15. После аварии прерванное исполнение не запускается повторно; результат сохраняется по возможности, а уже готовый PR не дублируется.
16. Poll не блокируется ожиданием Codex; перед захватом `pending` выполнена регистрация новых детей текущего прохода.

## 12. Границы V2.1

Данный документ определяет **поведение и инварианты**, а не физическую схему SQLite, формат миграций, конкретные имена YAML-полей/маркеров, CLI-синтаксис и детали реализации очереди. Они конкретизируются в последующих технических этапах без изменения утверждённой семантики.

За рамками V2.1: рекурсивное управление деревьями Sub-issues, принудительные пользовательские блокировки GitHub, автоматический rebase/force push, автоматические откаты ручных изменений, повторный запуск Codex в прежней Issue и расширенная система защит V1.
