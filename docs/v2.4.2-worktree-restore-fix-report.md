# V2.4.2 — диагностика worktree и безопасный restore

Рабочая ветка: `V2_4_2_RECOVERY_RECONCILIATION`. Дата: 2026-11-13.

## Итог и оставшееся ограничение

Исправлен отказ restore для исторического `reserved/preparing` без старта Codex.
Для уже начатого `executing/publishing` безопасное автоматическое разрешение **не
реализовано**: архитектура не даёт достаточного доказательства остановки неизвестного
исполнителя. Это предусмотренный заданием fail-closed исход, а не выполнение всех
критериев приёмки. В частности, положительный критерий stopped executing остаётся
открытым. Реальную установку, её SQLite, `../acpt.sqlite3`, worktree, Issues и PR
агент не изменял и не использовал для экспериментов. PR не создавался.

## Причина обнаружения worktree

Исходная нестабильность **не воспроизведена; корневая причина не установлена**.
Проверено на `/usr/bin/git` 2.53.0, Python 3.14, временных локальных репозиториях:
основной checkout плюс один/два worktree с внутренними ветками и незакоммиченными
файлами. Для каждого набора выполнено 12 последовательных циклов:

- `--porcelain` и `--porcelain -z`, CLI через Bash, subprocess с `-C` и с `cwd`;
- побайтовое сравнение stdout CLI/subprocess и UTF-8 представления Git.command/Git.run;
- returncode=0, пустой stderr, одинаковые пути и количество записей адаптера;
- неизменность refs, содержимого регистрационных файлов `.git/worktrees` и локальных файлов.

Конкурентных мутирующих процессов для этих репозиториев не запускали. Перечисление
не удаляло регистрационные записи; отдельный тест отсутствующего каталога получает
prunable запись и безопасный отказ. `worktree list` не заменён на `prune`, повторный
запрос или альтернативный источник «доверенной» регистрации. `Git.run().strip()` не
удаляет NUL и в проверенных данных не меняет output. Считать его причиной исчезновения
одной записи оснований нет. SQLite в перечислении Git не участвует.

Укреплён контракт машинного формата: worktrees читает stdout без strip и проверяет
полный завершающий NUL record, дубли полей/путей, абсолютность пути и наличие HEAD
(кроме bare). Ошибка Git или неоднозначность вызывают GitError. Это защита от
недоказанной регистрации, **не объяснение исходного инцидента**. Принадлежность для
cleanup не ослаблена. Отдельные тесты подтверждают отказ для чужой ветки/пути,
symlink, locked/prunable и смены HEAD между планированием и удалением, а также
положительную очистку одного принадлежащего dirty worktree с сохранением другого.

Для локализации исходной нестабильности при следующем наблюдении нужен одновременный
сбор из одного диагностического процесса: UTC/монотонное время, разрешённый путь и
версия git, cwd, returncode, byte length/SHA-256 stdout и stderr, число NUL records,
хеши регистрационных файлов до/после. Значения `GIT_*`, конфигов и stderr не выводить;
фиксировать имена переменных, наличие и приватный fingerprint окружения без секретов.
Сравнить абсолютный git и PATH, Bash без startup scripts и Python, обе формы porcelain,
`-C`/cwd; проверить доступность admin-каталогов и настройки prune/safe.directory.
Не запускать prune/repair/cleanup. Само совпадение fingerprint не доказывает отсутствие
гонки. Настройки/окружение реального инцидента здесь не исследовались и не исключены.

## Restore и границы доказательства

Убрана зависимость отказа от одного лишь `reserved/preparing`, если `codex_started_at`
NULL. По контракту Executor записывает старт перед запуском; корректной истории БД
доверяем только после прежних проверок DDL/integrity/UUID. Оба lock-файла по-прежнему
удерживаются на всём протяжении операции. Общая quiescent проверка теперь отвергает
также dangling symlink `.control.sock`. Проверки текущей БД, backup, WAL/SHM,
before-restore Backup API snapshot, staging/migration/fsync/atomic replace сохранены.
После restore `recovery_required=1`, местные файлы и ветки не меняются.

Почему для executing нельзя просто убрать запрос: ProcessRunner запускает supervisor,
который наследует lock descriptors, а Codex запускается через Popen с обычным
close_fds. Если отдельно убить supervisor (SIGKILL), ребёнок может пережить его без
lock. Свободные locks исключают штатный живой supervisor, но не такого ребёнка и не
произвольный внешний процесс. В схеме нет долговечной принадлежности процессу и
подтверждения завершения. PID, `kill(pid,0)`, просмотр `/proc` или отсутствие socket
не устраняют PID reuse, гонки и некооперирующиеся процессы. Поэтому started preparing
и executing/publishing по-прежнему получают диагностический отказ до архивирования.

Варианты следующего согласованного изменения:

1. Изолированный service/cgroup scope для каждого запуска, долговечная идентичность
   scope и проверяемое завершение всех его процессов; maintenance удерживает admission
   locks и проверяет отсутствие процессов через доверенный менеджер.
2. Долговечный протокол executor lease/завершения с обязательным наследованием защиты
   всеми исполнителями и миграционной политикой для старых записей без provenance.
   Сам lease или PID без гарантии удержания всеми потомками недостаточен.

Добавление новой модели и потенциально небезопасного override в эту корректировку
не включено. Статус running у Issue без активного технического execution, как раньше,
сам по себе restore не блокирует. Произвольную ложную ручную историю БД или процессы,
запущенные вне протокола, этот контракт не удостоверяет.

## Артефакты после старого backup

Recovery.collect уже отвергает неизвестный worktree и неизвестный внутренний ref до
GitHub reconciliation и снятия глобального барьера. Изменять алгоритм не потребовалось.
Новый интеграционный тест дважды вызывает recover после restore снимка, в котором нет
нового локального worktree: барьер остаётся, файлы и refs сохранены, внешние вызовы не
добавляются. Безопасный дальнейший путь — сохранить артефакты и найти более полный
проверенный snapshot либо отдельно доказать их контекст; автоматической очистки нет.

## Проверки и повторение

Все тесты используют временные SQLite/Git и fake transport, без настоящего Codex и
GitHub. Добавлены также повтор restore, проверка before-restore истории, живой ребёнок
с inherited locks после закрытия родительских handles, неизвестный запущенный executor
и dangling socket. Существующие тесты проверяют WAL, foreign/corrupt backup, fault
injection atomic replace, миграцию и recovery lifecycle.

Окружение системы не имело pytest; зависимости установлены в отдельный `/tmp` venv.
Команды повторной проверки из корня репозитория:

```bash
python3 -m venv /tmp/codex-v242-review-venv
/tmp/codex-v242-review-venv/bin/pip install -e '.[test]'
/tmp/codex-v242-review-venv/bin/pytest -q
/tmp/codex-v242-review-venv/bin/pytest -q tests/test_recovery.py -k 'raw_stability or registration_conflicts or older_snapshot or positive_unique'
/tmp/codex-v242-review-venv/bin/pytest -q tests/test_db_guard.py -k 'restore'
/tmp/codex-v242-review-venv/bin/python -m compileall -q src tests
git diff --check
```

Для ручного просмотра временных артефактов можно задать pytest `--basetemp` с новым
отдельным каталогом: pytest очищает этот каталог, поэтому нельзя указывать реальные
workspace, checkout или каталог с нужными данными. Не выполнять приведённые в задании
операции restore/cleanup на настоящей тестовой установке до отдельной ручной приёмки.

Результаты: `pytest -q` — **370 passed** (41.31 s); после дополнительного усиления
проверки неизменности регистрационных файлов `raw_stability` — **2 passed**.
`python -m compileall -q src tests` и `git diff --check` — exit code 0.
Первый прогон выявил недочёты новых тестовых fixtures (не закрытые после backup WAL
sidecars и ожидание отказа слишком поздно для symlink); fixtures исправлены без
ослабления production проверок. Повторный полный прогон прошёл.
