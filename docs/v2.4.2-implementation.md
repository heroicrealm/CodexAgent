# V2.4.2 — отчёт реализации

Рабочая ветка: V2_4_2_RECOVERY_RECONCILIATION. PR/merge не выполняются.
Нормативный контракт: [v2.4.2-spec.md](v2.4.2-spec.md).

## Изменения

- storage.py, db_guard.py: отдельные точные эталоны схем 1/2, явный upgrade с
  before-upgrade snapshot и транзакционным rollback, актуальный bootstrap,
  исторический restore только через staging, проверка metadata/version.
  Обычная connection сохраняет общий запрет; RecoveryStore — отдельный admin API.
- schema_v1.sql — неизменённый исторический DDL V2.4.1.
  schema.sql/recovery_schema.sql — шесть recovery-таблиц, FK, CHECK JSON,
  составная уникальность причин, частичный UNIQUE активной операции,
  append-only триггеры событий. Новых состояний issues нет.
- recovery.py — полный read-only сбор, детерминированная классификация,
  повторная внешняя проверка перед одной транзакцией admission, карантины,
  status/accept/cancel/retry, аудит и persistent-фазы retry. Ошибки admission
  диагностируются вне БД; debug API-метрики исключают свободный текст.
- services.py/storage.py — рекурсивный запрет для карантинной Issue, execution
  group и зависимых контейнеров. Poll не снимает карантины. Scheduler не считает
  карантинную running-Issue занятым процессным слотом. Старый approve новой
  обнаруженной после recovery Issue не получает доверия.
- execution.py/cleanup.py — проверки перед execution, salvage push, PR/OUTPUT/ERROR,
  восстановлением и удалением. Orphan maintenance запрещает очистку при наличии
  карантинов: принадлежность неизвестных ресурсов конкретной Issue не доказана.
- git.py — ownership retry-worktree по execution ID/UUID, проверка публикации,
  повторяемая локальная очистка и compare-and-delete внутреннего ref по SHA.
  Retry не изменяет remote refs.
- github.py — проверка repository_url при точечном чтении Issue.
- __main__.py, pyproject.toml, README.md — CLI, упаковка DDL, инструкции.
- tests/test_recovery.py — fake HTTP + реальные временные SQLite/local Git.
  В test_db_guard/test_execution_cleanup/test_storage обновлены ожидания
  bootstrap v2; в test_services исправлена repository identity fixture второго
  проекта, чтобы проверка реальной идентичности не ослаблялась.

## Retry и диагностика

Фазы: intent → archived → approval-reset → cleaned → reset → comment-intent →
commented → completed. Каждая фаза долговечна. До destructive Git сохраняется
архив execution: статус, даты, SHA, признаки публикации, ownership, исходная
идентичность, approval hash/дата и ссылки на все error_log записи.
Приватные error_message сохраняются в прежней error_log; собственное сообщение
execution перед удалением переносится туда. FK execution_id отвязывается, исходные
ID остаются в archive JSON. State_history не удаляется.

Архив не копирует worktree, Codex result и свободный текст постановки, предотвращая
дублирование секретов. Approved snapshot идентифицируется hash/датой; исходный
текст при необходимости берётся из сохранённого backup. Файлы workspace/results
сохраняются как диагностика и не подаются новому Codex автоматически.

GitHub POST и SQLite не атомарны. После неопределённого POST следующая команда
полностью читает комментарии и ищет operation_id; найденный receipt исключает
повторный POST. Ошибка чтения сохраняет запрет. Если полный успешный ответ не
содержит маркер, допускается повтор POST. Контракт опирается на достоверность
полного ответа GitHub; удаление/подмена комментариев пользователем находится
вне гарантии дедупликации и требует расследования. Одновременные команды
исключены InstanceLock.

## Консервативная политика и ограничения

- Неизвестные исполнения не реконструируются: preparing/running остаются в
  карантине. Доказанный PR принимается явным допустимым переходом.
- Disabled/удалённые repositories изолируются без невозможных GET; их Issues
  получают persistent state-conflict. Re-enable его не снимает.
- Имя PR/ветки не доказывает авторство. Нужна сохранённая PR identity либо точное
  dispatcher-тело и result SHA; иначе accept отказывает.
- Shared correction groups для retry требуют отдельного решения: нельзя
  безопасно сбрасывать общую branch identity и approval других участников.
  Также отказываем при опубликованном OUTPUT/результате, расхождении отношений,
  незавершённых детях, уже исполненном родителе, неизвестной local work branch,
  symlink, смене HEAD или непроверяемой remote reachability. Карантин сохраняется.
- Неподтверждённые причины pr-conflict/group-dependency не снимаются retry,
  доказавшим только безопасный discard локального исполнения. Проверяйте status.
- Неизвестные worktree и грязный основной checkout блокируют весь recover как
  неизвестная активность. Checkout origin должен доказывать текущий GitHub
  repository; произвольный local/credential-bearing URL не принимается.
  Тесты подменяют только identity URL, Git использует локальный bare remote.
- SQLite commit и внешний мир не образуют распределённую транзакцию: повторная
  проверка делается непосредственно перед SQL, применяются locks и fail-closed.
  Некооперирующие процессы не должны менять workspace во время команды.
- Непроверенные схемы, повреждённая текущая БД и чужой UUID по-прежнему
  не допускаются к destructive restore.
- Ручная приёмка Playground автоматически не выполнялась; тесты не обращаются
  к настоящему GitHub и не запускают Codex exec.

Дополнительно проверено, что архивные error_report_attempt/uncertain больше не
подавляют ERROR-отчёт нового исполнения после retry. Чистый подтверждённый
worktree может быть принят accept без удаления локальных файлов, если ownership,
HEAD и доказанный PR совпадают; незавершённая локальная работа остаётся в карантине.

Проверяются schema upgrade/rollback/idempotency, historical staging restore,
unique/FK/JSON/audit, UUID/locks/sidecars, канонические состояния,
PR open/merged/closed/retarget, закрытая отслеживаемая Issue, неизвестный Git,
disabled/re-enabled, новая Issue со старым approve, независимая очередь,
вложенные зависимости, самостоятельные side-effect пути, accept/cancel/retry,
crash после durable-фаз и внутри Git removal, неопределённый POST и receipt
reconciliation, повтор завершённой команды, поздняя remote-публикация,
сохранение error_log FK и обязательное новое approve.

## Сценарии ручной приёмки (отдельно)

1. Остановить Playground, upgrade V2.4.1; проверить before-upgrade backup,
   metadata=2, неизменность recovery_required и повтор команды.
2. Backup + restore без конфликтов: run/publish/cleanup запрещены; dry-run
   ничего не меняет; recover снимает барьер одной session.
3. Старый pending при уже существующем PR: карантин, нет повторного Codex.
   Принять доказанный PR; проверить open/merged/closed и base retarget.
4. Preparing/running с dirty worktree без push/PR: индивидуальный карантин.
   Независимая задача исполняется после успешного recover.
5. Retry: архив до удаления, absence approve наблюдено, worktree/local ref
   удалены, remote refs сохранены, execution удалена, диагностика и история
   сохранены, discovered, один comment с operation_id.
6. До нового approve запуска нет; заново установить approve после retry —
   обычный poll переводит pending и разрешает исполнение.
7. Карантин ребёнка блокирует прямой и вложенный контейнер без автоматического
   карантина родителя; независимая Issue работает.
8. GitHub unavailable/неполная пагинация/изменение наблюдений: общий барьер
   сохраняется, частичного применения нет.
9. Прервать retry на разных фазах и повторить команду: один архив и comment,
   сохранность чужих файлов, запрет до завершения.
10. Disabled repository: recover изолирует прежние Issues; включение проекта
    не снимает карантин без проверенного административного решения.
