# V2.4.2 — исправление WAL/SHM при backup/restore

## Воспроизведение до исправления

Работа выполнена в `V2_4_2_RECOVERY_RECONCILIATION`, только на временных
синтетических SQLite. Пользовательская БД и её архивы не открывались.
Среда: Linux 6.18.58.1-microsoft-standard-WSL2, Python 3.14.4,
SQLite 3.46.1. Это WSL2; реальный диспетчер и пользовательские исполнители
в ручном сценарии не запускались.

Минимальный опыт: создать WAL-mode SQLite, записать таблицу, commit и close.
Sidecar отсутствуют. Открыть URI `mode=ro`, выполнить Backup API в `:memory:`,
закрыть destination, затем source: остаются WAL размером 0 и SHM размером
32768 байт. Открытие той же БД через `mode=rw`, чтение и закрытие убирает
оба файла силами SQLite.

Новые регрессионные тесты запускались также с исходным `db_guard.py` из HEAD:
`2 failed, 33 deselected`. Offline-тест обнаружил оставшийся рабочий WAL;
тест restore с WAL у backup обнаружил изменение байтов его SHM.
После опыта исправленный файл возвращён на место.

## Доказанная техническая причина

`connection()` уже явно закрывал соединения. Порядок: Backup API, validate
на destination, commit/close destination, commit/close source. Причина
не в пропущенном `close()` и не в Python-контекстном менеджере транзакций.
Read-only подключение к WAL-mode main-файлу создаёт служебные файлы для
чтения, но не выполняет завершающую очистку WAL, доступную writable-клиенту.
Поэтому закрытое соединение и отсутствие sidecar — разные свойства.

`check(config, path=backup)` использует `inspection()`: копирует main и WAL
в приватный временный каталог, SHM строится там. Эта проверка не меняет
backup; отдельный тест сравнивает дерево файлов до/после check.
А прежний `backup(argument, staging)` открывал непосредственно исходный
backup через `mode=ro`: мог создавать WAL/SHM и менять существующий SHM.
`backup(path, before-restore-*)` тем же способом оставлял sidecar рабочей БД,
после чего restore вручную удалял их. Сам destination закрывался writable;
источником дефекта был source.

## Изменения и обоснование безопасности

* Обычный Backup API открывает существующую рабочую БД через `mode=rw`
  (не создаёт отсутствующую БД). SQL-записей в источник не добавлено.
  SQLite выполняет штатную очистку при закрытии последнего клиента,
  используя собственные блокировки. Отсутствие PID/socket не используется
  как доказательство эксклюзивности для cleanup.
* Online backup сохраняет Backup API и его консистентный снимок. Никаких
  явных checkpoint, переключений journal mode или удаления общих WAL/SHM
  нет. Пока другие клиенты работают, sidecar остаются. Решение о безопасной
  завершающей очистке принимает SQLite, а не код диспетчера.
* Для restore добавлен `private_source=True`: существующий `inspection()`
  копирует main и доступный WAL в приватный каталог; Backup API читает только
  эту копию. Исходный backup не открывается SQLite непосредственно.
  `immutable=1` не используется: committed WAL должен попадать в снимок.
  Снимок проверяется через validate, затем staging — через check с identity.
* После создания `before-restore-*` снова вызывается `quiescent()`.
  Ручное удаление рабочего WAL/SHM удалено. Даже появившийся пустой WAL
  вызывает отказ и сохраняется. Ошибка не маскируется как успешная очистка.
* InstanceLock, запрет restore при исходных WAL/SHM, проверки остановки
  исполнителей, schema/identity, quick_check/foreign_key_check, права и
  симлинки, архив предыдущей БД, fsync, атомарный replace и recovery barrier
  сохранены. Recovery/recover/accept/retry и GitHub-логика не менялись.

Offline и online не различаются эвристикой ливнеса: различается доступность
последнего-client cleanup внутри SQLite. При отсутствии других подключений
тесты подтверждают отсутствие новых файлов; при активных подключениях
подтверждают сохранность WAL и транзакций. Restore отдельно требует прежнего
протокола доказанной остановки и неизменяемого чтения backup.

## Оставшиеся риски и короткая ручная проверка WSL2

Рабочий источник теперь требует writable-доступа: при read-only filesystem
или недостаточных правах backup откажет, вместо возврата к ro с оставлением
sidecar. Backup-файл при restore может находиться на read-only filesystem:
SQLite работает с его приватной копией.

Копирование main/WAL в inspection не является online Backup API для
произвольно изменяемого внешнего backup. Вход restore должен быть стабильным;
при конкурентной записи возможен отказ проверки, следует остановить внешнего
писателя и повторить. Тест с открытым backup-подключением использует стабильный
committed WAL. Дополнительная временная копия требует дискового места.

InstanceLock исключает управляемые процессы; произвольный сторонний процесс,
игнорирующий протокол остановки и начинающий запись в момент replace, остаётся
ограничением прежнего restore-протокола. Повторная quiescent-проверка уменьшает
окно и не удаляет замеченные sidecar. Для проверки остановить все подключения.
При внешних подключениях online backup вправе оставлять WAL/SHM; их наличие
само по себе не доказывает утечку соединения. Отдельных checkpoint с игнорируемым
результатом или попыток ручной очистки общих sidecar в исправлении нет.

Короткая ручная проверка на отдельной тестовой установке WSL2:

1. Штатно остановить диспетчер и исполнителей; закрыть сторонние SQLite-клиенты.
2. Убедиться, что рабочие WAL/SHM отсутствуют. Не удалять их вручную.
3. Выполнить `codex-dispatcher --config <test.yaml> db backup <new-backup>`;
   проверить PASS, отсутствие новых sidecar и сохранить SHA-256 backup.
4. Выполнить `codex-dispatcher --config <test.yaml> db restore <new-backup>`;
   проверить PASS/BLOCKED, прежний SHA-256 backup, отсутствие его sidecar и
   sidecar рабочей БД/нового before-restore архива.
5. `db check` должен сообщить recovery admission blocked. Повторить с новым
   именем backup без ручного checkpoint. Reconciliation проводить штатно.
