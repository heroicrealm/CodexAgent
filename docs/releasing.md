# Публикация Standalone-релиза

Стабильный Release и тег создаются только после ручной приемки и отдельного разрешения владельца. Workflow `Standalone distribution artifacts` собирает проверочный bundle при push/PR или ручном запуске; прав записи и автоматической публикации у него нет. Существующий CI сохраняется.

1. Проверить чистую ветку, CI и отчет ручной приемки. Согласовать конкретный commit. Синхронизировать `pyproject.toml`, `config/config.example.yaml`, release notes и ожидаемую версию в `scripts/smoke-wheel.py` (для этого этапа `2.5.2.post2`). Схему менять только при несовместимости.
2. Выполнить `python3 scripts/embed-standalone.py --check`, pytest, `python3 -m build --wheel`, установить wheel в чистый venv, запустить `--help` и `scripts/smoke-wheel.py` вне checkout. Workflow выполняет эти проверки и сохраняет `standalone-release-candidate`.
3. Для предварительной проверки использовать bundle Actions либо отдельно разрешенный draft/check release. Установщик намеренно игнорирует drafts/prereleases: выбор конкретного проверочного артефакта требует тестового стенда с подменой ответов API, а не публикации стабильного релиза до приемки. Для локальной проверки wheel достаточно установить его в отдельный venv; это не заменяет окончательную проверку доставки после публикации.
4. После отдельного разрешения создать тег `v2.5.2.post2` на согласованном commit. Создать draft Release этого тега, загрузить из одного bundle: единственный `codex_dispatcher_v2-2.5.2.post2-py3-none-any.whl`, `install-standalone.sh`, `uninstall-standalone.sh`, `config.example.yaml`, `SHA256SUMS`, `v2.5.2.post2.md`. Сверить `sha256sum -c SHA256SUMS`, версию wheel и шаблона. Вставить notes из `v2.5.2.post2.md`.
5. Проверить assets и их GitHub SHA-256 digest, затем опубликовать стабильный Release (не prerelease). Проверить `/repos/heroicrealm/CodexAgent/releases/latest`, чистую установку и повторный запуск установщика. Не смешивать артефакты разных сборок. PyPI и git clone для установки приложения не требуются.

Издатель отвечает за доверенные release assets: SHA256SUMS доставляется через HTTPS из того же конкретного релиза; при наличии GitHub asset digest установщик сверяет и сам manifest. Это контроль целостности, не отдельная криптографическая подпись издателя. Зависимости Python устанавливаются pip из настроенного индекса; сам диспетчер — только из wheel релиза.

При изменениях протокола поставки загрузить свежий `install-standalone.sh` из нужного релиза. Исходник встроенного установщика — `scripts/standalone_distribution.py`; после правок выполнить `python3 scripts/embed-standalone.py`, закоммитить оба скрипта. При несовместимости старого установщика документировать это в release notes. Поставка поддерживает WSL2 и Ubuntu native без службы. Service (systemd) и Docker — отдельные этапы.

Переход с 2.5.2.post1 требует одного ручного скачивания нового установщика и SHA256SUMS из одного конкретного Release; затем используется `codex-dispatcher-install`. Проверка SHA выполняется до раннего выхода при равной версии. Никогда не редактировать опубликованный installer asset: даже комментарий меняет его SHA. При несовпадении пользователь получает URL релиза и вручную повторяет скачивание/проверку.

До публикации latest указывает на прежнюю стабильную версию. Новый скрипт будет отказывать по SHA — это ожидаемо. Проверять candidate в изолированном стенде с mock Release API (см. отчет приемки), не ослабляя production-проверку.
