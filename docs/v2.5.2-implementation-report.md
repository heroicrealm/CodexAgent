# Отчет V2.5.2 Standalone — передача на ручную приемку

Дата: 2026-11-16. Ветка: `V2_5_2_WSL_DISTRIBUTION`, репозиторий `heroicrealm/CodexAgent`.

Реализация: `9596fb9`; уточнение Standalone: `399f49f`. Обновленные ТЗ/задание из GitHub включены в основание ветки (`a6195cd`), реализация перенесена поверх них через rebase, без merge. Старое имя ветки сохранено. Результат еще не означает прохождения ручной приемки.

## Аудит и реализация

Проверены актуальные pyproject, CLI/config/example, Runtime, InstanceLock/monitoring, DB guard, тесты и CI. Команда запуска остается `run`, distribution — `codex-dispatcher-v2`; resolver `--config`/XDG и вложенный `dispatcher.root_path` сохранены.

- Версия пакета 2.5.2, схема 1; `--config-schema-version` получает схему без конфигурации/SQLite. CLI проверяет схему перед изменяющими командами, включая `worktree-cleanup --apply`. Справка, остановка и диагностическое чтение не блокируются несовпадением схемы.
- Только перед `run`/`run --once`: синхронные API → Releases, timeout 3 секунды на запрос, PEP 440, уведомление о новой версии, согласованный вопрос при недоступности API. Нет новых сетевых guards или изменений scheduler/Issue/PR.
- Автономные `install-standalone.sh`/`uninstall-standalone.sh` работают на обычном Linux. Используют metadata пакета, стабильный Release, SHA-256, отдельную генерацию venv и переключение `.venv` после подготовки. При сбоях восстанавливаются YAML/manifest/активная ссылка. Старые поколения сохраняются до удаления.
- При совместимой схеме меняется только метка версии с сохранением комментариев и остальных значений. При несовместимой — отдельный шаблон и ручное согласование. Существующий `config.new.yaml` требует отдельного подтверждения замены.
- Установщик удерживает штатные workspace/database locks. Общий shared-lock установленного пакета наследуется дочерними процессами через существующий механизм InstanceLock; installer/uninstaller требуют exclusive-lock. Это защищает и нестандартный `--config`, сохраняя возможность независимых runtime с разными рабочими каталогами.
- Удалитель проверяет ownership и сохраняет пользовательские данные/credentials. При размещении данных внутри программного venv отказывает в удалении.
- Workflow готовит проверочный bundle без тегов и публикации. Service (systemd) и Docker не добавлены.

## Ограничения и ручная приемка

Полная доставка из настоящего опубликованного Release, интерактивная авторизация, реальная Issue→PR и Ubuntu native вручную еще не проверены. Workflow подготовлен, но серверный CI агент не запускал: коммиты локальные, push не выполнялся. Зависимости bootstrap/runtime требуют настроенного pip-индекса или предварительно подготовленного wheelhouse; сам dispatcher берется из wheel Release, не PyPI. Подпись издателя не добавлена: SHA256SUMS доставляется через HTTPS того же релиза и сверяется с GitHub asset digest при его наличии.

Конфигурация обслуживается установщиком по стандартному/XDG пути; нестандартные YAML согласуются вручную. Полностью поврежденный YAML может привести к отказу, поскольку невозможно доказать остановку по его путям. Экзотическое YAML-представление метки версии, которое нельзя безопасно заменить одной строкой, отклоняется без пересериализации. Чужой venv/CLI не заменяется. Скрипты используют bootstrap venv с PyYAML/packaging, в том числе при удалении.

Приемку выполнить в отдельном Linux-пользователе/тестовой среде WSL2; затем повторить на Ubuntu native, где нет требования запускать/настраивать systemd:

1. Проверить локальный bundle и автономные тесты выше. Для проверки настоящего download/install нужен отдельно согласованный проверочный релиз/стенд; стабильный `/releases/latest` установщик не подменяет drafts/prereleases. До разрешения публикации использовать локальный smoke с подменой API. После разрешенной публикации выполнить `gh release download v2.5.2 --repo heroicrealm/CodexAgent --pattern install-standalone.sh --pattern uninstall-standalone.sh --pattern SHA256SUMS` в пустом каталоге, затем `sha256sum --check --ignore-missing SHA256SUMS` и `sh install-standalone.sh`.
2. В новом терминале, из другого каталога, без активации venv: `codex-dispatcher --help`, `~/codex-dispatcher/.venv/bin/python -m pip show codex-dispatcher-v2`. Проверить PATH и абсолютный `dispatcher.root_path` в основном YAML. Повторить с абсолютным XDG_CONFIG_HOME.
3. Выполнить `gh auth login`, `gh auth setup-git`, `codex login`. Настроить отдельный тестовый repository в `projects`. Для новой БД: `codex-dispatcher db bootstrap`, затем `init-labels`, `run --once`. Проверить `status`/`queue`; запустить `run`, остановить из другого терминала через `stop`. Повторить с `--config /absolute/path` перед подкомандой.
4. Вручную провести тестовую Issue до PR по существующему процессу. Убедиться, что `stop` ожидает текущую работу, а Ctrl+C/`stop --force` сохраняют прежнюю семантику. Это действие выполняет принимающий пользователь; агент PR не создавал.
5. Повторить установку той же версии. Для совместимого/несовместимого обновления использовать тесты `test_successful_compatible_upgrade` и `test_schema_upgrade_repeat_uses_package_metadata` либо изолированный release-стенд с двумя версиями; не менять metadata рабочей установки вручную. Сравнить комментарии/проекты и сохранность БД/worktree.
6. В тестовом YAML изменить схему на 999: `run --once` должен отказать до SQLite/locks, `--help` и остановка доступны. В тесте несовместимого обновления проверить `config.new.yaml` и отдельный вопрос при его наличии. Перенести настройки вручную в новый шаблон, заменить основной файл и повторить запуск.
7. В изолированной среде временно сделать основной API недоступным: выполнить `run --once`, проверить y/n/Enter/Ctrl+C и `codex-dispatcher run --once </dev/null`. Восстановить доступ. Для более новой версии/ошибки только Releases использовать автономные тесты, не публикуя фиктивный стабильный релиз.
8. Во время `run` повторный installer/uninstaller должен отказать, включая runtime с нестандартным конфигом. После остановки выполнить `sh uninstall-standalone.sh`; проверить сохранность YAML, SQLite, workspace/worktree, репозиториев и credentials и исчезновение только собственной CLI-ссылки/venv.
