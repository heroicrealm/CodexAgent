# STAGE_04 — Git worktree, Codex CLI, квоты, вложения и публикация результатов

Статус: утверждено. Репозиторий: heroicrealm/CodexAgent. Ветка: STAGE_04 от main.
Этот документ — нормативное ТЗ этапа 4. Сохранять контракты этапов 1–3; не хардкодить проекты, репозитории и пути.

## 1. Результат этапа
Подтвержденное задание pending автоматически резервируется, готовится изолированный Git worktree, скачиваются вложения Issue, выполняется codex exec, проверяются коммиты, выполняется обычный git push, результат переводится в review. Ошибки и успех публикуются комментариями GitHub Issue. Очередь учитывает лимиты Codex. Приемка, PR и merge не реализуются в этом этапе; контракт очистки после done подготовить.

## 2. Интеграция с существующим кодом
Использовать существующие config, runtime/Lifecycle.submit, storage/SQLite, github.sync, codex, cli и labels. Предыдущие команды init, doctor, poll, poll --watch, queue, show, approve, reject, start, stop, stop --force не должны ломаться.
Сейчас start не запускает polling автоматически — в рамках этапа 4 добавить штатный цикл диспетчера, объединяющий polling, планировщик и исполнение, с сохранением существующих ручных команд. При start обрабатывать только enabled-проекты с актуальным init_status=success и fingerprint; неподготовленные пропускать с предупреждением. Сохранять атомарные операции SQLite, блокировки и устойчивость к повторным запускам.
Статусы Issue: discovered -> pending -> running -> review -> done; failed/interrupted/revoked/rejected/cancelled — существующие альтернативы. Не вводить approved. Диспетчерские quota_available/quota_paused/quota_unknown не являются статусами Issue.

## 3. Планировщик и безопасность подтверждения
Запускать только доступную pending, у которой approved_version == version и актуальный trusted Issue. Непосредственно перед стартом перепроверять GitHub (открыто, ready, значимые поля и версия совпадают), иначе не запускать и привести состояние к утвержденной модели синхронизации. При недоступности GitHub запуск запрещен. Резервирование pending -> running атомарное в SQLite с уникальным attempt_id и started_at; исключить дубли при нескольких процессах и рестарте. Уважать max_parallel_tasks (по умолчанию 1), очередь справедлива между проектами; не запускать после stop. Для каждого задания сохранять repo, issue, версию, ветку, SHA, worktree, attempt, timestamps, exit code, diagnostics, push, comment publication.
Обновление меток GitHub выполняется существующей синхронизацией; ошибки сети не откатывают атомарные локальные решения.

## 4. GitWorkspaceManager
Linux FS Ubuntu/WSL2, не /mnt/c. Использовать paths.workspace/<project-id>/repository как служебный Git-клон и paths.workspace/<project-id>/tasks/issue-<number>/worktree как отдельный worktree. Не менять пользовательский clone. Использовать существующий механизм SSH/gh auth; не хранить пароли ключей.
Ветка берется из Target branch:/Целевая ветка: в подтвержденном Issue, иначе из default_branch/base_branch проекта. Если заданная ветка существует на origin — работать от ее актуального состояния; иначе создать от актуальной ветки по умолчанию. Если целевая ветка совпадает с default branch, создавать отдельную codex/issue-N, не коммитить напрямую в main. Проверять имена через git check-ref-format. Не допускать параллельной работы двух заданий в одной ветке и повторного использования чужой незавершенной работы. Обычный push, никогда force push/rebase/reset --hard/clean в пользовательском каталоге. При конфликте push сохранять локальную историю и диагностировать failed.
Никаких автоматических удалений worktree до done; failed/interrupted/review сохраняют файлы.

## 5. IssueAttachmentManager
До запуска Codex обработать подтвержденное Markdown-тело Issue: ссылки на вложения GitHub (включая изображения и обычные Markdown-ссылки на файлы), но не произвольные внешние гиперссылки. Проверять допустимые домены и редиректы, авторизацию для приватных GitHub вложений, HTTP ошибки, размер и число файлов, уникальность и безопасность имен, путь и symlink, checksum SHA256. Установить конфигурируемые лимиты размера/числа и безопасные значения по умолчанию; ограничить время загрузки и размер после перенаправлений. Внешние URL не скачивать автоматически. Не исполнять файлы. Если хоть одно распознанное вложение не скачано/не проверено, Codex не запускать: failed с error_code=attachment_download_failed, комментарий [ATTACHMENT], локальные артефакты сохранить.
Файлы: paths.workspace/<project-id>/tasks/issue-<number>/attachments/ и manifest.json (source_url, local_path, size, sha256, status); каталог вне worktree, не коммитить вложения. В prompt Codex передать абсолютные локальные пути и инструкцию использовать файлы; исходное описание Issue также передать. Не включать GitHub токены в prompt. Если вложений нет, работать штатно.

## 6. CodexExecutor
Независимый интерфейс CodexExecutor для запуска codex exec в cwd worktree, без интерактивных подтверждений; для утвержденного режима A использовать совместимый с установленной версией флаг автоматического исполнения (возможный --dangerously-bypass-approvals-and-sandbox); проверять доступность/версию, документировать риск широкого доступа к ОС. Формировать prompt из утвержденной версии Issue, ветки, вложений и инструкций: не делать push, не менять GitHub Issues/PR, выполнить доступные тесты и создать Git commit. Вывод сохранять в приватный файл, не в общий JSONL; запретить утечку секретов.
Запускать через существующий Lifecycle.submit() и дочерние группы процессов, не обходить его wait/poll/cancel. timeout_seconds настраиваемый; корректная обработка stop и stop --force. При success проверять git status, наличие коммитов/отсутствие неожиданных незакоммиченных изменений; no-op допустим только при явном подтвержденном объяснении. Диспетчер делает git push, фиксирует result_sha, затем review. При Codex error/timeout -> failed; при force -> interrupted. Автоматического retry Codex нет.

## 7. CodexQuotaProvider и App Server
CodexQuotaProvider независим от CodexExecutor; использовать codex app-server исключительно для чтения квот через поддерживаемый контракт account/rateLimits/read, проверив фактическую версию/протокол. Один служебный процесс app-server на процесс диспетчера, автоматически запускать при start только если quota.enabled=true; взаимодействие JSON-RPC по stdin/stdout с инициализацией, таймаутами, корреляцией ответов и событиями. Процесс зарегистрировать в управлении жизненным циклом, обеспечить отсутствие orphan-процессов. При обычном stop остановить после завершения заданий; при force прервать. При аварии app-server установить quota_unknown, с ограниченным backoff перезапускать; активные codex exec не трогать. App Server и exec работают с одним контекстом авторизации.
Конфиг:
codex.executable: codex
codex.timeout_seconds: 7200
codex.execution_mode: full-auto (название настройки диспетчера)
codex.quota.enabled: true
codex.quota.min_remaining_percent: 10 (валидировать 0..100)
codex.quota.check_interval_seconds: 300
codex.quota.retry_after_reset_seconds: 60
Перед каждым запуском проверять свежие квоты; применимый лимит ниже порога -> quota_paused; равен порогу -> разрешено; неизвестная/недоступная квота -> quota_unknown и блокировать новые задания, если контроль включен. Учитывать все применимые окна и resetsAt; повторная проверка после сброса с задержкой либо по интервалу; после восстановления автоматически возобновить pending. Polling и stop работают во время паузы. Уже запущенный exec не прерывать при достижении порога. Если во время исполнения пришла достоверная ошибка исчерпания квоты, сохранить артефакты, interrupted с reason quota_exhausted, поставить очередь на паузу, не повторять автоматически. Если quota.enabled=false, не запускать App Server и не блокировать очередь. Обычные сетевые ошибки не классифицировать как исчерпание квоты. Не выдумывать точный остаток, если API недоступен.

## 8. TaskResultPublisher
По каждой попытке публиковать один итоговый комментарий в соответствующий Issue (успех/ошибка), с категорией [CODEX], [GIT], [ATTACHMENT], [DISPATCHER], [GITHUB]. При успехе:
[CODEX] Task completed successfully.
Branch: <branch>
Commit: <sha>
Status: Awaiting review.
Started: YYYY-MM-DD HH:MM:SS UTC
Finished: YYYY-MM-DD HH:MM:SS UTC
Duration: HH:MM:SS
Started — атомарное резервирование pending -> running; Finished — завершение Git push и фиксации локального результата (не включать сетевую задержку публикации комментария); Duration — полное время обработки, включая worktree, вложения, exec, push. Время хранить UTC ISO 8601; duration в пределах процесса мерить монотонными часами, после рестарта восстанавливать консервативно по UTC. При ошибке указывать Reason, Status и доступные метрики; если Codex не стартовал, явно отметить.
Публикацию реализовать через SQLite outbox с attempt_id и детерминированным идентификатором комментария, безопасной повторной отправкой после ошибки; перед повтором искать уже опубликованный маркер, чтобы избежать дубликатов при неясном ответе сети. Секреты, токены, приватные пути и сырые stderr не публиковать; для непроверенных ошибок использовать безопасный код. Отказ комментария не отменяет push/review/failed, публикация повторяется позднее. Не публиковать комментарий при каждой временной паузе квоты, если конкретная попытка не завершилась.

## 9. SQLite и логирование
Миграции идемпотентные, сохраняют данные этапов 1–3. Хранить attempts, git paths/sha, start/finish, duration, status, error code, quota state/last observation, outbox. JSONL журнал структурированный без сырых секретов/вывода Codex. Права существующих каталогов 0700 и файлов 0600 соблюдать. Отдельные logs Codex ограничить доступом.

## 10. Остановка, аварии и восстановление
stop: запретить новые задания, дождаться активного Codex и фиксации результата, остановить App Server и завершиться. stop --force: остановить новые задания, SIGTERM/SIGKILL групп процессов через существующий Lifecycle, сохранить результаты, interrupted; App Server также завершить. После crash проверить running, процессы, git состояние, опубликованный SHA и outbox; не повторять Codex без явного решения; не потерять локальные коммиты и вложения; повторять только идемпотентную синхронизацию меток/комментариев. Не чистить данные при неоднозначности состояния.

## 11. TaskWorkspaceCleanup — контракт следующего этапа
При review, failed, interrupted все локальные артефакты сохранять. После успешной ручной приемки и перехода в done, удалить штатным git worktree remove чистый worktree, затем каталог attachments/ с manifest.json и пустой каталог задания. Не удалять удаленную ветку/коммиты. Если незакоммиченные изменения — не применять force, логировать ошибку. Очистка идемпотентна, повторяема после перезапуска, проверяет путь, границы workspace, symlink; после частичной очистки повторяет только оставшееся. Реализовать безопасный интерфейс TaskWorkspaceCleanup в этапе 4, его вызов при переходе в done — в следующем этапе.

## Исправления предварительной приёмки (#12)

Очистка вызывается только с подтверждённым состоянием `done`; подключение её к
приёмке остаётся задачей следующего этапа. `review`, `failed`, `interrupted`
сохраняют артефакты. Перед любым удалением проверяются границы workspace,
symlink, неизвестные файлы, реестр и manifest. Git status проверяет также
игнорируемые файлы. Используется только обычный `git worktree remove`;
ветки и удалённые коммиты сохраняются.

CodexExecutor до создания prompt/log регистрирует их имена в приватном
`.dispatcher-artifacts.jsonl` внутри каталога задания. Другие временные файлы
диспетчера должны регистрироваться через `register_artifacts`.
Для старых заданий без реестра допускаются только prompt/log с точным
`attempt_id` переданной записи (32 шестнадцатеричных символа); неизвестные
попытки автоматически не присваиваются текущему заданию.
Вложения удаляются только по локальным путям manifest; сам manifest и реестр
удаляются после перечисленных ими файлов. Повтор после частичного удаления
обрабатывает оставшиеся файлы. Неизвестные файлы сохраняются с ошибкой
`cleanup_unexpected_file`; некорректные метаданные — с
`cleanup_invalid_manifest` / `cleanup_invalid_registry`, небезопасные пути —
`unsafe_path`. Оператор должен выяснить происхождение неизвестных файлов,
прежде чем повторять очистку.

Распознаются следующие HTTPS URL (путь проверяется целиком):

- `github.com/user-attachments/assets/<uuid>`;
- `github.com/user-attachments/files/<numeric-id>/<filename>`;
- прежние `github.com/<owner>/<repo>/files/<numeric-id>/<filename>` и
  `github.com/<owner>/<repo>/assets/<numeric-id>/<uuid>`;
- `user-images.githubusercontent.com/<numeric-id>/<filename.ext>` и
  `private-user-images.githubusercontent.com/<numeric-id>/<filename.ext>`.

Query-параметры подписанных URL сохраняются. Обычные blob/tree/README/исходники,
release assets, внешние ссылки и произвольные пути не скачиваются. Остальные
разрешённые CDN используются только как назначения проверенных редиректов.
Токен передаётся только github.com/api.github.com; сохраняются лимиты, SHA256
и запрет запуска Codex при ошибке загрузки распознанного вложения.

Автотесты используют локальные Git-репозитории и подмены HTTP/Codex.
Ручная проверка вложений и квот не проводилась; квоты этим исправлением
не изменяются и остаются для отдельной приёмки.
