# ТЗ 6.4 — Мониторинг PR и обработка merge

Проект: heroicrealm/CodexAgent. Ветка: STAGE_06_04 (от STAGE_06).
Статус: утверждено пользователем, 2026-10-25.

## 1. Назначение
Завершить цикл GitHub Issue → Codex → PR → решение человека. Диспетчер никогда не делает merge. Мониторинг выполняется в существующем polling (start, poll, poll --watch), без отдельного сервиса или интервала.

## 2. Утвержденная модель
- Открытый PR: review, без изменений.
- merged PR: done (терминальное состояние), закрыть Issue с причиной completed, опубликовать в исходном Issue однократный комментарий: номер/ссылка PR, пользователь merged_by (если доступен), merged_at, фактическое closed_at Issue, статус done.
- closed PR без merge: rejected (НЕ revoked); сохранить историю и однократный комментарий: PR, закрывший пользователь (через timeline closed event при наличии), closed_at, статус rejected.
- revoked сохраняет прежнюю семантику отзыва подтверждения при изменении постановки; не подменять rejected.
- rejected → pending только после явного нового подтверждения ответственным через существующие CLI/GitHub механизмы; простое изменение Issue не запускает Codex. Повторный approve возможен без редактирования Issue при корректной проверке версии.
- Повторное исполнение: новая попытка, новая уникальная ветка от сохраненного SHA предыдущей попытки, новый PR; старые PR/ветки сохранять. Не переоткрывать старый PR. Если SHA недоступен, не начинать работу и не переходить молча на main.
- done и cancelled остаются терминальными; правила отмены cancelled из спецификации этапа 6 сохраняются.

## 3. Источники и порядок действий
Для merge использовать GitHub PR merged, merged_at, merged_by, merge_commit_sha. Для закрытия без merge — state closed, merged false, closed_at и actor события closed из GitHub Timeline API; при недоступности actor писать «Не удалось определить», не подставлять автора PR.
Время хранить в UTC. Для успешного merge сначала достоверно закрыть Issue и получить фактическое Issue.closed_at, затем опубликовать комментарий, включающий это время. После подтверждения всех обязательных действий финализировать синхронизацию. Отсутствующие операции восстанавливать после сбоя, не повторяя уже сделанные.
Для rejected комментарий писать после фиксации решения; комментарии должны публиковаться ровно один раз на попытку/событие, с устойчивым идемпотентным ключом и восстановлением после неопределенного результата GitHub API.
Сохранять права ответственного за Issue и отдельную роль ответственного за merge; проверить полномочия и свежесть управляющих событий технически.

## 4. SQLite и история
Переиспользовать миграции и таблицы этапов 6.1–6.3, не дублировать схему. Сохранять связь глобальных REST issue_id/pr_id с проектом, номера PR и Issue только в паре с репозиторием; историю попыток, PR, SHA, merge metadata, closed metadata, actor, timestamps, причину rejected, статусы синхронизации/публикации и ошибки. Не более одной активной попытки на Issue. Сохранять старые данные при миграциях. Не смешивать rejected и revoked.

## 5. Git/worktree
Новая ветка должна быть уникальной, начинаться от сохраненного последнего коммита предыдущей попытки; Codex продолжает исправления поверх этого результата. Перед публикацией проверить целевую ветку, наличие diff и корректность ancestry/сравнения; не делать force push. Предыдущие ветки и PR не удалять автоматически. Не начинать повторное выполнение при невозможности безопасно получить исходный SHA или при конфликте активных попыток.

## 6. Восстановление и безопасность
Polling выбирает активные review PR и незавершенные операции синхронизации, даже после перехода статуса или перезапуска. GitHub API errors, 404, таймауты: журналирование и retry, без ложных переходов. После rejected повторное открытие старого PR не должно автоматически менять статус или запускать Codex. После done не выполнять новую попытку. Не создавать дубликаты PR, веток, комментариев. Корректно работать с несколькими проектами и одинаковыми номерами Issue/PR.

## 7. CLI
queue/show отражают review/rejected/done; show содержит активную попытку, ссылку и статус PR, причины rejected, сведения о merge и предыдущей попытке. Сохранять утвержденный табличный формат и совместимость.

## 8. Проверки
Автоматические тесты: открытый PR; merge→done; закрытие Issue completed; комментарий с merged_by/merged_at/фактическим Issue.closed_at; closed-unmerged→rejected; timeline actor/closed_at и fallback; отсутствие дубликатов при повторном polling; retry после частичных сбоев, включая неизвестный результат публикации; перезапуск; явное подтверждение rejected; повторное выполнение с новым PR и новой веткой от прежнего SHA; отсутствие SHA; несколько проектов; reopening старого PR; терминальность done/cancelled; обратная совместимость тестов этапов 1–6.3.
Ручная приемка в heroicrealm/CodexAgentPlayground: (A) merge и проверка закрытия Issue/комментария; (B) закрытие без merge, rejected/комментарий, повторное подтверждение, новая ветка/PR, merge→done.

## 9. Критерии приемки
Все переходы, комментарии, история и восстановление работают, тесты проходят, ручные сценарии подтверждены. Никакого автоматического merge.

## 10. Приоритет решений
Этот документ отражает более поздние явно утвержденные решения пользователя и **заменяет** прежние положения docs/stages/stage-06-spec.md и stage-06-01-spec.md только в части стратегии повторного PR/ветки: вместо reopen старого PR и повторного использования старой ветки — новая ветка от SHA предыдущей попытки и новый PR. Агент должен актуализировать противоречащие документы, не менять остальные решения (включая cancelled) без согласования.
