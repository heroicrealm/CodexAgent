# ТЗ 6.4 — Мониторинг PR и обработка merge

Проект: heroicrealm/CodexAgent. Ветка: STAGE_06_04 (от STAGE_06).
Статус: утверждено пользователем, 2026-10-25.

## 1. Назначение
Завершить цикл GitHub Issue → Codex → PR → решение человека. Диспетчер никогда не делает merge. Мониторинг выполняется в существующем polling (start, poll, poll --watch), без отдельного сервиса или интервала.

## 2. Утвержденная модель
- Открытый PR: review, без изменений.
- merged PR: done (терминальное состояние), закрыть Issue с причиной completed, опубликовать в исходном Issue однократный комментарий: номер/ссылка PR, пользователь merged_by (если доступен), merged_at, фактическое closed_at Issue, статус done.
- closed PR без merge: rejected (НЕ revoked); сохранить историю и однократный комментарий: PR, закрывший пользователь (через timeline closed event при наличии), closed_at, статус rejected.
- revoked сохраняет прежнюю семантику отзыва подтверждения при изменении постановки; не подменять rejected.
- rejected → pending только после явного нового подтверждения ответственным через существующие CLI/GitHub механизмы; простое изменение Issue не запускает Codex. Повторный approve возможен без редактирования Issue при корректной проверке версии.
- Повторное исполнение: новая попытка в канонической ветке поверх опубликованного SHA, обычный push и reopen того же PR; историю сохранять. Если SHA недоступен, не начинать работу и не переходить молча на main.
- done и cancelled остаются терминальными; правила отмены cancelled из спецификации этапа 6 сохраняются.

## 3. Источники и порядок действий
Для merge использовать GitHub PR merged, merged_at, merged_by, merge_commit_sha. Для закрытия без merge — state closed, merged false, closed_at и actor события closed из GitHub Timeline API; при недоступности actor писать «Не удалось определить», не подставлять автора PR.
Время хранить в UTC. Для успешного merge сначала достоверно закрыть Issue и получить фактическое Issue.closed_at, затем опубликовать комментарий, включающий это время. После подтверждения всех обязательных действий финализировать синхронизацию. Отсутствующие операции восстанавливать после сбоя, не повторяя уже сделанные.
Для rejected комментарий писать после фиксации решения; комментарии должны публиковаться ровно один раз на попытку/событие, с устойчивым идемпотентным ключом и восстановлением после неопределенного результата GitHub API.
Сохранять права ответственного за Issue и отдельную роль ответственного за merge; проверить полномочия и свежесть управляющих событий технически.

## 4. SQLite и история
Переиспользовать миграции и таблицы этапов 6.1–6.3, не дублировать схему. Сохранять связь глобальных REST issue_id/pr_id с проектом, номера PR и Issue только в паре с репозиторием; историю попыток, PR, SHA, merge metadata, closed metadata, actor, timestamps, причину rejected, статусы синхронизации/публикации и ошибки. Не более одной активной попытки на Issue. Сохранять старые данные при миграциях. Не смешивать rejected и revoked.

## 5. Git/worktree
Каноническая ветка повторно используется поверх опубликованного SHA предыдущей попытки; Codex продолжает исправления поверх этого результата. Перед публикацией проверить целевую ветку, наличие diff и корректность ancestry/сравнения; не делать force push. Предыдущие ветки и PR не удалять автоматически. Не начинать повторное выполнение при невозможности безопасно получить исходный SHA или при конфликте активных попыток.

## 6. Восстановление и безопасность
Polling выбирает активные review PR и незавершенные операции синхронизации, даже после перехода статуса или перезапуска. GitHub API errors, 404, таймауты: журналирование и retry, без ложных переходов. После rejected повторное открытие старого PR не должно автоматически менять статус или запускать Codex. После done не выполнять новую попытку. Не создавать дубликаты PR, веток, комментариев. Корректно работать с несколькими проектами и одинаковыми номерами Issue/PR.

## 7. CLI
queue/show отражают review/rejected/done; show содержит активную попытку, ссылку и статус PR, причины rejected, сведения о merge и предыдущей попытке. Сохранять утвержденный табличный формат и совместимость.

## 8. Проверки
Автоматические тесты: открытый PR; merge→done; закрытие Issue completed; комментарий с merged_by/merged_at/фактическим Issue.closed_at; closed-unmerged→rejected; timeline actor/closed_at и fallback; отсутствие дубликатов при повторном polling; retry после частичных сбоев, включая неизвестный результат публикации; перезапуск; явное подтверждение rejected; повторное выполнение в прежней ветке и reopen прежнего PR; отсутствие SHA; несколько проектов; reopening старого PR; терминальность done/cancelled; обратная совместимость тестов этапов 1–6.3.
Ручная приемка в heroicrealm/CodexAgentPlayground: (A) merge и проверка закрытия Issue/комментария; (B) закрытие без merge, rejected/комментарий, новое подтверждение, прежняя ветка/PR, reopen, merge→done.

## 9. Критерии приемки
Все переходы, комментарии, история и восстановление работают, тесты проходят, ручные сценарии подтверждены. Никакого автоматического merge.

## 10. Приоритет решений
Стратегия новых ветки/PR на каждую попытку из первоначальной версии 6.4 заменена утверждённым [ТЗ 6.4.1](stage-06-04-01-spec.md): одна каноническая ветка/PR, повторное исполнение и reopen. Исторические отчёты 6.4 сохраняют результаты прежних проверок.

## 11. Уточнения Issue #27
В `rejected` штатная метка `labels.cancelled` является командой окончательной отмены.
Нужно новое доказанное событие `labeled` уполномоченного человека, привязанное к текущей
версии и позднее наблюдения `rejected`; простое наличие метки не разрешает отмену.
Действуют проверки approve (предыдущее наблюдение, version/hash, GraphQL identity/content,
server fence, события readiness, карантин и дедупликация). Событие отмены не может быть
позднее Date ответа GitHub. Одновременные cancelled и approve/reject запрещены, включая
конфликт, обнаруженный только при повторной GraphQL-проверке.
Решение, аудит автора/события и намерение доставки атомарны. Доставка закрывает Issue
`not_planned`, затем очищает доказанно принадлежащие задаче чистые worktree и артефакты.
Ошибки сохраняются; polling возобновляет недоставленные операции после перезапуска,
успешные фазы не повторяет. При неизвестном результате PATCH сначала читает Issue.
Историю SQLite не удаляет. Защита cancelled действует и при reopen.
При отсутствии доказательства исключительного владения веткой сохранять её: имя ветки,
PR и SHA сами по себе не доказывают, что ref не принадлежал человеку до запуска.
Это уточняет условие безопасного удаления ветки в общем ТЗ этапа 6.
Нормативный ручной сценарий и результаты анализа: [Issue #27](stage-06-04-issue27.md).


### Уточнение реализации 6.4.1.6 (Issue #36)

Терминальное состояние `review_on_error` с меткой `dispatcher:review-on-error`
сохраняется до ручного решения человека; автоматических переходов в done/cancelled
или повторных запусков нет. Доказанный merged канонический PR исключает reopen;
сетевые ошибки и одиночные HTTP-коды остаются retry/reconcile. До удаления owned
worktree обязателен обычный push и подтверждённый remote SHA; сбои сохраняют данные
и возобновляют только публикацию. Диагностический комментарий доставляется через
устойчивый outbox без дубликатов. Исправимые ошибки подготовки — discovered с
отзывом подтверждения. Подробности и границы классификатора:
[отчёт 6.4.1.6](stage-06-04-01-06-implementation.md).

без отмены; running завершается естественно. Для обычной и terminal публикации push/cleanup восстанавливаются
без повторного Codex; при ошибке публикации результаты сохраняются.
Требование публикации перед detach cleanup расходится с принятым текущим
контрактом 6.4.1.7: публикация блокируется, dirty cleanup допустим (D2 в отчёте).
Reattach требует свежего наблюдения и нового approve. Равные server timestamps
остаются принятой неоднозначностью, а не доказательством строгого порядка.
Правила конфигурации, безопасного восстановления и команды CLI приведены
