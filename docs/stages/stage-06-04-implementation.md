# Этап 6.4 — реализация и приёмка

## Изменения

`PullRequestMonitor` вызывается существующим `SyncService.poll` (start, poll,
poll --watch), после проверки управляющих команд. Открытый PR остаётся в review;
merged переводит задачу в done, closed-unmerged — в rejected. Источник решения —
аутентифицированный REST GET конкретного PR с проверкой глобальных ID, head/base,
SHA и серверного времени. GitHub проверяет права человека на merge/закрытие PR;
эта роль не ограничена allowlist владельцев Issue. Диспетчер merge не выполняет.

Для rejected actor берётся из последнего Timeline closed event с тем же closed_at.
При недоступности actor записывается «Не удалось определить», автор PR не используется.
Для merge сохраняются merged_by, merged_at, merge_commit_sha и SHA head.
Issue сначала закрывается completed, затем повторно читается фактический closed_at,
и только после этого публикуется комментарий со статусом и ссылкой на PR.

Решения проходят существующий CAS-контракт и сохраняются в истории переходов.
Intent и метаданные решения устойчивы к перезапуску; публикационные операции
продолжаются и после перехода в done/rejected или начала новой итерации.
Комментарий содержит устойчивый marker repository_id/issue_id/iteration_id/pr_id;
перед POST выполняется поиск marker среди всех страниц комментариев. Потерянный
ответ POST восстанавливается поиском уже созданного комментария. Потерянный ответ
закрытия Issue восстанавливается чтением его состояния. Межпроцессный flock
сериализует операции одного PR; сетевые операции не держат SQLite transaction.
Ошибки сохраняются в publication_operations/pr_resolutions и журналируются.

Повторный approve rejected через CLI или свежую allowlisted human GitHub-команду
создаёт новую итерацию даже без изменения текста. Старые approve до решения rejected
не принимаются. Проверяются версия, состояние и токен наблюдения; гонка approve/reject
не считается подтверждением новой итерации. Редактирование rejected обновляет версию
и snapshot, сохраняя rejected до явного подтверждения. Исторические snapshot остаются
в history; done/cancelled и прежний смысл revoked сохраняются.

Новая попытка использует уникальную ветку `codex/issue-N-iteration-I` от сохранённого
head SHA отклонённого PR. Если объекта нет локально, выполняется fetch SHA; при
недоступности Codex не запускается, задача остаётся pending, причина — в журнале.
Прежний чистый worktree перемещается в `previous-ATTEMPT`, вложения — в
`attachments-ATTEMPT`; ветка, PR и артефакты сохраняются. Грязный worktree или
конфликт имён останавливают подготовку. Публикация использует новый PR;
контракт запрещает reuse PR/ветки предыдущей итерации. Force push отсутствует.

queue сохраняет табличный формат и показывает состояния. show дополнительно содержит
текущую итерацию, историю попыток с previous_attempt_id, PR/URL/head SHA,
метаданные решения, фактический closed_at Issue и состояние доставки/ошибки.
JSON расширен соответствующими секциями.

## SQLite

Миграция 604 сохраняет данные 602/603: убирает только UNIQUE(issue_id) из
существующей task_pull_requests, оставляя глобальный pr_id и UNIQUE(repository_id,
pr_number). Перестроение таблицы атомарно, с проверкой foreign_key_check и rollback.
Связи iteration_pr_history и все старые строки сохраняются. Добавлена таблица
pr_resolutions; остальные таблицы и publication_operations переиспользуются.
Миграция повторяема, операционный reset 602 повторно не выполняется.

## Автоматическая проверка

Запуск: `bash scripts/test.sh` в окружении с установленным `.[test]`.
Новые тесты: open, merge, completed/actor/time, rejected и fallback Timeline,
404/невалидное доказательство, повтор polling, потерянные ответы PATCH/POST,
повторное чтение Issue, сбой меток, новая SQLite connection после сбоя,
сериализация мониторов, интеграция с polling, stale/new GitHub approve,
неизменённая/изменённая версия rejected, новый PR/итерация, multi-project,
терминальность, миграция с реальной историей и FK, сквозной scheduler retry
с настоящим локальным Git и новая ветка от предыдущего SHA.

Итоговый полный прогон: **446 passed, 30 subtests passed**; compileall и
`git diff --check` также прошли. Проверка выполнена во временном virtualenv
с установленным `.[test]`; зависимости проекта не изменялись.

Прежние тесты обновлены только там, где ТЗ 6.4 явно меняет договор: retry rejected,
новый PR вместо reopen, обновление версии rejected, версия схемы и поля show.

## Ручная приёмка в heroicrealm/CodexAgentPlayground

1. Настроить отдельный workspace и проект с repository
   `heroicrealm/CodexAgentPlayground`, allowlist ответственного и GitHub credentials.
   Выполнить init, создать ready Issue, poll, show, approve и start.
2. Сценарий A: дождаться review, вручную merge PR в GitHub, выполнить poll.
   Проверить done в queue/show, Issue closed/completed и единственный комментарий
   с PR, merged_by, merged_at и Issue.closed_at из GitHub. Повторить poll и restart:
   комментарий и переход не дублируются.
3. Сценарий B: для другого Issue закрыть PR без merge. После poll проверить rejected,
   actor Timeline и closed_at. Переоткрытие старого PR и редактирование Issue
   сами по себе не запускают Codex. Закрыть старый PR снова, явно выполнить approve
   текущей версии (CLI либо свежая командная метка от allowlisted human).
4. Дождаться новой попытки: проверить новый PR/ветку, прежние PR/ветку и историю
   show. `git merge-base --is-ancestor OLD_HEAD NEW_HEAD` должен завершиться 0,
   initial_sha новой попытки равен сохранённому OLD_HEAD. Вручную merge новый PR,
   затем poll: done и закрытый completed Issue.
5. Во время доставки отключить сеть/остановить процесс, восстановить и выполнить
   poll: недостающие операции доставляются, комментарии не дублируются.

Ручные операции в Playground оставлены отдельной приёмке; автоматические тесты
не меняют GitHub. Автоматическая очистка и окончательная отмена остаются объёмом
последующих этапов; прежние ветки/артефакты сохраняются. Гарантия восстановления
комментариев предполагает сохранность служебного marker в GitHub; удалённый
пользователем уже подтверждённый комментарий автоматически не восстанавливается.
