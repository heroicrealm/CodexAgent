# STAGE_03 — Очередь заданий и ручное подтверждение

Статус: утверждено. База: main. Репозиторий диспетчера: heroicrealm/CodexAgent.

## Границы этапа
Реализовать очередь, CLI-управление подтверждением, управление командами через GitHub Labels, начальную настройку меток и контроль готовности проектов. Не реализовывать Codex executor, worktree, публикацию PR и автоматический merge (последующие этапы). Сохранить совместимость с этапами 1–2, включая Store.confirm, миграцию №2, polling, lifecycle и существующие настройки.

## Состояния
discovered — ожидает подтверждения; pending — подтверждённая актуальная версия, ожидает исполнения; rejected — отклонено; revoked — утрачена готовность. Сохранить running, review, done, failed, cancelled, interrupted для последующих этапов. approved как отдельное состояние запрещён.
Утверждённый переход discovered -> pending по атомарному compare-and-set версии и доступности; discovered -> rejected при отклонении; снятие ready до запуска -> revoked; возврат ready -> discovered без подтверждения; значимое изменение Issue до запуска -> discovered и сброс approved_version. Активные/терминальные попытки polling не переписывает. Первое атомарно зафиксированное решение approve/reject выигрывает; последующее противоположное решение не меняет состояние молча. Повторный approve не создаёт повторного исполнения. Повторный запуск только через отдельный retry в соответствующем этапе.

## CLI
Реализовать queue, show PROJECT ISSUE, approve PROJECT ISSUE, reject PROJECT ISSUE. Учитывать существующий формат команд и --config. Команды работают при остановленной службе. Перед approve/reject сверять актуальность Issue и ожидаемую версию; при недоступности GitHub не подтверждать неподтверждённую актуальность. Операции SQLite атомарные, история включает источник cli/github, время, версию, действие и результат. Никаких запусков Codex в этапе 3.

## GitHub Labels
Конфигурация каждого проекта: labels.<key> в виде {name, color, description}; поддержать прежний строковый формат labels.ready. Цвет: RGB hex из 6 символов без #; description необязателен. Ключи: ready, discovered, approve, reject, pending, running, review, done, failed, rejected, revoked, cancelled, interrupted. Уникальные имена меток в пределах проекта, с учётом регистронезависимости GitHub. Имена настраиваемы; проектно-специфичных hardcode нет. Значения по умолчанию для новых меток: dispatcher:<key>; для ready сохранить codex-ready. Предложенная палитра: ready 0E8A16, discovered D4C5F9, approve 0E8A16, reject B60205, pending FBCA04, running 1D76DB, review 5319E7, done 0E8A16, failed D93F0B, rejected B60205, revoked C2E0C6, cancelled E99695, interrupted F9D0C4.

approve/reject — временные управляющие метки; другие dispatcher:<state> — индикаторы состояния. ready остаётся независимой меткой допуска. После подтверждения любым каналом убрать управляющие метки и прежнюю индикаторную метку, выставить pending; после отклонения — rejected. Ручная установка pending НЕ является подтверждением. Управляющие метки обрабатывать только от доверенного источника, применяя allowlist и доступность Issue; не принимать комментарии за команды. Для GitHub-решений обеспечить проверку инициатора: не доверять одному текущему наличию метки, если невозможно доказать, что её поставил уполномоченный пользователь (использовать проверяемую историю событий GitHub или иной безопасный механизм; при невозможности — не подтверждать и диагностировать). Не считать изменение меток диспетчером новым действием оператора. После решения управляющая метка снимается, чтобы не подтверждать новую версию автоматически. Если Issue меняется до применения команды, требовать нового подтверждения актуальной версии. Повторная доставка событий и ошибки сети не должны приводить к повторному подтверждению. Согласовывать GitHub с SQLite через идемпотентную повторяемую синхронизацию; SQLite — источник истины, сбой API не откатывает уже зафиксированное решение, но виден в журнале.

## init и doctor
Добавить команду init: для каждого enabled проекта проверить GitHub доступ, получить метки, создать отсутствующие с именем, цветом и описанием. Существующие не изменять. init --update дополнительно обновляет цвет/описание существующих меток (не переименовывает и не удаляет их). init повторяем, независим по проектам; ошибки одного не блокируют остальные. Не создавать тестовых меток. doctor — только read-only диагностика, проверяет конфигурацию, авторизацию, доступ, наличие меток, состояние инициализации и актуальность fingerprint; при невозможности достоверно проверить write-права честно сообщить ограничение.

После успешного init в конфиг проекта атомарно записать init_status: success, очистить init_message, сохранить init_fingerprint; при ошибке init_status: fail, init_message: безопасное описание, fingerprint недействителен. Отсутствующий статус означает неинициализированный проект. Записывать YAML атомарно (временный файл в той же директории, fsync/replace, сохранение прав, предотвращение потери конкурентных изменений). Не записывать секреты в init_message. Fingerprint — детерминированный SHA256 по существенным параметрам инициализации (repository, именам меток, при необходимости другим критичным настройкам), с канонической сериализацией; цвета/описания не должны блокировать start до init --update. Изменение repository или названий меток делает success неактуальным.

start, poll, poll --watch должны исключать enabled проекты без актуального init_status:success + fingerprint, писать предупреждение в лог и выводить диагностическое сообщение пользователю. При наличии готовых проектов остальные продолжают работу; при отсутствии готовых включённых проектов start завершается ошибкой. Не запускать автоматический init при start. Обычный start не должен создавать метки в репозиториях. Прямые CLI-команды обработки задач также не должны обходить проверку готовности.

## Надёжность и безопасность
SQLite транзакции и CAS, уникальность repo+issue, защита от гонок между CLI, polling и GitHub; журнал решений; безопасные повторные попытки синхронизации меток; ограниченные тайм-ауты; отсутствие автоматического Codex запуска; отсутствие секретов в логах. Не нарушить stop/stop --force и совместимость миграций. GitHub API писать через существующую авторизацию gh, без хранения токенов в YAML. Сохранить независимость проектов. При частичной ошибке init уже созданные метки не удалять.
