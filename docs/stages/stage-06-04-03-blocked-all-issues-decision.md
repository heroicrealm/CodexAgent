# Решение по состоянию blocked — все типы Issue

**Статус:** утверждённое архитектурное дополнение; реализация требует отдельной проверки и приёмки.
**Ветка:** STAGE_06_04_03. **Контекст:** выявленная при тестировании 6.4.3.3 неоднозначность pending при устранимых ошибках подготовки.

## 1. Область действия

Единое состояние `blocked` и метка `dispatcher:blocked` применяются ко **всем** управляемым Issue: обычная с Codex, ручная (`run_codex:false`), контейнер с Codex и контейнер без Codex. Это не синоним `failed`, `rejected` или `review_on_error`.

`blocked` означает: диспетчер установил **конкретное препятствие**, требующее действия пользователя, и безопасное автоматическое продолжение невозможно. У него должны быть фиксированный код, причина, действие, исходная фаза и поколение обработки. Контейнер в `awaiting_children` с конфликтом состава/детей тоже может потребовать `blocked` — интеграционную семантику закончить в 6.4.3.4–6.4.3.6, не имитируя её сейчас.

Не помещать Issue в `blocked` при нормальном ожидании очереди, детей или квоты, при одиночных временных API/сетевых отказах, при ещё выполняющемся Codex, при уже терминальном состоянии. Уважать текущий emergency stop/detach, `review_on_error`, `rejected`, `done`, `cancelled`.

## 2. Переходы и восстановление

- Для ошибок подготовки разрешить `pending → blocked` с зафиксированным достоверным диагностическим основанием.
- Из `blocked` после исправления — **не безусловное автоматическое продолжение**; новое `dispatcher:approve` с проверкой полномочий, version, GitHub observation и отсутствия нерешённого препятствия должно вернуть в `pending` с безопасной новой попыткой подготовки. Применить существующую модель повторных решений, защиту от повторных событий и version fencing.
- Если причина устранилась без изменения пользовательского YAML и без новой команды, наблюдение можно зафиксировать, но политика повторного запуска должна оставаться явной и одинаковой для всех типов. Не переводить чужую Issue автоматически в running.
- Сохранять каноническую ветку/PR и ранее опубликованные ресурсы; `blocked` не снимает branch ownership и не разрешает retarget. В частности, изменение YAML с чужой ветки на новую **само по себе** может остаться `container_branch_conflict`: при уже закреплённой ветке нужны безопасная явная процедура освобождения ещё не опубликованного claim либо новая Issue.
- Предусмотреть безопасный возврат из `blocked` в прежнюю фазу для поздних конфликтов (в том числе `awaiting_children`) лишь после согласования конкретной матрицы переходов, с сохранением immutable snapshots и intent/recovery. Нельзя бездумно возвращать поздние задачи в pending и терять интеграционные результаты.
- Избегать нарушения существующих правил `MUTABLE`, подтверждений, `command_guards`, ревокации при редактировании, ожидания после reject и SQLite CAS. Исключить двойное выполнение одной итерации.

## 3. GitHub и UX

- Добавить `blocked` в Config.COLORS, config.example.yaml, init/fingerprint, reconcile, show/queue и тесты; описание метки: «Обработка приостановлена: требуется устранить конфликт».
- Сохранять идемпотентные комментарии о блокировке и её устранении из текущей доработки 6.4.3.3; не отправлять одинаковые при каждом poll, не показывать приватные пути/токены.
- Комментарий указывает безопасное конкретное действие, а не всегда «переименуйте branch», поскольку локальный claim может быть уже закреплён. Состояние и диагностический комментарий согласованы по поколению.

## 4. Реализация и совместимость

Изменения охватывают хранилище состояний, переходы, lifecycle всех видов Issue, синхронизацию меток, CLI, журналирование и диагностику, и требуют тестов каждого режима. **Это сквозная доработка**, превышающая узкую функцию подготовки контейнера 6.4.3.3. Не встраивать частичную реализацию с одним `blocked` для контейнеров при обещании поддержки всех Issue; оформить как отдельный подэтап блока 6.4.3 с собственной матрицей приёмки или согласованным сквозным релизом.

## 5. Минимальная матрица тестов

1. Обычная Issue с Codex и конфликтом ветки: блокировка до запуска, no attempt; исправление и новое approve по правилам ownership.
2. Ручная Issue: аналогичная блокировка без Codex/автосоздания PR.
3. Контейнер с `run_codex=true/false`: блокировка подготовки с диагностикой; после допустимого восстановления нормальное `awaiting_children`.
4. Конфликт непосредственного ребёнка у контейнера после `awaiting_children`: не терять snapshot и интеграционное поколение.
5. Повторные события approve/reject, исправление YAML, изменение version, detach, emergency stop, restart, crash между SQLite и GitHub, duplicate/out-of-order events.
6. Регрессии `failed`, `review_on_error`, `rejected`, `done`, `cancelled` и реальных CLI show/queue.

**Приёмка:** состояние blocked наблюдаемо через GitHub, имеет конкретную причину, не запускает задачу, а разрешённый переход не нарушает прежние ветку/PR и гарантию отсутствия повторного выполнения.
