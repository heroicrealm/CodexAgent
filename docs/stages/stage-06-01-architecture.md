# Архитектура этапа 6: Issue → Codex → PR → завершение

**Статус:** согласованная архитектурная основа; подробные интерфейсы и миграции реализуются в 6.2–6.7.

## 1. Состояния и переходы

| Из | Событие | В | Действия |
|---|---|---|---|
| discovered | Авторизованный approve актуальной версии | pending | Сохранить подтверждение |
| pending | Резервирование | running | Новая попытка |
| running | Codex успешно, commit/push, PR создан или подтверждён | review | Сохранить SHA и ID PR; опубликовать отчёт |
| running / publishing | Ошибка исполнения/публикации | failed / publishing | Сохранить диагностику; публикацию повторять без Codex |
| review | GitHub PR merged | done | Зафиксировать merge, закрыть Issue completed, локальная очистка |
| review | GitHub PR closed unmerged | rejected | Сохранить branch/worktree и замечания |
| rejected | Свежий авторизованный approve | pending | Новая итерация, в том числе при неизменённом Issue |
| pending | Повторная работа | running | Reuse branch/worktree |
| running / publishing | Push и повторное открытие исходного PR | review | Подтвердить head/base/PR ID |
| rejected | Авторизованная окончательная отмена | cancelled | Терминальное решение; закрыть Issue not_planned; безопасно удалить ресурсы |
| done / cancelled | Любые изменения Issue/меток | то же | Не запускать Codex; восстановить терминальные индикаторы |

`publishing` — внутренняя фаза операции, не новая публичная метка без отдельного решения. Переходы должны быть транзакционными с защитой от гонок. При недоступности GitHub не делать вывод о merge или rejection.

## 2. Роли и доверие
- **Issue owner:** разрешает повторную доработку или окончательную отмену; подтверждает конкретную версию/итерацию. Возможен CLI или авторизованное GitHub событие.
- **Merge owner:** проверяет PR и сливает или закрывает его в GitHub. Диспетчер никогда не выполняет merge.
- Обе роли может выполнять один человек. Конкретная политика GitHub прав/allowlist и её конфигурационный контракт должны быть определены в 6.2 с обратной совместимостью; не полагаться на произвольный текст комментария.
- Проверка `approve` только техническая: actor, свежесть события, version/content fingerprint, текущий `rejected`, PR closed/unmerged. Изменение тела Issue не обязательно, но новое подтверждение обязательно.

## 3. Идентификаторы и схема данных
Новые связи — на основе глобальных числовых REST `issue_id`, `pr_id`, не `number`. Номера и repository сохраняются для API/UI. REST ID и GraphQL node_id не смешивать. Пример логической схемы (не готовая миграция):

```sql
CREATE TABLE task_pull_requests (
  issue_id INTEGER NOT NULL,
  pr_id INTEGER NOT NULL UNIQUE,
  repository TEXT NOT NULL,
  issue_number INTEGER NOT NULL,
  pr_number INTEGER NOT NULL,
  head_branch TEXT NOT NULL,
  base_branch TEXT NOT NULL,
  head_sha TEXT,
  pr_state TEXT NOT NULL,
  merged_at TEXT,
  ownership_proof TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  PRIMARY KEY (issue_id, pr_id)
);
```

Также требуются таблица/поля публикационных операций (operation_key, phase, outcome, retries), номер итерации и история переходов, флаги незавершённой очистки. Сохранить `tasks`, `attempts`, `result_outbox`, `history`, `decisions` и совместимость существующих записей. Миграция: additive schema → backfill GitHub ID по repository/number с проверкой → валидация уникальности/ссылок → новые ID-based связи. Не уничтожать старые данные и не подменять отсутствующий ID фиктивным.

## 4. PR и привязка
- Создавать PR только при реальном diff между head и base; no-op без PR не считается `review`, выдаётся явная диагностика.
- Сохранять `issue_id`, `pr_id`, repo, номера, head/base, SHA и URL. Связь PR с Issue не выводить лишь по имени ветки.
- Перед созданием искать существующий связанный PR; после ошибки записи сверять GitHub, проверяя repo/head/base, идентичность Issue и служебный marker в PR body. Маркер — дополнительное доказательство, не единственный источник истины.
- При доработке открыть тот же закрытый PR через GitHub API после push. Если GitHub не позволяет повторно открыть PR, не создавать новый молча: остановить публикацию с диагностикой и операторским решением.
- Удалённую ветку можно удалять только при подтверждённом ownership; пользовательская/общая/целевая ветка никогда не удаляется автоматически.

## 5. Порядок и восстановление
1. Persist intent (публикация/закрытие/очистка) до внешнего действия.
2. Выполнить GitHub/Git операцию.
3. Прочитать подтверждённое состояние удалённого объекта.
4. Транзакционно записать результат и следующий шаг.
5. При рестарте продолжить с первого неподтверждённого шага; reconcile внешние эффекты до повтора.

Повторить публикацию комментария через существующий outbox и маркер попытки. Ошибки push/PR/меток/комментария не должны перезапускать Codex. Merge фиксируется до очистки, cleanup failures записываются и повторяются без отмены `done`. Для `cancelled` решение терминально независимо от успеха cleanup; ошибка удаления требует retry/manual attention.

## 6. Контроль безопасности и гонок
- Отсутствие force push; проверка head SHA, branch ownership, expected state/version перед изменением.
- Сериализация переходов для одного `issue_id`, предотвращение дублирующих попыток и PR.
- Запрет reopen терминальных Issue как способа запуска; GitHub labels — индикаторы, SQLite — источник внутренней терминальности, GitHub PR — источник истины о merge.
- Секреты, сырые stderr, произвольный текст Issues не исполняются и не публикуются.
- Параллельные изменения PR/Issue между чтением и записью требуют повторной проверки, а не предположения.

## 7. Проверки
Автотесты с mock Git/GitHub: обязательный PR; отсутствие diff; PR API timeout после фактического создания; дубликаты; merged→done; closed unmerged→rejected; approve неизменённого Issue; stale approve; reuse worktree/branch; reopen PR; ошибка reopen; отмена и защита чужой ветки; повторный запуск после crash; закрытый Issue; терминальная защита; multi-project одинаковые issue_number; миграция SQLite; stop/force; outbox. Ручные интеграционные сценарии — на выделенном тестовом репозитории, без автоматического merge.
