# ТЗ 6.3 — Надёжная публикация Pull Request

**Репозиторий:** heroicrealm/CodexAgent  
**Ветка:** STAGE_06_03 от STAGE_06  
**Дата:** 2026-10-24  
**Статус:** утверждено (вариант А при отсутствии diff).

## 1. Основание и цель
Соблюдать docs/stages/stage-06-spec.md, stage-06-plan.md, stage-06-01-architecture.md и stage-06-02-spec.md. После успешного Codex обеспечить проверенный commit/push и обязательный PR, только затем атомарный переход running→review. Не нарушать этапы 1–5 и модель SQLite 6.2.

## 2. Commit, diff, push
- Использовать существующие Git/worktree/publisher и хранилища. Не создавать пустые коммиты; учитывать ранее созданные Codex коммиты.
- Проверять наличие фактического diff PR относительно целевой ветки проекта, включая уже существующие коммиты, а не только незакоммиченные файлы. Если diff отсутствует — **вариант А**: фиксировать ошибку выполнения и безопасную диагностику в SQLite, не создавать PR, не выставлять review и не перезапускать Codex автоматически. Сохранять историю попытки и возможность отдельного разрешённого решения; не переводить задачу в done.
- Выполнять только обычный push, без force/force-with-lease. Не перезаписывать чужие изменения; конфликты и non-fast-forward — диагностируемые ошибки. Целевая ветка определяется конфигурацией проекта, без hardcode main.
- После push подтверждать опубликованный SHA и ветку через GitHub/Git. Не трактовать только локальный успех команды как подтверждение PR.

## 3. Обязательный PR
- Искать PR по точной идентичности repository, head, base, с проверкой принадлежности текущей Issue и записи SQLite. Нельзя присваивать чужой PR лишь по похожему заголовку/ветке.
- Если подтверждённый подходящий открытый PR уже есть — повторно использовать. Иначе создать обычный (не draft) PR. Закрытый unmerged PR не открывать повторно в 6.3: это этап 6.5; не создавать молча новый.
- Заголовок: [Issue #N] <название Issue>. Body: ссылка на Issue, репозиторий, номер итерации, ветка, SHA, краткий итог; обеспечить явную связь с Issue, не закрывая её до merge.
- Перед созданием и после сетевых ошибок повторно сверять GitHub; учитывать случай «создан на сервере, ответ потерян». Не создавать дубли.
- Сохранять числовой GitHub REST pr_id, pr_number, repository_id, issue_id, head/base/SHA, состояние, привязку к итерации и операцию публикации в таблицах 6.2. Не путать REST ID и number/GraphQL node_id.

## 4. Переход в review
- Только после проверки GitHub, что PR открыт, относится к нужному repository/head/base и содержит diff, с сохранённым PR evidence.
- Использовать CAS/атомарные transitions 6.2 с проверкой версии, итерации, actor/evidence и идемпотентным event_key. Синхронизировать GitHub метку review без ложного успеха.
- Ошибка PR не является ошибкой Codex: сохранить публикацию для возобновления без повторного исполнения агента.

## 5. Сбои и восстановление
- Записывать intent/phase/outcome/retry_count в publication_operations; при рестарте продолжать незавершённую публикацию после сверки remote branch и PR.
- Покрыть сбои до/после push, до/после создания PR, потерянный ответ API, частичную запись SQLite, конкурирующие циклы scheduler и повторный polling.
- Не выполнять сетевые операции внутри долгих SQLite транзакций; безопасные ошибки и логирование без секретов.
- Не делать автоматический merge, мониторинг merge→done, reject/reopen/cancel, удаление веток — это 6.4–6.6. Общий outbox и сквозное восстановление — 6.7, но собственная публикация должна восстанавливаться уже сейчас.

## 6. Тесты
Покрыть mock Git/GitHub и временную SQLite: обычный happy path; PR уже существует; нет diff (вариант А); коммиты уже созданы; non-fast-forward; ошибка push; API timeout и потерянный ответ create; рестарт после push; рестарт после PR; чужой PR; закрытый PR; неверные head/base; многопроектность с одинаковыми issue number; недоступные GitHub REST IDs; гонки и повторные события; отсутствие автоматического Codex retry; невозможность review без PR; совместимость CLI, этапов 1–5. Запуск bash scripts/test.sh.

Агент выполняет commit/push в STAGE_06_03. PR в STAGE_06 только после отдельной приёмки.
