# Этап 6.1 — Аудит и архитектура жизненного цикла PR

**Проект:** Codex Task Dispatcher · **Ветка:** STAGE_06_01 от STAGE_06 · **Дата:** 2026-10-24
**Тип:** документальный этап; изменение runtime-кода не входит в объём.

## 1. Цель
Зафиксировать архитектуру обязательной публикации Pull Request, наблюдения за решениями ревью, повторного выполнения, окончательной отмены и восстановления после сбоев; устранить расхождения с первоначальным планом этапа 6.

## 2. Обязательные решения
1. Каждое успешно выполненное задание завершается обычным push и наличием PR в целевую ветку; только после подтверждения PR возможен `review`. Опциональный PR, `auto_create_pr`, override в Issue и отдельная команда ручного создания PR исключены.
2. Диспетчер не сливает PR. Merge в GitHub означает `done`, закрытие Issue как `completed` и последующую безопасную локальную очистку. Закрытие PR без merge означает `rejected`, ветка и worktree сохраняются.
3. В `rejected` ответственный за Issue может подтвердить новый цикл (даже без изменения текста Issue): `pending → running`; работа продолжается в той же ветке/worktree, PR открывается повторно. Либо ответственный выбирает `cancelled`: закрытие Issue как `not_planned`, безопасная очистка worktree и удаление только доказанно принадлежащей заданию удалённой ветки.
4. `done` и `cancelled` — технически необратимые состояния в SQLite; повторное открытие Issue или перестановка меток не возобновляет исполнение.
5. Две логические роли: ответственный за Issue принимает решение о повторном запуске/отмене; ответственный за merge принимает PR в GitHub. Роли могут совпадать. Авторизация и проверка событий должны быть описаны и применяться ко всем управляющим действиям.
6. Диспетчер проверяет только полномочия, состояние, версию постановки и действительность свежего `approve`, но **не** смысловую актуальность или качество ТЗ.
7. Для новых внутренних связей SQLite использовать числовые глобальные GitHub REST `issue_id` и `pr_id`. `number` сохранять только вместе с `repository` для UI и API. Миграции существующих составных ключей должны сохранять историю.
8. Хранить историю попыток, commit SHA, PR, переходов и публикаций. Восстанавливать частично выполненные операции без повторного Codex, дублирования PR/комментариев и force push.
