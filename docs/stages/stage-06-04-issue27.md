# Issue #27 — анализ и проверка

Рабочая ветка: `STAGE_06_04`. Ручная приёмка остаётся отдельной процедурой.

## Исходное поведение

A: дефект первого корректного подтверждения без редактирования не воспроизведён.
`stale_version` означает отсутствие предыдущего доступного наблюдения той же version/hash
либо несовпадение текущего command_guard. При первом наблюдении редактирования вместе с
управляющей меткой версия меняется; это событие не может подтвердить ещё не наблюдавшуюся
версию. Его отказ сохраняется в decisions/quarantine. Следующий poll с тем же event id
возвращает `duplicate` и прежнюю причину `stale_version`. Снятие/новое добавление создаёт
новый event id и позволяет подтвердить уже наблюдавшуюся версию.
Это воспроизводит форму исходного ответа, но без исходных events/предыдущего snapshot/guard
нельзя установить причину конкретного ручного эпизода Issue #9 задним числом.
Защита approve сохранена. Тест без редактирования доказывает цепочку
`review → rejected → pending` по первому новому корректному событию; `approved` — запись
решения approve и approved_version, отдельного публичного состояния approved в модели нет.
Тест изменения версии доказывает stale → duplicate → новое событие → pending v2.

Дополнительно событие должно быть строго позднее Date наблюдения rejection, lastEditedAt,
первого наблюдения доступной версии и событий title/ready/close/reopen. Одинаковые секунды
не дают достаточного доказательства. При неопределённом event id снятие/установка без
poll отсутствия метки не снимает карантин.

B: `queue.commands` распознавал только approve/reject, а reconcile считал cancelled
индикатором и восстанавливал состояние SQLite rejected. Добавлен action cancel только
для rejected с прежней моделью полномочий и проверки событий, запретом конфликтующих
команд, атомарной записью cancelled/аудита/намерения доставки.

## Реализация

- `queue.py`: распознавание отмены, проверка свежести/конфликтов, сохранение автора и события.
- `storage/__init__.py`, `storage/transitions.py`, `storage/migrations.py`: атомарная отмена
  и совместимая добавочная таблица cancellations; прежние таблицы/история сохраняются.
- `cancellation.py`, `github/sync.py`: доставка not_planned, проверка REST identity,
  восстановление после API/cleanup ошибок и restart, файловая блокировка конкурентных poll,
  отдельные устойчивые признаки успешного закрытия/очистки.
- `workspace.py`: терминальная очистка с общим preflight, поддержкой архивных worktree и
  вложений предыдущих попыток. Проверка SHA/ветки/общего Git repository по attempts/PR history,
  запрет dirty/ignored/untracked, неизвестных файлов и симлинков. Без force удаления.
- `tests/test_issue27.py`: регрессии подтверждения, stale/duplicate, неподтверждённой
  переустановки, версии, actor/bot/identity, исторической метки, конфликтов, терминальности,
  API ошибок/потерянного ответа/restart/очистки и реального Git с чужими данными.
- README и ТЗ: правила метки и ручной сценарий.

Ветки сохраняются консервативно: существующие данные не доказывают исключительное владение
remote ref. Очистка не удаляет ветку по одному имени или ссылке PR. Неизвестные/изменённые
артефакты остаются на диске с delivery_failed и повторной попыткой; терминальная отмена
при этом сохраняется. История attempts/PR/решений не удаляется.

## Ручная проверка heroicrealm/CodexAgentPlayground

Использовать конфигурацию, где Playground включён и инициализирован, текущий gh user входит
в security.allowed_authors. Ниже `codex-dispatcher` запускается с рабочей конфигурацией
(при необходимости добавить глобальный `--config PATH` перед подкомандой). Точное имя
approve взять из labels.approve конфигурации; далее оно обозначено `$APPROVE`.

1. Выбрать тестовый Issue (например #9, только если он ещё не терминальный); получить review
   с открытым PR. Сохранить show --format json, номер PR, SHA и current_iteration_id.
2. Закрыть PR без merge: `gh pr close PR --repo heroicrealm/CodexAgentPlayground`.
   Выполнить `codex-dispatcher poll`, затем `codex-dispatcher show CodexAgentPlayground 9 --format json`.
   Проверить rejected и однократный комментарий. Текст/ready не менять.
3. Удалить оставшиеся approve/reject/cancelled, если они есть. Выполнить poll до наблюдения
   отсутствия команд. Дождаться следующей серверной секунды после наблюдения rejected.
4. Один раз добавить approve:
   `gh issue edit 9 --repo heroicrealm/CodexAgentPlayground --add-label "$APPROVE"`.
   Один `codex-dispatcher poll` должен показать action approve/outcome applied и pending
   с новой итерацией. Повторный poll не создаёт дополнительную итерацию.
   При работающем start состояние может уже перейти в running.
5. Дождаться нового PR, проверить новую ветку от прошлого SHA. Закрыть новый PR без merge,
   выполнить poll, убедиться в rejected. Удалить все командные метки, выполнить poll,
   дождаться следующей серверной секунды. Добавить только отмену:
   `gh issue edit 9 --repo heroicrealm/CodexAgentPlayground --add-label dispatcher:cancelled`.
6. Выполнить poll. Проверить action cancel/applied, cancelled, отсутствие новых попыток;
   `gh issue view 9 --repo heroicrealm/CodexAgentPlayground --json state,stateReason,labels`
   должен показать CLOSED/NOT_PLANNED. Проверить чистые worktree удалены, история SQLite
   и прежние PR сохранены; refs без доказанного исключительного владения сохранены.
7. Повторить poll и перезапустить dispatcher: закрытие/очистка не дублируются. Переоткрыть
   тестовый Issue и добавить approve: SQLite остаётся cancelled, запусков нет.
8. На **другом rejected тестовом Issue** проверить отсутствие разрешения у неуполномоченного
   пользователя и одновременные approve/cancelled: rejected сохраняется. Для повторной
   попытки снять команды и выполнить poll отсутствия, затем добавить ровно одну новую.
9. Для проверки stale изменить текст вместе с approve до poll: ожидать stale_version;
   повтор того же события — duplicate. Изучить show, снять команду, poll отсутствия,
   добавить новую после наблюдения версии. Для карантина при недоступной истории API
   просто восстановить API недостаточно: требуется наблюдённое отсутствие и новое событие.

Эти команды документированы для отдельной приёмки; агент не изменял Playground.
