# Реализация STAGE_03

`config` нормализует строковые и объектные метки в Label; значения по умолчанию
проектно независимы. `initialization` вычисляет канонический SHA256 по repository
и именам, создаёт метки через gh и сохраняет результаты в YAML атомарно под flock.
Цвета/описания не входят в контракт допуска. Конфигурация процесса неизменна до
перезапуска команды. Init не назначает ready ни одному Issue.

`Store` сохраняет миграцию №2 и контракт confirm/reset_confirmation. Дополнительная
таблица decisions создаётся идемпотентно без изменения старых tasks/history.
Транзакция BEGIN IMMEDIATE сериализует решения; проверяет state, available, version
и ожидаемую отметку наблюдения. История решения и переход фиксируются вместе.
Для GitHub уникальность (repository,event_id) блокирует повторную доставку, в том
числе после редактирования Issue. Терминальные и активные попытки неизменяемы.

`queue.decide_cli` получает свежий полный снимок проекта, применяет versioning и
только затем выполняет CAS ожидаемой версии. Сбой fetch не допускает решения.
`queue.commands` использует REST events с проверяемым actor.type=User и allowlist,
GraphQL databaseId/title/body/author/lastEditedAt и локальную историю текущей версии.
Для защиты edit/revert и ready remove/restore проверяются также renamed,
transferred, closed/reopened и labeled/unlabeled ready. Консервативно требуется,
чтобы событие было строго новее всех значимых временных границ. События той же
секунды и события до первого обнаружения требуют нового подтверждения. Отказ
проверки виден в журнале; одно наличие текущей метки не даёт права на переход.

`SyncService` изолирует проекты. После полного fetch SQLite обновляется атомарно;
после проверки команд синхронизируются только настроенные управляющие и индикаторные
метки. Ready и чужие метки сохраняются. Запись SQLite не откатывается при ошибке API;
каждый poll заново сверяет метки, обеспечивая восстановление после частичного сбоя.
Текущие индикаторные метки никогда не используются для подтверждения. Комментарии
не читаются как команды, бот не признаётся оператором.

`doctor` использует только чтение, включая проверку меток и init; локальные каталоги
не создаются. Permissions с GitHub сообщаются как данные диагностики; отсутствие
надёжного доказательства write-доступа даёт WARN без тестовой записи.
Start/_serve требуют хотя бы один подготовленный проект. Poll/watch пропускают
неподготовленные проекты с сообщением и журналом, остальные продолжают работу.
CLI show/approve/reject также требуют актуальный init, queue фильтрует проекты.

Границы: GitHub и SQLite не имеют распределённого CAS. Изменение после финального
сетевого чтения сбрасывает подтверждение при следующем poll; исполнения в этапе 3
нет. Проверяемая история и GraphQL должны быть доступны через текущую авторизацию gh.
Метки до первого poll и неоднозначные по времени события намеренно не принимаются.
Внешние редакторы YAML должны соблюдать sidecar flock, чтобы исключить гонку в
узком интервале между optimistic check и os.replace; изменения до проверки выявляются.
Сбой сохранения YAML возвращает ошибку init, повторный init восстанавливает состояние.

Проверка: `bash scripts/test.sh` (в окружении с test dependencies). Тесты используют
временные YAML/SQLite, подменённый Adapter/gh, гонку независимых SQLite connections,
проверки lifecycle/watch и отсутствие запуска executor. Реальных сетевых вызовов нет.
