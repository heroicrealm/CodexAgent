# Реализация STAGE_03

`config` нормализует строковые и объектные метки в Label. `initialization` вычисляет
канонический SHA256 по repository и именам, создаёт метки через gh и сохраняет
результаты в YAML атомарно под flock. Цвета/описания не входят в контракт допуска.
Конфигурация процесса неизменна до перезапуска команды. Init не назначает ready Issue.

SQLite сохраняет миграцию №2, старые tasks/history и контракт confirm/reset_confirmation.
Таблицы decisions, command_guards и command_quarantine создаются идемпотентно при
открытии существующей базы. Исполнения заданий, retry, worktree, PR и merge нет.
Start остаётся инфраструктурной службой; polling запускают poll/poll --watch.

## Проверяемая привязка GitHub-команды к версии

1. Успешный REST GET списка Issues с `Cache-Control: no-cache` сохраняет HTTP Date
   соответствующей страницы как `server_observed_at`. Заголовок парсится в дату с
   часовым поясом; отсутствие/ошибка Date не мешают регистрации, но запрещают
   неподтверждаемое решение через GitHub. Дата не берётся из локального времени.
2. В той же транзакции, что и Store.apply, command_guards сохраняет серверную
   границу первого наблюдения текущих version/content_hash/available. Обычные
   повторные poll не меняют её; изменение версии/содержимого и отзыв/восстановление
   ready сбрасывают границу. Если Date ранее не был доступен, первый датированный
   ответ устанавливает её. Базы предыдущей реализации не получают разрешение по
   старому локальному history.created_at: сначала требуется серверное наблюдение.
3. Команда принимается только для уже зарегистрированной, доступной версии.
   Если version/hash/доступность изменились с предыдущего наблюдения, команда
   отклоняется и необходима новая подача после регистрации актуальной версии.
   Это намеренно консервативно, даже когда оператор поставил метку после правки,
   но до того, как диспетчер зарегистрировал эту правку.
4. GraphQL проверяет databaseId/title/body/author/state и текущие ready/command
   labels, получает lastEditedAt. После этого REST читает полную историю событий:
   labeled/unlabeled доказывают последнего инициатора конкретной метки. Требуются
   actor.type=User и login из allowed_authors; бот и одно наличие метки недостаточны.
   История после GraphQL покрывает также rename/ready churn между чтениями.
5. GitHub created_at команды должен быть строго больше серверной границы версии,
   lastEditedAt, а также created_at событий renamed/transferred/closed/reopened
   и labeled/unlabeled ready. Значимые события с id не меньше id команды также
   запрещают решение. Edit/revert тела выявляет lastEditedAt; title edit/revert
   и снятие/возврат ready между poll выявляет история, даже при прежнем hash.
   Равенство секунд не трактуется как доказанный порядок и требует новой команды.
6. BEGIN IMMEDIATE атомарно сверяет версию, состояние, available и случайный
   observation_token. UUID обновляется при каждом Store.apply и передаётся вместе
   со снимком из его транзакции. Это защищает от конкурентного polling/CLI, включая
   остановившиеся либо переведённые локальные часы. Старый expected_synced_at остаётся
   совместимым контрактом, но реальные пути CLI/poll используют также UUID.
   Решение и decisions фиксируются вместе; первое решение выигрывает. Уникальный
   (repository,event_id) запрещает повторную доставку, в том числе в новой версии.

Локальные timestamps используются для аудита и совместимости, а не для сравнения
с часами GitHub. Задержка polling сама по себе не инвалидирует новую команду для
неизменившейся зарегистрированной версии. Отсутствие Date/истории/полей proof,
неполный список labels или неоднозначный порядок приводят к отказу.

Границы: доверяем серверным Date/created_at/lastEditedAt и истории GitHub, полученным
через текущую авторизацию gh. GraphQL proof ограничен 100 labels; hasNextPage требует
отказа, чтобы усечённый список не считался полным. REST ограничен 10 000 страницами.
GitHub и SQLite не имеют общей транзакции: изменения после последнего сетевого
чтения будут обнаружены следующим poll, который сбросит pending. Исполнения здесь
нет. Потеря самой SQLite означает потерю локальной истории event id и требует новой
регистрации/подтверждения. Одинаковые секунды могут потребовать повторной команды.

## Отказы, диагностика и безопасная повторная подача

`commands` возвращает отдельный результат для каждого Issue/action; отказ не прерывает
обработку других задач. JSON poll включает outcome/reason/retry, а новый отказ также
попадает в errors с безопасным текстом. Структурированный журнал сохраняет project,
task, action и код причины. Show выводит decisions и command_diagnostics. Содержимое
Issues, stderr/body gh, токены и пути из исключений в эти сообщения не попадают.

Известный event id записывается как использованный даже при отказе. Повторная доставка
даёт duplicate без новой попытки перехода или повторного предупреждения. Новая метка
с новым event id требует новой проверки и может быть подтверждена для актуальной версии.

При недоступном proof или неизвестном event id command_quarantine запрещает повторную
проверку оставшейся метки: восстановление сети само по себе не даёт согласия. Эту
блокировку проверяет также транзакция Store.decide для source=github. Новое предупреждение
пишется однократно. Синхронизация продолжает попытки удалить управляющие метки, сохраняет
ready и посторонние метки, выставляет индикатор состояния из SQLite. Ошибка API не
откатывает решение и не снимает локальную блокировку.

Оператор изучает show, удаляет управляющие метки и выполняет poll до наблюдения их
отсутствия более поздним серверным ответом. Блокировка без event id снимается только
таким наблюдением; равная секунда требует ещё одного poll. Если дата отказа отсутствовала,
первое датированное отсутствие устанавливает границу, следующее более позднее очищает
блокировку. Очистка проверяет актуальный observation_token. После этого можно заново
поставить approve/reject. Явный CLI approve/reject после просмотра show остаётся
альтернативой и всегда проверяет свежий снимок GitHub.

## Init и doctor

GitHubError переносит отдельно числовой HTTP status и тип транспортной ошибки.
init_message формируется из фиксированного имени операции (доступ к repository,
получение/создание/обновление меток) и безопасной категории/HTTP-кода. Сырые ошибки
сервера и исключений не интерполируются. Например: `Label creation (approve) failed:
HTTP 403: forbidden (permissions, policy or rate limit)`. Успех очищает сообщение.
Ошибки проектов независимы, частично созданные метки не удаляются.

Если YAML не удалось сохранить, CLI сообщает `YAML save not confirmed`, безопасную
категорию (права, нехватка места, read-only filesystem, конфликт конфигурации и т.п.)
и возвращает ошибку. Журнал init_save_failed пишется, если доступен. Не утверждается,
что ошибка сохранена в YAML; при невозможности записи лога остаётся CLI-диагностика.
Запись YAML использует временный файл/fsync/replace/fsync директории, сохранение прав,
sidecar flock и проверку конкурентного изменения. Внешние редакторы должны соблюдать
тот же flock, чтобы исключить гонку между финальной проверкой и replace.

Doctor строго read-only: PASS подтверждает только чтение repository и наличие меток;
INFO перечисляет заявленные GitHub push/maintain/admin; WARN всегда поясняет, что
возможность создавать/изменять метки без записи не подтверждена, и предлагает init
или init --update. Флаги repository не выдаются за доказанное управление labels.
Каталоги, конфигурация и внешние метки диагностикой не создаются и не изменяются.

Start/_serve требуют хотя бы один подготовленный проект. Poll/watch пропускают
неподготовленные проекты с сообщением и журналом; остальные продолжают работу.
CLI show/approve/reject также требуют актуальный init, queue фильтрует проекты.

## Проверка

`bash scripts/test.sh` в окружении с test dependencies. Автотесты используют временные
YAML/SQLite и подменённый gh, без реальных сетевых вызовов и запуска executor. Покрыты
рассинхронизация часов, одинаковые секунды, задержка polling, новая версия и replay,
edit/revert и ready churn, потеря доказательства/сбой очистки/повторная подача,
независимые задачи и проекты, HTTP-коды и безопасные init_message, ошибка сохранения
YAML, read-only вывод doctor и совместимость этапов 1–2.
