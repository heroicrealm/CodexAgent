# ТЗ 6.4.1 — единая ветка и PR на Issue; прекращение отслеживания

**Репозиторий:** heroicrealm/CodexAgent  
**Базовая ветка:** STAGE_06  
**Рабочая ветка:** STAGE_06_04_01  
**Статус:** утверждено заказчиком 2026-10-25.  
**Приоритет:** настоящая спецификация заменяет противоречащие положения документов этапа 6 о новой ветке и новом PR при повторной доработке.

## 1. Цель и инварианты
1. Одна GitHub Issue — одна каноническая рабочая ветка и один канонический PR в течение всего срока жизни Issue, включая доработки и повторное подключение после снятия `codex-ready`.
2. Не создавать новую ветку/PR на каждую попытку. Сохранять историю попыток, commit SHA, решений и публикаций в SQLite.
3. Не выполнять merge автоматически, не использовать force push. Учитывать многопроектность: внутренние связи по глобальному REST `issue_id`/`pr_id`, номера только с репозиторием.
4. Сохранять защиту авторизации, `stale_version`, идемпотентность, outbox, восстановление после сбоев, безопасность чужих веток и файлов.

## 2. Повторная доработка
- `review` + закрытие PR без merge → `rejected`, с сохранением ветки, PR, worktree и истории.
- Только новое авторизованное подтверждение → `pending` → `running`; Codex продолжает в той же ветке поверх последнего опубликованного SHA. Новая запись попытки допустима, новая ветка/PR — нет.
- После Codex: commit и обычный push в прежнюю ветку; затем повторное открытие *того же* закрытого PR через GitHub API. Проверить repository, issue_id, pr_id, head/base, SHA и фактическое состояние PR; после подтверждения reopen → `review`.
- Временные ошибки GitHub → устойчивый retry без повторного Codex. Неразрешимая ошибка reopen → `review_on_error`; второй PR не создавать.

## 3. review_on_error
- Новое публичное терминальное состояние `review_on_error`, метка `dispatcher:review-on-error`.
- Применяется при неразрешимой ошибке, например невозможности reopen PR. Обязательно выполнить/подтвердить push имеющихся результатов до очистки.
- Однократный комментарий в Issue: причина, ветка, SHA, прежний PR, состояние публикации и указание на ручное решение.
- После подтверждения сохранности данных безопасно удалить принадлежащий задаче worktree и временные загруженные файлы, исключить Issue из автоматического выполнения и мониторинга. При неудачном push worktree сохраняется и публикация повторяется; терминальное решение не означает разрешение потерять данные.
- Дальнейшее решение — человек в GitHub: при необходимости вручную создаёт PR, затем вручную завершает/отменяет Issue. Диспетчер не меняет терминальное состояние автоматически.

## 4. Снятие codex-ready (detach)
- Удаление `codex-ready` означает прекращение отслеживания, НЕ `cancelled`; вводится внутренний признак `detached`.
- В `discovered`, `pending`, `rejected`, `review` прекратить планирование новых запусков, завершить необходимые публикационные операции, затем безопасно очистить owned worktree и временные файлы; не закрывать PR автоматически.
- В `running` дождаться завершения Codex CLI без принудительного прерывания, сохранить доступные результаты, выполнить commit/push, затем очистить. После обнаружения detach запрещать новые запуски.
- Если push не удался — worktree и неопубликованные результаты сохраняются до успешной публикации или ручного вмешательства. После рестарта операции возобновляются, Codex не перезапускается.
- Однократный комментарий в Issue: отслеживание прекращено, UTC-время, автор снятия метки (по достоверному GitHub timeline событию, если доступен; иначе «Не удалось определить»), ветка, SHA, результат публикации. Не доверять произвольному тексту Issue.
- Исключить detached Issue из очереди/мониторинга после завершения обязательных операций; не удалять аудит, идентификаторы и идемпотентные ключи физически.

## 5. Повторное появление codex-ready
- Новое достоверное событие метки после detach создаёт новую логическую tracking_generation и состояние `discovered`; требуется новое подтверждение. Предыдущие approve/события/outbox не применяются к новой генерации.
- Восстановить канонические ветку и PR; новый PR/ветку не создавать. Проверить фактическое состояние GitHub и наличие SHA. Если PR merged, ветка недоступна, обнаружены несовместимые legacy-PR или иная неоднозначность — безопасно остановиться с диагностикой, не выполнять работу вслепую.
- Терминальные `done`, `cancelled`, `review_on_error` нельзя оживлять повторной меткой.

## 6. Параметры подготовки ветки в GitHub Issue

### 6.1. Формат и значения по умолчанию
В тексте Issue разрешён **один** fenced code block с информационной строкой `codex-config`. Пример:

```markdown
```codex-config
base_branch: develop
branch_name: feature/csv-export
```
```

- `base_branch` (необязательная строка): существующая удалённая ветка **того же** проектного репозитория, от которой создаётся рабочая ветка. Если отсутствует — использовать основную ветку проекта из конфигурации диспетчера (не угадывать default branch GitHub вместо неё).
- `branch_name` (необязательная строка): имя новой рабочей ветки. Если отсутствует — генерировать из номера и заголовка Issue.
- При отсутствии блока применяются оба значения по умолчанию. Неизвестные ключи, дубли блоков/ключей, неверные типы и некорректный YAML — ошибка конфигурации, а не повод молча применить defaults.
- Парсить безопасным YAML loader; никакого исполнения команд, подстановок shell или произвольных YAML объектов. Имена проверять как Git refs, в том числе `git check-ref-format --branch`. Учитывать ограничения длины и нормализацию Unicode, запрет путей/небезопасных символов.

### 6.2. Автоматическое имя
Человеко-читаемый шаблон: `[CODEX-NNNN] Имя issue`, где NNNN — **номер GitHub Issue в её репозитории**, дополненный нулями слева до минимум четырёх цифр. После 9999 номер не обрезается.

Квадратные скобки и пробелы в таком шаблоне не являются допустимым буквальным именем Git ref; фактическая ветка имеет Git-совместимый формат `CODEX-NNNN-<нормализованный-заголовок>`, например `CODEX-0027-Исправить-авторизацию` и `CODEX-12345-Исправить-API`. Нормализация должна быть детерминированной и не допускать пустой суффикс (при пустом/полностью недопустимом заголовке использовать безопасный фиксированный суффикс), коллизии и превышение ограничений Git. Сформированное имя проверяется теми же правилами, что и пользовательское.

### 6.3. Когда параметры действуют
- Перед первым созданием ветки прочитать, проверить и зафиксировать выбранные `base_branch`, `branch_name`, базовый commit SHA, источник значения (explicit/default), номер и версию Issue. Перед фактическим запуском ещё раз проверить актуальность подтверждённой версии и remote refs.
- Codex CLI работает в подготовленном диспетчером worktree; создание веток, push и PR — ответственность диспетчера.
- После создания канонической ветки её имя, исходный SHA и привязка к Issue **не изменяются** при `rejected → pending`, detach/reattach и последующих редакциях YAML. Повторно использовать только прежнюю ветку/PR, даже если параметры Issue были изменены; несовместимое изменение диагностировать, не создавать новую ветку.
- Не использовать существующую чужую ветку, даже если имя совпало с явно указанным или сгенерированным. Не выполнять force push, reset чужой ветки или автоматический выбор альтернативного имени.

### 6.4. Ошибки подготовки и возврат в discovered
Если до запуска Codex обнаружены конфликт имени с чужой удалённой веткой, отсутствие `base_branch`, некорректный YAML/ключи/значения или иная исправимая ошибка параметров:
1. Не создавать worktree, не запускать Codex, не создавать PR.
2. Атомарно перевести `pending → discovered`, отозвать подтверждение и сохранить `configuration_error` (код, безопасное описание, версия/хеш параметров Issue, timestamp, ключ идемпотентности).
3. Однократно опубликовать комментарий GitHub с причиной и инструкцией по исправлению; при сбое публикации комментария использовать outbox/retry, без повторного комментария на каждом poll.
4. Пока версия параметров не изменилась, блокировать новые подтверждения и запуски. После изменения Issue выполнить повторную проверку и требовать **нового** авторизованного подтверждения. Само исправление YAML не запускает Codex.
5. Не использовать `review` или `review_on_error` для ошибки подготовки: результата исполнения и опубликованного PR ещё нет.

Конфликт **любой** чужой ветки в remote является блокирующим, а не поводом присвоить её, добавить числовой суффикс или создать другую. Для одной Issue повторный запуск в доказанно принадлежащей ей канонической ветке — не конфликт.

## 7. SQLite, миграция и совместимость
- Несколько attempts на одну Issue с одним каноническим `pr_id`; сохранить исторические PR от прежнего алгоритма как legacy, без уничтожения данных.
- Добавить необходимые поля/таблицы для tracking_generation, detached_at/by, detach operation intents, review_on_error, состояния push/cleanup и ошибок; определить ограничения уникальности канонического PR и безопасный backfill.
- Хранить выбранные base_branch, branch_name, base SHA, explicit/default, версию Issue, configuration_error, ключи однократных комментариев и историю исправлений; не терять каноническую привязку при повторных попытках.
- Существующие Issue с несколькими PR не переназначать наугад: аудит и диагностика, выбор канонического PR только при однозначном доказательстве.
- Транзакционный persist-intent → внешний GitHub/Git эффект → проверка → persist-result; блокировка на issue_id, retry, идемпотентность, безопасный crash recovery.

## 9. Приёмочные сценарии
1. Issue → PR → rejected → новое approve → та же ветка → push → reopen прежнего PR → merge → done; ровно одна каноническая ветка/PR.
2. Reopen невозможно → push подтверждён → review_on_error, комментарий, cleanup, отсутствие автоматического возобновления.
3. Снятие codex-ready во время running → Codex заканчивает → commit/push → комментарий с actor/time → cleanup → detach.
4. Push error → worktree сохранён, retry без Codex, очистка только после подтверждения публикации.
5. Повторная метка codex-ready → новая generation/discovered, подтверждение, прежние branch/PR, отсутствие действия stale events.
6. Снятие метки в остальных состояниях; рестарты, гонки и повторные события; недоступный Timeline actor; многопроектность и одинаковые issue_number; сохранение legacy-истории; защита чужих ресурсов.
7. YAML: отсутствующий блок/частичные поля/explicit значения, неверный синтаксис и типы, дубли, недоверенный ввод; default base из конфига, генерация CODEX-0001/CODEX-9999/CODEX-12345, кириллица, длинные заголовки, Git ref validation.
8. Конфликт чужой remote ветки, отсутствующий base или неверные параметры → pending→discovered, configuration_error, одноразовый комментарий, блокировка без изменения версии, повторная проверка и новое подтверждение после исправления; Codex/worktree/PR не запускаются.
9. При rejected и reattach параметры YAML не заменяют каноническую ветку/PR; при гонках проверки версии и remote невозможно присвоить чужую ветку.
10. Регрессия тестов этапов 1–6.4, включая stale_version, cancelled, merge и отсутствие force push.

## 10. Границы и приёмка
Этап 6.4.1 выполняется до общей приёмки этапа 6 и PR STAGE_06 → main. Сначала отдельный аудит с отчётом и планом изменений; реализацию начинать только по следующему заданию после рассмотрения аудита. Ручные интеграционные проверки — на отдельном тестовом репозитории.
