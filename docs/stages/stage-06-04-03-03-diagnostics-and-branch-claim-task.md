# Доработка 6.4.3.3 — диагностика блокировок и исправление неопубликованного branch claim

**Статус:** утверждено пользователем к доработке, не принято в эксплуатацию.
**Ветка:** `STAGE_06_04_03`.
**Основание:** ручные испытания контейнеров #80, #84, #88, #92, #100 и успешный #104 в `heroicrealm/CodexAgentPlayground`.

## 1. Проблема

При ошибках подготовки контейнер сохраняет состояние `pending`; диагностику видно только через CLI `show`, в GitHub Issue нет понятной причины и действия. Кроме того, при `branch_ownership_conflict` ветка уже может быть записана как canonical `work_branch` в SQLite: редактирование `dispatcher.branch` в YAML создаёт `container_branch_conflict`, а не исправляет первоначальную ошибку. Предлагать пользователю «переименовать ветку в Issue» без оговорок запрещено: совет невыполним для закреплённого claim.

## 2. Диагностика через GitHub

1. При блокировке подготовки контейнера публиковать понятный комментарий в родительской Issue: код, безопасное описание, этап подготовки, действие для пользователя, статус `pending`. Не раскрывать токены, абсолютные пути, сырой stderr или приватный Git URL.
2. Идемпотентность: durable outbox/receipt для диагностик; одинаковые причины и их повторные poll не создают дублей, включая restart/timeout после отправки комментария. Изменение причины публикует обновление; подтверждённое устранение блокировки — однократное сообщение о возобновлении. Предпочесть стабильный редактируемый комментарий или существующий проверяемый marker, если это согласуется с уже принятой архитектурой.
3. Временные сетевые/лимитные ошибки отделить от конфликтов пользователя: не спамить на каждом poll; при устойчивой недоступности применять ограниченный порог/дедупликацию. `show` сохраняет полную локальную диагностику.
4. Не менять состояния на `failed` или `review_on_error` только ради отображения диагностик. Подготовка остаётся `pending`.

## 3. Разрешение конфликта имени ветки

Не ослаблять инвариант **одна Issue — одна каноническая ветка — один PR** после появления принадлежащих задаче внешних ресурсов. Не реализовывать автоматический retarget по одному факту редактирования YAML.

При конфликте `branch_ownership_conflict` различать:
- **A. Ветка только зарезервирована локально**, ни remote ref, ни локальной рабочей ветки/worktree, ни попыток Codex/PR, ни child YAML с этой базой, ни иных публикаций/владений, ни подтверждённого remote-intent. Допустимо предложить **явную операторскую операцию** освобождения только такого claim, с повторной проверкой текущей GitHub/SQLite identity, уникальности, iteration/version, remote refs и отсутствия зависимых ресурсов. Операция должна быть атомарной на уровне SQLite, идемпотентной и журналируемой; после неё можно изменить `dispatcher.branch` и повторно подтвердить по штатным правилам. Не удалять чужую remote ветку.
- **B. Ветка опубликована или есть хоть один зависимый ресурс, либо подтверждение отсутствия невозможно.** Освобождение запрещено; в диагностике указать безопасный путь — создать новую Issue, а не переименовывать ветку той же задачи.
- **C. Remote ветка уже существовала и принадлежит кому-то другому.** Ни переименование YAML без освобождения claim, ни удаление чужой ветки не допускаются.

**Обязательное проектное ограничение:** если невозможно надёжно доказать критерии A в пределах 6.4.3.3, не включать рискованное освобождение claim. Тогда реализовать лишь диагностическое руководство «создайте новую Issue» и представить отдельное техническое предложение оператора reset-claim на утверждение. Не добавлять произвольный SQL reset, авто-снятие закрепления или новую CLI-команду без тестирования и явного описания полномочий/guards.

## 4. Особенности recovery и пользовательских инструкций

- `branch_ownership_conflict`: «Ветка уже существует или закреплена за другой задачей. Изменение branch в этой Issue может быть отклонено, так как прежнее имя уже сохранено. Пока нет безопасного подтверждённого reset-claim, создайте новую Issue с новым именем».
- `container_branch_conflict`: «Canonical branch этой Issue уже закреплена. Не менять YAML branch повторно; использовать поддерживаемую операцию только при доказанном отсутствии ресурсов либо новую Issue».
- `child_body_conflict`: назвать конкретную дочернюю Issue и сообщить, что автоматическое обновление остановлено; не рекомендовать безусловно переписывать её body.
- `invalid_branch`: показать безопасное имя/контекст проверки и конкретное диагностическое действие.
- После restart сначала reconcile реальные внешние эффекты, а затем обновлять комментарии; нельзя объявлять решение на основании одной локальной записи.

## 5. Тесты

1. Дедупликация одинаковых блокировок через poll, restart, lost response; изменение причины, устранение и единичное сообщение.
2. Пример: существующая чужая remote ветка, возникший `branch_ownership_conflict`, затем изменение `dispatcher.branch` → диагностируемый `container_branch_conflict`, без захвата чужой ветки и без ложного «переименуйте».
3. Доказанно пустой локальный claim (без внешних эффектов) → только явное защищённое освобождение, если оно реализовано; тесты на identity/version/iteration/CAS.
4. Remote published branch, child body уже изменён, PR, attempt, active worktree, ambiguous remote read или конкурентный poll → освобождение запрещено.
5. Регрессия успешного контейнера #104: `awaiting_children`, отсутствие лишних диагностических сообщений и новых PR/commits.
6. Выполнить полный `bash scripts/test.sh` с активированной venv, `git diff --check`.
