# Реализация 6.4.1.3 (Issue #32)

Повторное авторизованное подтверждение `rejected` создаёт одну новую итерацию.
Scheduler использует сохранённую `tasks.work_branch`, проверяет связь предыдущей
итерации, Issue, репозитория и PR, затем читает PR и проверяет GitHub ID, head/base,
репозиторий и отсутствие merge. При неоднозначности Codex не запускается.
При первом исполнении scheduler сохраняет существующим CAS API привязку ветки.
Ранее созданные задачи без сохранённой привязки требуют проверки оператором:
автоматический выбор ветки по похожему имени не выполняется.

## Git и история

При повторной подготовке обязательный `fetch --prune origin` обновляет remote refs;
отсутствующая ветка и ошибка fetch блокируют исполнение. Новая рабочая копия
создаётся точно из текущего `origin/<work_branch>`, независимо от отставания
локальной ветки. Старый чистый worktree переносится в `previous-<attempt_id>` и
остаётся detached; его локальная ветка переименовывается в `archive/<attempt_id>`.
Ни коммиты, ни файлы не удаляются. Незакоммиченные, untracked и ignored файлы
блокируют подготовку. Занятая чужим worktree ветка также блокируется.
Исторический путь попытки обновляется после успешной подготовки.

Резервирование попытки сериализовано SQLite; существующие ограничения владения
веткой и проверки активных попыток сохраняются. Перед push повторно читается
удалённый SHA: допустим исходный SHA или уже опубликованный SHA результата
(восстановление после потерянного ответа push). Иное значение блокирует push.
Push обычный, с дополнительной защитой Git от non-fast-forward; force, merge и
rebase не используются. `initial_sha`, `result_sha`, `remote_sha`, `pushed` и
`recovery_diagnostic` различают исполнение, публикацию и ошибки.

## PR и восстановление

Повторная публикация читает прежний PR по сохранённому номеру и обязательно
сверяет числовой GitHub ID с историей. Поиск похожих PR и создание замены в этой
ветви кода отсутствуют. Открытый PR переиспользуется; закрытый без merge получает
PATCH `state=open`. После PATCH, включая timeout, состояние перечитывается.
Окончательная проверка также подтверждает SHA, repo/head/base, отсутствие merge,
открытое состояние и diff. Только затем допускается переход в `review`.

Основной журнал `pr:<attempt_id>` продолжает обслуживаться существующим recovery
и блокировкой publisher. Дополнительная запись в том же журнале
`reopen:<iteration_id>:<pr_id>` сохраняет устойчивую идентичность операции и её
результат. Отказ reopen, недоступный/merged/чужой PR сохраняют ошибку и оставляют
публикацию на повторе. Новый Codex и новый PR не создаются. После исправления
прав/состояния оператором обычный цикл `start` продолжает публикацию; повторное
подтверждение Issue для этого не требуется. Сырые stderr в сообщения не попадают.

## Миграция 606

`pr_resolutions` получает составной PK `(pr_id, iteration_id)` вместо `pr_id`:
иначе второе решение по переоткрытому PR перезаписало бы первую приёмку. Столбцы,
данные и FK сохраняются. Перестройка таблицы, проверка целостности и маркер 606
выполняются в одной транзакции Store, повторный запуск идемпотентен. Остальные
таблицы и модель статусов не меняются.

Первая операция решения сохраняет ключ `resolution:<pr_id>`; последующие решения
повторно используемого PR получают суффикс `:<iteration_id>`. Уже сохранённые
legacy-операции (в том числе отдельный PR второй итерации) сохраняют свои ключи.
Маркеры комментариев включают итерацию, поэтому повторный poll не дублирует их.

## Ручная приёмка

1. В отдельном тестовом репозитории выполнить Issue до `review`, записать PR ID,
   номер, ветку и SHA первой итерации. Закрыть PR без merge; дождаться `rejected`.
2. Внести и отправить ручной коммит в ту же ветку origin; изменить требования Issue
   и заново подтвердить актуальную версию разрешённым пользователем.
3. Проверить `initial_sha` второй попытки: он должен равняться SHA ручного коммита.
   После исполнения проверить сохранность ручных изменений, тот же PR ID,
   открытый PR, состояние `review`, две итерации и историю SHA.
4. Повторить poll/перезапуск: дополнительных Codex/итераций/PR/комментариев нет.
5. Отдельно запретить reopen: после push остаётся `running` с ошибкой публикации,
   `pushed=1`, новый PR не возникает. Исправить доступ или открыть PR вручную;
   следующий цикл завершает публикацию без Codex.
6. Закрыть PR второй раз: должны сохраниться оба решения и отдельные комментарии.

Живые GitHub PR/Issue для приёмки автоматически не изменялись; ручной сценарий
оставлен оператору. Для доступа к GitHub при разработке использован HTTPS с
credential helper GitHub CLI, поскольку SSH-ключ среды не авторизован.
