# Исправление 6.4.3.4 — семантическая свежесть снимка контейнера

**Статус:** утверждено пользователем; блокирующее замечание ручной приёмки.
**Ветка:** `STAGE_06_04_03`.
**Контрольный пример:** `heroicrealm/CodexAgentPlayground#104`, контейнер `awaiting_children`, blocker `monitor:parent / child_snapshot_stale` после закрытия двух непосредственных детей (#105, #106).

## Проблема

`src/dispatcher/container_monitor.py:collect` сопоставляет `parent['updated_at']` с `accepted['updated_at']` как обязательное равенство. На GitHub timestamp может измениться без изменения значимых данных диспетчера (сервисная активность Sub-issues, метки, комментарии и иные события — точный эффект каждого события проверить тестом и не утверждать без evidence). Изменение времени **само по себе** не является признаком устаревшего снимка. Монитор блокирует исправный контейнер кодом `child_snapshot_stale`.

## Требования

1. Убрать безусловное равенство `updated_at` из проверки актуальности **родительской Issue на этапе мониторинга**. Вместо него применять проверку identity, значимого содержимого, approved version, state, ready, emergency stop, author/ownership, command guards, актуальной итерации и неизменности выбранной canonical branch. Использовать принятые в проекте content hash/semantic fields, не дублируя произвольную модель.
2. Метки, не участвующие в правилах диспетчера, изменения описания/цвета меток, служебная активность Sub-issues и комментарии не должны самостоятельно приводить к `child_snapshot_stale`. Изменение `codex-ready`, `dispatcher:emergency-stop` и других реально управляющих меток должно по-прежнему учитываться и при необходимости останавливать монитор.
3. Изменение **значимых** полей parent (body/YAML, title, author/identity, управляющих меток, approved version, iteration, branch, состояния и т. п.) сохраняет прежние защитные проверки. Нельзя объявлять снимок актуальным, если изменение требует нового подтверждения.
4. Включить семантическую защиту в повторное чтение parent и в проверку перед SQLite commit, сохраняя fail-closed при неоднозначном наблюдении и защите от гонок. Не ослаблять отдельные GET/PATCH safeguards в child body update: там `updated_at` может быть частью precondition против конкурентной записи, и его не надо удалять механически.
5. Разделить общий `child_snapshot_stale` хотя бы в логах/локальной диагностике по фактическому источнику отказа (parent mismatch, child mismatch, remote read, local race); не выводить приватные данные.
6. После достоверной успешной повторной проверки снять старый `monitor:parent / child_snapshot_stale` и восстановить нормальный мониторинг контейнера без ручного изменения SQLite.
7. Автотесты: parent `updated_at` изменился, но существенные поля неизменны — монитор продолжает; произвольная метка/комментарий — не блокировать; изменения управляющих меток/body/title/iteration — блокировать; два закрытых ребёнка и третий non-ready; проверка существующего durable monitor blocker, restart/poll, отсутствие повторного комментария и лишнего поколения; отдельная регрессия child-body CAS.
8. Полный `bash scripts/test.sh`, `git diff --check`. Обновить `docs/stages/stage-06-04-03-04-report.md`, указать фактическую причину и то, что GitHub parent timestamp может изменяться по разным причинам и лишь в данном кейсе является гипотезой до непосредственного сравнения.

## Ручная проверка

Не изменяя #104 и не очищая SQLite, запустить исправленный код и `poll`; `monitor:parent` должен исчезнуть **если** значимые данные совпадают. Далее наблюдать конкретные blockers отсутствующего merge или готовность по действующим правилам 6.4.3.4. Не считать состояние `done` дочерней Issue достаточным без подтверждённого merge её канонического PR в parent branch.

Не создавать PR и не объявлять приёмку без решения пользователя.
