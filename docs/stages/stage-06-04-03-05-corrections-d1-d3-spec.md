## 1. Основания и цель

Ручные функциональные проверки 6.4.3.5 пройдены; при проверке контейнера `run_codex: false` создан ровно один контейнерный PR с коммитами обоих детей. Обнаружены три замечания:

- **D1**: ложноположительная диагностика `child_snapshot_stale` после **запуска ребёнка**, хотя подготовка одного контейнера без запуска детей проходит нормально. Дополнительно утверждена единая для всех Issue семантика `codex-ready` и `approve`.
- **D2**: функция `queue` после рамочной таблицы печатает избыточные строки `Issue N: issue_type=... execution_mode=...`.
- **D3**: наблюдались задержки порядка нескольких минут от запуска контейнера до появления `dispatcher.base_branch` в дочерней Issue при настроенном `poll_time: 15`. Причина неизвестна; до оптимизации требуется инструментирование времени и границ запросов к GitHub API.

Цель — исправить D1/D2 и добавить **временно включаемую** диагностику D3, **не** изменяя пока порядок или частоту исполнения ради ускорения.

## 2. D1 — общий контракт наблюдения и утверждения для всех Issue

### 2.1. Значение меток и состояний

1. `codex-ready` = Issue передана под наблюдение диспетчера. Для прямого ребёнка контейнера наличие этой метки означает, что ребёнок **учитывается и удерживает контейнер в ожидании**, пока не достигнуто терминальное безопасное состояние. Само наличие метки **не** разрешает запуск.
2. `discovered` до первого успешного `approve` = **черновая постановка**. Автор может свободно редактировать title, body, параметры `dispatcher`, добавлять файлы/уточнения. Диспетчер синхронизирует последнее состояние GitHub без конфликта `child_snapshot_stale` только из-за такой правки, без выдачи approve и без создания ветки/запуска ребёнка.
3. `dispatcher:approve` = момент фиксации **актуальной** версии постановки и разрешения на выполнение. Диспетчер должен перед переходом в `pending` прочитать и проверить актуальный GitHub документ; закрепить версию/снимок/guard атомарно согласно действующей модели. Конкурентная правка при подтверждении: перечитать/перепроверить; **не** исполнять версию, которую пользователь не утвердил. Нельзя безусловно `approve` после замеченного изменения, если не доказано, какая редакция была утверждена. Безопасный отказ или повторное утверждение допустимы при неоднозначности.
4. После подтверждения `pending`, `awaiting_children`, `running`, `review` сохраняют действующие барьеры актуальности и процедуры изменения постановки, `rejected` и повторного подтверждения. Редактирование после `approve` **не** получает автоматического нового разрешения.
5. Техническая копия/история несогласованного текста в SQLite допустима для sync и аудита; она **не** является immutable approved snapshot и не должна блокировать свободную редакцию в `discovered`. Не удалять механизмы версий и авторизации, существующие migration/guard и историю согласований.
6. Правило действует одинаково для обычных Issue, непосредственных детей и Issue-контейнеров. Для контейнера после его approve утверждается собственная постановка, но дочерняя Issue в `discovered` остаётся редактируемой и удерживает контейнер в `awaiting_children` без конфликта.

### 2.2. Пример ожидаемого поведения

Контейнер A содержит трёх прямых детей B, C, D. B и C утверждены, выполнены, их канонические PR слиты в ветку A. D имеет `codex-ready`, но ожидает окончания формулировки ТЗ и остаётся в `discovered`. Пользователь многократно редактирует D. A **не** готов к интеграции, однако причина — `waiting`, а не диагностический конфликт. Как только пользователь утвердит D и тот корректно завершится/будет разрешён по общим правилам, A может получить readiness.

Никогда не управлявшийся ребёнок **без** `codex-ready` по-прежнему игнорируется (общее ТЗ 6.4.3). Дочерняя Issue с уже закреплённой веткой/PR, утратившая `codex-ready`, по-прежнему подчиняется ограничениям detach и существующим конфликтам. Это не механизм обхода безопасности.

### 2.3. Служебные правки контейнера

- Нормализация `dispatcher.base_branch` дочерней Issue в `discovered` — допустимое **служебное** изменение. Оно не равно пользовательскому approve, не фиксирует навсегда постановку, не обнуляет `codex-ready`.
- При редактировании пользователем и служебном PATCH одновременно: fresh GET/повторная сверка, сохранение Markdown, неизвестных несвязанных полей не добавлять; применить действующую безопасную YAML-схему, без слепого overwrite. GitHub PATCH не является атомарным CAS, поэтому при неизвестности — fail closed на конкретной операции и безопасная повторная синхронизация, без потери правки.
- Не переназначать `base_branch` у уже закреплённой/исполняемой Issue и не retarget PR автоматически; прежние реальные конфликты `child_active_base_conflict` и т. п. должны работать.
- Проверка timestamp `updated_at` **сама по себе** не должна объявлять `child_snapshot_stale` в `discovered` и не должна инвалидировать доказанную служебную правку после approve; значимые пользовательские изменения в защищённых состояниях сохраняют guards.
- Разделять предварительный sync snapshot, **approved execution snapshot** и **container integration snapshot**. Последний создаётся только по подтверждённой готовности участвующих детей согласно 6.4.3.4.

### 2.4. Ложная ошибка при запуске ребёнка (D1-B)

Проследить фактический источник `child_snapshot_stale` в обработке запуска `discovered → pending → running` ребёнка, включая изменения label/status/updated_at, sync, подготовку и monitor родителя. Различать:
- законные переходы состояния и служебные обновления, выполненные диспетчером;
- изменение неутверждённой постановки в `discovered`;
- существенную редакцию **после** `approve` или конфликт ownership/PR/parent, которая обязана блокировать небезопасную операцию.

Не «лечить» D1 удалением всех guards или игнорированием ошибок. При штатном запуске и завершении детей родитель должен видеть обычное ожидание, затем подтверждённую готовность, без ложных логов `child_snapshot_stale`. Не подавлять настоящие конфликты GitHub/SQLite.

## 3. D2 — восстановить компактный вывод queue

Убрать внерамочную печать `Issue N: issue_type=... execution_mode=...` после таблицы в `src/dispatcher/rendering.py` (`render_queue`). Рамочная таблица `queue` должна оставаться единственным табличным выводом по всем Issue, включая done/cancelled; допустимый существующий отдельный блок контейнерной readiness оставить только если он уже часть принятого UX и не создаёт построчного спама. Поля `issue_type` и `execution_mode` сохранить в `show` и JSON-выводе CLI. Не менять формат JSON без необходимости.

## 4. D3 — опциональный временный timing-trace

### 4.1. Хранилище

Добавить диагностическую таблицу SQLite, например `dispatcher_timing_events`, совместимой безопасной миграцией либо через существующий допустимый механизм schema bootstrap (выбор обосновать). Минимальные поля:
`id`, `timestamp_utc` (точность хотя бы миллисекунды), `project_id`, `repository`, `issue_id` (nullable), `issue_number` (nullable), `cycle_id` (nullable), `operation_id` (nullable), `request_id` (nullable), `event`, `phase` (`start|success|failure|skip|observed`), `duration_ms` (nullable), `queue_wait_ms` (nullable), `http_status` (nullable), `details` (краткий структурированный JSON без секретов). Для нескольких проектов не использовать `issue_number` как глобальный идентификатор.

Приоритет: отсутствие заметного влияния измерителя на ход выполнения. По умолчанию запись **выключена**:
```yaml
diagnostics:
  timing_enabled: false
```
При выключенном режиме никакой дополнительной GitHub активности и минимальные накладные расходы. Не держать SQLite writer lock на время Git/GitHub/ожидания или длительных измерений; не вмешиваться в транзакции состояния. Краткие независимые записи, с разумными busy-timeout/failure isolation: сбой диагностики логируется ограниченно и **не** останавливает выполнение Issue. Предусмотреть ограничение роста данных (ручная очистка/retention конфиг либо документированная команда и безопасное индексирование).

### 4.2. Точки измерения

Регистрировать:
1. старт/конец каждого `poll`/daemon cycle, `poll` без событий, межцикловое ожидание, поиск/выбор задач;
2. обнаружение `codex-ready`, `approve`, переходы `discovered/pending/running/review/done` в SQLite и подготовку дочернего `base_branch`;
3. durable intent/outbox enqueue, dispatch start, successful acknowledgment, retry/error и queue wait для публикаций GitHub labels/comments/issue PATCH;
4. начало/конец GitHub API вызова с method, endpoint *без query tokens*, status/latency/тип операции и безопасным идентификатором request; частичные ошибки, rate limits и повторные попытки;
5. для модификаций Issue/меток: `github_request_start` (отправлен), `github_response_success` (успешный API ответ), **необязательный** `github_readback_confirmed` (отдельный GET совпал по значимому полю). Реализовать **выборочное** readback только в активном diagnostic режиме, без беспредельных повторов и без подмены им корректного state machine;
6. обработку children/monitor, readiness/generation, запуск Codex, Git fetch/worktree/push, создание/обнаружение PR — на уровне, позволяющем видеть долгие ожидания, без дублирования лишних событий.

Для duration использовать `time.monotonic_ns()`; timestamp — UTC wall clock. `cycle_id` и `operation_id` позволяют связать цепь даже при нескольких циклах/retry. Указывать факт, а не предположительное действие: success API != visible UI.

### 4.3. GitHub API и веб-интерфейс — разные события

Разделить:
- **A**: диспетчер фактически послал HTTP/API запрос;
- **B**: GitHub API прислал успешный ответ;
- **C**: последующий API GET подтвердил изменение;
- **D**: пользователь увидел изменение на сайте GitHub.

A–C могут быть инструментированы автоматически; D **нельзя** вывести из ответа API и запрещено автоматически объявлять `github_web_visible` по GET. Для D допускается ручная отметка пользователя вне приложения/в аннотациях к анализу с собственной временной меткой и указанием погрешности наблюдения. Разница B–D не называется «лагом GitHub» без проверки и учёта частоты обновления страницы/браузера.

### 4.4. Просмотр результатов

Предусмотреть CLI `codex-dispatcher timing --project <id> [--issue <number>] [--format table|json|csv] [--limit N]` или столь же удобный согласованный синтаксис. Таблица: локальное читаемое время **с явным часовым поясом** (или UTC), project, issue, event, phase, duration, delta от предыдущего события в выбранном фильтре, cycle/request/operation identifiers. Форматы json/csv сохраняют точные UTC timestamp, без потери миллисекунд. Операции без issue видны в общепроектном выводе. Не включать полные issue bodies, prompts, авторизационные headers, токены или секретные пути в traces.

## 5. Тесты

Обязательны тесты:
1. **Все типы Issue**: правки body/title/YAML до approve в `discovered` обновляются, не запускают Codex, не требуют переутверждения; переход `approve` фиксирует актуальную редакцию, а изменение после утверждения не исполняется молча.
2. Контейнер с B/C done и D в `discovered` с `codex-ready`: D многократно правится, контейнер ждёт без `child_snapshot_stale`; после approve/merge D контейнер готов.
3. Служебная правка `base_branch` контейнером не отзывает approve и не теряет текст; конкурентная пользовательская правка обнаруживается/сохраняется; работающее ownership/branch guard не ослаблено.
4. **Воспроизведение D1-B**: подготовить родителя, отдельно approve и запустить ребёнка, повторные poll/labels, потом merge; нет ложного `child_snapshot_stale`; существенный конфликт всё ещё блокирует.
5. Queue — ровно рамочная таблица без построчного хвоста, `show`/JSON содержат нужные поля.
6. Timing выключен — нет диагностических событий/дополнительных GET; включён — последовательность poll, state, PATCH send/response/readback, циклы без изменений, retry, длительности и корреляционные ID. Failure diagnostic storage не срывает основную операцию.
7. Multi-project и повторные номера Issue корректно фильтруются, CSV/JSON экспорт корректен; sensitive information не логируется.
8. Полный регрессионный набор (6.4.3.3/4/5, обычные Issue, manual Issue, review/rejected, detach, PR resolution, SQLite migration).

## 6. Приёмка

- D1: воспроизведён исходный сценарий «контейнер отдельно → затем approve ребёнка», устранены ложные события, работает свободное редактирование `discovered` у всех Issue, реальная защита после approve сохраняется.
- D2: табличный `queue` снова компактный; JSON и `show` работают.
- D3: на тестовом контейнере доступна временная шкала «сигнал GitHub → sync SQLite → очередь/outbox → отправка API → API success → (при диагностике) readback»; задержки измеримы, а веб-появление отдельно помечается ручным наблюдением.
- Отдельно подтвердить, почему при `poll_time: 15` подготовка `base_branch` заняла приблизительно три минуты. **Не** оптимизировать скорость до сбора измерений и согласования следующего решения.
- Прогнать тесты и показать результаты, обновить документацию конфигурации и CLI, подготовить ручные сценарии Playground. Не закрывать 6.4.3.5, не создавать PR/merge автоматически.

## 7. Не входит в это исправление

Автоматический merge, массовая перестройка scheduler, изменение `poll_time` ради скрытия задержек, переинтеграция 6.4.3.6, единый `blocked` 6.4.3.8, автоочистка веток. Отдельно согласованный постоянный редактируемый комментарий контейнера — другой подэтап.
