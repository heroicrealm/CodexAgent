# Этап 2 — Интеграция с GitHub Issues

**Проект:** Codex Task Dispatcher. **Статус:** утверждено. **Дата:** 2026-10-24. **Ветка:** STAGE_02.
Основание: [общее ТЗ v1.0](../specification.md), разделы 3–6, 9, 11. Принят вариант A синхронизации.

## 1. Цель и границы
Реализовать получение GitHub Issues из всех включённых проектов, проверку доверенности, синхронизацию содержимого и регистрацию в SQLite без дублирования. Реализация должна интегрироваться с инфраструктурой этапа 1, не подменяя её. Очередь подтверждения и команды approve/reject — этап 3; запуск Codex — этап 4; изменение меток и публикация отчётов — этап 5; полноценная служба — этап 6. Допустим отдельный однократный polling-метод/тестовый CLI для проверки этапа.

## 2. Источник и настройки
Использовать существующий YAML и executables.github (обычно gh), штатную авторизацию gh; не хранить токены в YAML, SQLite и логах. Интервал dispatcher.poll_interval_seconds, по умолчанию 30 секунд. Для каждого projects[] с enabled=true использовать repository owner/name, labels.ready и security.allowed_authors. Не хардкодить идентификаторы прикладных проектов. Пустой allowlist не означает «разрешить всех»: fail closed. Поддержать произвольное количество проектов; сбой одного не блокирует остальные. GitHub-запросы выполняются через gh api с безопасным списком аргументов, без shell=True.

## 3. Обнаружение и фильтрация
Получать открытые Issues с настроенной ready-меткой; обрабатывать все страницы, исключать Pull Requests (включая REST-ответы, содержащие pull_request). Сравнивать метки и GitHub login автора согласно правилам GitHub; проверять принадлежность Issue именно настроенному repository, а не доверять полям текста. Для каждого допустимого Issue сохранять GitHub issue id, number, repository, project id, title, body, author, state, labels, updated_at, ссылку, target branch (если указан и валиден), версию/хеш значимых полей, timestamps синхронизации. Текст Issue — недоверенные данные: не исполнять и не интерпретировать как shell-команду. Комментарии не являются командами диспетчеру. Target branch, если отсутствует, трактовать как default_branch, но создание веток не выполнять.

## 4. Хранение и идемпотентность
Использовать SQLite/миграции этапа 1. Уникальный ключ задачи — repository + issue number (или неизменяемый GitHub issue id при сохранении уникальности пары). Повторный polling и перезапуск не создают дублей; обновления атомарны. Сохранять историю существенных изменений/версию, чтобы этап 3 мог сравнивать снимок с подтверждённой версией. Для новой допустимой задачи состояние `discovered` (ожидает ручного подтверждения), `available=1`, `approved_version=NULL`; без автоматического подтверждения и исполнения. `pending` означает подтверждённую актуальную версию, ожидающую запуска; отдельного состояния `approved` нет. Не сбрасывать терминальные состояния и не создавать новую попытку только из-за ready-метки.

## 5. Синхронизация — вариант A
До подтверждения актуализировать title, body, target branch и другие значимые поля; при изменении увеличить версию/обновить content hash. После подтверждения, но до начала исполнения, изменение значимых полей обязано аннулировать подтверждение и вернуть задачу в `discovered`; реализовать безопасный интерфейс/операцию сброса для этапа 3 и тесты с подтверждённой записью. Изменение только updated_at, несодержательных метаданных или комментариев не должно само по себе сбрасывать подтверждение. Для running/review/done и других завершённых попыток не заменять зафиксированный исполняемый снимок: сохранить наблюдаемое изменение отдельно для диагностики. Проверка версии непосредственно перед запуском относится к этапу 3/4.

## 6. Отзыв готовности
Если Issue закрыт, ready-метка снята или автор перестал удовлетворять политике, ранее обнаруженное, но ещё не запущенное задание не должно оставаться пригодным к запуску: перевести в `revoked`, установить `available=0` и сбросить подтверждение. При возвращении готовности перевести существующую запись в `discovered` без подтверждения, не создавая дубль и не перезапуская терминальные попытки. Не считать отсутствие Issue в неполном/ошибочном ответе API доказательством отзыва; сверять состояние только после успешного полного обхода или адресной проверки.

## 7. Ошибки и безопасность
Обрабатывать gh auth failure, timeout, rate limit, secondary limit, сетевые ошибки, malformed JSON и неполную пагинацию. Ограниченные повторы с backoff, учёт Retry-After/соответствующих заголовков при наличии; без бесконечных циклов. Ошибка отдельного проекта не прерывает остальные. Не выводить секреты, содержимое токенов и приватные заголовки. Использовать параметризованный SQL, транзакции и ограничения целостности. Не выполнять операции записи в GitHub на этапе 2.

## 8. Интерфейсы
Выделить тестируемый GitHub adapter (получение, нормализация, фильтрация) и sync service (сопоставление с SQLite, изменения, отзыв, результат прохода). Явно определить контракт результатов: discovered, updated, unchanged, revoked, skipped_untrusted, errors. Не ломать существующие команды этапа 1. Предусмотреть корректную остановку цикла polling через сигнал управления; полноценная systemd-интеграция остаётся этапом 6.

## 9. Тестирование
pytest с замоканным gh и временной SQLite:
1. Два проекта и раздельные настройки; отключённый проект пропускается.
2. Разрешённый/недоверенный автор, отсутствие метки, PR вместо Issue.
3. Несколько страниц, повторный polling и перезапуск — без дублей.
4. Изменение текста до подтверждения обновляет запись.
5. Изменение после подтверждения сбрасывает подтверждение; только метаданные — нет.
6. Закрытие Issue/снятие метки отзывает незапущенное задание; повторная готовность не создаёт дубль.
7. Неполный обход/сетевая ошибка не вызывает массовый отзыв.
8. Rate limit, неверный JSON, ошибка авторизации, сбой одного проекта.
9. Терминальные/исполняемые попытки не перезапускаются и не переписываются.
10. Проверка отсутствия shell-интерполяции и секретов в логах.

## 10. Критерии приёмки
Демонстрация однократного polling по двум проектам, правильной регистрации и синхронизации в SQLite, повторного polling без дублей, сброса подтверждения при изменении текста, безопасного отзыва, устойчивости к сбоям. Все тесты этапа и существующие тесты проходят. Документация включает настройку gh, пример конфигурации и способ ручного запуска проверки. Не требуется реальный запуск Codex, push, PR или изменение меток.

## 11. Артефакты
Исходный код адаптера и синхронизации, необходимые миграции/модели, тесты, обновлённая документация, краткий отчёт разработчика. Все изменения выполнять только в STAGE_02; без merge в main до приёмки.
