# Отчёт приёмки этапа 6.4.1.5

**Этап:** Исправление обработки повторного утверждения `rejected → pending` через GitHub Labels.  
**Репозиторий:** heroicrealm/CodexAgent  
**Рабочая ветка:** STAGE_06_04_01_05  
**Целевая ветка:** STAGE_06_04_01  
**Решение:** принят, разрешена публикация PR для CI и слияния после проверки.

## 1. Исходный дефект
При немедленном добавлении `dispatcher:approve` к Issue в состоянии `rejected` управляющая метка могла исчезнуть, а состояние оставалось `rejected`. Повторная подача команды либо ожидание комментария об отклонении позволяли перейти в `pending`. Через CLI дефект не наблюдался.

## 2. Реализация
Установлена причина: вызов GitHub label reconcile из доставки комментария об отклонении либо из синхронизации удалял ещё не проверенную очередь команду approve. Исправлен `Adapter.reconcile`: удаление управляющей метки производится после подтверждения обработки конкретного GitHub event по SQLite decision receipt либо при подтверждённом карантине. Необработанные события сохраняются до следующего poll. Runtime callers передают Store; без Store команда не удаляется. Сохранены проверки свежести, идентичности, полномочий, версий и CAS, а также политика A для недостоверных команд.

## 3. Проверка соответствия ТЗ
- Переход `rejected → pending` с первого корректного GitHub approve: соответствует.
- Отсутствие зависимости от публикации комментария: реализовано и покрыто тестами.
- Сохранение CLI approve: соответствует.
- Отсутствие дублирования итераций/решений при повторных poll: покрыто тестами.
- Отрицательные сценарии для устаревших событий, неверного actor, отсутствия proof, запрещённых состояний: покрыты тестами.
- Изменения схемы БД и публичного CLI: отсутствуют.
- Отчёт агента о проверках: 577 passed, 30 subtests passed, compileall; результаты получены из отчёта агента, а не независимо запущены при приёмке.

## 4. Ручная проверка
Пользователь провёл проверку в реальном окружении: после появления `dispatcher:rejected` комментарий об отклонении публиковался одновременно либо почти сразу. Добавление `dispatcher:approve` переводило задачу в `pending` с первой попытки; исходный дефект не воспроизвёлся.

**Ограничение:** вручную не удалось обеспечить окно между установкой `rejected` и публикацией комментария. Данный сценарий проверен автоматическими регрессионными тестами; отсутствие ручного воспроизведения не рассматривается как блокирующее замечание.

## 5. Остаточные риски
GitHub DELETE label не поддерживает CAS по идентификатору события; сохраняется узкое внешнее окно гонки при одновременном remove/reapply одной метки. События с равными серверными timestamp по-прежнему отклоняются как неоднозначные. Эти ограничения задокументированы и не требуют ослабления защит.
