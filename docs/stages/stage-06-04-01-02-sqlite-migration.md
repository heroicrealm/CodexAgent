# Этап 6.4.1.2 — модель данных и миграции SQLite

## Зафиксированное решение
Вариант А: одна актуальная ветка на Issue; отдельная таблица истории веток не создаётся. История выполнения остаётся в attempts и журнале событий.

## Анализ
Текущая схема находится в `src/dispatcher/storage/migrations.py`: VERSION=602 и отдельная миграция upgrade604. Таблица tasks хранит идентичность Issue и current_iteration_id; attempts.branch хранит ветку конкретной попытки. Изменять историческое значение attempts.branch нельзя. Механизм prepare выполняет destructive reset для старых версий, поэтому новая миграция должна исключить сброс актуальной БД.

## Изменение модели
Добавить в tasks nullable base_branch, work_branch, branch_source, branch_status, branch_error, branch_prepared_at. Не дублировать существующие поля. NULL обозначает отсутствие определённых параметров. Состояния branch_status: unresolved, resolved, prepared, conflict, failed. branch_source: explicit, generated.

## Миграция
Неразрушающая, идемпотентная, транзакционная миграция после 604; корректная интеграция с version markers, prepare и upgrade604. Сохранить все задачи, попытки, итерации, PR, историю, решения и публикации. Не менять state существующих задач. Выполнить проверки FK и целостности; при ошибке отказать в запуске.

## Ограничения
Защита от коллизий work_branch внутри одного репозитория для активных задач; корректная работа при конкуренции. Без YAML, Git-операций и запуска Codex в рамках этого подэтапа.

## Проверка
Тесты чистой/существующей БД, повторной миграции, rollback, конкуренции, сохранности связей и регрессии. Полная постановка: https://github.com/heroicrealm/CodexAgent/issues/30
