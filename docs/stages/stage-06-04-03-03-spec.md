# ТЗ 6.4.3.3 — первичная подготовка контейнера и дочерних Issue

**Статус:** подготовлено для реализации, на основе принятого ТЗ 6.4.3 и аудита 6.4.3.2.  
**Ветка:** `STAGE_06_04_03`  
**Источники:** [общее ТЗ](stage-06-04-03-spec.md), [аудит](stage-06-04-03-02-audit.md).

## 1. Цель и границы

Поддержать безопасный начальный цикл контейнера: `discovered → pending → awaiting_children`, публикацию собственной канонической ветки контейнера **раньше** подготовки детей, синхронизацию его **непосредственных** Sub-issues и идемпотентную правку `dispatcher.base_branch` учитываемых детей. При этом контейнер не управляет lifecycle ребёнка.

Не реализовывать в этом подэтапе: проверки терминальности/merge детей и их PR; интеграционный Codex или контейнерный PR; ручные обычные Issue; циклы изменения состава после `review`; автоматическое удаление remote branches. Эти функции распределены по 6.4.3.4–6.4.3.7.

## 2. Разбор конфигурации

В существующем fenced YAML `dispatcher` дополнить строгие поля:
- `issue_type: issue|container`, default `issue`;
- `run_codex: true|false`, YAML boolean, default `true`.

Существующие `branch` и `base_branch` 6.4.2 остаются неизменными. Ошибки формата/дубли/неизвестные поля обрабатываются в принятом error-flow (никакого запуска). Исходный body сохраняется, служебный YAML не передаётся Codex. Изменение значимых параметров до исполнения инвалидирует устаревшее подтверждение; служебное изменение `base_branch` ребёнка не должно порождать произвольную отмену подтверждения. Для уже закреплённых веток/PR — fail-closed, не делать скрытого rebase или retarget.

## 3. SQLite

Сделать добавочную, атомарную, повторяемую `upgrade614(db)` в `src/dispatcher/storage/migrations.py`, вызываемую после `upgrade613` в `Store.__init__`. Не менять `VERSION=602` и старые миграции. Сохранить legacy данные и каскадную безопасность; проверить `foreign_key_check` и `integrity_check` до записи marker.

Поля задач: `issue_type` с default `issue`, `run_codex` с default true. Хранить прямые отношения parent/child и метаданные участия; операции подготовки с устойчивыми ключами идемпотентности, фазы `intent → observed/confirmed` и блокировки. Использовать `task_iterations`, `task_pull_requests`, existing branch ownership; не дублировать их. Таблицы интеграционных поколений можно создать по контракту аудита 614, но их функциональное использование перенести в 6.4.3.4–6.4.3.6.

Нельзя терять связь с ребёнком, когда удалена Sub-issue: сохранять историю/diagnostic footprint уже закреплённых ресурсов. При нескольких проектах использовать GitHub ID и repository identity, а не один issue number.

## 4. GitHub и метки

Добавить `awaiting_children` в перечень управляемых состояний, конфигурируемых labels, init fingerprint, reconcile и CLI show/queue. Имя по умолчанию: `dispatcher:awaiting-children`. Создание/проверка выполняется штатным `init`; не назначать новую метку вручную как команду.

Реализовать `Adapter.list_direct_children(project,parent)` через актуальный GitHub Sub-issues endpoint; валидировать identity, полную пагинацию, отсутствие дубликатов/неполных ответов, лимиты API и same-repository принадлежность. При ошибке ни один неполный набор не считается достоверным. Не нужен рекурсивный обход. Не использовать `sub_issues_summary.completed` как доказательство завершения.

Операция обновления body ребёнка: прочитать актуальный Issue, проверить прямую связь, ready и допуск по автору, сравнить прежний body/version/remote freshness, изменить **только** ключ `dispatcher.base_branch`, сохранить остальные YAML/Markdown. Если условная запись GitHub не даёт надёжного CAS и возникла конкурентная правка, блокировать/перечитать, не перезаписывать чужую правку вслепую. Никогда не ставить дочерний `codex-ready` или approve. Игнорировать ребёнка, никогда не управлявшегося и сейчас не отмеченного ready.

## 5. Последовательность контейнера

1. Допустить только актуальную подтверждённую итерацию `pending` с `issue_type=container`; проверить `stop/detach`, конфигурацию, ownership и GitHub freshness.
2. Зафиксировать намерение создания/публикации канонической ветки и target PR base.
3. `fetch origin`, проверить коллизии, существующие refs, владение, защиту базовой ветки; создать или безопасно переиспользовать закреплённую контейнерную ветку.
4. Опубликовать ref без искусственного commit; перечитать origin и подтвердить HEAD, затем записать подтверждение. Не создавать контейнерный PR.
5. Получить полный непосредственный список детей.
6. Для включённых ready-детей без конфликтующих веток/PR подготовить и безопасно сохранить `dispatcher.base_branch=<container branch>`. Остальные сохраняют диагноз/правило игнорирования.
7. При полном подтверждении подготовки перейти `pending → awaiting_children`; при временном сбое выполнить recovery по durable intents, не создавать новых ресурсов.
8. Повторный poll не должен повторять уже подтверждённые записи и комментарии; контейнер не запускает Codex в этой стадии.

Для вложенного контейнера та же логика; вложенный контейнер проверяет наличие подготовленной родительской ветки до закрепления собственной.

## 6. Переходы и совместимость

Расширить охраняемый state machine для `pending → awaiting_children` без обхода проверок `version`, `iteration_id`, ownership и GitHub evidence. Нельзя применять `pending → running` к контейнеру напрямую; у обычных Codex Issue прежний цикл без изменений.

Если некорректная child base, родитель изменён, branch уже закреплена на другом владельце или child active/PR incompatible, записать blocker и операторскую диагностику, не править Issue. Повторять только безопасные операции после нового достоверного наблюдения. При отмене контейнера не отменять и не удалять ресурсы детей.

## 7. Автоматизированные тесты

- Старые схемы → 614, повторное открытие, прерывание миграции, новые поля default, целостность PR/outbox/history.
- `issue_type`, `run_codex`, типы YAML, конфликтующие значения, source stripping.
- Новое состояние в transitions/init/reconcile/queue/show и совместимость legacy задач.
- Container `pending → awaiting_children`, ранее доступная ветка в origin, отсутствие synthetic commits и PR.
- 0, 1, 100+ непосредственных детей, пагинация/частичная ошибка/duplicate/другой repo.
- Учитываемый готовый child с/без YAML; сохранение остального body, повторный poll.
- Не-ready и никогда не управляемый ребёнок: ни правок, ни переходов, ни запуска.
- Already-running/PR-owned child: blocker без переписывания base.
- Crash после remote push до SQLite confirmation: повторное обнаружение, без новой ветки.
- Stale GitHub body, competing edit, lost API response, restart, parallel poll, branch collisions.
- Регрессия обычных Codex Issue и 6.4.1/6.4.2, detach, review_on_error.

## 8. Ручная приёмка

На `heroicrealm/CodexAgentPlayground`: создать контейнер с 2 ready детьми и 1 non-ready; проверить опубликованную ветку до child base, отсутствие дочерних approve, корректную YAML-правку только двух ready, `awaiting_children`, отсутствие PR контейнера и Codex запуска; проверить повторный poll и restart. Отдельно проверить вложенный контейнер с существующей parent branch, незапланированный re-target активного ребёнка и диагностику конфликта.

**Критерий:** контейнер безопасно закрепил свою remote branch, обработал непосредственные учитываемые дети и вошёл в `awaiting_children`, без выполнения детей/создания PR и без регрессий. Приёмка только после CI и ручной проверки.
