# ТЗ 6.4.3.5 — Интеграция контейнерной Issue, публикация PR и ручные Issue

**Репозиторий:** `heroicrealm/CodexAgent`  
**Рабочая ветка:** `STAGE_06_04_03`  
**Дата:** 2026-11-02  
**Статус:** окончательное ТЗ, подготовлено на основании утверждённой архитектуры и решения о варианте А  
**Основания:** [общее ТЗ 6.4.3](stage-06-04-03-spec.md), [приёмка 6.4.3.4](stage-06-04-03-04-acceptance.md).

## 1. Цель

Реализовать потребление подтверждённой готовности контейнера (`ready_for_integration`) и доведение контейнерной Issue до `review`: опциональный запуск Codex, публикация изменений в закреплённую ветку, создание/привязка канонического PR в закреплённую целевую ветку. Также реализовать самостоятельный ручной режим обычной Issue (`issue_type: issue, run_codex: false`) с публикацией ветки и обнаружением созданного человеком PR.

## 2. Инварианты и границы

1. Одна Issue — одна закреплённая каноническая ветка и один канонический PR; повторные `poll` и рестарт не порождают дубликатов.
2. GitHub — источник истины о Sub-issues, ветках, PR и merge; SQLite — durable состояние, история, снимки и намерения операций. Ключи учитывают репозиторий и глобальный GitHub ID.
3. Контейнер проверяет только непосредственных детей; не инициирует их исполнение, не подтверждает, не отменяет и не сливает их PR.
4. Merge PR выполняет только человек. Запрещены автоматический merge, force push, искусственные коммиты для создания diff и присвоение чужой ветки/PR.
5. Переход в `review` контейнера возможен только после подтверждённой публикации канонического PR. Ручная обычная Issue переходит в `review` после публикации ветки, **без** автоматического PR.
6. Существующая обычная Codex Issue (`issue_type: issue, run_codex: true`) сохраняет прежнее поведение.
7. Использовать уже существующие инфраструктуру task operations/outbox/PR resolution, state transitions, защиты branch claim, `review_on_error` и detach; не создавать параллельную модель PR.
8. Повторные циклы после `rejected`, автоматическое повторное выполнение интеграции после изменения состава, расширенные race/crash recovery — функциональный объём 6.4.3.6; при этом **базовые проверки свежести, идемпотентность и сохранность результатов обязательны сейчас**. Общий `blocked` — отдельно 6.4.3.8.

## 3. Модель состояний

| Режим | Переходы данного этапа |
| --- | --- |
| `container, run_codex: true` | `awaiting_children` → `running` → публикация результата/PR → `review` |
| `container, run_codex: false` | `awaiting_children` → публикация/PR → `review`; без вызова Codex |
| `issue, run_codex: false` | `pending` → создание/публикация ветки → `review`; затем подтверждённый merge → `done`, закрытие без merge → `rejected` |
| `issue, run_codex: true` | Без изменений в действующем процессе |

При `no_diff`, ошибке проверки или изменении существенных условий **не** устанавливать `review`. Для контейнера без запущенного Codex сохранять `awaiting_children`. Для контейнера с начатой работой — сначала безопасно сохранить результат; дальнейшую перепланировку передать 6.4.3.6 и не допускать некорректного `review`. Ошибки подчиняются существующей политике `review_on_error`, если она применима, без ложного утверждения об успешном PR.

## 4. Активация готового контейнера

Исполнитель интеграции выбирает только контейнер с `awaiting_children`, подтверждённой `ready_for_integration`, актуальным `integration_generation` и без **активных** блокировок. Записи блокировок `active=0` служат истории и не мешают запуску.

До необратимого действия:
1. Повторно прочитать актуальные непосредственные Sub-issues, их значимые данные и подтверждение merge канонических PR в **закреплённую ветку контейнера**.
2. Сверить семантический состав и readiness snapshot/generation из 6.4.3.4. Не использовать один `updated_at` как основание неактуальности: служебные комментарии/неуправляющие метки не должны создавать ложный конфликт.
3. Проверить согласованность pinned branch/PR identities, подтверждение владения веткой, доступность `origin`, конфликты detach/relations и целевую ветку собственного будущего PR.
4. Получить актуальный удалённый HEAD контейнерной ветки; перед запуском Codex обновить worktree из `origin` без потери локальных результатов и без перезаписи чужого ref.
5. Сохранить durable намерение интеграции с ключом `project + issue_id + generation + operation`; повторный `poll` должен его продолжать, а не создавать новую параллельную работу.

При несовпадении evidence или GitHub API ошибке — fail closed, диагностика через текущий outbox, отсутствие запуска Codex и PR. При изменении состава до запуска повторно проводить мониторинг 6.4.3.4. Готовность `ready=1` из старого poll сама по себе не разрешает исполнение.

## 5. Контейнер с `run_codex: true`: утверждённый вариант А

### 5.1. Prompt

**Основное задание** — текст **самой контейнерной Issue**, исключая fenced YAML-блок `dispatcher` согласно правилам 6.4.2. Служебный контекст отдельно содержит только подтверждённый снимок непосредственных учитываемых детей: GitHub идентификатор/номер, название, URL и канонический PR (номер/URL, факт merge и целевая ветка). Не включать полные тексты дочерних Issue, их YAML и комментарии автоматически.

Явно указать Codex, что изменения детей уже находятся в текущей ветке, повторно выполнять их постановки не нужно; задача Codex — **интеграция согласно тексту контейнера**, а не автономное управление GitHub. Не передавать в prompt secrets, токены и недоверенные служебные инструкции из metadata. Использовать существующую фильтрацию входного Markdown и доверенные поля. Содержимое заголовков/названий детей считать недоверенным контекстом, не управляющими инструкциями.

### 5.2. Исполнение и публикация

1. После валидации готовности перевести контейнер в `running` с сохранением claim/operation.
2. Подготовить актуальный worktree закреплённой контейнерной ветки; Codex CLI не создаёт ветки и PR.
3. Однократно выполнить интеграционное задание для выбранного поколения, используя действующий executor, журналирование, квоты и обработку ошибок.
4. Сохранить результаты и выполнить commit/push **только** через диспетчер по действующим гарантиям. Не терять результат при ошибках push/restart/detach; не force push.
5. Перед публикацией PR повторно проверить значимое состояние и children evidence. При изменениях не переходить в `review`; сохранить опубликованные результаты и передать дальнейший цикл логике 6.4.3.6.
6. Если действительные различия с целевой веткой есть, найти/создать/привязать **один** канонический PR. Только после подтверждения PR и сохранения устойчивой привязки установить `review`.

Если Codex ничего не меняет, но в контейнерной ветке уже есть diff от детей, PR всё равно допустим: `no_diff` оценивается между веткой контейнера и его **целевой** веткой, а не по отсутствию новых правок Codex.

## 6. Контейнер с `run_codex: false`

После той же проверки готовности, актуального `origin` и закреплённых веток **не запускать Codex** и не создавать коммиты. Проверить diff контейнерной ветки относительно закреплённой `base_branch`. При diff — создать либо восстановить каноническую привязку PR в эту base, записать evidence и перевести в `review`. При отсутствии diff — остаться в `awaiting_children`, зафиксировать `no_diff`, опубликовать одно дедуплицированное объяснение. Повторная попытка допустима после доказанного изменения значимых условий, без бесконечного цикла одинаковых операций.

## 7. Контейнерный PR и review

- Head PR — закреплённая контейнерная ветка, base — закреплённая родительская/проектная ветка; не ориентироваться на случайно изменённый пользовательский YAML.
- Перед созданием искать существующие PR (`state=all`) с верификацией идентичности, canonical claim и истории. Чужой/неоднозначный PR — диагностический конфликт; второй PR не создавать.
- Описание PR должно использовать стандартную действующую схему публикации результата; включать ссылку на контейнерную Issue и уместную интеграционную сводку, не раскрывая служебные данные. Для `run_codex:false` не изображать сводку как результат Codex.
- Успешный переход в `review` закрепляет generation/snapshot интеграции. В `review` состав детей автоматически не переписывается и новое выполнение не запускается.
- После ручного merge контейнерного PR действующий монитор PR переводит контейнер в `done`. Принятое в 6.4.3.4 правило допускает осознанную смену пользователем **base собственного PR** с подтверждённым merge, сохраняя проверки PR/head/identity. Это **не** отменяет требования к правильной base PR дочерних Issue, учитываемых контейнером.

## 8. Обычная ручная Issue (`issue_type: issue, run_codex: false`)

1. После отдельного пользовательского подтверждения и проверки версии Issue создать/закрепить каноническую ветку по правилам 6.4.2, выполнить `fetch`, безопасно опубликовать ref в `origin` без искусственного коммита.
2. После подтверждения публикации перейти напрямую в `review`: Codex не запускать, автоматический PR не создавать; `running` не нужен.
3. Человек выполняет commit/push, создаёт и может немедленно слить PR в закреплённую base между двумя poll.
4. В каждом poll искать PR по `state=all` и по устойчивой identity репозитория, head, ожидаемой base и истории. Не требовать предварительно замеченного open PR. Проверять однозначность и ownership; при ambiguities — fail closed.
5. Зафиксировать канонический PR в SQLite; подтверждённый `merged=true` и merge evidence → `review → done`; закрытый без merge → `rejected`; открытый → ожидать в `review`.
6. Удаление remote head после merge не препятствует `done`, если PR/история достоверно доказывают merge. Смена человеком base собственного PR обрабатывается в соответствии с решением 6.4.3.4; для ребёнка контейнера отдельная проверка слияния **в parent branch** обязательна.
7. При повторном подтверждении отклонённой Issue сохранять ветку/каноническую привязку PR. Новые правила повторного цикла не реализовывать заново в обход 6.4.3.6.
8. Для обеих разновидностей manual/codex показать `issue_type` и `execution_mode` в `show/queue`; не маскировать ожидание человека статусом ошибки.

## 9. Сбои и идемпотентность

- Частично выполненные операции отражать в SQLite и продолжать через durable operation/outbox. Статусы не должны опережать фактическую GitHub-публикацию.
- Повторный poll, рестарт daemon, параллельная попытка запуска и повтор HTTP-ответа не создают повторных Codex invocation, веток, PR или комментариев.
- Если GitHub/SQLite недоступны, нельзя принимать непроверенный merge, терять результат Codex либо необоснованно переходить в `review/done`.
- При `no_diff` — один активный диагностический blocker и дедуплицированный комментарий; восстановление после появления diff с сохранением history.
- Если обнаружено изменение children во время исполнения, **сохранить результат**, не выдавать `review` на устаревшем снимке; подробный корректирующий цикл относится к 6.4.3.6. Никаких скрытых retarget PR детей.
- Сохранить правила `review_on_error`, `detach`, отмены контейнера (без каскадной отмены детей), чистки worktree и Git lock. Не удалять ветку контейнера, пока на неё опираются дети.

## 10. Тесты и проверка на реальном GitHub

Автоматические тесты (stub GitHub/Git, SQLite, daemon, CLI), включая:
1. Ready контейнер `run_codex=true`: один Codex run, верный prompt, commit/push, PR, `review`.
2. Ready контейнер `run_codex=false`: **ноль** вызовов Codex, PR из результата детей, `review`.
3. Не-ready и конфликтные дети: отсутствие запуска/PR; неактивная историческая блокировка не мешает.
4. Повторная семантическая проверка, изменение существенного снимка/merge до старта, незначимое изменение `updated_at`, удаление связей, incorrect child PR base.
5. Нулевой состав детей: публикация только при наличии реального diff; `no_diff` без искусственных коммитов.
6. Изменение HEAD container origin, конфликт пуша, отсутствие сети, duplicate poll, restart/lease, отказ outbox; отсутствие повторных операций.
7. Запуск Codex с нулевыми собственными изменениями и существующим diff от детей — PR создаётся.
8. Изменение children во время `running`: сохранность результата без ложного `review`.
9. Manual Issue: branch published, `review` без Codex/PR, open PR waiting, closed unmerged → `rejected`, merged → `done`.
10. Manual PR создан и мгновенно слит между poll, включая удалённый head; ownership/identity, ambiguous PR → fail closed.
11. Вложенный контейнер в качестве непосредственного ребёнка; нет рекурсивного исполнения.
12. Регрессия обычных Codex Issue, branch claim, PR merge/base-change, `review_on_error`, detach, очистки worktree и ранее принятых 6.4.3.3–6.4.3.4.

Ручная приёмка на `heroicrealm/CodexAgentPlayground`: отдельно контейнеры `run_codex:true/false`, минимум два слитых ребёнка, manual Issue с мгновенным merge PR и `no_diff`. Проверять GitHub PR/ветку, SQLite/CLI, комментарии и отсутствие повторного запуска. Привести итог полного `scripts/test.sh` и CI.

## 11. Критерии приёмки

Этап принимается, когда оба режима готового контейнера доводят собственный PR до `review` без нарушения children guards, а обычная ручная Issue корректно заканчивается в `done` после ручного merge, включая merge между poll. Все перечисленные проверки проходят; отказоустойчивость и идемпотентность не нарушают уже принятых этапов. Никаких автоматических слияний и дополнительных веток/PR.

## 12. Вне объёма

- 6.4.3.6: полный повторный цикл после `rejected`, переинтеграция при изменениях состава во время running, сложное восстановление и расширенный lifecycle.
- 6.4.3.7: итоговая межэтапная интеграционная приёмка и обобщение документации.
- 6.4.3.8: унифицированный `blocked` для всех Issue.
- Отдельная согласованная UX-доработка: один редактируемый постоянный комментарий контейнера со сводкой детей.
- Автоматическая очистка Git-веток — после завершения Sub-issues.

При расхождении с более краткими рабочими заметками приоритет имеют утверждённое общее ТЗ 6.4.3 и явно согласованные решения 6.4.3.4–6.4.3.5.
