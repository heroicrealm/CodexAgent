# ТЗ 6.4.3 — GitHub Sub-issues, контейнерные и ручные задачи

**Репозиторий:** `heroicrealm/CodexAgent`  
**Этап:** `6.4.3`  
**Статус:** утверждено 2026-11-01  
**Дата:** 2026-11-01  
**Предполагаемый путь:** `docs/stages/stage-06-04-03-spec.md`

## 1. Цель и область действия

Обеспечить использование GitHub Sub-issues как связанных задач, результаты которых интегрируются через контейнерную Issue. Контейнер работает с **непосредственными** дочерними Issue, готовит собственную ветку, назначает её базовой веткой учитываемым детям, ожидает окончания их работы, при необходимости запускает Codex и публикует собственный PR. Дочерняя Issue может быть обычной задачей, ручной задачей либо другим контейнером. Дополнительно разрешить обычные ручные Issue с `run_codex: false`.

Основные инварианты:

1. Одна Issue — одна каноническая рабочая ветка и один канонический PR на весь жизненный цикл, включая повторную доработку.
2. Пользователь отдельно подтверждает каждую исполняемую дочернюю Issue; контейнер не ставит `codex-ready` и не выдаёт approve от её имени.
3. Контейнер не запускает, не отменяет и не переводит дочерние задачи по их жизненному циклу. Он проверяет их состояние и достоверность merge.
4. GitHub — источник истины о связях Sub-issues и PR/merge; SQLite хранит локальную историю, привязки, снимки и намерения операций.
5. Merge PR — только вручную, диспетчер не делает auto-merge; `force push` и безусловное присвоение чужих веток запрещены.
6. Диспетчер управляет Git, публикацией собственных результатов и подготовкой worktree; Codex CLI не управляет ветками и PR.
7. Рестарты и повторный `poll` не создают повторные ветки, PR, комментарии и запуски Codex.
8. Поддерживается несколько проектов; GitHub issue number не используется как глобальный ключ.

## 2. Настройки в Issue

Единственный поддерживаемый служебный блок — fenced YAML с корневым ключом `dispatcher` по правилам этапа 6.4.2:

```yaml
dispatcher:
  issue_type: container
  branch: complex_task
  base_branch: main
  run_codex: false
```

| Поле | Значения | По умолчанию | Значение |
|---|---|---|---|
| `issue_type` | `issue`, `container` | `issue` | Тип исполнения |
| `run_codex` | YAML boolean `true`, `false` | `true` | Запуск Codex для самой Issue |
| `branch` | валидное имя Git branch | действующая автогенерация 6.4.2 | Каноническая рабочая ветка |
| `base_branch` | валидное имя Git branch | базовая ветка из конфигурации проекта | Основание для создания ветки / целевой PR |

`run_codex: false` допустим **как для контейнерной, так и для обычной Issue**. Отсутствие `issue_type` означает обычную Issue. Незнакомые ключи, дубли, неоднозначные блоки и недопустимые типы обрабатываются как ошибки конфигурации согласно 6.4.2. Исходный Markdown хранится для аудита, служебный YAML не передаётся Codex в составе prompt.

### 2.1. Режимы

| `issue_type` | `run_codex` | Действие |
|---|---|---|
| `issue` | `true` | Действующая обработка через Codex |
| `issue` | `false` | Ручное исполнение, диспетчер не запускает Codex |
| `container` | `true` | Ожидание детей, затем интеграционный запуск Codex |
| `container` | `false` | Ожидание детей, затем публикация контейнерного PR без Codex |

## 3. Структура веток и Sub-issues

Пример:

```text
main
└── feature-A                  [Container A; PR → main]
    ├── feature-B              [Container B; PR → feature-A]
    │   └── codex/issue-C      [Issue C; PR → feature-B]
    └── codex/issue-D          [Issue D; PR → feature-A]
```

Каждый контейнер взаимодействует **только с непосредственными детьми**; дочерний контейнер сам обслуживает своих детей. Рекурсивный обход потомков, специальный рекурсивный планировщик и каскадное управление статусами не нужны. Для родителя дочерний контейнер равнозначен обычной дочерней Issue: важны терминальное состояние и подтверждённый merge его PR в ветку родителя.

Контейнерная ветка должна быть опубликована на `origin` **до** того, как дети смогут использовать её как `base_branch`. При создании новой контейнерной ветки выполняется ранняя публикация ref без искусственного коммита и без преждевременного контейнерного PR. Это осознанное исключение из обычного сценария 6.4.2, где публикация ветки может откладываться до результата. Ранняя публикация не даёт права присваивать существующие чужие ветки.

Вложенный контейнер может начинать подготовку только при существующей и проверенной родительской ветке. Изменение родительских связей после начала работы не перенаправляет уже исполняемые ветки/PR автоматически.

## 4. Состояния

Новое публичное состояние: `awaiting_children`; соответствующая конфигурируемая метка — `dispatcher:awaiting-children` (создаётся/проверяется через `init`).

**Контейнер:** `discovered → pending → awaiting_children → [running, если run_codex=true] → review → done`; при `run_codex=false` после готовности детей — подготовка публикации → `review`. При отклонении: `review → rejected → pending → awaiting_children`, с прежними веткой и PR. Отмена — `cancelled` по действующим правилам, без каскада к детям. `review_on_error` и `detach` сохраняют прежние гарантии.

**Обычная ручная Issue:** после подтверждения диспетчер подготавливает и публикует ветку, затем переводит Issue в `review` **без Codex и без автоматического PR**. В таком режиме `review` означает, что исполнение передано человеку и диспетчер ждёт его PR/merge. Состояние `running` ручной Issue не требуется. После проверенного merge `review → done` автоматически. После закрытия канонического PR без merge — `rejected`; при повторном подтверждении используются те же ветка и PR.

В `queue`/`show` следует показывать `issue_type` и вычисляемый `execution_mode` (`codex`/`manual`), чтобы семантика `review` была однозначна.

## 5. Подготовка контейнера

После утверждения контейнерной Issue диспетчер:

1. Проверяет актуальность подтверждения, доверенность GitHub-событий, конфигурацию и права.
2. Определяет и закрепляет каноническую рабочую ветку, её источник и целевую ветку PR.
3. Делает `fetch origin`, проверяет владение веткой/отсутствие коллизий и создаёт ветку при необходимости.
4. Публикует контейнерную ветку в `origin` и подтверждает её наличие.
5. Получает **непосредственных** детей через GitHub Sub-issues API.
6. Для учитываемых детей безопасно нормализует `dispatcher.base_branch` на контейнерную ветку.
7. Сохраняет результаты подготовки и переходит в `awaiting_children`.

При частичном отказе GitHub/SQLite операция повторяется из устойчиво сохранённого намерения, без повторного создания ресурсов и без потери пользовательских изменений.

## 6. Какие дочерние Issue учитываются

1. Дочерняя Issue **без `codex-ready`, никогда не управляемая диспетчером**, игнорируется: не блокирует контейнер, её YAML не изменяется, ветка не создаётся.
2. Дочерняя Issue с `codex-ready` входит в учитываемый набор. Подтверждается отдельно. Для неё настраивается `base_branch` контейнера, пока это безопасно.
3. Дочерняя Issue, с которой **сняли** `codex-ready` после начала управления, обрабатывается с учётом `detach`, уже созданных ресурсов, PR и возможных конфликтов.
4. Дочерняя Issue в `done` считается выполненной для контейнера только при подтверждённом merge её канонического PR **в контейнерную ветку**.
5. Дочерняя Issue в `cancelled` не обязана иметь merge; наличие конфликтующих незавершённых операций должно быть проверено.

Наличие GitHub-связи Sub-issue само по себе не выдаёт разрешения на выполнение и не запускает Codex.

### 6.1. Служебное обновление YAML

Если у учитываемого ребёнка нет блока `dispatcher`, он добавляется. Если `base_branch` отсутствует или отличается от контейнерной ветки, поле устанавливается на ветку контейнера при условии, что изменение не перенаправляет уже закреплённую или исполняемую ветку/PR. Прочие параметры и Markdown сохраняются. Служебная правка распознаётся как изменение диспетчера и не должна произвольно отзывать подтверждение. При конкурентной редакции применяется перечитывание актуальной версии и безопасный повтор, а не слепая запись.

Если задача уже исполняется, имеет несовместимый PR или зафиксированную каноническую ветку, меняющуюся `base_branch` не переписывают вслепую: выставляется диагностическая блокировка до вмешательства пользователя.

## 7. Мониторинг и критерии готовности

На каждом `poll` контейнер в `awaiting_children` получает актуальные **непосредственные** Sub-issues, учитывает правила отбора (§6), проверяет состояние, PR, целевую ветку merge и конфликты.

Контейнер готов к интеграции, когда:

- все **учитываемые** дочерние Issue в `done` или `cancelled`;
- для каждой `done` факт merge канонического PR именно в ветку контейнера подтверждён GitHub;
- отсутствуют блокирующие изменения связей, `detach` с открытым PR, несохранённые операции и другие неоднозначности;
- контейнерная ветка доступна и принадлежит контейнеру.

`sub_issues_summary.completed` в GitHub не заменяет этих проверок. Порядок готовности детей не должен иметь значения. При **нуле учитываемых детей** отсутствие детей само по себе не создаёт изменений: допустимость публикации определяется общими правилами интеграции и `no_diff` (§10); не следует искусственно запускать дочерние задачи.

## 8. Интеграционный цикл контейнера

**При `run_codex=true`:** сохранить снимок учитываемых детей и их PR, получить свежий HEAD контейнерной ветки, подготовить worktree, выполнить Codex, сохранить/опубликовать его результаты, повторно сверить состав, состояния и merge. Если состав изменился во время `running`, завершить уже начатую работу с гарантией сохранения результатов, но **не переходить в `review`**: вернуться в `awaiting_children` и после готовности обновлённых детей повторить интеграцию на существующей ветке.

**При `run_codex=false`:** после выполнения условий готовности проверить наличие diff и создать/обновить контейнерный PR без запуска Codex. Переход в `review` — только после подтверждённой публикации PR.

Переход в `review` фиксирует состав учитываемых детей и результаты их PR текущего цикла. В `review` новые/удалённые дети не включаются автоматически и YAML не исправляется. Для новой интеграции нужен возврат на доработку и повторное подтверждение: `review → rejected → pending → awaiting_children`.

В повторном цикле сохраняются прежняя каноническая ветка и **тот же PR**; допускается обновление или повторное открытие прежнего PR по действующим правилам, но не второй канонический PR. Завершённые дети повторно не запускаются. Изменения в пользовательском YAML не переназначают уже закреплённую ветку.

## 9. Ручная обычная Issue (`issue_type: issue`, `run_codex: false`)

После отдельного подтверждения диспетчер создаёт/проверяет и **публикует** каноническую ветку; не вызывает Codex и не создаёт автоматических коммитов. Он переводит задачу в `review`, ожидая действий человека.

Человек делает commit/push, создаёт PR из закреплённой `head`-ветки в закреплённую `base`-ветку, проверяет и сливает PR самостоятельно. Диспетчер **не требует промежуточного наблюдения открытого PR**: каждый `poll` ищет PR со `state=all`, включая закрытые и уже слитые между вызовами `poll`. PR определяется по репозиторию и паре `head`/`base`; затем строго проверяются принадлежность закреплённой ветке, отсутствие конкурирующих PR и однозначность привязки к Issue. При неоднозначности — диагностика, а не произвольный выбор.

Обнаруженный канонический PR записывается в SQLite. Его `merged=true` (с подтверждением GitHub) вызывает автоматический `review → done`; отдельная метка `done` от человека **не требуется**. Если PR закрыт без merge — переход в `rejected` по действующим правилам. Если PR остаётся открытым — задача остаётся в `review`.

Отсутствие удалённой исходной ветки после merge **не мешает** подтверждению `done`, если принадлежность и merge доказаны по PR/истории. Ручное создание и немедленное слияние PR между двумя `poll` — обязательный приёмочный сценарий.

## 10. Ошибки и специальные случаи

### 10.1. Нет diff

Контейнер с `run_codex=false` либо с завершённой интеграцией, но без различий между контейнерной и целевой ветками, не может создать обычный PR. Искусственные коммиты запрещены. Контейнер остаётся в `awaiting_children` с диагностикой `no_diff` и однократным комментарием, не переходит в `review`. Повторные `poll` не должны бесконечно пытаться создать PR; после изменения условий проводится перепроверка.

### 10.2. Удалена Sub-issue из состава

Если удалённая связь относится к уже исполняемой дочерней Issue или Issue с PR, контейнер блокирует завершение и публикует диагностику. Диспетчер не закрывает PR, не отменяет ребёнка и не меняет целевую ветку. Пользователь разрешает конфликт вручную. Для ещё не исполнявшегося ребёнка без закреплённых ресурсов безопасное исключение допустимо.

### 10.3. Снят `codex-ready` с ребёнка с открытым PR

Контейнер блокируется в `awaiting_children`; диагностический код `child_detached_with_open_pr`. Публикуется однократный комментарий со ссылкой на ребёнка и PR; ручное разрешение: восстановить отслеживание с новым подтверждением, слить PR в правильную ветку или закрыть PR без merge. После этого повторно проверить фактическое состояние и отсутствие прочих незавершённых операций. Простое закрытие PR не означает автоматического `done` или безусловного снятия всех блокировок.

### 10.4. Отмена контейнера

`cancelled` воздействует **только на контейнер**. Дочерние Issue продолжают собственный жизненный цикл. Контейнер прекращает оркестрацию и публикует состояние детей; контейнерную ветку нельзя удалять, пока на неё опираются активные дочерние задачи или PR. Безопасность публикации и очистки worktree обеспечивается существующими правилами.

### 10.5. Перемещение детей между родителями

Автоматически не перенаправлять уже созданные ветки и PR в другой контейнер. Если существует закреплённый ресурс или активная операция, зафиксировать конфликт и потребовать ручного решения. Отсутствие рекурсивного обхода не отменяет проверки согласованности непосредственной родительской связи.

## 11. Модель данных и синхронизация

Конкретные миграции определяются после аудита схемы в 6.4.3.2. Логически требуются:

- `issue_type`, `run_codex` и/или вычисляемый `execution_mode`, привязка к проекту;
- канонические `branch`, `base_branch`, `issue_id`, `pr_id`, состояние публикации;
- непосредственные отношения `parent_issue_id` ↔ `child_issue_id`, последнее наблюдение и признаки участия/конфликта;
- `integration_generation` и неизменяемый снимок участвующих детей, их состояний, PR и целевых веток для каждого цикла;
- устойчивые операции подготовки веток, правки YAML, поиска/привязки PR, публикации, комментариев, блокировок и восстановления после сбоя;
- причины `no_diff`, `child_detached_with_open_pr`, конфликтов связей и веток.

Реализация должна использовать действующие паттерны SQLite, outbox и idempotency keys, не дублировать существующие сущности и обеспечивать миграцию старых баз без потери истории. GitHub `issue_id`/`pr_id` используются как стабильные ключи в области соответствующего репозитория/проекта; номера Issue сами по себе не уникальны между проектами.

## 12. Наблюдаемость, безопасность, совместимость

- `init` создаёт/проверяет метку `dispatcher:awaiting-children` через конфигурируемые настройки меток.
- `queue`/`show` отражают тип задачи, режим исполнения, родителя, количество непосредственно учитываемых детей, завершённость, поколение интеграции, ветки, PR и блокировки.
- Неизвестные/отсутствующие дочерние ресурсы или неоднозначность GitHub PR не трактуются как успешное завершение.
- Не допускается потеря неопубликованных результатов при `detach`, отмене, ошибке push, сбое сети или рестарте.
- Параллельные `poll`, гонки редактирования Issue и конкурентные изменения Git refs должны корректно диагностироваться и не повреждать состояние.
- Существующие сценарии обычных Codex Issue (`run_codex` по умолчанию `true`), `rejected`, `review_on_error`, detach/reattach и очистки worktree сохраняются без регрессий.
- Автоматическая очистка опубликованных веток **не входит** в 6.4.3 и проектируется после принятия Sub-issues.

## 13. Приёмочные сценарии

1. Контейнер с тремя дочерними задачами создаёт/публикует собственную ветку до настройки детей.
2. Для отмеченных `codex-ready` детей корректно вставляется/исправляется `base_branch`, другой Markdown и YAML сохраняется, подтверждения не выдаются.
3. Никогда не отмеченные `codex-ready` дети полностью игнорируются при ожидании; их YAML не изменяется.
4. Дочерние `done` требуют проверенного merge в ветку контейнера, `cancelled` не требует merge при отсутствии конфликтов.
5. Два Codex-ребёнка и один ручной ребёнок завершаются, затем контейнер публикует PR.
6. `run_codex=true` и `false` для контейнера; повторное использование его ветки и PR после `rejected`.
7. Ручная Issue получает ветку и `review` без запуска Codex, человек создаёт PR, диспетчер обнаруживает и привязывает его.
8. Человек создаёт и **сливает PR между двумя poll**; диспетчер находит закрытый merged PR и устанавливает `done` без требования существующей head-ветки.
9. Ручной PR закрыт без merge → `rejected`; повторная попытка использует прежнюю ветку/PR; чужие или неоднозначные PR не принимаются.
10. Добавление/удаление ребёнка в `awaiting_children`; изменение состава во время `running` → повторная интеграция после сохранения текущего результата.
11. После перехода контейнера в `review` состав зафиксирован, изменения учитываются только через новый цикл доработки.
12. Снятие `codex-ready` с ребёнка с открытым PR блокирует контейнер; повторные `poll` не дублируют комментарий; блокировка снимается только после безопасного разрешения.
13. Удаление связи активного ребёнка/ребёнка с PR вызывает диагностируемую блокировку.
14. `no_diff` оставляет контейнер в `awaiting_children` без искусственного коммита и без PR.
15. Отмена контейнера не отменяет детей и не удаляет нужную им ветку.
16. **Вложенные контейнеры**: ребёнок-контейнер завершает собственный цикл независимо; родитель проверяет только непосредственное `done` и merge его PR.
17. Неоднозначности владения веткой/PR, неверный YAML, несовпадающий `base`, гонки редактирования, сбои GitHub API/SQLite, идемпотентность и crash recovery.
18. Полный регрессионный набор этапов 1–6.4.2 и ручная проверка на `heroicrealm/CodexAgentPlayground` (включая демонстрационный #72).

## 15. Критерий завершения этапа

Пользователь создаёт контейнер, добавляет непосредственные дочерние Issue (включая вложенный контейнер и ручную задачу), отдельно подтверждает нужных детей, получает их PR в контейнерную ветку и затем собственный контейнерный PR в родительскую ветку. Все переходы, повторные попытки, исключения и разрешение конфликтов проходят без нарушения ранее принятой модели «одна Issue — одна ветка — один PR».
