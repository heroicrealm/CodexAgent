# ТЗ 6.4.3.4 — мониторинг непосредственных детей и проверка merge

**Статус:** подготовлено к реализации на основе принятого общего ТЗ 6.4.3 и принятого пользователем этапа 6.4.3.3.  
**Ветка:** `STAGE_06_04_03`.

## 1. Предмет и границы

Реализовать мониторинг контейнеров в `awaiting_children`: актуальное получение **только непосредственных** Sub-issues, классификация учитываемых детей, доказательная проверка их терминальности и GitHub PR/merge, устойчивые диагностические блокировки, снимок готовности и данные для последующей интеграции.

В этом этапе **не запускать Codex контейнера, не создавать контейнерный PR, не сливать PR автоматически, не реализовывать исполнение обычной manual Issue**. Реальное продолжение готового контейнера в running/review — 6.4.3.5; повторные интеграционные циклы — 6.4.3.6. Общий статус `blocked` для всех типов Issue утверждён, но вынесен в 6.4.3.8; здесь контейнер остаётся `awaiting_children` и сообщает о препятствии диагностикой.

## 2. Источники истины и идентификация

GitHub — источник истины о непосредственных связях, Issue-состоянии, PR identity, head/base и merge. SQLite — локальный учёт, history, canonical branch, PR, operations, integration generation и подтверждённые снимки. Номер Issue не глобально уникален; использовать GitHub issue_id + repository identity. Все данные из GitHub проверять после получения, при неполной странице/ошибке — fail closed. Обход внуков не выполнять, вложенный контейнер — обычный непосредственный ребёнок.

На каждом `poll` в `awaiting_children` читать полный список детей и актуальные состояния и PR. Нормально ожидающая Issue — не ошибка; сообщение о блокировке для технических конфликтов должно быть дедуплицировано средствами 6.4.3.3.

## 3. Учитываемые дети

- Неуправляемая ранее Issue без `codex-ready` игнорируется без побочных эффектов.
- Ранее управляемая Issue, потерявшая `codex-ready`, требует проверки уже созданных ресурсов, особенно PR; при **открытом PR** блокировать с кодом `child_detached_with_open_pr` и один диагностический комментарий. Нельзя молча исключать её из готовности.
- Не выдавать дочерним Issue approve/reject, не запускать их, не изменять их GitHub состояния или PR из контейнерного монитора.
- Изменение или исчезновение **ранее учитываемой** прямой связи, либо перемещение ребёнка с активной веткой/PR, фиксировать как конфликт; не делать скрытого retarget.
- При наличии обычных работающих детей оставаться в `awaiting_children` без ложного диагностического «failed».

## 4. Терминальность и GitHub merge

- Child `done` удовлетворяет контейнеру **только** при достоверном подтверждении merge канонического PR именно **в work_branch контейнера**. Проверить постоянный `pr_id`, repository ID, head, base, `merged=true`, `merged_at`, GitHub PR state; не считать достаточно закрытие PR, label `done`, локальную запись или существование commit в истории main.
- Искать PR по всем состояниям (`state=all`), учитывать удалённую head-ветку после слияния и проверять каноническую принадлежность без принятия чужих или неоднозначных PR. Использовать уже существующую `task_pull_requests`, историю итераций и принятые guard/PR resolution контракты; не создавать второй источник canonical PR. При неопределённости — отдельный blocker, а не произвольный выбор.
- Child `cancelled` не обязан иметь merged PR. Однако подтвердить отсутствие незавершённого/конфликтующего PR либо иных открытых операций, которые могут изменить контейнерную ветку. При конфликте — blocker.
- Все другие состояния ребёнка — ожидание, без подтверждения готовности контейнера. Не считать `revoked` и `rejected` терминальным успехом.
- Отдельно учитывать children-container: их собственное `done` и корректный merge их канонического PR в ветку родителя, без чтения их потомков.
- Если ребёнок `done`, а GitHub evidence ещё не подтверждено, не переводить контейнер дальше.

## 5. Integration generation и момент готовности

Сформировать устойчивый счётчик поколений и **неизменяемый снимок** непосредственных участвующих детей, идентичностей, статусов, канонических PR, проверенных merge targets, SHA/времени наблюдения и HEAD родительской ветки. Снимок создавать только после полного успешного мониторинга и повторной проверки неизменности набора. Не подтверждать готовность на частичном списке.

Зафиксировать `ready_for_integration` как durable факт/фазу при оставшемся `awaiting_children`. Следующий подэтап потребит этот факт и повторно проверит его свежесть непосредственно перед запуском интеграции. Любая перемена состава или PR/merge до запуска инвалидирует прежнюю готовность и требует нового поколения, но не удаляет историю.

## 6. Восстановление, диагностика, CLI

Идемпотентная повторная проверка, восстановление после потери ответов/перезапуска, работа без GitHub-сети внутри SQLite writer-lock. Коды блокировок как минимум: `child_detached_with_open_pr`, `child_relation_removed`, `child_merge_unverified`, `child_merge_wrong_base`, `child_pr_identity_conflict`, `child_cancelled_with_open_pr`, `child_snapshot_stale`. Снимать только устранённые блокировки после нового доказанного наблюдения, не все сразу.

Использовать существующий диагностический outbox, дедупликацию и сообщения о восстановлении. CLI `show/queue` отображают число учитываемых детей, ожидающих, завершённых, конфликтных и интеграционное поколение/готовность.

## 7. Проверки

1. 0 детей, 1 ребёнок, 101 ребёнок, неполная пагинация, duplicate ID, ошибки HTTP, смена набора между проверками.
2. `discovered/pending/running/review/rejected` → ждать; `done` с подтверждённым merge в parent branch → готов; `done` с чужой base/closed unmerged/no PR → не готов.
3. `cancelled` без PR → готов; `cancelled` с открытым PR/конфликтующими операциями → blocker.
4. Ребёнок снял `codex-ready` с открытым PR → `child_detached_with_open_pr`, однократный комментарий; без PR — применять правило игнорирования только при отсутствии исторического конфликта.
5. Не-ready, никогда не управлявшийся ребёнок полностью игнорируется.
6. Вложенный контейнер как child, только непосредственный merge и terminal state.
7. Ручной PR, открытый и слитый между poll, находится через `state=all`, даже если branch удалена. Если сценарий завершения manual Issue реализуется лишь в 6.4.3.5 — тестировать только корректность чтения/проверки evidence на этом подэтапе.
8. Canonical PR mismatch, неоднозначный PR, неверная head/base, PR в другой репозиторий → fail closed.
9. Удаление связи/новый ребёнок, restart, гонки, повторный poll — устойчивые generations/snapshots без дублей.
10. Регрессия 6.4.3.3 и старых Codex tasks, отсутствие запуска Codex/создания PR контейнера.

## 8. Критерии приёмки

На Playground контейнер с двумя `done` детьми и merged PR в контейнерную ветку получает подтверждённую готовность (но ещё не запускает интеграцию); с ожидающей задачей — ждёт; с detached и открытым PR — блокируется и сообщает. Автоматические тесты проходят. Разграничение с 6.4.3.5 и 6.4.3.8 сохраняется.
