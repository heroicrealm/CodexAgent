# Задание Codex: 6.4.3.4 — корректная обработка изменения целевой ветки PR

**Репозиторий:** `heroicrealm/CodexAgent`
**Рабочая ветка:** `STAGE_06_04_03`
**Тип работы:** исправление обнаруженного при ручной приёмке дефекта; не создавать другую ветку или PR без отдельного согласования.
**Основание:** [утверждённое решение](stage-06-04-03-04-pr-base-change-decision.md), а также [ТЗ этапа](stage-06-04-03-04-spec.md).

## Исходный сценарий

В тестовом репозитории `heroicrealm/CodexAgentPlayground` дочерняя Issue **#114 BadKid** получила канонический PR **#115**. Пользователь вручную сменил целевую ветку PR с `ContainerBranchwrongpr` на другую, затем слил PR. PR закрыт как merged; Issue #114 продолжила находиться в `review`.

Локальная диагностика `codex-dispatcher show CodexAgentPlayground 114`:
- `task_pull_requests`: PR #115, state=open (снимок в SQLite не актуализирован);
- `publication_operations`: `operation_key=resolution:5120612290`, `phase=retry`, `outcome=failed`, `retry_count=4`;
- результат публикации комментария об исполнении `published=1`.

Непосредственная причина: `src/dispatcher/pr_monitor.py`, метод `PullRequestMonitor.resolve()`, трактует `pr['base']['ref'] != linked['base']` как `GitHubError(invalid_response)`. Монитор не доходит до перехода `review → done`.

## Утверждённое поведение

1. **Обычная Issue:** если пользователь поменял *только* целевую ветку канонического PR, а затем PR действительно слился, переход `review → done` выполняется автоматически и с обычными процедурами доставки результата, закрытия Issue и комментариями. Смена base — осознанное действие пользователя, не основание для бесконечных retry.
2. **Контейнер:** если этот ребёнок по-прежнему входит в непосредственные GitHub Sub-issues контейнера, но его канонический PR слит не в `work_branch` родителя, контейнер остаётся в `awaiting_children`, `ready_for_integration=0`, блокер `child_merge_wrong_base`. Диспетчер не retarget-ит PR и не пытается повторно сливать изменения.
3. **Разрешение конфликта:** пользователь вручную исключает ребёнка из Sub-issues родителя. Такой ребёнок перестаёт участвовать в readiness; блокер снимается после достоверной перепроверки GitHub и пересчёта снимка. Дочерняя Issue остаётся `done`. История связей сохраняется. Не следует сохранять `child_relation_removed` как вечную блокировку для этого конкретного подтверждённого сценария.
4. **Защитные проверки:** сохраняются стабильные PR ID/number, repo/head identity, SHA, iteration, closed/merged timestamps, guard/evidence и запреты на подмену; **не** считать любое изменение PR легальным. Отличать фактический `merged_base` от ожидаемого `base`, не перезаписывать исходное ожидание.
5. При неслитом PR `review` сохраняется. В случае закрытия без merge действует прежний `rejected` workflow. Не менять жизненный цикл других типов Issue или базовое правило `one Issue → one branch → one PR`.

## Реализация

- Изучить `src/dispatcher/pr_monitor.py`, `src/dispatcher/container_monitor.py`, `src/dispatcher/storage/transitions.py`, модель `task_pull_requests`, `pr_resolutions`, `container_blockers`, `sub_issue_relations` и существующие тесты.
- Адаптировать PR-монитор: аутентифицированный факт merge признавать несмотря на изменение `base`; удержать все независимые safeguards; обеспечить recovery/idempotence операции `resolution:...` после прежних retry. Сохранить фактическую base в надёжном свидетельстве для проверки контейнером. Если нужна миграция SQLite — обратная совместимость, миграционные тесты.
- Адаптировать монитор контейнера к фактическому `merged_base` и явному удалению ребёнка из прямых Sub-issues. Не ослаблять установленное ранее правило `child_detached_with_open_pr` при снятии `codex-ready` и прочие блокировки. Описать, как отличать допустимое исключение ребёнка после wrong-base merge от остальных нарушений связи.
- Дать точные диагностические сообщения (ожидаемая/фактическая база, шаг для пользователя), без утечек секретов и без спама комментариями.
- Не менять непосредственно тестовые Issue #114, родителя, PR #115 и SQLite пользователя; ручные действия оставляем для приёмки.

## Обязательные автотесты

1. PR merged в ожидаемую base: `review → done`, Issue закрыта, нормальная доставка комментария.
2. PR retargeted и merged в другую base: `review → done`, корректная фактическая base, никакого бесконечного retry.
3. Retargeted, но PR ещё open: остаётся `review`, без ложного `done`.
4. Closed unmerged после изменения base: `review → rejected`.
5. Изменён ID, repo, head или отсутствуют достоверные merge evidence: fail closed.
6. Child merged в неверную ветку, связь Sub-issue существует: `ready=0`, `child_merge_wrong_base`, понятная диагностика.
7. Пользователь явно исключил того же ребёнка из Sub-issues: соответствующий blocker снят, readiness пересчитана, child остаётся `done`; повторный poll и рестарт не возвращают конфликт.
8. Другие участвующие дети, дети без `codex-ready`, `child_detached_with_open_pr`, конфликтная/неожиданная утрата связи сохраняют действующую семантику.
9. Recovery старой операции `phase=retry/outcome=failed`, идемпотентность переходов, отсутствие повторных комментариев.
10. Прогнать полный тестовый набор (в т. ч. `bash scripts/test.sh`) и `git diff --check`. Не заявлять об успешном прохождении без фактического запуска.
