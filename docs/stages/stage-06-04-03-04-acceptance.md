## 1. Объём принятого этапа

Реализован мониторинг контейнеров в `awaiting_children`, чтение непосредственных GitHub Sub-issues без рекурсивного обхода, классификация участвующих детей, проверка терминальности с доказательствами слияния канонического PR именно в ветку контейнера, диагностика конфликтов, durable readiness snapshot и счётчик integration generation. CLI `show`/`queue` отображают состояние детей, активные конфликты и готовность.

Установленная граница: `ready_for_integration=1` **не переводит контейнер из `awaiting_children`**. Запуск интеграции/дальнейшее исполнение и контейнерный PR относятся к 6.4.3.5. Общий статус `blocked` остаётся задачей 6.4.3.8.

## 3. Замечания и исправления при приёмке

### 3.1. Ложный `child_snapshot_stale` из-за `updated_at`

Первоначальная проверка сравнивала время обновления GitHub Issue с принятым снимком. Комментарии, посторонние метки или сервисные обновления могут изменить timestamp без изменения значимых для диспетчера данных. Утверждён семантический guard: identity, body/YAML, title, author, управляющие метки, версия подтверждения, iteration, ветка и допустимость команд. Время `updated_at` само по себе не блокирует контейнер. При повторном опросе #104 блокировка снялась, readiness достигла `ready=1`. Конкретный триггер изменения timestamp у #104 не устанавливался отдельно.

### 3.2. Ручное изменение base PR препятствовало `review → done`

Для PR #115 операция `resolution` переходила в `retry/failed`, поскольку PR-монитор требовал равенства текущей base исходно сохранённой. Утверждено: осознанное изменение пользователем *только целевой ветки* не препятствует завершению обычной Issue при доказанном merge. Исходная и фактическая base сохраняются раздельно, идентичность PR/head/repository и другие safeguards остаются обязательными. После исправления #114 автоматически завершилась.

### 3.3. Неверная base дочернего PR должна блокировать контейнер до явного удаления связи

Для ребёнка в прямых Sub-issues, чей канонический PR слит в другую ветку, устанавливается `child_merge_wrong_base` и `ready=0`. Диспетчер не делает retarget или повторный merge. Пользователь удаляет ребёнка из Sub-issues; монитор перепроверяет evidence, сохраняет историю исключения и снимает блокер. Подтверждено на #113. Временный `child_snapshot_stale` во время изменения связи также был снят штатным повторным наблюдением.

## 5. Принятые ограничения и отложенные улучшения

- Монитор проверяет только непосредственных детей; вложенный контейнер рассматривается как ребёнок без рекурсии.
- GitHub не предоставляет атомарного снимка множества Issue/PR/ref. Повторные полные наблюдения и guard сокращают окно гонки, но потребитель readiness на этапе 6.4.3.5 должен повторно проверить свежесть.
- `awaiting_children` сохраняется после `ready=1` до реализации 6.4.3.5; автоматического merge PR здесь нет.
- Неуниверсальная диагностика `blocked` будет обобщена на все типы Issue на этапе 6.4.3.8.
- Согласована, но ещё не реализована доработка: один **редактируемый постоянный комментарий** родительской Issue со сводкой состояний дочерних Issue. Выполнять отдельно после приёмки 6.4.3.4.
- Отдельные улучшения UX: разделить активные и снятые блокировки в `show`; сократить задержку между появлением `review` и комментарием о выполнении с сохранением durable outbox/retry. Они не являются условием данной приёмки.
- Не заявлены как отдельно проверенные пользователем массовые 101-child тесты, аварийные race/kill/restart и сетевые сбои; покрытие этих сценариев описано в отчёте агента.
