# Задание Codex-агенту: исправить ложный child_body_conflict (6.4.3.3)

Репозиторий: heroicrealm/CodexAgent. Ветка: STAGE_06_04_03.
Статус этапа 6.4.3.3: не принят.

## Воспроизведение

В тестовом репозитории heroicrealm/CodexAgentPlayground контейнер Issue #88 находится в pending. Его ветка ContainerBranch3 успешно создана: операция branch имеет phase=confirmed, outcome=success. Дочерние Issue #89 и #90 имеют codex-ready, но их операции child остались в intent, а контейнер получил два активных blocker с code=child_body_conflict. Дочерняя Issue #91 не имеет codex-ready и должна игнорироваться.

В src/dispatcher/containers.py, метод ContainerService.update_child(), имеется проверка полного равенства fresh и proof['original']. При этом original получен из GET /issues/{number}/sub_issues, а fresh — из GET /issues/{number}. Формы JSON различаются даже без пользовательских изменений (например, repository и closed_by). Это создаёт ложный конфликт и препятствует PATCH с добавлением dispatcher.base_branch.

## Требуемое исправление

1. Убрать сравнение полных JSON-объектов разных API. Сделать явную проверку стабильных значимых полей: issue id, repository identity, number, state, title, author identity, состав значимых labels, body с корректной обработкой null, updated_at. Прямую родительскую связь проверять через Sub-issues endpoint. Учитывать локальную version, approved state, guard, branch/PR ownership. Не ослаблять проверки на реальные конкурентные изменения.
2. При необходимости нормализовать proof snapshot для новых операций. Обязательно поддержать ранее сохранённые intents в прежнем формате: повторная обработка Issue #88 должна работать без удаления операций, блокировок или SQLite.
3. Сохранить утверждённый вариант A: перед PATCH повторно читать Issue; проверять права; записывать durable intent до внешнего эффекта; после PATCH независимо проверять результат; при неопределённом исходе выполнять read-back и безопасное восстановление. Не заявлять атомарную CAS-гарантию.
4. После успешной подтверждённой подготовки ребёнка снимать его устаревший child_body_conflict; не снимать другие blockers без доказательства устранения. Обеспечить достижение awaiting_children у контейнера после обработки всех учитываемых детей.
5. Не обновлять non-ready Issue #91; не подтверждать дочерние задачи, не запускать Codex для контейнера и не создавать его PR.

## Обязательные тесты

- Разные реальные формы REST и Sub-issues JSON с дополнительными полями — без ложного конфликта.
- Два ready ребёнка с пустым body и один non-ready: меняются только ready, parent переходит в awaiting_children.
- Recovery старых intent после рестарта без повторной публикации контейнерной ветки.
- Изменения body, updated_at, author, state, ready labels или родительской связи — обнаружение конфликта без PATCH.
- Повторный poll идемпотентен; отсутствуют дублирующиеся PATCH и комментарии.
- Регрессия существующих контролируемых обновлений, approve и отказов владения веткой.
- Полный прогон тестов и git diff --check.
