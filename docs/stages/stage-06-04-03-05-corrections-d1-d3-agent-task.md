# Задание Codex-агенту — исправления D1–D3 для 6.4.3.5

**Репозиторий:** `heroicrealm/CodexAgent`  
**Ветка:** `STAGE_06_04_03`  
**Обязательное ТЗ:** [stage-06-04-03-05-corrections-d1-d3-spec.md](stage-06-04-03-05-corrections-d1-d3-spec.md)  
**База:** работа агента 6.4.3.5 (`a8309fc`) и утверждённые функциональные сценарии.

## Цель

Исправить D1 и D2; реализовать **диагностическое инструментирование**, но не оптимизацию D3. Сохранить все принятые гарантии 6.4.3.3–6.4.3.5, включая ручные Issue, контейнерные PR, canonical ownership и approval fences.

**Работать только в `STAGE_06_04_03`; PR/merge, закрытие Issue и объявление приёмки не выполнять.**

## Этап 1 — короткий технический аудит

Перед правкой:
1. Воспроизвести точку появления `child_snapshot_stale` при последовательности: контейнер `codex-ready + approve`, затем ребёнок `codex-ready + approve` и штатный переход ребёнка через `pending/running`. Проследить различия GitHub/SQLite snapshot, body/title/updated_at, управляющих label и parent monitor.
2. Проверить существующую логику изменения обычных Issue в `discovered`, версионирования, `approve`, revoke/rejected, доставки служебного `base_branch`, устойчивых container intents и child guards. Не предполагать, что проблема только в `updated_at`.
3. Посмотреть `src/dispatcher/rendering.py`, вызовы CLI `queue`, `show`, JSON.
4. Составить карту действующего GitHub API adapter, scheduler poll, outbox/reconciliation, SQLite schema/migration и конфигов для D3.
5. Отразить реальные корневые причины/гипотезы в отчёте с кодовыми указателями. Если воспроизведение требует stub, написать регрессионный тест с типичной последовательностью событий.

## Этап 2 — D1: единый контракт наблюдения и утверждения

- Унифицировать для **обычной Issue, дочерней Issue и контейнера** смысл `codex-ready` как наблюдения и `approve` как утверждения актуальной редакции. В `discovered` автор свободно правит title/body/YAML: sync обновляет технический снимок, без ложного `child_snapshot_stale`, без автоматического approve, запуска и утверждения текста.
- Не удалять все версии/snapshots из SQLite: хранить согласованное актуальное наблюдение и после `approve` отдельный доказанный защищённый snapshot. Проверить, как текущая модель отличается от требуемой, и сделать минимально необходимое изменение.
- В момент `approve` использовать актуальное подтверждённое содержимое GitHub с безопасными version/content guards; не исполнять позднюю конкурентную правку без нового подтверждения. Сохранить действующую обработку edits после утверждения.
- Подготовка дочернего `base_branch` в `discovered` не должна уничтожать пользовательский Markdown, сбивать approved version или вызывать длительную блокировку. Применить механизмы safe intent/refresh/retry; не делать blind PATCH при race. После закрепления ресурсов запрет скрытого retarget оставить.
- Устранить ложный `child_snapshot_stale` **именно после запуска ребёнка**. Отличать штатные изменения состояния/меток/времени от реальной изменённой утверждённой постановки и от конфликта branch/PR/parent. Проверить сам monitor и preparation, включая historical blocker auto-clear.
- Сценарий B,C выполнены, D `codex-ready` и `discovered` с незавершённым ТЗ: контейнер стабильно ждёт D; повторные правки D до approve допустимы. После approve и подтверждённого merge D контейнер становится готов.
- Сохранить: ребёнок без `codex-ready`, никогда не управлявшийся, игнорируется; detached ребёнок с открытым PR блокирует; wrong-base merge блокирует до явного безопасного разрешения.

## Этап 3 — D2: устранить спам queue

Удалить внерамочную построчную печать `Issue N: issue_type=... execution_mode=...` из `render_queue`. Сохранить таблицу, `show`, `--format json` и поддержку Unicode. Не переводить формат `queue` на несогласованные дополнительные таблицы. Добавить тест отсутствия хвоста.

## Этап 4 — D3: временная диагностическая трассировка

- Реализовать таблицу `dispatcher_timing_events` и безопасный schema upgrade/инициализацию по нормативному ТЗ. Доступная опция:
  ```yaml
  diagnostics:
    timing_enabled: false
  ```
  По умолчанию выключена, измерения включаются только явно. Описать обратную совместимость конфигов и хранения.
- В событиях сохранить timestamp UTC (мс или точнее), project/repo, issue_id и number где доступны, cycle_id, operation_id, request_id, event/phase, duration_ms, queue_wait_ms, HTTP status, безопасные details.
- Для длительности измерять monotonic clock, не вычислять её только вычитанием UTC timestamp. Открывать короткие транзакции вне долгих Git/GitHub операций; запись диагностических событий — best-effort и не влияет на выполнение.
- Инструментировать начало/конец `poll`, пустые циклы, delay/wait между poll, обнаружение управляющих меток, sync в SQLite, state transitions, подготовку и PATCH `base_branch`, enqueue/outbox delivery/retry, запрос/ответ GitHub API, verify-readback в диагностическом режиме, child monitor/readiness, запуск Codex и Git/PR публикацию. Выбирать разумную гранулярность для компактного журнала.
- Запись этапов GitHub:
  1. `github_request_start` — запрос реально отправляется;
  2. `github_response_success` / `github_response_failure` — ответ получен, HTTP status и latency;
  3. `github_readback_confirmed` — **только** когда независимый GET действительно доказал изменение.
  `github_web_visible` **не** выводить из API. Видимость на сайте фиксируется вручную с погрешностью наблюдения.
- Не запускать бесконечный GET loop. Readback ограниченный/выборочный; не увеличивать latency штатной операции или количество API вызовов в выключенном режиме.
- Реализовать CLI `codex-dispatcher timing --project <project-id> [--issue N] [--format table|json|csv] [--limit N]` либо равноценный с документированной грамматикой. В таблице отобразить timezone, delta с предыдущим событием, durations. Безопасный CSV/JSON и многопроектная фильтрация.
- Предусмотреть индексы, безопасный способ ограничить/очистить временные записи и тест отсутствия секретов. Не менять частоту `poll_time`, расписание очереди или публикацию из соображений скорости: задача — собрать доказательства задержек.

## Этап 5 — тесты

Сделать профильные тесты, включающие:
1. Свободная редакция обычной/контейнерной/дочерней Issue в `discovered`, до `approve` без блокировки; после `approve` несовпадающая версия не исполняется.
2. Реальная гонка edit vs container YAML patch: пользовательский текст не теряется и child branch не переписывается при закреплённом PR.
3. Отдельный запуск ребёнка после готовой подготовки контейнера, переходы его меток/состояний, повторные poll → нет ложного `child_snapshot_stale`; настоящие конфликты продолжают блокировать.
4. B,C done + D waiting/discovered → контейнер ждёт до approve/merge D.
5. Queue вывод, show, JSON и Unicode.
6. Timing enabled/disabled, API request/response/readback, empty poll, timing correlators, duration, retry/outbox, CSV/table/JSON, мультипроектность, хранилище недоступно, секреты не попадают в лог.
7. Регрессии 6.4.3.3–6.4.3.5, ручной PR мгновенно слит между poll, detached open PR, wrong-base child merge, `review_on_error`/detach/PR ownership.
8. Полный `PATH="$PWD/.venv/bin:$PATH" bash scripts/test.sh`, `python3 -m compileall -q src tests`, `git diff --check`. Указать точные результаты; не скрывать ошибки тестов.
