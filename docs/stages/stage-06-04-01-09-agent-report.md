## Обнаруженные расхождения и известные ограничения

**D1 — §6.1/6.2: генератор имени и нормализация не реализованы.**
`workspace.GitWorkspaceManager.branch` возвращает `codex/issue-N` для base/default
либо `target_branch`. В коде нет CODEX-NNNN по title, нормализации Unicode и
явного ограничения длины. Требования номеров 0001/9999/12345, длинного/пустого
заголовка нельзя объявить подтверждёнными проверкой нынешнего генератора.
Реализация такого генератора — новая возможность вне ограничений этого задания.

**D2 — §4/§5: общий контракт публикации Detach/Reattach расходится с принятым
поведением 6.4.1.7.** `scheduler.collect` при stop вызывает finalize до публикации;
`detachment.fence` запрещает дальнейшие эффекты. Существующий
`test_running_detach_natural_exit_no_publication_dirty_cleanup` явно утверждает
`not pushed`, отсутствие PR и удаление dirty worktree. `workspace.detach_branch`
архивирует локальную неопубликованную branch и начинает от свежей base;
remote branch/PR/pushed вызывают конфликт вместо восстановления опубликованного
канонического результата. Это подтверждено `tests/test_detach_repeat.py`.
Natural drain, аудит и отсутствие повторного запуска покрыты; обязательные
commit/push до detach cleanup и опубликованный Reattach — нет.
Нельзя безопасно исправить это минимальной правкой без изменения принятой
политики detach/публикации/cleanup. Требуется отдельное согласованное решение.

**D3 — §4: нет подтверждения обычного detach-комментария с actor/time.**
`StopController.diagnostics` выбирает `reason='emergency_stop'`; её outbox-тест
подтверждает emergency-комментарий, не обычное снятие ready. Автоматический
Timeline fallback из PR rejection также не доказывает обычный Detach.
Добавление отдельного механизма комментариев оставлено вне регрессионной задачи.

**D4 — §6.3/§7: неполная provenance параметров.**
`tasks.branch_source` допускает explicit/generated; `scheduler.admit` выбирает
его сравнением branch с `target_branch`, а не присутствием ключей YAML. Для base
нет самостоятельного explicit/default source. Это пробел доказательства полного
контракта, не основание менять схему в задаче регрессии. Base/branch/SHA и версия
имеются в tasks/attempts/iterations; автоматическая сохранность этих данных
не означает полноту provenance.

**L1 — принятое ограничение равных server timestamps.**
Строго старые наблюдения отклоняются; при равном времени противоречивые снимки
могут приниматься, порядок внутри секунды не доказан. Legacy-снимок без server time
не доказывает автоматический Reattach. Ограничение принято в 6.4.1.8 и не менялось.

Для D1–D4 не вносились исправления: это отсутствующие возможности либо изменения
явно защищённого принятого контракта, а не локальный дефект нового кода.
Новых падающих тестов требований с последующей сменой production-политики нет;
красные проверки не скрыты skip/xfail. Существующие тесты, воспроизводящие D2,
оставлены без изменения. Матрица не объявляет их соответствием общему ТЗ.

## Рекомендации аудитору и ручная проверка

1. Сначала сверить D1–D4 с общим ТЗ и принятыми решениями 6.4.1.7/.8;
   решить отдельно, требуется ли новое задание по реализации. До этого
   не считать весь §1–§9 выполненным даже при зелёной автоматической регрессии.
2. Пройти [чек-лист M1–M9](stage-06-04-01-09-manual-checklist.md) на
   `heroicrealm/CodexAgentPlayground`, сохранив Issue/PR URLs, IDs, SHA,
   server timestamps, show и логи без секретов. Небезопасную инъекцию ошибок
   заменять изолированной средой и помечать local/stub, оставляя live непроверенным.
3. При ошибках push сохранять результат и worktree; не применять force/reset,
   не удалять БД/чужие refs. Terminal `review_on_error` требует решения человека,
   relabel/approve его не восстанавливает. Обычный Detach сейчас не использовать
   как доказательство remote сохранности из-за D2.
4. После независимого аудита и решения пользователя по ручным результатам
   оформить отдельную приёмку. Агент её заранее не создаёт.

Commit SHA передаётся в сообщении после коммита и push; самоссылка SHA
внутри коммита не требуется. На аудит передаются все перечисленные изменения.
