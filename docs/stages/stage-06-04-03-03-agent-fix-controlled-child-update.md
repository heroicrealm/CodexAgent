# Доработка 6.4.3.3 — контролируемое обновление GitHub Issue ребёнка (вариант A)

**Решение пользователя:** вариант A утверждён.  
**Ветка:** `STAGE_06_04_03`  
**Статус:** задание Codex-агенту, не приёмка реализации.  
**Основание:** [ТЗ 6.4.3.3](stage-06-04-03-03-spec.md), [отчёт реализации](stage-06-04-03-03-report.md), [общее ТЗ 6.4.3](stage-06-04-03-spec.md).

## Цель

Устранить функциональный блокер `child_body_cas_unavailable` для учитываемых непосредственных дочерних Issue: если их `dispatcher.base_branch` отсутствует или отличается от канонической ветки контейнера, диспетчер должен **контролируемо обновить только это поле**, сохранив весь пользовательский Markdown и остальные параметры. Не применять слепой PATCH. GitHub REST Issue PATCH не гарантирует атомарного compare-and-swap: ограничение и остаточное race window должны быть явным образом задокументированы.

## Изменения

1. В `src/dispatcher/containers.py` и, при необходимости, GitHub Adapter реализовать отдельную операцию безопасного обновления body ребёнка. Повторно прочитать актуальную Issue **непосредственно перед PATCH**. Сравнить GitHub `id`, `repository_url`, `number`, `state`, текущую родительскую связь, `codex-ready`, допустимого автора, `body`, `updated_at`, валидность `dispatcher` YAML и состояние задач/веток/PR в SQLite. При любом несовпадении с исходным подтверждённым снимком — не записывать, зафиксировать диагностируемый конфликт.
2. Проверить право на обновление именно этой Issue; не выдавать approve и не добавлять ready. Применять `with_base_branch` к **повторно прочитанному** body и менять только поле `dispatcher.base_branch`, сохраняя остальные YAML/Markdown. Если изменений нет, PATCH не отправлять.
3. **До внешнего эффекта** сохранить устойчивое намерение с issue_id, iteration_id, хешами исходного/целевого body, ожидаемой веткой и версией наблюдения. Между предварительной проверкой и PATCH повторно проверить локальный guard/поколение; обернуть попытку существующим project lock. Не держать SQLite writer transaction во время сети.
4. Выполнить один контролируемый PATCH с новым body, затем независимо перечитать Issue и проверить фактические body/hash, `base_branch`, идентичность, ready и родительскую связь. Только доказанное совпадение позволяет пометить operation `confirmed` и продолжить подготовку контейнера. Неполный/неизвестный исход — не трактовать как успех.
5. Recovery после timeout/потери ответа/рестарта: сначала read-back; если записан ожидаемый целевой body — подтвердить intent без второго PATCH; если исходный body остался прежним и конфликты отсутствуют — разрешён контролируемый повтор; если body изменён третьей стороной, status/parent/ready уже другой или результат неоднозначен — остановиться с blocker, не перезаписывать изменения человека.
6. Обновить соответствующий локальный snapshot ребёнка через действующий механизм sync с корректной границей подтверждения. Служебная правка не должна автоматически одобрять ребёнка и не должна приводить к произвольному снятию уже валидного approve; если действующий content-hash/version contract препятствует этому — внести ограниченную, доказуемую корректировку с тестами, без обхода правил для пользовательских правок.
7. Снимать `child_body_cas_unavailable` только после подтверждения успешной операции или после достоверной проверки того, что требуемый `base_branch` уже установлен. Для несовместимых активных веток/PR сохранить `child_active_base_conflict`; для снятого ready с открытым PR — утверждённый вариант блокировки A, не выполнять retarget.
8. Исключить повторяющиеся диагностические комментарии, изменение чужих веток и PR, автоматические merge/approval, каскадное управление детьми и несогласованное изменение конфигурации.

## Явная граница гарантии

Предпроверка + PATCH + post-verification **не является атомарным CAS**. Между последним GET и PATCH другая сторона может изменить Issue, и PATCH потенциально затрёт такую правку. Даже успешный read-back не доказывает, что подобной потери не было. Это **принятое пользователем остаточное ограничение** варианта A; не утверждать «полной защиты от потери изменений». При обнаруженной гонке — остановить операцию и потребовать вмешательства человека; невозможно обнаруженную постфактум потерю текста автоматически восстановить без доказуемого источника. По возможности добавить диагностику и исследовать альтернативу условной записи без предположений об If-Match.

## Тесты

- Child без блока YAML, без `base_branch`, с неверным `base_branch` → корректная правка только целевого поля.
- Проверка эквивалентности остального Markdown, fenced-блоков, Unicode и YAML, отсутствие лишней правки, идемпотентный повтор.
- Уже корректная child base → без PATCH.
- Изменение body/`updated_at`/ready/parent/author/state перед PATCH → blocker, без записи.
- Несовместимый `work_branch`/PR → blocker, без записи.
- Успешный PATCH и последующая проверка; фальшивый успех API; timeout после фактического PATCH; восстановление после crash.
- Повторный poll/restart не создаёт повторного PATCH после confirmed; сбой повторной проверки не выдаёт ложный успех.
- Служебная правка и уже подтверждённый ребёнок: не выдавать новое approve, не терять законное подтверждение; пользовательская правка инвалидирует подтверждение как прежде.
- Параллельные попытки и гонки, включая **детерминированный тест остаточного окна** GET→PATCH, в котором фиксируется известное ограничение и отсутствие недоказанных гарантий.
- End-to-end: контейнер с двумя ready детьми, у которых нет `base_branch`, и одним никогда не ready ребёнком → правятся только двое, контейнер переходит в `awaiting_children`, Codex и контейнерный PR не создаются.
- Полный регрессионный набор, `bash scripts/test.sh`, `git diff --check`.
