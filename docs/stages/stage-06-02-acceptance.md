## Проверенные требования
- Глобальные числовые GitHub REST repository_id, issue_id, pr_id и проверки уникальности в SQLite; номер Issue используется только вместе с репозиторием.
- Отдельные логические итерации и технические попытки; повторное approve после rejected при неизменной версии формирует новую итерацию.
- Атомарные и идемпотентные переходы, проверка actor, state/version, event и evidence; терминальность done/cancelled.
- Отдельные сущности task_pull_requests, iteration_pr_history, task_transitions, publication_operations.
- Сохранена совместимость существующего CLI и legacy runtime до этапа 6.3; push сам по себе не считается подтверждением PR в новом контракте.
- Одноразовая миграция старой SQLite с предварительным согласованным backup и транзакционной очисткой операционных таблиц, без повторной очистки новых данных.

## Замечание #20
В исходном варианте prepare() вызывал SQLite backup из отдельного соединения после BEGIN IMMEDIATE в первом соединении; это создавало риск блокировки. Исправлено: backup выполняется до начала write-транзакции под эксклюзивным runtime flock, затем BEGIN IMMEDIATE, повторная проверка версии и атомарная миграция. Проверены сценарии непустой старой БД в режимах DELETE/WAL, тайм-аут дочернего процесса 10 секунд, backup integrity, блокировка daemon, конкурентный opener и отказ backup.

## Ограничения и остаточные риски
1. Реальный GitHub PR lifecycle, reopening, merge/rejection reconciliation и очистка веток не подключены: относятся к 6.3–6.7.
2. Runtime legacy push→review сохраняется до 6.3; новый контракт не трактует такой review как доказанный PR.
3. Между чтением GitHub evidence и SQLite-переходом остаётся окно внешних изменений; последующая reconciliation обязательна.
4. Доверенное происхождение Evidence должно обеспечиваться интеграцией следующих этапов.
5. Миграция рассчитана на остановленный диспетчер и процессы, соблюдающие runtime flock; сторонние писатели SQLite вне этого контракта.

## Решение
**Этап 6.2 рекомендован к слиянию из STAGE_06_02 в STAGE_06.** Замечание #20 устранено. Следующий этап — 6.3; не считать PR workflow уже активированным. Слияние выполнять после проверки PR ответственным.
