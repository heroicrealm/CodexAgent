# Этап 6 — Публикация результатов и управление жизненным циклом PR

**Проект:** Codex Task Dispatcher · **Репозиторий:** heroicrealm/CodexAgent · **Рабочая ветка:** STAGE_06 · **Редакция:** 2026-10-24 (заменяет исходную спецификацию этапа 6).

## 1. Цель
Обеспечить обязательную публикацию результата Codex в GitHub Pull Request и полный управляемый жизненный цикл задачи: review, merge/done, закрытие без merge/rejected, повторная доработка и окончательная отмена/cancelled.

## 2. Нормативные правила
1. Успешный Codex → проверка коммитов → обычный push → создание или подтверждение связанного PR → `review`. Без PR `review` запрещён; пустые коммиты, force push и PR без diff запрещены.
2. Merge PR выполняется только ответственным человеком через GitHub; диспетчер лишь наблюдает. Merge → терминальное `done`, Issue закрыть с причиной `completed`, локальные ресурсы очистить безопасно.
3. PR closed unmerged → `rejected`. Ветка и worktree сохраняются. Ответственный за Issue либо явно подтверждает повторный запуск (`pending`, новая итерация в прежней канонической ветке поверх опубликованного SHA, push и reopen прежнего PR), либо отменяет (`cancelled`, Issue `not_planned`, безопасное удаление принадлежащих задаче ресурсов и удалённой ветки).
4. `done` и `cancelled` необратимы даже при внешнем изменении меток/повторном открытии Issue. Состояние PR определяется GitHub, терминальность защищает SQLite.
5. Ответственный за Issue и ответственный за merge — разные логические роли, могут совпадать. Полномочия и свежесть управляющих событий проверяются технически. Python-диспетчер не оценивает содержательную актуальность ТЗ. Повторное approve возможно без редактирования Issue.
6. Внутренние связи Issue–PR–попытки использовать по глобальным числовым REST GitHub `issue_id` и `pr_id`; `number` только совместно с `repository` для API и отображения. Миграции сохраняют существующие данные.
7. Вести историю итераций, commit SHA, PR ID/number, решений, публикаций и ошибок; операции идемпотентны, возобновляемы после рестарта и не перезапускают Codex при сбое только публикации.
8. При повторной попытке использовать каноническую ветку и переоткрывать прежний PR после подтверждённого push. При недоступности SHA не начинать работу. Не удалять ветку без доказательства владения диспетчером. Не выполнять merge автоматически.
9. Сохранять совместимость принятых этапов 1–5, использовать существующие SQLite, scheduler, worktree, GitHub adapter и outbox. Отчёты Issue должны содержать итерацию, ветку, SHA, PR, краткий итог и безопасную диагностику; дубликаты запрещены.

## 3. Состояния
`discovered → pending → running → review`; из `review`: `done` (merged) либо `rejected` (closed unmerged). Из `rejected`: `pending` (новое подтверждение) либо `cancelled` (окончательная отмена). Ошибки исполнения и публикации обрабатываются отдельно, без ложного review. Внутренние фазы публикации и очистки не обязаны быть публичными метками.

### Уточнение реализации 6.4.1.6 (Issue #36)

Терминальное состояние `review_on_error` с меткой `dispatcher:review-on-error`
сохраняется до ручного решения человека; автоматических переходов в done/cancelled
или повторных запусков нет. Доказанный merged канонический PR исключает reopen;
сетевые ошибки и одиночные HTTP-коды остаются retry/reconcile. До удаления owned
worktree обязателен обычный push и подтверждённый remote SHA; сбои сохраняют данные
и возобновляют только публикацию. Диагностический комментарий доставляется через
устойчивый outbox без дубликатов. Исправимые ошибки подготовки — discovered с
отзывом подтверждения. Подробности и границы классификатора:
[отчёт 6.4.1.6](stage-06-04-01-06-implementation.md).

## Эксплуатационная сверка 6.4.1.9 (2026-10-31)

Действующие требования: [ТЗ 6.4.1](stage-06-04-01-spec.md).
Проверенные механизмы, расхождения реализации и границы stub-проверок перечислены
в [матрице](stage-06-04-01-09-traceability.md); подготовлен
[ручной чек-лист Playground](stage-06-04-01-09-manual-checklist.md).
`done`, `cancelled`, `review_on_error` терминальны. Detach прекращает отслеживание
без отмены; running завершается естественно. Для обычной и terminal публикации push/cleanup восстанавливаются
без повторного Codex; при ошибке публикации результаты сохраняются.
Требование публикации перед detach cleanup расходится с принятым текущим
контрактом 6.4.1.7: публикация блокируется, dirty cleanup допустим (D2 в отчёте).
Reattach требует свежего наблюдения и нового approve. Равные server timestamps
остаются принятой неоднозначностью, а не доказательством строгого порядка.
Правила конфигурации, безопасного восстановления и команды CLI приведены
в [README](../../README.md#регрессия-и-ручная-приёмка-6419).
Общая приёмка 6.4.1.9 не объявлена.
