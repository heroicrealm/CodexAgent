# Этап 6 — Публикация результатов

**Проект:** Codex Task Dispatcher  
**Репозиторий:** heroicrealm/CodexAgent  
**Ветка:** STAGE_06 (от main)  
**Статус:** утверждено, 2026-10-24

## 1. Цель и критерий завершения

Обеспечить публикацию результатов Codex CLI в GitHub, управление Pull Request, отчётность и повторную доработку по замечаниям ревью. Результат исполнения доступен в GitHub, а Issue получает `review` после успешного `push`, независимо от создания PR. Слияние PR только вручную.

## 2. Базовые требования

### 2.1. Commit и push

После завершения Codex CLI проверить рабочее дерево, сохранить необходимые изменения коммитом (если они ещё не закоммичены), выполнить обычный push рабочей ветки, подтвердить результат и сохранить branch и SHA. Не создавать пустые коммиты, не выполнять force push, не коммитить посторонние файлы. Если результат уже опубликован, повторная проверка не должна создавать новый коммит.

### 2.2. Статус review

После успешного push перевести Issue в `review`. Это сигнал ответственному, что агент завершил работу и требуется проверка. PR не является условием перехода в review. Ошибка создания PR не откатывает review, но отражается в отчёте и журнале. Если синхронизация меток не удалась, сохранить операцию для повторной доставки.

### 2.3. Автоматическое создание PR

В общем конфиге:

```yaml
defaults:
  auto_create_pr: true
```

В теле Issue допускается переопределение через именованный раздел «Параметры Codex» с единственным YAML-блоком:

```yaml
codex:
  auto_create_pr: false
```

Приоритет: настройка Issue > общий конфиг > true. При некорректном YAML, неизвестном типе или неоднозначном повторении настройки — явная диагностическая ошибка, не молчаливое игнорирование. Парсинг настроек не должен трактовать произвольные фрагменты текста как управляющие команды. Целевая ветка PR берётся из конфигурации проекта или согласованного поля Target branch в Issue; необходимо сохранить совместимость с существующим форматом.

При true создать PR после push; при false не создавать. При существующем открытом PR, соответствующем репозиторию, рабочей и целевой веткам задания, повторно его не создавать. Если GitHub сообщает об уже существующем PR, найти и переиспользовать его. Не выполнять автоматический merge.

### 2.4. Ручное создание PR

Добавить команду `codex-dispatcher pr create <task-id>` (формат идентификатора согласовать с существующими CLI-командами и однозначным выбором проекта). Команда не запускает Codex; проверяет наличие опубликованной ветки и изменений относительно base; создаёт PR или возвращает ссылку на существующий. Ошибки возвращают ненулевой код и понятную диагностику.

### 2.5. Отчётность

Публиковать в исходном Issue номер итерации, итог выполнения, рабочую ветку, SHA и ссылку на коммит, PR при наличии, краткое описание изменений, доступные результаты тестов и безопасную диагностику ошибок. При отсутствии PR указать ссылку на ветку. Сохранять историю итераций. Повторная доставка отчёта той же итерации не должна создавать дубликаты; для этого использовать устойчивый идентификатор публикации и проверку фактического состояния GitHub. Не раскрывать токены, секреты, полные stderr и конфиденциальные данные.

### 2.6. Повторная доработка

Поддержать `review → pending → running → review` без статуса `approved`. Ответственный оставляет замечания в исходном Issue и явно переводит задачу в pending. Обычный комментарий или событие Request changes в PR сами по себе не запускают Codex. Диспетчер должен обнаружить авторизованный переход, сохранить историю и контекст исходного ТЗ, замечаний и предыдущих итераций, переиспользовать рабочую ветку и открытый PR, выполнить доработку и после успешного push снова выставить review. Повторная итерация должна иметь отдельный идентификатор/номер. Изменения тела Issue и меток не должны обходить механизм подтверждения или позволять недоверенному автору запускать задачу. Если PR закрыт, не создавать новый автоматически без отдельно согласованного безопасного правила; сообщить ответственному.

### 2.7. Ошибки и восстановление

- Сбой Codex или commit: не переходить в review; сохранить безопасную диагностику.
- Сбой push: не переходить в review; повторить публикацию без повторного исполнения Codex.
- Сбой меток: сохранить и повторить синхронизацию, не терять успешный push.
- Сбой PR: оставить review, сохранить ошибку и возможность повторной попытки.
- Сбой комментария: сохранить outbox-запись и повторить доставку.
- Сбой сети, остановка или перезапуск: сверить удалённое состояние до повторного действия.

Использовать существующие SQLite, outbox, scheduler, Git worktree и GitHub-интеграцию, не строить параллельную подсистему. Все операции должны быть идемпотентны и восстанавливаться после перезапуска. Сохранять ограничения безопасности, allowlist авторов и запрет force push.

## 3. План реализации

| Подэтап | Работы | Приёмка |
| --- | --- | --- |
| 6.1 | Аудит Git workflow, SQLite/outbox, конфигурации и модели состояний; согласование контрактов | Нет дублирования существующих механизмов |
| 6.2 | Доработка commit/push, сохранение SHA и подтверждения публикации | Результат доступен в GitHub |
| 6.3 | Общий default и override Issue, поиск и создание PR | PR создаётся согласно настройкам, без дубликатов |
| 6.4 | CLI-команда ручного создания PR | PR без повторного Codex |
| 6.5 | Отчёты, комментарии, метки и переход в review | Issue содержит сведения для проверки |
| 6.6 | Повторная доработка в исходной ветке и PR | Цикл review→pending→running→review |
| 6.7 | Повторные попытки и восстановление после ошибок | Идемпотентность после рестарта |
| 6.8 | Интеграционная приёмка и документация | Все обязательные сценарии пройдены |

Реализация: дочерние ветки `STAGE_06_01` … `STAGE_06_08` от `STAGE_06`; каждый подэтап принимается отдельно и вливается в родительскую ветку. По завершении — PR из STAGE_06 в main.

## 4. Обязательные тесты

1. Успешный push с автоматическим PR.
2. Успешный push без PR, статус review.
3. Ручное создание PR после выполнения.
4. Повторное создание PR без дубликата.
5. Review с замечаниями → pending → повторный Codex → push → review, тот же открытый PR.
6. Сбой commit или push без ложного review.
7. Сбой PR при успешном push с сохранением review.
8. Сбой меток и комментариев с восстановлением через outbox.
9. Перезапуск после частичной публикации без повторного исполнения и дубликатов.
10. Недоверенные команды/авторы, невалидные настройки Issue, секреты и запрет force push.

Автоматические тесты: `bash scripts/test.sh`, с mock/stub Git и GitHub, без реальных токенов. Для полной приёмки провести ручной интеграционный тест на выделенном тестовом репозитории.

## 5. Совместимость и ограничения

README и пример конфига обновить по фактической реализации. Не изменять ранее утверждённую семантику состояний и жизненного цикла без явного согласования. Существующие механизмы push и итогового комментария расширять, а не заменять. Для новой логики предусмотреть миграции SQLite при необходимости. Поддержать остановку `stop` и `stop --force` с безопасным восстановлением публикации.

**Критерий общей приёмки:** успешное выполнение Codex завершается опубликованной веткой и статусом review, при включённой настройке — PR, а при замечаниях — контролируемой повторной доработкой без потери истории.
