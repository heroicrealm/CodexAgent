# 6.4.1.8 — аудит изоляции tracking_generation

Дата: 2026-10-31. Ветка: `STAGE_06_04_01_08`.

## Архитектурное заключение

Отдельного счётчика `tracking_generation` нет и добавлять его для проверенных
сценариев не требуется. Логическое поколение задаётся совокупностью границ:

- `tasks.version` — версия содержимого, а не поколение отслеживания. При
  Detach/Reattach без изменения текста она остаётся прежней.
- `stop_requests` сохраняет request_id, version, iteration_id, attempt_id,
  доказательство с серверным observed_at и факт завершения остановки.
- Reattach разрешён только для `detached`, после finalized_at, при отсутствии
  незавершённых cleanup_jobs и строго более новом серверном наблюдении метки.
  Он снимает active у stop_request, очищает approved_version и current_iteration_id,
  возвращает `discovered`. Старые iteration/attempt/решения сохраняются.
- `command_guards.server_at` фиксирует серверную границу доступности/версии.
  После Detach/Reattach она обновляется. `observation_token` обновляется при
  каждом apply; он защищает от конкурентной обработки прежнего результата poll,
  но сам по себе не является постоянным идентификатором поколения.
- GitHub approve проверяет автора, актуальное содержимое/метки и timeline;
  время события должно быть строго новее границы и изменений readiness.
  Уже записанный event_id дедуплицируется в пределах repository. Поэтому также
  безопасно событие, которое до Detach ещё не было доставлено диспетчеру.
- Новое подтверждение создаёт монотонную task_iteration. Резервирование attempt
  проверяет актуальную версию, подтверждение, iteration и observation_token.
- `control_observations` сохраняет максимальное серверное время принятого
  наблюдения по issue_id. Более старый снимок не вызывает новый Detach ни через
  Store.apply, ни через targeted StopController.observe; граница переживает рестарт.
- PR intent и result outbox привязаны к attempt/iteration; fence проверяет stop,
  версию и текущую iteration перед публикацией. Старый result остаётся в outbox,
  но не публикуется в новом поколении. Cleanup также проверяет поколение и attempt.
  stop/timeout diagnostics публикуют исторические комментарии с собственными
  маркерами и не выполняют переходов задач. Reconcile перечитывает текущую task.

Это реализует §5 ТЗ для проверенных достоверных серверных снимков: возврат метки
не является подтверждением; старые команды и публикации не разрешают новую работу.
Канонические ветки/PR, принятый natural-drain Detach и stop --force не менялись.

## Подтверждённый дефект и исправление

Новый тест `test_terminal_state_never_revives_on_ready[review_on_error]` падал:
снятие ready переводило терминальную `review_on_error` в `detached`, открывая путь
к Reattach. `done` и `cancelled` уже были защищены. Минимально добавлена такая же
защита для `review_on_error` в request_in_transaction и обоих путях финализации.
При emergency stop намерение остановки по-прежнему сохраняется, терминальное
состояние не заменяется на detached. Миграций и изменений схемы нет.

## Новые автоматические проверки

`tests/test_tracking_generation.py` — 13 параметризованных сценариев:

- Старый approve после running → Detach → реального CleanupService.tick → Reattach:
  ранее доставленный и впервые доставленный event_id, с рестартом SQLite и без.
  Повторная доставка не создаёт iteration/attempt; новое событие затем применяется.
- Два Detach/Reattach с тем же содержимым, рестарт, обратный порядок и повтор
  снимков удаления ready: через poll API и targeted observation API, пока поколение B находится в running.
- Сохранение done, cancelled, review_on_error при снятии/возврате метки.
- Старые result outbox и PR intent не публикуют результат в новой iteration.
- Рестарт между получением наблюдения команды и её commit: старый token отклонён.
- Одинаковые Issue number и event_id в двух repositories не смешиваются.

Используются временная настоящая SQLite, реальные Store/commands/StopController,
CleanupService и publishers. Сетевые ответы подменены структурированными GitHub
снимками и событиями с серверными timestamps; проверки актуальности не обходятся.
Здесь running attempt резервируется без запуска процесса и файловых артефактов.
Реальное естественное завершение Codex-stub и очистку worktree дополнительно
покрывает существующий test_running_detach_natural_exit_no_publication_dirty_cleanup.

## Ограничения и остаточные риски

- Это адаптер снимков, не webhook inbox: для удаления ready используется HTTP
  server observation time. Строго более старые времена отбрасываются; равные
  timestamps принимаются. Разный порядок противоречивых снимков в пределах одной
  секунды HTTP Date не позволяет доказать по одному timestamp. Эта неоднозначность
  не устранена новым счётчиком: он сам по себе не доказывает порядок внешних событий.
- Legacy-снимки без server_observed_at принимаются для совместимости, но не
  разрешают автоматический Reattach. Гарантии тестов запоздалого удаления относятся
  к ответам с достоверным серверным временем; replay legacy-снимков не аттестован.
- Исторические диагностические комментарии stop/timeout могут доставляться поздно;
  это аудит прежней операции, не команда новому поколению. Непубликуемый старый
  result outbox сохраняется; политика его архивирования в эту задачу не входит.
- Live GitHub и настоящий Codex не вызывались; CI/локальные stub-тесты проверяют
  поведение диспетчера. ТЗ и план не менялись: исправление следует существующему §5.
