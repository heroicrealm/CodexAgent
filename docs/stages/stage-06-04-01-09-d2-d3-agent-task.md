# Дополнительное задание агенту 6.4.1.9 — D2 и D3

**Решение заказчика:** 2026-10-31. **Ветка:** `STAGE_06_04_01_09`. Основание: `stage-06-04-01-09-agent-report.md`, общее ТЗ §4–§5.

## Принятые решения
- **D1:** генерация/выбор ветки — отложить на следующий этап, после приёмки остановки и возобновления отслеживания.
- **D4:** provenance explicit/default параметров ветки — отложить вместе с D1.
- **D2:** устранить в текущем этапе. Detach обязан сохранить и опубликовать доступные результаты до очистки worktree.
- **D3:** устранить в текущем этапе. Обычный Detach обязан публиковать идемпотентный диагностический комментарий.

## D2 — обязательная публикация при Detach
1. При снятии `codex-ready` блокировать новые запуски, но не прерывать выполняющийся Codex; дождаться natural exit.
2. Сохранить изменения текущего owned worktree, выполнить commit (при наличии diff) и **обычный push** в доказанно принадлежащую Issue каноническую ветку. Не создавать новую ветку/PR и не выполнять force push. Существующий PR не закрывать автоматически.
3. Подтвердить наличие результата в remote до cleanup. Если нет изменений — зафиксировать отсутствие diff и подтверждённую сохранность имеющегося SHA; не считать неудачный push успешным.
4. При ошибке commit/push/проверки сохранить worktree и неопубликованные данные; durable intent + retry после poll/restart **без повторного запуска Codex**. Не удалять dirty worktree.
5. После успешного подтверждения публикации безопасно очистить owned worktree и временные файлы. Сохранить branch/PR/SHA и историю в SQLite. Reattach должен использовать прежние канонические ресурсы; конфликт/legacy неоднозначность — fail closed.
6. Проверить и при необходимости скорректировать `scheduler.collect`, `detachment.fence/finalize`, `workspace.detach_branch`, публикацию, cleanup и восстановление. Запрет stale событий нового поколения не ослаблять. Развести запрет новых запусков и разрешение обязательных публикационных эффектов текущего поколения.

## D3 — комментарий об обычном Detach
1. Однократно опубликовать в Issue комментарий о прекращении отслеживания: UTC-время, actor снятия `codex-ready` по достоверному GitHub timeline, либо «Не удалось определить», каноническая branch, SHA и статус публикации.
2. Использовать outbox и идемпотентные ключи; при потере ответа/рестарте не создавать дублей. Если публикация ещё в retry — корректно отражать ожидающее состояние или обновлять прежний комментарий после успешного push; не заявлять об успешной публикации преждевременно.
3. Не доверять actor из произвольного текста Issue. Не путать ordinary detach с `emergency_stop`. Повторный poll и relabel не должны дублировать комментарии.

## Тесты и отчёт
- Сначала воспроизводящие падающие тесты D2/D3, затем исправление. Пересмотреть существующие тесты, утверждающие `no publication` и `dirty cleanup`; не удалять проверки защиты и не подменять требования.
- Покрыть idle и running detach, natural exit, push failure/retry/restart, PR open, reattach с опубликованным SHA, duplicate timeline/poll, actor fallback, outbox lost response, terminal states и многопроектность.

- Отложенные D1/D4 явно обозначить как **согласованные исключения из приёмки 6.4.1.9** и задачи следующего этапа. Не выдавать их за выполненные.
- Не выполнять live операции, PR, merge или закрытие Issue без указания пользователя. Не оформлять финальную приёмку самостоятельно.

## Критерии готовности
Ни один Detach не удаляет неопубликованные результаты; успешный push подтверждён до cleanup; повторный Codex при retry не запускается; обычный detach-комментарий идемпотентен и содержит достоверные сведения; reattach не теряет канонические ресурсы; полная регрессия зелёная.
