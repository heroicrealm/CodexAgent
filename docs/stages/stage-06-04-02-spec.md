# 6.4.2 — Параметры Git-веток в GitHub Issue (D1/D4)

Статус: проект окончательного ТЗ, вариант А согласован 2026-10-31. Реализация и приемка отдельно.

## 1. Назначение

Позволить автору доверенного GitHub Issue задать имя рабочей ветки и, для новой ветки, источник ее создания. Сохранить автоимя `codex/issue-N` и текущий жизненный цикл исполнения и публикации. Исполнитель Codex CLI работает только с подготовленным dispatcher worktree и не управляет Git.

## 2. Синтаксис

В описании Issue разрешается один fenced code block с языком `yaml` и корневым ключом `dispatcher`:

```yaml
dispatcher:
  branch: feature/new-api
  base_branch: develop
```

* `branch` — необязательное имя рабочей ветки; при отсутствии или отсутствии самого блока применяется `codex/issue-<issue number>`.
* `base_branch` — необязательная базовая ветка, используемая **только при создании** рабочей ветки; при отсутствии — `default_branch` / legacy `base_branch` из конфигурации проекта.
* При наличии удаленной рабочей ветки `base_branch` не влияет на ее историю: диспетчер берет актуальный `origin/<branch>`.
* Пустые значения, нестроковые значения, дубли ключей, неизвестные ключи внутри `dispatcher`, несколько блоков `dispatcher` и невалидный YAML считаются ошибкой параметров данного Issue. Остальные произвольные YAML/Markdown-блоки не интерпретируются как конфигурация диспетчера.
* Совместимость: прежние отдельные строки `Target branch: ...` и `Целевая ветка: ...` продолжают поддерживаться. Если одновременно присутствуют legacy строка и поле `dispatcher.branch`, задача отклоняется как неоднозначная (даже при совпадении значений). Не создавать скрытый приоритет.
* Доступны только явно описанные параметры; другие команды через содержимое Issue не добавляются.

## 2.1. Граница между параметрами диспетчера и инструкциями Codex

* YAML-блок `dispatcher` является служебными данными **только для диспетчера**, а не частью пользовательского задания Codex CLI. До сборки prompt диспетчер должен разобрать блок из исходного Markdown и удалить **весь fenced-блок вместе с ограничителями** из текста, передаваемого агенту. Не заменять его пересказом или другими инструкциями.
* Сохранять исходный `body` Issue без изменений в snapshot/observed SQLite, для аудита, хеша версии и повторной синхронизации. Для Codex формировать отдельный очищенный `task_body` (производное значение), не подменяя оригинал.
* Границы блока определять структурным разбором Markdown fenced code blocks (с учетом длины fence, отступов и закрывающего fence), а не глобальным поиском/заменой текста: одинаковый YAML-пример в обычном тексте не должен удаляться ошибочно.
* Любой неоднозначный или некорректный служебный блок (повтор, недопустимые ключи, незакрытый fence, невалидные значения) приводит к отказу подготовки данного задания **до запуска Codex**, а не к передаче потенциальных служебных данных в prompt.
* Другие обычные code blocks, включая YAML без корневого ключа `dispatcher`, сохранять в тексте задания. Legacy строку `Target branch:` / `Целевая ветка:`, если она распознана как метаданные, также удалять из prompt.
* Очищение выполняется при **каждой попытке запуска**, включая повторную, из сохраненной утвержденной версии Issue. Вложения и дополнительные системные инструкции диспетчера остаются в своих штатных каналах.
* Зафиксировать тестами: очистка служебного блока и legacy строки; сохранение обычного YAML; отсутствие остаточных fence; сохранение оригинального body; поведение при неоднозначном/незакрытом блоке; повторное исполнение и неизменность существующих механизмов публикации результатов.

## 3. Определение ветки (вариант А)

1. Для утвержденной версии Issue определить рабочую ветку: `dispatcher.branch` → legacy `Target branch` → `codex/issue-N`.
2. Определить базовую ветку: `dispatcher.base_branch` → конфигурация проекта.
3. Валидировать имена как Git branch через существующие ограничения и `git check-ref-format --branch`; запрещать имена, совпадающие с защищенной основной веткой (`default_branch` проекта, а также актуальный default origin, если он отличается); не пытаться автоматически заменить явное пользовательское имя.
4. Выполнить `fetch origin` перед подготовкой; проверять наличие рабочей и базовой веток на origin, не угадывая по устаревшим локальным refs.
5. Если рабочая ветка существует на origin — использовать ее актуальный HEAD как основание изолированного worktree; если отсутствует — создать ее от текущего origin/<base_branch>. Отсутствие базовой ветки в случае создания — ошибка без fallback.
6. Не создавать и не публиковать ветку на GitHub до возникновения результата, если действующий workflow не требует более ранней публикации. Использовать существующие commit/push/PR механизмы.
7. Никогда не выполнять force push, автоматический rebase или reset чужой истории; изменения origin после подготовки обнаруживаются при обычном push и приводят к диагностике конфликта, без потери локальных коммитов.
8. При переходе rejected → pending (новая попытка) заново fetch и заново проверить origin. Не продолжать со старым HEAD. Учитывать существующий contract повторной попытки и публикации результата.

## 4. Защита от коллизий

* На одном репозитории нельзя одновременно исполнять две задачи с одинаковой рабочей веткой. Проверку и резервирование проводить атомарно средствами SQLite существующего механизма execution; учитывать различие проектов и совпадение repository.
* Не использовать `git worktree add -b` с существующим локальным именем без проверки принадлежности. Остаточная локальная ветка от завершенной попытки не должна вызывать потерю коммитов, сброс чужой истории или ошибочное повторное использование.
* Перед повторным использованием локального имени необходимо безопасно определить, что прежняя попытка завершена и все ее результаты опубликованы, а старый worktree не активен. Если доказать безопасность нельзя — остановиться с диагностикой; не удалять и не переписывать данные «на всякий случай».
* Ошибка параметров, занятость ветки либо отсутствие base должны быть привязаны к конкретной Issue: другие Issue в том же проекте продолжают синхронизироваться. При ошибке подготовки не запускать Codex CLI.
* Причину блокировки публиковать в комментарии Issue и показывать в `show`/журналах без секретов; не менять статус на `review`, так как выполнение еще не происходило. Использовать согласованный в системе механизм состояния ошибки подготовки, не создавать новый статус без отдельного решения.

## 5. Версии и модель данных

* Разобранные параметры относятся к версии содержимого Issue. Изменение `branch`/`base_branch` до старта должно сбрасывать подтверждение в рамках текущей модели `discovered → pending`.
* При уже запущенной или завершенной попытке изменения Issue не должны незаметно переориентировать ее ветку.
* Фиксировать для каждой попытки рабочую ветку, базовую ветку (если использована), исходный HEAD и признак существовавшей/новой ветки — в существующих структурах, при необходимости с миграцией SQLite.
* В `show` отображать фактическую рабочую ветку, а не только исходное поле `target_branch`; API и старые записи должны оставаться совместимы.

## 6. План реализации

1. Парсер YAML-блока и legacy-синтаксиса, проверки, тесты на неоднозначность и недоверенные тексты.
2. Разрешение ветки и источника, подготовка worktree, безопасная обработка существующих локальных имен и конфликтов origin.
3. Связь с попытками, блокировкой веток, `rejected → pending`, отображением и диагностикой.
4. Актуализация README, образца Issue и технической документации; автоматические и ручные проверки.

## 7. Приемочные сценарии

1. Issue без параметров → `codex/issue-N` от настроенной основной ветки.
2. `branch: feature/new` при отсутствии на origin → ветка создана от default branch.
3. `branch: feature/new`, `base_branch: develop` → новая ветка создана от актуального `origin/develop`.
4. Существующая `feature/existing` → подготовка строго от ее актуального HEAD; `base_branch` игнорируется для истории ветки.
5. Изменение origin между fetch и push → обычный push отклоняется, коммиты сохраняются; force push отсутствует.
6. Некорректный YAML, пустые/повторные/неизвестные ключи, две секции, YAML + legacy строка → локальная диагностируемая ошибка Issue, другие Issues не блокируются.
7. Имя основной защищенной ветки → отказ, без создания рабочего дерева и без публикации коммитов.
8. Не существующая `base_branch` при создании → отказ, без silent fallback.
9. Две одновременно активные задачи на одной ветке → атомарный отказ второй; разные ветки работают независимо.
10. `rejected → pending` после изменения удаленной ветки → новая попытка использует свежий HEAD, не теряя предыдущие результаты.
11. Локальное имя ветки осталось после старой попытки → отсутствие перезаписи, безопасное повторное использование или диагностированный отказ.
12. Старый `Target branch:` сохраняет прежнюю семантику; отсутствие параметров не меняет сценарий автоимени.
13. `queue`/`show`, миграции SQLite, публикация PR, detach и очистка worktree после done не регрессируют.
14. Полный `bash scripts/test.sh` и ручные проверки минимум трех основных сценариев на тестовом GitHub-репозитории успешны.

## 8. Границы

* Не разрешать выбор чужого репозитория, непосредственную запись в default branch или произвольные Git-команды через Issue.
* Не менять алгоритмы утверждения, PR, detach и cleanup, кроме интеграции с новыми параметрами и устранения выявленных конфликтов.
* Приемку, отчет и PR оформлять после выполнения и проверки отдельным шагом.
