# ТЗ 6.4.1.3 — Повторное выполнение в старой ветке и reopen старого PR

Статус: утверждено. Базовая ветка: `STAGE_06_04_01`. Рабочая ветка: `STAGE_06_04_01_03`.

## 1. Цель и границы
После отклонения результата Issue обеспечить новую подтверждённую итерацию Codex в прежней рабочей ветке, сохранение всей истории и повторное открытие ранее закрытого без merge PR. **Утверждён вариант A:** если reopen невозможен, новый PR не создавать; сохранить диагностическую ошибку публикации и ожидать оператора. Не восстанавливать автоматически удалённые ветки, не создавать заменяющий PR, не делать force push, не выполнять автоматическое разрешение конфликтов.

## 2. Существующая модель
Использовать таблицы `tasks`, `task_iterations`, `attempts`, `task_pull_requests`, `iteration_pr_history`, `publication_operations`, `task_transitions` и уже реализованное повторное подтверждение из `rejected`. Ключи связи — GitHub issue_id, repository_id, pr_id; номер Issue сам по себе не глобально уникален. Не терять историю прошлых итераций. Не вводить вторую параллельную модель статусов. Любые изменения схемы — только при обоснованной необходимости, через атомарную идемпотентную миграцию с тестами.

## 3. Предусловия и новая итерация
Повторное исполнение допустимо только для актуальной подтверждённой версии Issue после отклонения, при наличии предыдущей итерации, закреплённой рабочей ветки и соответствующего PR без merge. Не должно быть параллельного активного исполнения того же Issue или ветки. Одно подтверждение создаёт не более одной итерации. Проверять разрешённого автора и существующие правила безопасности команд. При невозможности достоверно определить предыдущую ветку/PR остановить выполнение с безопасной диагностикой, без эвристического выбора чужого PR.

## 4. Синхронизация origin — обязательно перед каждым повторным взятием в работу
1. Прочитать сохранённую `work_branch`, проверить привязку к конкретному Issue/репозиторию.
2. Выполнить `git fetch origin` и проверить существование `origin/<work_branch>`; ошибку fetch считать блокирующей.
3. Зафиксировать фактический SHA удалённого HEAD. **Начальное состояние нового worktree должно точно соответствовать актуальному HEAD из origin**, включая ручные исправления, внесённые после прошлого исполнения.
4. Не использовать устаревший локальный HEAD, не сбрасывать и не удалять незакоммиченные данные прежнего worktree. При невозможности безопасно создать/синхронизировать worktree остановить запуск Codex и сообщить причину.
5. Запускать Codex CLI только после успешной подготовки; Codex не управляет git.
6. Перед push повторно сверить удалённый HEAD с зафиксированным перед исполнением; при расхождении блокировать публикацию, не делать force push, merge или rebase автоматически. Проверки не должны заменять обычные гарантии Git от non-fast-forward.

## 5. Публикация и reopen PR
После успешного Codex/commit/push получить сохранённый PR по устойчивому идентификатору, проверить принадлежность репозиторию и Issue, совпадение head/base и факт отсутствия merge. Если PR открыт — переиспользовать; если закрыт без merge — запросить reopen и перечитать состояние. Только после подтверждения успешного состояния публикации перевести задачу в `review`. Если PR merged, удалён, неоднозначен или GitHub запрещает reopen — не создавать новый PR, не подменять ветку, зафиксировать ошибку публикации и оставить возможность операторского исправления/повторной попытки без повторного Codex. Успешный push и неудачный reopen должны оставаться различимыми фактами.

## 6. Восстановление и идемпотентность
Использовать устойчивый ключ операции публикации, привязанный к iteration_id и прежнему pr_id. При timeout, неизвестном результате GitHub API, рестарте демона и повторном poll сначала сверять фактическое состояние GitHub, затем завершать локальную операцию; не запускать Codex повторно из-за сбоя публикации, не создавать дублирующую итерацию/PR/комментарий. Сохранять последовательные попытки, SHA до/после, pr_id, итог reopen и безопасную диагностику. Историю предыдущих итераций не перезаписывать. Не публиковать секреты или необработанный stderr в комментариях.

## 7. Ошибки
Отсутствие ветки, конфликт владения веткой, грязный worktree, ошибка fetch, изменение origin HEAD при работе Codex, merged PR, несовпадение head/base, невозможность reopen и сбой сети должны иметь различимые диагностические причины. До успешного reopen не устанавливать `review`. Не допускать автоматического создания нового PR при ошибке reopen.

## 8. Тесты и приёмка
Автоматические тесты должны покрыть: повторное подтверждение rejected и сохранение истории; отсутствие дублирующих итераций; fetch и старт с обновлённого origin HEAD; локальную ветку позади origin; грязный worktree; ошибку fetch; отсутствие удалённой ветки; чужую занятую ветку; изменение удалённого HEAD во время Codex; reopen закрытого PR; переиспользование открытого PR; merged PR; отказ reopen без создания нового PR; timeout после успешного reopen; восстановление после рестарта без повторного Codex; идемпотентные комментарии/публикацию; корректный перевод в review только после успеха. Интеграционный тест с Git remote и заглушками GitHub/Codex. Ручная приёмка на тестовом репозитории: первое выполнение → закрытие PR без merge → ручное изменение той же ветки на origin → изменение Issue и повторное подтверждение → повторный запуск из обновлённого HEAD → push → reopen прежнего PR → review. Зафиксировать вывод тестов и отчёт, подготовить PR в `STAGE_06_04_01`.

## 9. Ограничения реализации
Сохранять существующий CLI, статусы и правила подтверждения, не изменять поведение первого исполнения без необходимости. Следовать существующим интерфейсам GitHub API, хранилища и scheduler; минимальные изменения, совместимость миграций, безопасные логи. Не изменять GitHub Issues/PR вне проверяемого сценария.
