# Задание Codex-агенту — реализация этапа 6.4.3.5

**Репозиторий:** `heroicrealm/CodexAgent`  
**Рабочая ветка:** `STAGE_06_04_03`  
**Нормативный документ:** [ТЗ 6.4.3.5](stage-06-04-03-05-spec.md)  
**Основания:** [общее ТЗ 6.4.3](stage-06-04-03-spec.md), [приёмка 6.4.3.4](stage-06-04-03-04-acceptance.md).

## Цель

Довести готовую контейнерную Issue из `awaiting_children` до собственного канонического PR и `review`, с опциональным интеграционным запуском Codex. Реализовать также обычную ручную Issue (`issue_type: issue`, `run_codex: false`), которая публикует ветку, переходит в `review` без Codex и автоматически завершает цикл при доказанном merge созданного человеком PR.

**Выполнить изменения кода, миграций (только если необходимы), тестов и документации в указанной ветке. Не создавать PR и не сливать ветку без отдельного распоряжения.**

## 1. Подготовительный аудит

1. Подтянуть актуальную `STAGE_06_04_03` и проверить чистоту рабочего дерева. Убедиться, что в ней присутствует `docs/stages/stage-06-04-03-05-spec.md`.
2. Проследить существующие пути: state machine и dispatcher loop, `ready_for_integration` и snapshots/generation из 6.4.3.4, branch ownership/worktree, executor Codex, publication pipeline, канонический PR resolution, durable operations/outbox, PR monitor, `review_on_error`, detach и CLI.
3. Перед внесением изменений описать краткую карту затрагиваемых модулей. Переиспользовать существующие механизмы; не строить вторую архитектуру PR или веток.

## 2. Реализовать активацию готового контейнера

- Выбирать только `issue_type=container` в `awaiting_children` с подтверждённым `ready_for_integration`, актуальным generation и **нулём активных** блокировок (записи `active=0` не блокируют).
- Перед запуском повторно проверить текущее семантическое состояние непосредственных Sub-issues, их PR/merge в контейнерную ветку, ветку контейнера и соответствие закреплённому readiness snapshot. Не использовать только `updated_at` как guard.
- Проверить remote HEAD, branch claim и доступность origin. Перед Codex актуализировать worktree без потери неопубликованных результатов.
- Durable claim/operation: не допустить параллельного выполнения одного поколения и повторных запусков при очередном poll или рестарте.
- При устаревшем snapshot, неполном ответе GitHub, конфликте веток/PR — fail closed, диагностика, не запускать Codex и не создавать PR.

## 3. Контейнер `run_codex: true`

- После успешного guard перевести в `running`, подготовить worktree, выполнить **один** интеграционный запуск Codex.
- **Утверждённый вариант А prompt:** основное задание — текст **контейнерной** Issue без fenced `dispatcher` YAML. Отдельно приложить краткий проверенный перечень **непосредственных учитываемых детей**: номер/ID, заголовок, URL, канонический PR и подтверждённый merge/base. Полные тексты и комментарии детей **не** включать. В служебном контексте сообщить, что результаты дочерних PR уже в ветке и их задачи повторно выполнять нельзя.
- Не отдавать Codex управление Git, PR или ветками.
- Использовать существующие executor, сохранение результата, commit/push, ошибочные состояния и логирование. Даже если Codex не создал новых изменений, PR допустим при наличии diff **контейнерной ветки относительно её целевой base**.
- Перед переходом в `review` перепроверить значимый состав детей и evidence. При изменении состава во время исполнения **сохранить результат**, но не переводить контейнер в `review`; не запускать автоматический повторный цикл в этом подэтапе (6.4.3.6).

## 4. Контейнер `run_codex: false`

- Использовать те же readiness guards, не запускать Codex и не добавлять искусственных коммитов.
- При существующем diff создать/найти и закрепить единственный канонический контейнерный PR (head — контейнерная ветка; base — закреплённая ветка), подтвердить публикацию, затем перевести в `review`.
- При отсутствии diff оставить `awaiting_children`, зафиксировать `no_diff` и одно дедуплицированное диагностическое сообщение. Не устраивать бесконечные повторные попытки без изменения условий.

## 5. Обычная ручная Issue (`issue_type: issue`, `run_codex: false`)

- После отдельного подтверждения безопасно создать/закрепить и опубликовать ветку в origin без Codex, искусственного коммита и автоматического PR.
- После подтверждения публикации перевести сразу в `review` (не в `running`).
- В `poll` искать PR по `state=all`, включая созданные и слитые человеком между двумя poll и PR с удалённой после merge head-веткой.
- Проверить однозначность и canonical ownership (репозиторий, head, ожидаемая base, PR identity/history), сохранить привязку в существующей модели.
- Merged PR → автоматически `done`; закрыт без merge → `rejected`; открыт → оставить `review`. При неоднозначности — fail closed. Соблюдать принятое в 6.4.3.4 разрешение на ручную смену base **собственного** PR после подтверждённого merge, не ослабляя guard дочернего PR в ветку контейнера.

## 6. Общие гарантии

- Одна Issue — одна каноническая ветка и один PR. Повторные poll/restart не создают дубли веток, PR, комментариев, Codex runs.
- Использовать SQLite operations и существующий outbox; не держать writer lock на Git/GitHub I/O. Не объявлять `review` до подтверждённой публикации PR контейнера.
- Не делать auto-merge/force-push, не назначать детям codex-ready/approve, не управлять их жизненным циклом, не обходить внуков.
- Нельзя терять изменения при ошибке push, detach, network failure, restart.
- `show/queue`: показывать понятные `issue_type` и `execution_mode`, корректное состояние контейнера и PR.
- Сохранить совместимость обычных Codex Issue, PR monitoring, `review_on_error`, `detach` и работающей чистки worktree.
- Полный повторный цикл после rejected, расширенная переинтеграция и аварийная оркестрация относятся к 6.4.3.6; общий `blocked` — к 6.4.3.8. Не подменять их незаметными недоделанными реализациями.

## 7. Проверки

Добавить автоматические тесты, как минимум:
1. Готовый контейнер `run_codex=true`: ровно один запуск, правильный prompt, сохранение результата, PR и `review`.
2. `run_codex=false`: ноль запусков Codex, PR из готовой ветки, `review`.
3. Waiting/conflicting container, detached child с открытым PR, wrong base child PR → без запуска и PR; `active=0` не блокирует.
4. Семантическая повторная проверка snapshot/generation (несущественный `updated_at` не мешает; существенное изменение блокирует).
5. `no_diff` для контейнера; нулевой набор детей; diff от детей без новых правок Codex.
6. Origin HEAD/branch claim, сбой push/API/SQLite/outbox, double poll/restart/concurrency — без потери данных/дублей.
7. Изменение состава детей во время выполнения: результат сохраняется, ложного `review` нет.
8. Ручная Issue: публикация ветки, `review` без Codex/PR, open PR, closed unmerged, merged PR, PR слит между poll, удалённая head-ветка, неоднозначные PR.
9. Вложенный контейнер как непосредственный ребёнок.
10. Регрессия обычных Codex задач, детских PR и принятого правила смены PR base.

Запустить полный `bash scripts/test.sh` в рабочем окружении проекта, при необходимости установить dev-зависимости в venv, выполнить `git diff --check` и проверку компиляции. Исправить найденные регрессии, не подменять упавшие тесты пропуском.

## 9. Критерий завершения

Готовый контейнер надёжно получает собственный PR и `review` в обоих режимах, ручная Issue корректно проходит `review → done` при проверенном ручном merge (включая быстрое создание/слияние PR), не нарушены инварианты, тесты и регрессии проходят. Подробные правила — в нормативном ТЗ 6.4.3.5.
