# 6.4.1.7 — Detach при снятии codex-ready и emergency-stop

Статус: утверждено к реализации. База: STAGE_06_04_01. Рабочая ветка: STAGE_06_04_01_07.

## Цель
Безопасно прекратить управление конкретной GitHub Issue при снятии настроенной ready-метки (по умолчанию codex-ready); поддержать отдельную управляющую метку аварийной остановки (по умолчанию dispatcher:emergency-stop). Не останавливать остальные задачи и службу.

## Семантика
- Обычный Detach: снятие ready-метки для управляемой Issue, включая running. Немедленно зафиксировать durable intent в SQLite; запретить новые действия подготовки/публикации; если Codex уже запущен — дождаться естественного завершения без сигнала. После подтверждённого завершения перевести задачу в detached, очистить принадлежащие ей локальные артефакты и синхронизировать метки.
- Emergency: наличие emergency-stop имеет приоритет над ready и всеми обычными командами. Не допускать нового запуска, зафиксировать durable intent; адресно завершить только группу процессов данной попытки через существующий Lifecycle (SIGTERM, ограниченное ожидание, SIGKILL при необходимости). Не использовать глобальный stop --force. Не удалять worktree, пока невозможно подтвердить завершение всех использующих его процессов.
- После emergency оставить ТОЛЬКО emergency-stop среди управляемых данным проектом меток: удалить ready и остальные конфигурируемые метки диспетчера. Все сторонние пользовательские метки сохранить. Не удалять чужие метки лишь по префиксу dispatcher:. Метка emergency-stop сохраняется до ручного удаления и блокирует повторное подключение даже при добавлении ready.
- После обычного Detach удалить управляемые метки состояния; сторонние сохранить. Повторное добавление ready без emergency-stop — новый цикл с discovered, новая iteration_id, прежние attempts/history сохраняются. Не восстанавливать старое выполнение.
- Для done/cancelled не менять исторический результат обычным снятием ready. Emergency-stop не должна разрушать уже завершённые результаты; оставлять блокирующую метку и безопасно очищать управляемые метки. Существующие удалённые ветки, коммиты, PR не удалять.

## Согласованность и приоритет
1. SQLite — источник durable intent и прогресса остановки; переходы и публикация ограждены транзакционными проверками версии/iteration/attempt.
2. С момента обнаружения команды запрещены commit, push, PR, обычные result comments и новые операции публикации. Если операция уже началась до обнаружения команды, не утверждать, что её можно откатить; записать фактический результат. Проверять fencing перед каждым внешним необратимым шагом; повторно проверять актуальные метки при критических операциях. Учитывать неизбежное окно между удалённым изменением метки и обнаружением.
3. Polling emergency-stop для активных попыток — отдельная ограниченная по частоте проверка (настраиваемый интервал, по умолчанию 5 секунд); обычный poll продолжает работать. Никакая синхронизация меток не вправе стереть emergency-stop, даже при устаревшем снимке. Сохранить идемпотентность и защиту от конфликтующих записей.
4. Внедрить emergency-stop в конфигурацию меток (name/color/description), init/init --update и fingerprint. Не хардкодить имена меток и имена обслуживаемых репозиториев. Проверять доверенность команды по принятой в проекте модели GitHub-управляющих меток; не полагаться только на наличие метки, если действующий security-контракт требует подтверждения инициатора.
5. Данные SQLite: terminal state detached; durable reason (ready_removed/emergency_stop), requested_at, finalized_at, attempt/process/cleanup/comment status и ошибки. Миграции идемпотентные, совместимы со старой БД. Результат attempt отделён от состояния task: не маскировать реальный exit_code; для штатно закончившегося Codex при detach не создавать PR. Обеспечить restart recovery без повторного Codex.
6. Детализированный диагностический комментарий при emergency: причина, предыдущее состояние, этап остановки (preparation/codex/publication/idle), попытка, метод SIGTERM/SIGKILL/не требовался, результат подтверждения остановки, очистки, уже опубликованные SHA/ветка/PR, ошибки. Комментарий доставлять через durable outbox, с дедупликацией; сбой GitHub не должен отменять блокировку. Если невозможно подтвердить завершение процессов — оставить артефакты и статус незавершённой безопасной очистки, сообщить диагностически и повторять восстановление; не считать cleanup успешным.
7. Для detached разрешить безопасное удаление грязного worktree только при доказанном владении и отсутствии живых процессов; проверять symlink, границы workspace, git metadata, зарегистрированные артефакты. Не удалять чужие/неизвестные файлы и удалённые ветки. Ошибки очистки сохранять и повторять идемпотентно.
8. После detach освободить активную бронь ветки/попытки, но не ослаблять проверку принадлежности уже существующей удалённой ветки при новом цикле. Если имя ветки занято — применить существующую политику branch_ownership_conflict/review_on_error, не перезаписывать.
9. Предусмотреть гонки: снятие ready во время подготовки, во время Codex, перед commit/push/PR, после PR; установка emergency при наличии/отсутствии ready, одновременные poll и reconcile, повторная доставка команды, перезапуск посреди остановки и очистки, завершение дочернего процесса с живыми потомками.
10. Сохранить существующие сценарии rejected→pending, review_on_error, done/cancelled cleanup, stop/stop --force и многопроектную изоляцию.

## Критерии приёмки
- pending/discovered/revoked/review/rejected: снятие ready приводит к detached, без новых запусков/публикаций.
- running + снятие ready: Codex заканчивает естественно; PR/commit/push диспетчером не выполняются; безопасная очистка.
- running + emergency: только соответствующая группа процессов остановлена, другие продолжают работу; диагностический комментарий и сохранённая emergency-метка.
- После emergency пользовательские метки не затронуты, ready и управляемые проектом метки удалены; добавление ready при emergency не запускает задачу.
- Повторное подключение после обычного detach создаёт новую итерацию без потери истории; существующая ветка не перезаписывается.
- Crash/restart, сетевые ошибки и повторные poll не создают повторных запусков, PR, комментариев или опасной очистки.
- Автоматические unit/integration tests, включая реальные границы процессов с подменённым Codex/gh, и успешный scripts/test.sh; документация и пример конфигурации обновлены.

## Ограничение
Невозможно гарантировать остановку до публикации при ещё не обнаруженной удалённой команде; реализация должна минимизировать окно и фиксировать реальные факты, не обещать атомарности между GitHub и SQLite.

Уточнение контракта процессов, согласованное пользователем 2026-10-26: гарантия
остановки и подтверждение отсутствия живых процессов перед cleanup относятся к
исходной process group попытки, в границах существующего Lifecycle. Исполнители
должны сохранять принадлежность группе; самовольные setsid/setpgid и демонизация
выходят за эти гарантии. Cgroup-изоляция не является требованием этого этапа.


## Дополнение к приёмке — вариант Б: контроль отделившихся потомков (2026-10-26)

Предыдущее допущение о достаточности контроля только исходной process group ОТМЕНЕНО. Для аварийной остановки и последующей очистки worktree требуется доказуемо учитывать потомков Codex/подготовительных Git/gh-процессов, которые могли покинуть исходную группу через setsid/setpgid. Сам факт исчезновения исходного PGID НЕ является подтверждением безопасности удаления worktree.

Требования:
1. Исследовать подходящий для Ubuntu/WSL2 механизм надёжного удержания и наблюдения дерева процессов (предпочтительно cgroup v2 при подтверждённой доступности и делегировании; либо иной доказуемо эквивалентный механизм). Не считать разовый обход /proc, проверку cwd, process group или parent PID полноценным доказательством отсутствия отделившихся процессов из-за гонок, смены cwd и reparenting.
2. Запускать Codex и относящиеся к попытке внешние процессы внутри контролируемой границы с самого начала, до возможного fork/setsid. Хранить устойчивую привязку к attempt и обеспечивать restart recovery; предотвращать PID reuse и ложную идентификацию. При emergency останавливать все процессы этой границы с TERM/grace/KILL; при обычном Detach не отправлять сигналы, а ждать естественного завершения всей границы.
3. Cleanup разрешать только после доказуемого отсутствия живых процессов во всей границе, включая отделившихся потомков. При недоступности/непроверяемости контроля — fail closed: сохранить worktree, статус pending/unconfirmed, диагностировать причину и позволить безопасное повторение после устранения проблемы.
4. Если выбранная платформа не предоставляет надёжного механизма (например, cgroup v2 недоступен в конкретном WSL2 окружении), не объявлять гарантию выполненной и не использовать небезопасный fallback. Явно документировать требуемые права, обнаружение возможностей, настройку и ограничения; предложить реализуемые варианты окружения на согласование.
5. Дополнить автоматические integration tests реальными subprocess: escaped setsid/setpgid descendants, orphan/reparent, leader exit, обычный Detach, emergency TERM/KILL, crash/restart, параллельные задачи, PID reuse/races, отказ контроллера и запрет cleanup. Изменить tests/test_stage60417_blocker.py: сценарий должен подтверждать безопасность, а не документировать допускаемую утечку.
6. Обновить README, implementation report и инструкции ручной приёмки. Сохранить совместимость с существующими режимами stop/stop --force, миграциями, публикацией, другими задачами.

Критерий: если нельзя доказать завершение всей границы, worktree НЕ удаляется. Запрещено менять этот критерий без отдельного согласования.


## Актуальное решение — добровольное завершение, диагностический timeout (2026-10-26)

**Этот раздел заменяет противоречащие ему положения выше, включая вариант Б о принудительной остановке и обязательном cgroup backend.** Причина: переносимость в WSL2, Docker (Windows/Linux) и Ubuntu VPS. Управление задачей через метки не управляет сигналами процессов.

1. Снятие ready и метка emergency_stop немедленно (после обнаружения) фиксируют durable stop intent, блокируют новые запуски, подготовку, commit/push/PR и result publication. Если Codex уже работает, диспетчер **не посылает ему SIGTERM/SIGKILL**, а ждёт естественного завершения. Emergency имеет более высокий приоритет, сохраняет диагностический комментарий и метку; обычный Detach сохраняет свою семантику.
2. Тайм-аут Codex становится **диагностическим**: при первом превышении заданного лимита времени по конкретной attempt диспетчер формирует один комментарий в Issue («превышено время выполнения, Codex продолжает работать»). Комментарий через durable outbox с idempotency marker, защитой от lost response, рестартов и повторного poll; ошибки доставки повторяются. Превышение не прерывает Codex, не изменяет статус задачи на failed/review/review_on_error и не запускает новый attempt. При обычном завершении дальнейшее поведение определяется актуальным состоянием и stop intent.
3. Только явная административная CLI-команда **stop --force** вправе принудительно останавливать процессы; штатный stop сохраняет прежнюю семантику ожидания. Сигналы от GitHub label, timeout, detach, emergency_stop запрещены. Принудительная административная остановка не должна фиксироваться как естественный успех.
4. Обязательная cgroup v2/systemd граница и принудительное завершение всех escaped descendants исключаются из требований этого этапа. Удалить временный безусловный production admission/exec/publication gate descendant_boundary_unverified. Диспетчер должен работать без делегирования cgroup.
5. Контроль cleanup остаётся консервативным: сохранять проверки владения, зарегистрированных процессов, PID identity/PGID и отсутствие известных живых пользователей worktree; не объявлять такой контроль абсолютным доказательством отсутствия произвольно отделившихся setsid/setpgid потомков. Если состояние неоднозначно (включая crash/restart, потерю identity, признаки живых потомков), **не удалять worktree**, сохранять диагностику и возможность ручного вмешательства. Автоматическую очистку допускать только при достаточных доказательствах в пределах документированного контракта Lifecycle; явно описать остаточный риск escaped descendants и предложить optional stronger containment как отдельное развитие.
6. Сохранить existing stop requests/outbox, label reconciliation, generation fencing, branch ownership, migration compatibility, idempotence, rejected→pending, review_on_error, multi-project isolation.
7. Переписать tests: natural drain при Detach/emergency, timeout comment ровно один раз, повтор доставки после GitHub outage/restart, отсутствие сигналов, stop --force, cleanup refusal on uncertainty, отсутствие cgroup в runtime. Прежние kernel acceptance tests варианта Б удалить из обязательной матрицы или явно перенести в отдельный future feature, не выдавать skip за пройденную приёмку.
8. README/implementation/variant-b report обновить с явной ссылкой на изменение решения и новой матрицей ручной приёмки.

Приоритет: **безопасность данных и отсутствие ложных гарантий**, затем переносимость. Запрещено заменять невозможность доказать безопасность очистки безусловным force-remove.

## Повторное утверждение после завершённого Detach (#41/#42)

После natural drain, подтверждённого завершения stop request и cleanup новая
утверждённая iteration начинает работу от свежего `origin/<base_branch>` после
fetch. Она не наследует результаты отменённой попытки. Классификация основана на
неактивном durable stop request предыдущего attempt; rejected PR сохраняет
существующий repeat_branch и продолжает историю актуальной remote ветки.

Локальная ветка отменённой попытки переименовывается без force в
`archive/detach/<attempt_id>`. Миграция 611 добавляет `detach_refs`: cleanup
записывает точный SHA после проверки ownership и до удаления worktree. Журнал
сохраняется вместе с архивом; повторный prepare после rename проверяет тот же
SHA и не создаёт дубликат. Отсутствующий ref не требует искусственного архива.
Для cleanup, завершённого старой версией, допустим bootstrap только при совпадении
clone origin, task/project/branch/iteration/attempt, подтверждённом cleanup,
сохранённом reflog создания от initial_sha и непрерывной истории commit entries.
Неоднозначность, отсутствующий reflog или изменённый ref означают отказ.

До архивирования проверяются актуальная base, отсутствие активных worktrees,
незавершённых зарегистрированных процессов, чужих branch claims и опубликованных
результатов. Любая существующая remote рабочая ветка означает
`detach_remote_branch_conflict`; dispatcher не удаляет её и не выполняет force push.
Прочие отказы: `detach_identity_conflict`, `detach_cleanup_incomplete`,
`detach_active_worktree`, `detach_branch_ownership_conflict`,
`detach_archive_conflict`, `detach_published_result_conflict`.
Git-диагностика содержит операцию, return code и классификацию stderr;
произвольные stderr, argv, URL и credentials в журнал не записываются.
