# ТЗ 6.4.1.5 — Исправление повторного утверждения rejected → pending

Статус: утверждено к реализации. Базовая ветка: STAGE_06_04_01. Рабочая ветка: STAGE_06_04_01_05.

## 1. Проблема и воспроизведение
После закрытия PR без слияния задача переходит review → rejected. Если сразу добавить к Issue с метками codex-ready и dispatcher:rejected метку dispatcher:approve, через некоторое время approve исчезает, rejected остаётся. При повторном добавлении approve задача иногда переходит в pending. Если дождаться комментария об отклонении, первый approve переводит в pending. Через CLI повторное утверждение работает корректно.

## 2. Цель
Первое корректное событие GitHub labeled(dispatcher:approve) после зафиксированного rejected переводит задачу в pending без необходимости ждать публикации комментария об отклонении. Комментарий — асинхронный побочный эффект, а не барьер разрешения следующего перехода.

## 3. Требования
1. Исследовать реальную последовательность review → rejected, синхронизации меток, GitHub labeled event, command guard, CAS, комментария; определить и документировать корневую причину, не предполагать её заранее.
2. Исправить обработку GitHub approve при rejected; сохранить безопасную проверку actor allowlist, event proof, версий, server timestamps, GitHub identity, availability и idempotency.
3. Не принимать событие approve, созданное до фактического отклонения, и не превращать старые/карантинные события в новое согласие.
4. После успешного approve атомарно создать ровно одну новую итерацию, записать историю/решение, перейти в pending, очистить управляющие метки approve и rejected, сохранить codex-ready. Повторный poll не создаёт дубликат.
5. Публикация комментария об отклонении должна быть независимой и идемпотентной; задержка публикации не должна блокировать approve.
6. Если команда реально не проходит проверку, сохранить политику A: не менять состояние, согласовать метки с SQLite, зафиксировать диагностическую причину и безопасный способ повторной подачи. Не ослаблять ограничения и не скрывать отказ.
7. Сохранить CLI approve/reject и переходы discovered → pending, review → rejected, rejected → cancelled; не разрешать повторный запуск из running/done/cancelled.
8. Не менять формат БД или публичный CLI без доказанной необходимости. Если миграция нужна — отдельное обоснование и тест обратной совместимости.
9. Не затрагивать другие этапы и не создавать PR автоматически.

## 4. Анализ кода
Начать с src/dispatcher/queue.py (_reason, commands), src/dispatcher/github/sync.py, src/dispatcher/storage/__init__.py, src/dispatcher/storage/transitions.py, мониторинга PR, доставки комментариев и GitHub adapter. Особое внимание: timestamp rejected transition evidence.observed_at, command guard.server_at, событие labeled.created_at, момент reconcile и публикации комментария. В storage/transitions.py переход rejected → pending уже разрешён; нельзя ограничиться добавлением ребра.

## 5. Обязательные тесты
- approve сразу после rejected, ДО комментария → pending с первого раза;
- approve после комментария → pending с первого раза;
- повторные poll и повторная доставка комментария → одна итерация, одно решение, без повторного исполнения;
- устаревший approve до rejected, неверный actor, неверная версия, отсутствие event proof → отказ без перехода;
- гонка между отклонением, reconcile и labeled event; отсутствие ложного карантина корректного события;
- CLI approve из rejected без регрессии;
- сценарий полного цикла review → rejected → pending → running → review → done (с подходящими stub/fixture);
- состояния running, done, cancelled не допускают повторного approve.

## 6. Приёмка
Все автоматические тесты проходят; в ручном окружении approve, поставленный непосредственно после появления rejected (не дожидаясь комментария), приводит к pending при первом корректном событии. Метки и SQLite согласованы, повторная обработка идемпотентна, поздний комментарий не откатывает состояние. Представить доказательство причины дефекта и краткий отчёт о тестах.
