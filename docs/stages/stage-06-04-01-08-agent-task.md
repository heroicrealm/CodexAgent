# Задание Codex-агенту — 6.4.1.8: аудит tracking_generation и защита от устаревших событий

**Репозиторий:** heroicrealm/CodexAgent  
**Базовая ветка:** `STAGE_06_04_01`  
**Рабочая ветка:** `TAGE_06_04_01_08`  
**Тип:** аудит, регрессионные тесты, исправление только подтверждённых дефектов.

## Контекст
Ручные проверки Detach → Reattach → discovered → новое approve, SQLite (iterations/attempts/stop_requests), идемпотентности poll и перезапуска диспетчера успешно пройдены. Осталось проверить изоляцию событий предыдущего поколения. См. `docs/stages/stage-06-04-01-spec.md`, §5.

## 1. Аудит
Изучить `tasks.version`, `approved_version`, `task_iterations`, `current_iteration_id`, `attempts`, `stop_requests`, `observation_token`, обработку `dispatcher:approve`, снятия/возврата `codex-ready`, outbox, идемпотентность и восстановление после рестарта. Установить, каким механизмом обеспечена логическая `tracking_generation`. Не вводить отдельное поле без необходимости.

## 2. Автотест: запоздавший approve
1. Обнаружить Issue, утвердить, создать iteration A, начать выполнение.
2. Выполнить Detach, дождаться завершения и безопасной очистки.
3. Вернуть `codex-ready`; проверить `discovered` без подтверждения.
4. Повторно доставить событие approve поколения A (включая после рестарта).

**Ожидается:** задача остаётся `discovered`, `approved_version IS NULL`, новая iteration/attempt не создаётся, Codex не запускается. Старое событие не считается новым подтверждением.

## 3. Автотест: запоздавшее снятие codex-ready
1. В поколении A снять `codex-ready`, завершить Detach.
2. Вернуть метку, выполнить Reattach, начать поколение B.
3. Доставить устаревшее событие удаления метки из поколения A.

**Ожидается:** B остаётся активным; повторный `detached`, новый `stop_request` и cleanup B не возникают; новое подтверждение возможно.

## 4. Дополнительная регрессия
- Повторная доставка одного события; обратный порядок событий.
- Два последовательных Detach/Reattach.
- Рестарт между получением и обработкой события.
- Старые операции outbox не воздействуют на новую генерацию.
- `done`, `cancelled`, `review_on_error` не оживают от `codex-ready`.
- Два проекта с одинаковым номером Issue изолированы.
- Если адаптер работает со снимками GitHub, а не с webhook-событиями, воспроизводить старые снимки с реалистичными timestamps/токенами через существующий API; не обходить реальные проверки актуальности.

## 5. Исправления
При обнаружении дефекта: сначала воспроизводящий падающий тест, затем минимальное исправление и повторный запуск тестов. Не менять без необходимости модель состояний, канонические branch/PR, cleanup, stop/stop --force и принятый Detach. Не делать рефакторинг ради рефакторинга.

## 6. Документация
Создать `docs/stages/stage-06-04-01-08-audit.md`: фактическая модель поколений, соответствие §5, тесты, дефекты/исправления, ограничения и результаты проверок. При необходимости актуализировать ТЗ и план, явно указав причины изменений.

## 7. Критерии готовности
- Доказана или исправлена изоляция поколений.
- Добавлены автоматические тесты запоздавших событий и идемпотентности.
- Проверены рестарт и терминальные состояния.
- Регрессионные тесты проходят.
- Документация соответствует коду.

## 8. Отчёт
Предоставить архитектурное заключение, дефекты, изменённые файлы, новые тесты, команды/результаты запуска и остаточные риски.

**Не создавать PR, не выполнять merge.** Остановиться после коммита в рабочую ветку и передать результаты на проверку.
