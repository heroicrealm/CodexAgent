## 3. Автоматические проверки (по отчёту агента)

Отчёт реализации содержит: `pytest -q` — **231 passed**, `compileall` — exit 0, `git diff --check` — exit 0. Эти результаты предоставлены агентом и не воспроизводились независимо при составлении отчёта. Результаты GitHub CI для создаваемого PR необходимо проверить отдельно.

## 4. Подтверждённые свойства

- Fail closed при отсутствующей, повреждённой, неподходящей по структуре или чужой базе.
- Обычный запуск не создаёт новую SQLite молча.
- Явная регистрация совместимой V2.3 сохраняет существующие рабочие данные.
- Backup не перезаписывает существующий destination.
- Restore проверяет источник и идентичность; прежняя SQLite сохраняется.
- После restore блокировка `recovery_required` предотвращает новое исполнение до внешней восстановительной сверки.

## 5. Ограничения и последующие работы

1. **Restore при повреждённой/отсутствующей текущей SQLite** в V2.4.1 намеренно запрещён: невозможна надёжная проверка состояния связанных исполнителей. Нужна отдельная проработка безопасного аварийного восстановления; небезопасный `force` не вводить.
2. **Recovery admission** после restore не реализован в V2.4.1. Барьер нельзя снять текущей штатной командой; сверка с GitHub, worktree, PR и локальными попытками относится к V2.4.2.
3. `db check` проверяет локальный снимок базы и не подтверждает согласованность с GitHub; конкурентные изменения могут потребовать проверки после остановки.
4. Реальный сбой питания/диска и поведение посторонних процессов не проверялись ручными тестами; подробности — в отчёте реализации.

## 6. Заключение и следующий шаг

**V2.4.1 принята по проведённым функциональным ручным тестам**, с явно перечисленными ограничениями. Изменения направляются в PR `V2_4_1_SQLITE_GUARD_RECOVERY` → `CODEXAGENT_V2`. До слияния необходимы зелёный GitHub CI, просмотр diff и окончательное решение пользователя. Автоматическое слияние запрещено.
