## 2. Цель

Разработать безопасную, воспроизводимую и наглядную диагностику расхождения между наблюдениями Git и `Git.worktrees`, установить доказанную причину, если возможно, и устранить только подтверждённый дефект. Не прибегать к обходу проверки принадлежности и не удалять неизвестные рабочие данные.

## 3. Задача A: диагностический инструмент

Предпочтительно реализовать отдельный read-only CLI-инструмент `python -m dispatcher.tools.worktree_diagnostics --config config/config.yaml --project PROJECT_ID` (или эквивалентную утилиту в `tools/` с тестами), который:

1. Находит checkout проекта только из конфигурации, без clone/fetch/prune/repair/checkout mutation; явно запрещает symlink и неожиданные пути.
2. В **одном** процессе выполняет последовательные вызовы `git worktree list --porcelain` и `--porcelain -z` с одинаковыми args и окружением, сравнивает непосредственный `subprocess.run`, `Git.command` и `Git.worktrees()`; сообщает число записей по каждому источнику и различие наборов нормализованных абсолютных путей.
3. Использует метки UTC/монотонного времени, returncode, размер вывода, SHA-256 исходных bytes stdout/stderr и число NUL-записей. По умолчанию не записывает сырые stdout/stderr в журнал: там могут встречаться приватные пути/сообщения.
4. Снимает read-only метаданные регистрации Git `.git/worktrees` **до и после** вызовов: имена служебных подкаталогов, типы файлов, стабильные fingerprint/hash метаданных, ссылки gitdir/commondir/HEAD в редактированном/санитизированном виде. Не читать произвольные пользовательские файлы worktree и не публиковать секреты.
5. Сравнивает абсолютный путь `/usr/bin/git` и `shutil.which('git')`, `git --version`, `cwd`, `-C` vs `cwd=`, наличие значимых переменных окружения по **именам** (значения не логировать), fingerprint конфигурации Git без раскрытия credential/remote URL.
6. Позволяет несколько повторений с заданным количеством, печатает итоги одним отчётом; по умолчанию **никаких изменений состояния**.
7. Должен быть пригоден для точного воспроизведения на WSL2/Python 3.14 и доступен пользователю с конкретной командой.

Не запускать инструмент автоматически в циклах `run`, `poll`, `recover`; диагностический режим только по явному вызову. Контролировать влияние вызываемых Git-команд: `worktree list` обычно read-only, но проверь потенциальные служебные side effects и явно документируй ограничения. Если невозможно строго гарантировать отсутствие изменений — укажи это в отчёте и не предлагай запуск на реальных данных до одобрения.

## 4. Задача B: выяснение причины и корректировка

1. Воспроизвести на временных локальных Git-репозиториях с двумя и тремя linked worktrees; различать `--porcelain` / `-z`, строки/bytes, окружение Python, Git metadata, возможные гонки.
2. Проверить наличие непреднамеренной мутации/очистки регистрации другим процессом, влияние `git worktree list` на prunable entries, Git config (`worktree.guessRemote`, `gc.worktreePruneExpire` и сопутствующие свойства только если уместны).
3. Изучить фактические implementation contracts `Git.run()`, `Git.worktrees()`, `Recovery.local()`, `Git.recovery_cleanup_plan()` и `Git.recovery_remove()`; не дублировать прошлые несостоятельные предположения.
4. Если найден доказанный дефект — минимальная правка с регрессионным тестом, включая fail-closed для неполного списка, чужих путей/веток, locked/prunable/dirty, symlink, изменения HEAD, неконсистентной SQLite. Исключить ложный успешный cleanup.
5. Если первопричина снова не воспроизведена — **не менять safety-логику наугад**; предоставить read-only diagnostic и план сбора данных на пользовательской тестовой установке, с критериями различения гипотез.

## 6. Запреты

## 7. Критерии готовности

- Имеется поддерживаемый, задокументированный диагностический способ сравнить **в одном запуске** сырой вывод Git, Git-адаптер и регистрационные метаданные.
- Утилита безопасна для тестового применения, не запускает Codex и не меняет удалённые репозитории.
- При наличии доказанного дефекта исправление минимально и покрыто тестами; иначе корневая причина явно отмечена как открытая без притворного PASS.
- `Git.recovery_cleanup_plan` по-прежнему отказывает при недоказанной принадлежности.
- Все автоматические тесты проходят. Пользовательская приёмка worktree остаётся открытой до повторного испытания.
