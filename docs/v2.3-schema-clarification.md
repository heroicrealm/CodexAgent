# V2.3 — уточнение структуры групп и корректировок

**Статус:** уточнение, согласованное пользователем 2026-11-07; применяется к реализации V2.3 поверх V2.2.  
**Нормативные документы:** `docs/specification_v2.md`, `docs/v2.2-architecture-sqlite.md`.

## Решение

Группа и непосредственная связь корректировки хранятся в **той же таблице `issues`**, без девятой таблицы. Одна Issue входит ровно в одну группу исполнения (после регистрации управляемой задачи), а корректирующая Issue ссылается не более чем на одну предыдущую Issue. Несколько Issue могут иметь одно и то же `correction_of_issue_id` — ветвление допускается. Структура ссылок не задаёт параллельный запуск: в группе одновременно не более одной активной Issue.

## Минимальное изменение DDL `issues`

Вставить в `CREATE TABLE issues` после `project_id`:

```sql
    execution_group_id INTEGER REFERENCES issues(issue_id),
    correction_of_issue_id INTEGER REFERENCES issues(issue_id),
```

Добавить в список `CHECK` таблицы:

```sql
    CHECK (correction_of_issue_id IS NULL OR correction_of_issue_id <> issue_id),
    CHECK (is_virtual = 1 OR execution_group_id IS NOT NULL)
```

Индекс для быстрого поиска непосредственных корректировок:

```sql
CREATE INDEX idx_issues_correction_of ON issues(correction_of_issue_id);
```

Итого: **8 таблиц, 11 индексов**. Первая чистая V2 SQLite создаётся сразу с этими столбцами и `schema_migrations.version=1`; новая запись истории миграции не нужна. Отказ от миграции V1 сохраняется. Упоминания числа индексов в задании и тестах соответственно обновить.

## Идентификатор группы и правила операций

**Утверждено пользователем:** идентификатор группы — глобальный GitHub ID её исходной Issue (корня истории корректировок). У исходной Issue `execution_group_id = issue_id` и `correction_of_issue_id IS NULL`; у корректирующей Issue `execution_group_id` наследуется из непосредственного `correction_of_issue_id`, а сама ссылка указывает именно выбранную пользователем Issue, необязательно последнюю. Таким образом хранится точная история происхождения, включая ветви.

Виртуальный родитель может не иметь `execution_group_id` до материализации; при появлении `codex-ready` ему назначается собственная группа либо корректирующая группа согласно утверждённым параметрам. Это не меняет `issue_id` и существующие связи Sub-issues. `issue_relations` остаётся независимой от `correction_of_issue_id`.

Приложение обязано проверять внутри транзакции:
- источник `correction_of_issue_id` существует, является реальной Issue в том же репозитории и принадлежит незавершённой группе, разрешённой для корректировки;
- `execution_group_id` соответствует группе непосредственного источника, а корень принадлежит тому же репозиторию;
- ссылка на корректировку не может образовать цикл;
- внутри группы не более одной активной Issue;
- базовая и рабочая ветки определяются группой, а не произвольной предыдущей Issue;
- `correction_of_issue_id` **не уникален**: несколько дочерних исправлений одного источника допустимы, если не нарушают правило одной активной Issue.

Отдельную таблицу `execution_groups` не вводить. Корректировки к исходной Issue после завершения группы запрещены согласно V2.1.

## Граница согласования

Поля, кардинальность связей и правило `execution_group_id = GitHub issue_id` исходной Issue **утверждены пользователем**. Это нормативное правило для V2.3. При реализации проверить совместимость с поведением групп V2.1. Если выявится противоречие, вынести его на отдельное решение; не заменять незаметно схему.


## Комментарии INPUT/OUTPUT — уточнение при приёмке V2.3.A

**Утверждено пользователем:** идентификаторы комментариев INPUT и OUTPUT должны сохраняться в SQLite. INPUT извлекается и фиксируется **при approve**, OUTPUT фиксируется **после подтверждённой публикации комментария**. Не выполнять постоянную проверку существования, редактирования или удаления опубликованного OUTPUT.

В `issues` добавить четыре поля:

```sql
    input_comment_id INTEGER,
    approved_input TEXT,
    output_comment_id INTEGER,
    output_body TEXT,
```

- `input_comment_id` — GitHub comment ID утверждённого INPUT (NULL, когда комментарий отсутствует).
- `approved_input` — неизменяемый текст INPUT, использованный при утверждении, включая исходный YAML; `parameters_yaml` продолжает хранить извлечённый YAML. При отсутствии INPUT оба значения NULL.
- `output_comment_id` — GitHub comment ID опубликованного OUTPUT, фиксируется только после подтверждения GitHub.
- `output_body` — последний подтверждённый опубликованный текст OUTPUT. Если OUTPUT обновляется штатно, после успешного обновления сохранять его ID и новое содержимое; при ошибке публикации не считать содержание подтверждённым.

Первичное создание/обновление OUTPUT не должно зависеть от повторного чтения комментария при каждом poll. При аварии между подтверждением GitHub и фиксацией идентификатора возможна повторная публикация, риск дубля ранее принят в V2.2. При `approve` сохранять ID и текст INPUT атомарно с утверждённой постановкой; при ошибке чтения/парсинга не принимать неполный снимок. Снимок INPUT не изменять вслед за редактированием комментария пользователем.

Эти поля входят в первоначальную **V2 schema version 1**, так как V2.3 ещё не принят и не требуется мигрировать тестовые SQLite из промежуточной реализации A. Число таблиц и явно заданных индексов остаётся прежним: 8 и 11.
