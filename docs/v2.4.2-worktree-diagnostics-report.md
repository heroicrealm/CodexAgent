# V2.4.2 — диагностика обнаружения worktree

Ветка: `V2_4_2_RECOVERY_RECONCILIATION`. Пользовательская приёмка #42 остаётся **открытой**. Причина расхождения в активной установке **не установлена**: её каталоги, SQLite, refs и GitHub не читались и не изменялись. PR и merge не выполнялись.

## Реализация

Добавлен явный CLI `dispatcher.tools.worktree_diagnostics`. Он читает checkout только из конфигурации, не создаёт каталогов, не открывает SQLite, не вызывает dispatcher run/poll/recover или Codex. Принимается существующий основной checkout с обычным `.git`; linked checkout, отдельный common directory, symlink в компонентах checkout/регистраций и неожиданные регистрационные объекты отклоняются. Наличие repository/config redirect переменных и `GIT_TRACE*` приводит к отказу до запуска Git: последние способны писать trace-файлы.

В одном процессе последовательно сравниваются `shutil.which('git')` и `/usr/bin/git`, `-C` и `cwd=`, porcelain с LF и NUL, непосредственный subprocess, исходные `Git.command`, `Git.run(check=False)` и `Git.worktrees`. Окружение между источниками не меняется. Вызовы адаптера инструментируются только на границе subprocess: исходные bytes сохраняются для хеширования, затем выполняется декодирование с правилами text mode (локальная кодировка/UTF-8 mode и universal newlines). Дополнительно выполняются исходные, неинструментированные text-mode вызовы `Git.command` и `Git.worktrees`: `native_commands`, `native_parsed`, `native_matches_instrumented`. Их decoded_* hashes относятся к UTF-8 представлению уже декодированного текста и намеренно не названы raw hashes. Это позволяет заметить влияние самого инструментирования. Это диагностическое инструментирование, а не изменение production-адаптера; ошибки декодирования остаются ограничением text mode. LF-сканер независимо снимает C quoting, NUL-сканер сохраняет пробелы и специальные символы. Нормализация путей лексическая абсолютная, без перехода по ссылкам.

Каждый вызов имеет UTC, начало/конец monotonic_ns, returncode, длину и SHA-256 stdout/stderr, количество NUL-полей и двойных NUL-разделителей записей, формат, источник и идентификатор cwd. Для перечислений есть count и набор path IDs. В каждом повторе — снимки регистраций до/после, результат строгого parser, `parser_matches_raw`, различия наборов относительно первого непосредственного вызова и `config_changed`. Конфигурация Git с origins хешируется до/после; её значения в JSON не попадают. `--version` выводится отдельно.

Снимки содержат санитизированные имена регистраций/файлов, тип, размер, mode, inode, mtime_ns, ctime_ns; для каталогов также mode и признаки readable/searchable через os.access. Содержимое читается только у небольших известных файлов `gitdir`, `commondir`, `HEAD`, `locked`, `prunable`, сохраняются лишь хеши. Index и пользовательские файлы утилита не читает. Снимки не атомарны; изменение внутри одного снимка или изменение с последующим возвратом не всегда обнаруживается. Межпроцессной блокировки нет. Диагностика не является доказательством ownership и не используется для cleanup.

## Проверенные гипотезы и контракты

- Временные репозитории с двумя и тремя **linked** worktrees (всего 3 и 4 записи), включая пробелы, TAB и кириллицу: в двух повторах источники совпадают. Общая гипотеза «Python или `-z` всегда теряет записи» опровергнута для этой среды. Это не опровержение ошибки WSL/filesystem или гонки в активной установке.
- При отсутствующем каталоге linked worktree Git сохраняет prunable-регистрацию; два прохода диагностики не удаляют её. Проверены bytes файлов и mtime всего disposable дерева до/после.
- **Подтверждён механизм тихого пропуска:** в disposable репозитории служебный `gitdir` сделан пустым. `.git/worktrees/<id>` существует, но непосредственный Git и adapter одинаково показывают только основной checkout, parser корректно возвращает одну запись. Это воспроизводимый контрольный пример, **не доказанная причина #42** (в задании указано, что его gitdir был корректен).
- В Git 2.53.0 `get_worktrees_internal()` при неудачном `opendir` не добавляет linked entries, а `get_linked_worktree()` пропускает регистрацию при ошибке/пустом чтении gitdir. Наличие каталога само по себе недостаточно. Причины доступа, видимость файловой системы и конкурентные изменения остаются гипотезами. Источник: [worktree.c v2.53.0](https://github.com/git/git/blob/v2.53.0/worktree.c), функции `get_linked_worktree`, `get_worktrees_internal`.
- `worktree list` вызывает перечисление и вычисляет prunable reason, не вызывает prune/repair/maintenance. `worktree.guessRemote` относится к выбору ветки при add, а параметры expiry не дают list полномочий удалять регистрации. Источник: [builtin/worktree.c v2.53.0](https://github.com/git/git/blob/v2.53.0/builtin/worktree.c), `list`, `show_worktree_porcelain`, отдельно `prune`. Специального config fallback не добавлено.
- Искусственное усечение NUL transport обнаруживается строгим parser. Искусственное исключение целой записи оставляет валидный неполный список: parser совпадает с raw, но отчёт показывает различия источников. Это важное различие между ошибкой разбора и потерей данных до parser.
- Имитация внешнего касания HEAD выявляется через `metadata_changed`. Реального постороннего процесса, удаляющего регистрацию #42, не обнаруживали и не исключали: активная установка не обследовалась.
- `Git.command` использует text=True; `Git.run(check=True)` вызывает strip, но `worktrees()` использует check=False, сохраняя NUL и пробелы. `worktrees()` отвергает усечённые/неоднозначные записи; не может определить отсутствие целой валидной записи.
- `Recovery.local()` проверяет configured checkout, читает remote через ls-remote и получает список через `worktrees`; диагностическая утилита его **не вызывает**, поскольку это уже сетевое обследование. `recovery_cleanup_plan()` требует согласованных execution/path/branch/HEAD/remote, а при существующем незарегистрированном каталоге отказывает. `recovery_remove()` повторно проверяет identity/HEAD/locked/prunable/symlink и перед удалением ref проверяет его значение. Эти контракты не изменены; существующие отрицательные тесты recovery продолжают выполняться, в том числе неполный список, чужой путь/ветка, изменение HEAD, locked/prunable, symlink и несогласованное состояние. Dirty-owned cleanup — существующий явно административный сценарий, его поведение не менялось.

## Ограничения read-only и приватность

Утилита не содержит команд изменения Git, сети, prune (даже dry-run), repair или удаления. Для штатного Git 2.53.0 проверенные команды не меняют содержимое регистрации, refs, index или пользовательских файлов. При этом **строгая гарантия отсутствия любых изменений невозможна**: чтение может менять atime, Python может создавать `__pycache__`, сторонний executable Git или внешняя trace/config-инфраструктура могут иметь собственные эффекты; конкурентная замена пути после проверки symlink остаётся TOCTOU. Поэтому запуск на реальных данных до отдельного одобрения не предлагается. `PYTHONDONTWRITEBYTECODE=1` исключает запись Python bytecode. Окружение с `GIT_TRACE*` отклоняется. Это не sandbox против недоверенного executable или конкурентного злоумышленника.

JSON не содержит raw stdout/stderr, remote URL, credential/config values, имён веток, содержимого HEAD или абсолютных repository/worktree путей. Пути и имена представлены стабильными SHA-256 идентификаторами: они позволяют сопоставление между вызовами, но не обеспечивают криптографическую анонимность предсказуемых строк. Открыто выводятся **абсолютный путь модуля адаптера**, пути executable Git, версии Python/Git, тип ОС, имена значимых env variables, timestamps и размеры/fingerprints. Перед передачей отчёта отредактировать путь адаптера (домашний каталог), нестандартные пути Git и при необходимости временные метки. Значения переменных не выводятся. Сообщения исключений подавлены; ошибка CLI даёт error_type и exit 2 без потенциально приватного текста. Exit 0 означает завершение сбора, а не успешную приёмку/доказанную принадлежность.

## Минимальный следующий ручной шаг #42

Только **после одобрения** запуска диагностики на тестовой установке, в том же WSL-сеансе и окружении, где наблюдалась проблема, с установленной этой версией пакета:

```bash
PYTHONDONTWRITEBYTECODE=1 python -m dispatcher.tools.worktree_diagnostics \
  --config config/config.yaml --project PROJECT_ID --repeat 5
```

`PROJECT_ID` заменить на id CodexAgentPlayground из конфигурации. На системах, где интерпретатор называется python3, использовать python3 из нужного venv. В текущей среде проверки использован Python 3.14 и Git 2.53.0. Не делать pip install, recover/retry/restore или cleanup в рамках этой ручной проверки. JSON выводится одним отчётом в stdout; сохранение его в согласованное место — отдельная явная запись пользователя. Сначала проверить `adapter_file`, executable/version, environment_names и checkout ID, чтобы исключить запуск другой установки.

Ожидается count=2 у каждого перечисления, parsed.count=2, parser_matches_raw=true, differences=[], metadata_changed=false, config_changed=false. Иначе:

1. Все raw дают 1 и parser=1: причина до parser. Сравнить наличие и размеры/hash файлов регистрации в before/after; отдельно проверить права доступа и filesystem visibility в этом же процессе. Не принимать наличие каталога за доказательство читаемости gitdir.
2. Raw NUL даёт 2, parsed даёт 1/ошибку: изучать text decoding/parser; сравнивать хеши и байтовые длины соседних вызовов. Секретный raw автоматически не собирать.
3. Отличается только executable или `-C`/cwd: исследовать разрешение binary, discovery/config и окружение. Fingerprint config показывает изменение без публикации URL.
4. metadata_changed/config_changed или число меняется во времени: искать параллельный dispatcher/maintenance/ручной процесс, фиксировать временной интервал. Снимки сами не устанавливают автора изменений; следующий сбор OS-level событий согласовать отдельно.
5. Все источники показывают 2: проблема в данном запуске не проявилась, #42 всё равно не считать принятой. Не запускать бесконечный автоматический опрос, не менять safety-логику.
