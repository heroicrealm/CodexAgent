# ТЗ V2.4.3 — CLI Monitoring & Project Management

**Статус:** УТВЕРЖДЕНО заказчиком, 2026-11-14  
**Репозиторий:** heroicrealm/CodexAgent  
**Базовая ветка:** CODEXAGENT_V2  
**Предшествующий этап:** V2.4.2 Recovery Reconciliation  
**Тип:** рефакторинг CLI, мониторинг, конфигурация, управление проектами

## 1. Цель и границы

Создать удобный CLI для мониторинга и администрирования Codex Task Dispatcher V2: человекочитаемые Rich-экраны `status`, `queue`, `show`; необязательный `--config`; пользовательская конфигурация и `root_path`; операции `project list/show/add/enable/disable/remove`, включая безопасное полное локальное удаление `--purge`.

Не менять модель состояний Issue, принцип единственного активного автоматического исполнителя, штатные алгоритмы poll, Scheduler, Executor, Publisher, публикации веток/PR, меток GitHub и защиту V2.4.1–V2.4.2. Мониторинг не выполняет запросы к GitHub, Git, не запускает poll и не изменяет данные. Исключение: команда `project add` делает ограниченные *читающие* проверки репозитория и разрешений через GitHub API и Git; другие административные операции `project` не изменяют GitHub.

Система пока не в эксплуатации: миграция прежних конфигураций, поддержка исторических переименований project.id и миграция V1 не требуются. Совместный многопользовательский экземпляр не входит в работу. Автозапуск через systemd, перенос WSL2 → Linux, горячая перезагрузка конфигурации — отдельный следующий этап.

## 2. Общие контракты вывода

Использовать установленную зависимость Rich (как в V2.4.2 recovery). Единые рамки и секции, цветовая индикация, компактные таблицы, выравнивание чисел вправо. Ориентир — терминал 80 символов; при большей ширине давать больше места Title и Project. При малой ширине обрезать прежде всего длинные строки (с многоточием), не ломать номера, состояния и числа переносом. Корректно работать при NO_COLOR и перенаправлении stdout.

`status --json`, `queue --json`, `show ... --json`: один JSON-документ с устойчивыми машинными ключами, без Rich/ANSI и без потери полных строк. Переход default status/queue с построчного JSON на Rich — намеренное изменение CLI; не требуется побайтовая совместимость старого JSONL. В JSON указывать полные значения исходных полей, исходные timestamps, идентификаторы. Ошибки команд возвращать с ненулевым exit code и понятной диагностикой.

## 3. Экран status

Команды:

```sh
codex-dispatcher status
codex-dispatcher status --json
```

Верхний блок:
- CODEX DISPATCHER · STATUS; состояние daemon RUNNING / STOPPED / UNKNOWN;
- Database: OK либо диагностическая ошибка; Recovery: READY / BLOCKED;
- Last poll и Next poll (при неизвестных данных N/A);
- Executing: project.id и #issue, elapsed HH:MM:SS от момента reservation, включая preparing; если исполнитель свободен — IDLE.

`preparing` и `running` принадлежат единственному автоматическому слоту; `manual-running` его не занимает. Нельзя считать строку SQLite с running доказательством живого процесса: проверять доступную локальную информацию о daemon, при неоднозначности показывать UNKNOWN / диагностический признак, а не ложное RUNNING.

Устойчивые значения Last/Next poll сейчас недоступны внешнему CLI: разработать минимальный локальный механизм публикации оперативных метаданных daemon (без GitHub и без изменения планирования). Протухшая метаинформация не доказывает живой daemon. Предпочтительно не мигрировать основную SQLite-схему ради эфемерного состояния.

Нижняя часть: таблица по проектам из *текущей конфигурации* в порядке следования, включая проекты с нулевыми значениями; отключённые проекты отличать визуально. Название проекта — только `project.id`, без owner/repo.

| № | Project | Open | Disc. | Appr. | Review | Reject | Error |
|---:|---|---:|---:|---:|---:|---:|---:|
| 1 | Playground | 12 | 3 | 2 | 4 | 2 | 1 |
| 2 | CodexAgent | 9 | 2 | 3 | 1 | 2 | 1 |
| | **TOTAL** | **21** | **5** | **5** | **5** | **4** | **2** |

*Числа условные.* Open — количество отслеживаемых реальных Issue с последним известным `github_state='open'`, независимо от внутренней фазы, но исключая виртуальные записи. Остальные счётчики — только такие открытые Issue в состояниях: Disc.=discovered, Appr.=pending, Review=review, Reject=rejected, Error=error. TOTAL суммирует отображённые проекты. Open не обязан равняться сумме пяти состояний (существуют другие фазы). Не добавлять крупные дублирующие глобальные KPI.

## 4. Экран queue

Команды:

```sh
codex-dispatcher queue
codex-dispatcher queue --project Playground
codex-dispatcher queue --state review
codex-dispatcher queue --project Playground --state review
codex-dispatcher queue --all
codex-dispatcher queue --json
```

По умолчанию только открытые отслеживаемые реальные Issue из текущей конфигурации. Закрытые GitHub Issue исключаются, даже если SQLite state ещё нетерминальный. `done` и `cancelled` — архив; `--all` добавляет сохранённые закрытые/терминальные записи, относящиеся к выбранным проектам. Без запроса GitHub; использовать последнее известное состояние.

Набор данных: Project, Issue, Title, State, PR, Age. По умолчанию отдельный заголовок блока на каждый `project.id` вместо дублирования проекта в каждой строке; внутри блока таблица Issue | Title | State | PR | Age. При `--project` показывать только выбранный блок. При `--state` убрать колонку State, вынести единственное значение в заголовок. При двух фильтрах: Issue | Title | PR | Age. Высвободившаяся ширина передаётся Title. Для JSON не удалять фильтрованные поля из записей.

Сортировка: сначала по порядку проектов в конфигурации, затем группы по состояниям:
1. error
2. review
3. rejected
4. need-fix
5. manual-running (отдельное ожидание внешней работы, НЕ автоматический исполнитель)
6. preparing / running (равный приоритет)
7. pending
8. awaiting-children
9. discovered
10. done / cancelled, только в архивном режиме.

Внутри одного приоритета первыми идут задачи, дольше находящиеся в текущем состоянии; при равенстве сортировка по номеру Issue. `Age` — время от последнего фактического перехода в `state_history`, *не* от `issues.updated_at` (оно обновляется на poll). Формат отображения 12m, 2h, 3d; в JSON сохранять точный timestamp и/или seconds. Если история недоступна, N/A, без искусственных значений.

## 5. Экран show

```sh
codex-dispatcher show PROJECT ISSUE
codex-dispatcher show PROJECT ISSUE -v
codex-dispatcher show PROJECT ISSUE --verbose
codex-dispatcher show PROJECT ISSUE --json
```

PROJECT — `project.id`, ISSUE — номер Issue *в данном репозитории*, не глобальный GitHub issue_id. Разрешить просмотр конкретной сохранённой закрытой Issue, не только текущей очереди. При неизвестном проекте/Issue понятная ошибка.

Обычный режим — карточка с тремя блоками:

1. Заголовок: Issue #, Title, State.
2. Project / Execution: project.id, owner/repository, номер Issue, state, base/work branch (с учётом execution group), PR # и статус, данные последнего исполнения и утверждения. Не выдумывать числовой `Issue version`: в V2 схема хранит approved snapshot/hash/approved_at, а не обязательный номер версии.
3. Execution Result: динамическое сообщение или результат, без повторения PR. Для discovered — ожидание подтверждения; pending — в очереди; awaiting-children — ожидание и перечень *блокирующих* детей; preparing — подготовка worktree; running — исполнение Codex; manual-running — внешняя работа; review — последний текстовый ответ Codex; rejected — последний ответ + информация об отказе; need-fix — требуется корректирующая Issue; error — конкретная причина; done — последний сохранённый ответ (если есть); cancelled — сообщение об остановке.

Файл исходного stdout Codex хранится в `<workspace>/results/<execution_id>.txt`. Проверить, содержит ли он последний текстовый ответ как на экране Codex CLI; при необходимости выделить финальный ответ при чтении, не изменяя оригинал. Не перефразировать, не смешивать попытки, не подменять отсутствующий результат старым `output_body`; если файла нет — показать «недоступен». Длинные ответы переносить, не обрезать произвольно.

Для awaiting-children в *обычном* show отображать Blocking Children: #, Title, State. Выбирать только действительно блокирующих детей по действующим правилам `GroupService` и SQLite `issue_relations`; не дублировать независимую логику готовности. Независимые/терминальные не блокирующие дети не показываются.

Подробный режим `-v / --verbose` включает всё вышеперечисленное и:
- Timeline: достоверные переходы `state_history`, причины/время, доступные события executions, PR, Recovery; без реконструкции вымышленных дат;
- Execution details: execution ID, started/finished, codex started/finished, exit code, worktree, SHA, push/pr публикация;
- Diagnostics: ошибка, стадия, карантин, доступные recovery events.

Не выводить полный текст утверждённой постановки, дамп полного stdout/stderr всех попыток, большие журналы, diff. Их можно смотреть отдельными инструментами, а постановку — на GitHub.

Источники: `issues`, `executions`, `pull_requests`, `state_history`, `error_log`, `issue_relations`, `recovery_events`, `recovery_quarantine`. Новая Timeline-таблица не нужна.

## 6. Конфигурация и root_path

`--config` необязателен *для всего основного CLI*, включая db и project. Выбор:
1. явно переданный `--config`;
2. `$XDG_CONFIG_HOME/codex-dispatcher/config.yaml` при корректной абсолютной XDG_CONFIG_HOME;
3. `~/.config/codex-dispatcher/config.yaml` иначе.

Если конфигурация отсутствует — понятная ошибка с ожидаемым путём. Не искать автоматически в CWD, в репозитории исходного кода или /etc. Явный --config всегда переопределяет значение по умолчанию. Отдельный `worktree-cleanup` также перевести на общий resolver.

Новая конфигурация:

```yaml
dispatcher:
  root_path: /home/user/codex-dispatcher
  database: runtime/dispatcher.sqlite3
  workspace: workspace
  poll_interval: 30
projects: []
```

`root_path` — абсолютный каталог данных, для новых конфигураций обязателен. Относительные `database`, `workspace` и `project.checkout` разрешаются относительно `root_path`; абсолютные пути разрешены, но внешний checkout не считается автоматически удаляемым. Расположение не зависит от CWD и bin. Новые пользовательские конфиги создаются с ограниченными правами; SQLite 0600, приватные каталоги с безопасными правами. Не ослаблять проверки идентичности экземпляра, UUID, marker, WAL/SHM и DB Guard. Старые тестовые установки допускается пересоздать: автоматические миграции не нужны.

Системное развертывание через /etc,/var/lib и systemd — следующий этап, с возможностью явно указать --config и абсолютные пути.

## 7. Команды project

```sh
codex-dispatcher project list
codex-dispatcher project show PROJECT
codex-dispatcher project add PROJECT REPOSITORY [--base-branch BRANCH] [--checkout PATH]
codex-dispatcher project disable PROJECT
codex-dispatcher project enable PROJECT
codex-dispatcher project remove PROJECT
codex-dispatcher project remove PROJECT --purge
codex-dispatcher project remove PROJECT --purge --dry-run
```

`list` — Rich таблица № | Project ID | Repository | Status, включая disabled. `show` — id, полное owner/repository, enabled, base_branch, checkout, effective labels.

`add`: локально проверить project.id, owner/repo, отсутствие повторного id, отсутствие повторного repository, конфликт с уже существующей историей того же репозитория в SQLite. Проверки удалённого репозитория *обязательны* перед изменением YAML:
- авторизованным GitHub API проверить существование и доступность репозитория (404/403 могут не позволить различить «не существует» и «нет доступа»);
- проверить доступ текущей учётной записи на чтение;
- проверить git remote access без изменения удалённой стороны (например `git ls-remote` с согласованным способом аутентификации);
- проверить права записи и работу с Issues / Pull Requests настолько полно, насколько API предоставляет достоверную информацию, без попыток записи;
- если API явно сообщает о недостаточных необходимых правах, **отказать**;
- если доступ и необходимые доступные проверки прошли, но часть полномочий без тестовой записи проверить невозможно, **показать WARN и разрешить add**;
- если проверка существования, авторизации или Git-доступа неуспешна / неопределённа из-за сетевой ошибки, **отказать** (fail closed).
- НЕ создавать тестовые issues, branches, labels, PR, comments или иные объекты GitHub.
- в случае отказа YAML не меняется; при успехе сохранить и сообщить о необходимости restart.

GitHub API разрешён для этих разовых читающих проверок `project add`, но запрещён для `status`, `queue`, `show`, `remove`, `--purge`, `disable/enable`, `list/show`. Разовые проверки не должны добавлять обращения к штатному poll.

`disable`/ `enable`: только переключение enabled и сохранение конфигурации; локальная история неизменна. Повторная установка того же состояния — безопасная операция.

`remove` без `--purge`: удалить запись проекта только из YAML, SQLite и артефакты оставить. Запретить незаметное новое подключение того же репозитория через add до очистки истории. Переименование project.id не поддерживается; штатный способ сменить название с чистой историей — purge + add.

**Утверждён вариант A:** запущенный daemon не перечитывает YAML; изменения вступают в силу только после перезапуска. После любой изменяющей команды напечатать явное `Restart dispatcher to apply changes`. Команда не должна создавать впечатление, что работающий daemon уже перестал обслуживать удалённый/disabled проект.

Сохранять YAML безопасно: прочитать, проверить, сформировать, проверить итог, записать временный файл рядом с конфигурацией (ограничительные права), fsync и атомарно заменить; синхронизировать конкурентных редакторов CLI, не повреждать исходный файл при отказе. Не терять действующие пользовательские параметры и локальные переопределения без необходимости.

## 8. Удаление project --purge

`codex-dispatcher project remove PROJECT --purge [--dry-run]`

**Только локальные данные!** Не удалять и не изменять на GitHub Issues, PR, labels, comments, ветки или сам репозиторий. Запрещены любые изменяющие и диагностические сетевые действия в GitHub в рамках purge.

`--dry-run` печатает реальный план и количества: записи issues/state_history/executions/PR/errors/debug/recovery, результаты Codex, принадлежащие worktree, ветки, управляемые каталоги. Никаких изменений данных, конфигурации, Git refs/worktree. Не делать ложных заявлений о подтверждённой очистке на основании dry-run.

Настоящий purge:
- диспетчер остановлен, executor полностью завершён; доказаны блокировки InstanceLock и отсутствие control socket, WAL/SHM и других небезопасных признаков в соответствии с существующими правилами V2.4.2;
- SQLite доступна, схема и UUID проверены, общий recovery_required снят, нет незавершённых блокирующих recovery operations/карантина;
- принадлежность всех удаляемых локальных ресурсов однозначно доказана;
- если есть неоднозначность, shared checkout, внешние пользовательские данные или иные риски — отказ ДО разрушительных действий;
- основной явно пользовательский внешний checkout не удалять;
- основной shared workspace и данные иных проектов не удалять;
- перед разрушительными действиями создать проверенный SQLite backup через Backup API, не удалять этот backup в рамках purge;
- показать реальный план, интерактивно запросить точное project.id как подтверждение (при неинтерактивном запуске без подтверждения — безопасный отказ; обходящий безопасность --force не добавлять);
- удалить собственные worktree через существующий безопасный Git API и рабочие refs только при подтверждённой принадлежности;
- удалить локальные файлы результатов, связанные таблицы, связи и диагностику, без нарушений внешних ключей;
- удалить запись конфигурации только после успешной очистки критических ресурсов;
- предусмотреть безопасное завершение или повтор операции после прерывания между изменением файлов, Git и SQLite; не требовать ручного SQL;
- не удалять чужие данные при неполной очистке.

При purge удаляется вся локальная история данного репозитория. Исторические переименования project.id не поддерживаются, но проверять принадлежность и связи по repository и реальным FK необходимо. После успешного purge разрешить add того же репозитория с новым project.id: новый локальный учёт начинается с чистого листа. При следующем poll ранее существовавшие на GitHub **открытые** Issue с codex-ready могут обнаружиться вновь, поскольку GitHub не изменяется — это ожидаемо.

## 9. Read-only мониторинг при Recovery

`status`, `queue`, `show` должны быть доступными при `recovery_required` после `db restore`, несмотря на то, что штатный `Storage.connection()` запрещает доступ при глобальном барьере. Реализовать отдельный безопасный read-only доступ, который сохраняет проверку схемы, целостности и идентичности, не пишет SQL, не обходит запрет исполнения, не меняет Recovery и не вызывает GitHub/Git. При повреждённой/отсутствующей БД `status` по возможности выводит диагностику, без traceback; неизвестное = N/A.

## 10. Рекомендуемая организация кода

Разделить парсинг аргументов, query-layer мониторинга, Rich/JSON renderers, resolver + writer конфигурации, project manager, purge planner/executor. Переиспользовать Storage, GroupService, DB Guard, InstanceLock, Cleanup; не строить новый сервер мониторинга и не дублировать алгоритмы зависимостей. Миграция схемы SQLite не планируется; если неизбежна, агент должен отдельно обосновать её до изменения схемы.

## 11. Автоматические тесты

Проверить:
- status: RUNNING/STOPPED/UNKNOWN, IDLE, preparing/running, протухшая running без процесса, last/next poll, несколько/пустой/disabled проект, TOTAL, открытые/закрытые;
- queue: группировка и порядок, все состояния включая need-fix/manual-running, sort-by-history (не issues.updated_at), --project/--state/combined, --all, width 80/120, длинный Title;
- show: обычный/-v/--verbose, без исполнения, результат Codex, отсутствие файла, ошибка, повторная попытка, awaiting-children с реально блокирующими детьми, closed, timeline/recovery;
- config: XDG/default/--config, root_path absolute and path resolution, CWD independence, отсутствующий/ошибочный YAML, secure permissions;
- project: list/show/add, duplicate ID/repository/history, недоступный/отсутствующий GitHub repo, недостаточные права, неполностью проверяемые права→WARN, ошибка git ls-remote, отсутствие побочных эффектов; enable/disable/remove, повторный add после purge, рестарт-граница;
- purge: dry-run no effects, сохранение GitHub, неподходящий daemon/recovery, неизвестная принадлежность/shared resources/внешний checkout, backup, восстановление после прерывания, сохранение всех прочих проектов и FK;
