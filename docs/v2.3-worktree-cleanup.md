# V2.3.B — восстановление очистки и ручная утилита осиротевших worktree

**Решение пользователя:** вариант A для восстановления по существующей SQLite; отдельно разработать утилиту ручного поиска и удаления осиротевших worktree. Утверждено в обсуждении V2.3.B.

## 1. Автоматическое восстановление при запуске

- Не вводить таблиц/флагов `cleanup_pending`: использовать `issues`, `executions.worktree_path`, `issues.work_branch`, статусы исполнения и публикации.
- При старте проверять известные по SQLite временные ресурсы, не сканируя весь компьютер. Удалять локальные worktree только если достаточно подтверждений публикации/отсутствия единственной неопубликованной копии.
- Отказ очистки не отменяет `done`/`cancelled`; ошибку записывать и пробовать безопасно повторить позже.
- Рабочую ветку группы сохранять в `rejected` и `need-fix`, так как она нужна последующим корректировкам; удалять лишь после терминального завершения группы при подтверждённой сохранности результата.
- Диспетчер не удаляет произвольные пользовательские worktree или ветки.

## 2. Ручная сервисная утилита `worktree-cleanup`

Отдельный CLI инструмент (например, `python -m dispatcher.tools.worktree_cleanup` или команда `codex-dispatcher maintenance worktrees`; конкретный интерфейс выбрать в B). Не запускать его автоматически из poll/scheduler.

Режимы:
- По умолчанию **dry-run**: список кандидатов и причина, без изменений Git и файловой системы.
- `--apply`: явное разрешение удалить только безопасные кандидаты после повторной проверки.
- `--project`: ограничить область одним настроенным проектом (необязательно).

Порядок:
1. Загрузить конфигурацию V2 и **успешно открыть/проверить SQLite V2**; при ошибке базы — отказаться от удаления.
2. Для выбранных проектов определить **только управляемые каталоги V2** и рабочие Git-репозитории. Считать `git worktree list --porcelain` для соответствующего репозитория (учитывать несколько проектов и пути с пробелами). Не считать любой найденный каталог Git worktree кандидатом.
3. Составить набор канонических `executions.worktree_path` из SQLite; при совпадении путь защищён, независимо от статуса Issue. Также исключить основной checkout, чужие worktree, пути вне настроенной директории временных worktree V2, символические ссылки с выходом за её пределы и неидентифицированные ресурсы.
4. Кандидат: работающий Git worktree, **в управляемой области диспетчера V2**, которого нет среди `executions.worktree_path`. Проверить отсутствие активного диспетчера/исполнения, чтобы не удалить worktree, ещё не внесённый в SQLite. Если нельзя надёжно установить отсутствие активной работы — отказаться от `--apply`.
5. До удаления проверить чистоту worktree (`git status --porcelain`), отсутствие невыпушенных коммитов/единственного локального результата и что это не основная рабочая копия. При любом сомнении пометить `SKIP` и показать причину, не применять force.
6. Удалять через `git worktree remove` без `--force`, для каждого кандидата фиксировать итог/ошибку. Никаких `rm -rf`, автоматического удаления веток, `git worktree prune` для чужих записей или изменения SQLite. Перед удалением каждого кандидата ещё раз проверять путь и отсутствие ссылки в SQLite.
7. Фиксировать число обнаруженных, безопасных, пропущенных, удалённых worktree; не логировать секреты и полный вывод внешних команд.

Безопасность: сам факт отсутствия записи в SQLite **не является достаточным разрешением на удаление**; нужен также подтверждённый статус временного ресурса V2, отсутствие выполняемой работы и риск-проверки данных. Если подтверждение безопасности отсутствует, утилита сообщает путь для ручной проверки.

## 3. Тесты

- Dry-run ничего не удаляет.
- Указанный в SQLite worktree никогда не удаляется.
- Чистый осиротевший worktree под управляемым каталогом V2 обнаруживается и удаляется только по `--apply`.
- Worktree вне области V2, основной checkout, активная работа, грязный worktree, локальные неопубликованные коммиты, symlink escape и ошибки доступа пропускаются.
- Несовместимая/недоступная SQLite блокирует удаление.
- Повторный запуск после удаления идемпотентен.
- Несколько проектов не смешиваются; идентичные пути сравниваются в каноническом виде.
- Падение отдельной очистки не меняет статусы Issue и не повреждает зарегистрированные ресурсы.

## 4. Граница работ

Реализовать в V2.3.B вместе с автоматическим восстановлением по варианту A. После реализации предъявить ручной dry-run на новом тестовом окружении V2, затем испытание `--apply` только на специально созданном безопасном осиротевшем worktree. Никаких операций с V1.
