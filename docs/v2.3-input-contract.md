# V2.3.B — утверждённый контракт INPUT и момент привязки корректировок

**Статус:** согласовано пользователем (2026-11-07); применяется при реализации V2.3.B.
**Основание:** V2.1, V2.2, приёмка V2.3.A и последующее согласование регистрации.

## Формат INPUT

В отдельном пользовательском INPUT-комментарии размещается YAML-блок:

```yaml
dispatcher:
  base_branch: main
  branch: my_task01
  correction_for: 23
  run_codex: true
```

Все ключи необязательны:
- `base_branch`: целевая базовая ветка PR; при отсутствии брать настройку проекта (если её нет, при реализации отдельно определить источник основной ветки).
- `branch`: рабочая ветка; при отсутствии генерировать уникальное имя группы.
- `correction_for`: положительный номер исправляемой Issue **в том же репозитории**, не глобальный GitHub ID. При отсутствии создаётся новая самостоятельная группа.
- `run_codex`: логическое значение, по умолчанию `true`.

В корректирующей Issue `base_branch` и `branch` не переопределяют закреплённые ветки группы: если эти параметры явно заданы в корректировке, отклонить approve с понятной причиной. Реализация должна явно валидировать YAML, типы и допустимые ключи. Отдельный формат маркеров комментария INPUT/OUTPUT будет соблюдать V2.1.

## Моменты чтения и фиксации

1. `codex-ready`: **только регистрация** Issue (`discovered`) и необходимых непосредственных Sub-issue-связей. Содержимое Issue и INPUT не утверждается, `correction_for` не интерпретируется. Редактирование Issue/INPUT до approve свободно. Временная группа для вновь зарегистрированной Issue — собственный GitHub `issue_id` согласно NOT NULL-инварианту V2.3.A.
2. `approve`: получить актуальный текст Issue и INPUT, разобрать `dispatcher` и параметры. Если `correction_for` задан, разрешить номер в GitHub ID данного репозитория и проверить наличие существующего разрешения `need-fix` в соответствующей незавершённой группе, отсутствие активной Issue и другие групповые ограничения. Затем **одной SQLite-транзакцией** связать Issue с окончательной группой (`execution_group_id`, `correction_of_issue_id`), сохранить неизменяемые `approved_*` + `input_comment_id` + `approved_input` + исходный `parameters_yaml` и перейти `discovered → pending/awaiting-children` с историей.
3. При невалидном INPUT, запрете корректировки или изменившемся внешнем контексте не утверждать Issue и не оставлять частично переназначенную группу; Issue остаётся `discovered`. После исправления INPUT/разрешения `need-fix` можно повторить approve.
4. После успешного approve изменения текста Issue или INPUT не переснимаются. OUTPUT сохранять отдельно только после подтверждения публикации согласно V2.3.A.

## Техническая доработка Storage

Существующий `Storage.register_issue(..., correction_of=...)` V2.3.A привязывает корректировку слишком рано. Для V2.3.B изменить пользовательский поток: регистрация должна быть без интерпретации correction_for, а `commit_approval` (или транзакционно эквивалентный сервис) должен проверять и фиксировать привязку к группе вместе со снимком. Не допускать частичного обновления, повторного approve либо параллельного approve с созданием двух активных Issue в одной группе. При этом `issue_relations` (GitHub Sub-issues) — независимая связь и не должна меняться от `correction_for`.

Эта доработка относится к **V2.3.B** и не отменяет уже принятую V2.3.A. Смысл `need-fix` как разрешения корректировки сохраняется — его не требуется выставлять до простой регистрации Issue.

## Тесты

- Обычная Issue с `codex-ready` регистрируется без INPUT и без `need-fix`.
- Корректирующая Issue с `correction_for` до approve регистрируется как `discovered` и свободно редактируется.
- При approve корректировки без `need-fix` нет привязки группы и нет снимка.
- При `need-fix` approve фиксирует корректируемую Issue, корневой GitHub ID группы и снимок атомарно.
- Две корректировки одной Issue возможны как структура истории, но одновременно активна только одна.
- Повторное/конкурентное approve не меняет утверждённый снимок и не нарушает групповые ограничения.
- Отсутствие `base_branch`/`branch` использует настройки/генерацию, а явная попытка заменить ветки при корректировке отклоняется.
