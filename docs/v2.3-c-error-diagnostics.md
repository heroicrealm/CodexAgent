# V2.3.C — Расширенная диагностика ошибок: оригинал в SQLite, безопасный отчёт на GitHub

**Статус:** задание агенту. **Ветка:** `V2_3_IMPLEMENTATION`. **Основание:** утверждённое пользователем требование в ходе V2.3.C. После реализации пользователь проверит вместе с изменением имён веток по `issue_number`.

## 1. Цель и границы

При реальном запуске Issue #1 в `heroicrealm/CodexAgentPlayground` отсутствие `origin/main` вызвало `preparation_failed`, но публичный ERROR содержал лишь общую фразу «Task failed; surviving local results are retained», и первопричина была потеряна. Issue #2 после подготовки репозитория выполнилась успешно. Это **не дефект создания ветки**, а недостаточная диагностируемость.

Требуются **две разные формы одной ошибки**:
1. **Локальный полный оригинал** (исключение, traceback, подлежащие сбору stderr/вывод команд и этап/операция) в существующей SQLite `error_log`, **без маскировки секретов**.
2. **Публичный ERROR-комментарий на GitHub** с подробной, но **безопасной** диагностикой. Никакой непроверенный stderr, traceback, переменные окружения, абсолютные домашние пути, токены или credentials не могут попасть на GitHub.

Не изменять переходы состояний, правила PR, один слот Codex, recovery, идемпотентность ERROR/OUTPUT и сам INPUT. Не увеличивать число опросных GitHub GET. Не менять поведение именования веток, реализованное в `docs/v2.3-c-branch-naming.md`.

## 2. Локальная запись (SQLite)

- Использовать существующие поля `error_log.error_message` (TEXT), `error_stage`, `error_code`, `issue_id`, `execution_id`. Для исполнения хранить в `error_message` **полный исходный контекст**: тип исключения, `str(exc)` без очистки, traceback с причинной цепочкой, имя компонента/операции, код возврата, полные stdout/stderr **только тех операций, для которых вывод реально получен**. Допустим структурированный формат JSON в TEXT, но предоставить удобочитаемый способ локально просмотреть содержимое; не разрывать обратную совместимость `error_log`.
- `Git.run` и `git clone` сейчас выбрасывают `GitError('Git fetch failed')` или аналог без stderr. Сохранить исходный stderr/stdout/returncode из `subprocess.run` внутри исключения или объекта диагностики, не отправляя их напрямую в общий лог/публичный текст. Не терять исключение в `Executor.execute`: передать его в `Publisher.fail` с актуальным этапом/операцией.
- `GhTransport` сейчас сохраняет лишь HTTP status. При сбое предоставить полную локальную диагностику `gh` (из полученного stderr, stdout, returncode), но сохранить `GitHubError.status` и текущие retry-правила. Не помещать тела INPUT/OUTPUT или секреты в безопасную публикацию.
- `ProcessRunner` сейчас направляет stderr Codex в DEVNULL. Собирать stderr в локальную диагностику **без deadlock и без хранения всего процесса в RAM**, по возможности в ограниченный доступом временный файл/поток на диске. По требованию пользователя в SQLite сохранять полный stderr при аварии/ненулевом коде. Не изменять сохранение оригинального stdout результата в `workspace/results/<execution_id>.txt`; stderr, traceback и stdout не смешивать в публичном OUTPUT. Если ошибка запуска произошла до получения stderr, честно отразить отсутствие данных. Учесть таймауты и аварии процесса.
- Не подменять первичную причину ошибкой последующей попытки `commit_push` при аварийном сохранении результата: если сохранение тоже упало, записать вторичную ошибку отдельно, сохранив первичную.
- Ошибки без `execution_id` (например, отказ approve, ошибка poll) обрабатывать с учётом доступного контекста; не раскрывать данные через `Runtime` stdout/stderr. **Не создавать фиктивную ERROR-задачу** при poll-ошибке, у которой нет связанной зарегистрированной Issue.
- **Схема SQLite v1:** попытаться выполнить в существующих 8 таблицах без миграции. Если для технической полноты потребуется изменение схемы, сначала указать обоснование в отчёте и не проводить непринятую миграцию V2 самовольно. Предпочтительно не менять DDL.

## 3. Безопасный публичный ERROR

Формат (пример):

```text
<!-- codex-dispatcher:ERROR:v2 -->
Dispatcher execution failed

Stage: preparation
Operation: git.prepare
Error code: base_branch_not_found
Repository: heroicrealm/CodexAgentPlayground
Base branch: main
Execution ID: 1

Reason: Remote branch origin/main was not found.
Local diagnostics: saved in SQLite error_log.
Local results: preserved where possible.
```

- Поля `Stage`, `Operation`, `Error code`, `Repository`, `Base branch`, `Execution ID` брать из **проверенного структурированного контекста**, а не извлекать регулярками из произвольного traceback.
- Для часто встречающихся случаев использовать структурированные безопасные причины: `base_branch_not_found`, `work_branch_exists`, `git_clone_failed`, `git_fetch_failed`, `git_worktree_failed`, `git_push_failed`, `codex_exit_nonzero`, `codex_start_failed`, `github_http_error` и т. п. Имя base/work-ветки (потенциально пользовательский ввод) валидировать перед публикацией.
- Для нераспознанных ошибок выводить безопасный **шаблон** (тип операции + этап + код + reference execution), **НЕ** непроверенные `str(exc)` и `stderr`. Применять redaction для дополнительных публичных полей (известные токены GitHub/OpenAI, Authorization, пароли/URL userinfo, SSH private key, чувствительные параметры), но redaction **не** считается достаточным основанием публиковать произвольный traceback/stderr: при неопределённости — шаблон. Не публиковать абсолютные локальные пути и значения env.
- Публиковать понятные GitHub комментарии без секретов и скрытых локальных данных даже при `debug.mode=verbose`. Независимо от отладочного режима, ошибки исполнения фиксируются локально.
- Идемпотентность: один ERROR-комментарий при подтверждении, `error_report_sent` устанавливать только после успешного ответа GitHub; не создавать массовых повторных сообщений. При неясном ответе POST соблюсти существующее правило минимального риска дубля, без повторного Codex.
- При нескольких ошибках одного execution первичная причина должна быть очевидна, а вторичные действия помечены отдельно. Размер сообщения на GitHub ограничен (например, 4000 символов), в SQLite **нет искусственного усечения захваченного диагностического текста**.

## 4. Доступ к локальным секретам

- Поскольку SQLite может содержать токены, сделать строгие права для **новых** директорий/файлов диагностики: директорий `0700`, файлов `0600` с учётом umask; проверить защиту SQLite и sidecar файлов `-wal`, `-shm`, а также временных файлов stderr.
- Не менять права произвольных пользовательских родительских каталогов вне собственных runtime/workspace. Для уже существующей базы/каталога с более широким доступом выдавать понятное локальное предупреждение или безопасно ужесточать права только управляемых файлов без нарушения совместимости, описать решение в отчёте.
- Ни обычный CLI `status/queue`, ни диагностическое журналирование `debug_operations` не должны автоматически выводить полный секретосодержащий traceback. Чтение `error_log` — осознанное локальное действие оператора.
- Не включать полную SQLite/сырые диагностические файлы в commits, PR и тестовые фикстуры с реальными credentials. Сохранять текущие правила хранения и очистки worktree; не удалять единственную копию результатов.

## 5. Тесты

1. Нет `origin/main`: локальный оригинал в SQLite + публичный `base_branch_not_found` с `main`; состояние `error`; имя новой ветки берётся из `issue_number` (например, `codex/task-0011`).
2. Неуспешный git fetch/clone/worktree/push: локально полный stderr/stdout/returncode, публично только безопасные проверенные факты.
3. Синтетический секрет в stderr, traceback, URL с учётными данными, `Authorization` и локальном пути: **присутствует в локальном оригинале**, полностью отсутствует в GitHub ERROR/OUTPUT, CLI status и debug_operations.
4. Codex с ненулевым exit code и значительным stderr: нет deadlock, локальные данные не усечены, публичный текст безопасен; stdout результата не потерян.
5. Ошибка на стадии `preparation` не запускает Codex и PR; ошибки после запуска не вызывают повторного запуска Codex.
6. Ошибка salvage commit/push не перекрывает исходную ошибку.
7. ERROR-публикация: подтверждённый POST не дублируется; сбой публикации не теряет локальную диагностику; recovery сохраняет прежнюю идемпотентность.
8. Проверки прав файлов/каталогов и SQLite sidecars; тесты выполняются в изолированных временных каталогах.
9. Все тесты V2 без регрессий, в том числе именование веток по `issue_number`, OUTPUT-ссылки и cleanup; `compileall`, `git diff --check`.
