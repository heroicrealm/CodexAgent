# V2.4.3.D — исправления ручной приёмки

Ветка `V2_4_3_CLI_MONITORING`. PR и merge не создаются; ручная приёмка ожидается.
Этот этап намеренно отменяет прежний контракт удаления в исторических заданиях
V2.4.3/V2.4.3.C. Сохранение истории: `project disable ID`; возврат: `project enable ID`.

## Реализация

- BUG-01: `monitoring.daemon` удерживает успешно полученные существующие lock
  одновременно через ExitStack. При свободных обоих lock и отсутствующем socket
  либо ENOENT/ECONNREFUSED на socket возвращает STOPPED. Доступный socket,
  занятый хотя бы один lock, небезопасный путь или неоднозначная ошибка оставляют
  UNKNOWN, если нет полного прежнего подтверждения RUNNING (оба lock, socket,
  instance UUID, PID+starttime, свежий heartbeat). Старый heartbeat сам по себе
  никогда не доказывает RUNNING. Файлы не удаляются и не создаются. Это снимок
  состояния: последующий старт другого процесса возможен после возврата команды.
  `stop` перехватывает ошибки сокета, включая отсутствие, отказ и timeout,
  выводит состояние и причину без traceback. Новый `run` использует прежний
  InstanceLock и безопасную замену socket под блокировками.
- BUG-02: `Publisher.reconcile` после успешного `GitHubAdapter.close_issue`
  записывает `github_state='closed'` по глобальному issue_id. Только после SQL
  успеха добавляет ID в `_closed`. Это действует для done и cancelled. При ошибке
  API closed не записывается. PATCH повторного закрытия идемпотентен. После crash
  между API и SQLite следующий существующий reconciliation повторяет close;
  после рестарта `_closed` пуст. Новые массовые GET и дополнительные запросы
  на каждом poll не добавлены. Счётчик Open по-прежнему читает github_state;
  done без успешного close не исключается искусственно. `queue --all` хранит
  терминальные записи.
- CHANGE-01: CLI и внутренний `projects.mutate(remove)` используют прежний
  `purge.execute`, без обходного YAML-only пути. Устаревший ключ отклоняется
  argparse. Безопасность SQLite UUID/schema/FK/triggers, Recovery admission,
  InstanceLock, ownership Git/files, повторная проверка плана и журнал фаз
  сохранены. GitHub/remote не вызываются. Показываются полный план, Project,
  Repository и предупреждение о необратимости. Точное подтверждение в TTY;
  неверный ID, EOF, Ctrl+C и pipe отказывают до backup. После подтверждения
  повторяются проверки под блокировками; затем создаётся проверенный SQLite
  backup. Временные backup/журнал в `backups/purge/` удаляются после успеха;
  при ошибке сохраняются с явными путями, блокируя незаметную новую попытку.
  Порядок SQL → локальные Git/files → YAML и восстановление прежние; см.
  техническое описание V2.4.3.C. Backup SQLite не восстанавливает удалённые файлы.
- UI-01/04: единая палитра Rich Text, окрашиваются значения; подписи, рамки,
  заголовки и счётчики нейтральны. Project list: enabled зелёный, disabled красный.
  Оба State в show и State в queue используют согласованную палитру.
- UI-02/03: даты human status/show/-v переводятся в локальную TZ CLI,
  `YYYY-MM-DD HH:MM:SS`; отсутствующие N/A. Base branch и Work branch отдельные.
- UI-05/06/07: Timeline хронологически сортируется по времени с учётом offsets,
  выводит реальные state/execution/PR/Recovery события. Execution details —
  Parameter/Value с переносом длинных значений. Нулевой exit code и флаги
  публикации сохраняются как значимые 0; отсутствующие значения N/A. Diagnostics
  показывает таблицы ошибок и quarantine либо краткий текст об отсутствии.
  Пользовательский текст передаётся через Text, без интерпретации markup.
  JSON renderer возвращает исходные поля/ISO timestamps без Rich и преобразований.

Изменённые модули: `__main__.py`, `monitoring.py`, `monitoring_output.py`,
`execution.py`, `projects.py`, `purge.py`; тесты `test_monitoring_projects.py`,
`test_services.py`; README и документы этапов.

## Повторная ручная проверка

1. Подготовить отдельный тестовый root/config, два проекта Playground и Control.
   Сохранить явный `db backup` и копии локальных файлов вне managed roots.
   Зафиксировать состояние GitHub и строки/файлы/refs Control для сравнения.
2. Запустить daemon, проверить RUNNING и штатный `stop`, затем STOPPED.
   Запустить снова, завершить daemon принудительно (без активного Codex-потомка).
   Убедиться, что socket остался: status должен дать STOPPED, stop — понятную
   диагностику без traceback; файлы socket/lock не исчезают от этих команд.
   Запустить run снова и проверить восстановление управления. Если процесс или
   унаследовавший lock потомок жив — ожидать UNKNOWN, не ложный STOPPED.
3. Подготовить несколько Issue, последовательно завершить через штатный merge PR
   и dispatcher. После его poll проверить GitHub closed и SQLite github_state
   closed для каждого глобального ID; Open уменьшается, Disc. не включает closed,
   `queue --all` показывает историю. API failure проверять в тестовом stub:
   фиктивного closed нет; после повторного reconciliation всё согласовано.
4. Проверить status, project list, queue (включая pending/running/need-fix), show
   и show -v на ширине 80/120. Цвет только у значений; оба State в show одинаковы.
   Проверить Timeline, execution ID/branch/exit code/commits/publication/path,
   ошибки и quarantine, а также вариант без ошибок/исполнений.
5. Повторить human экраны с `TZ=UTC` и `TZ=Europe/Moscow`, включая даты около
   полуночи. Проверить локальные даты без fractions/offset, раздельные branches.
   Повторить с NO_COLOR=1, через pipe и с --json; ANSI отсутствует, JSON сохраняет
   полные исходные ISO/поля, пользовательские `[red]` остаются литералом.
6. Проверить disable/enable и restart: история сохраняется. Остановить daemon,
   выполнить `project remove Playground --dry-run`; сверить counts, row IDs,
   Recovery summary, files/hashes, worktrees/refs/OID, blockers и отсутствие
   изменений DB/WAL/SHM/YAML/Git/backup. Устаревший аргумент должен отвергаться.
7. Проверить remove в pipe, неверный регистр ID, EOF, Ctrl+C: отказ без backup
   и изменений данных. Проверить refusal с живым daemon, Recovery barrier,
   чужим/dirty/shared Git-ресурсом; устранить причины штатными средствами.
8. В TTY выполнить `project remove Playground`, сверить Project/Repository и
   полный план, ввести точный ID. После PASS проверить отсутствие всех локальных
   данных проекта и YAML записи, временных backup/журнала; `db check`, FK и оба
   append-only trigger. Сравнить Control и GitHub с шагом 1: они сохранены.
9. Повторно `project add Playground owner/repo` (либо новый ID) с обычными
   read-only проверками add; retained-history конфликта быть не должно.
   При новом poll старые открытые ready Issue могут обнаружиться снова.
10. Сбои SQL/Git/files/YAML проверять только на одноразовой копии через существующий
    checkpoint execute из test_purge.py: до SQL COMMIT rollback восстанавливает
    строки и DDL; после него файлы могут быть частично удалены. Backup/журнал
    должны сохраниться, следующий dry-run показывает попытку и блокирует новую.
    Восстановить YAML из original_config, `db restore BACKUP`, выполнить штатную
    Recovery reconciliation; явно архивировать файлы неудачной попытки вне
    backups/purge перед повтором. Не обходить quarantine ручным SQL.

Live GitHub/Codex и ручная приёмка не выполнялись. Атомарность между SQLite,
Git, файлами и YAML невозможна; после позднего сбоя требуется описанное
