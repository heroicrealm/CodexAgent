# Codex Dispatcher Standalone — WSL2 и Ubuntu native

Standalone запускается вручную в Linux-терминале и поддерживает Ubuntu native и Ubuntu под WSL2. Для Ubuntu Server реализация V2.5.3 добавляет пользовательскую службу отдельно от установки пакета.

Нужны Python ≥3.11 с pip/venv, git, GitHub CLI (`gh`), Codex CLI (`codex`), доступ к GitHub и индексу зависимостей Python. Работайте обычным пользователем, без sudo для установщика. В Ubuntu установите системные пакеты `python3`, `python3-pip`, `python3-venv`, `git`, `curl`; `gh` и Codex CLI установите по официальным инструкциям их поставщиков. На Ubuntu с Python <3.11 сначала установите поддерживаемый Python.

Самостоятельно настройте авторизацию:

```sh
gh auth login
gh auth setup-git
codex login
gh auth status
codex login status
```

Установщик проверяет команды и сообщает об отсутствии авторизации, но не меняет credentials.

## Подготовка WSL2

Запустите Ubuntu в WSL2 и выполните подготовку и авторизацию выше в Linux-терминале. Используйте Linux-каталоги внутри WSL для workspace. Включать systemd или настраивать автозапуск Windows не требуется.

## Подготовка Ubuntu native

Откройте терминал обычного пользователя Ubuntu, установите те же prerequisites и выполните ту же авторизацию. Далее команды установки, конфигурации и запуска полностью совпадают с WSL2. Foreground-режим доступен без systemd. Службу настраивают отдельно по операторской инструкции.

## Получение и установка

После публикации стабильного релиза `v2.5.2.post2` (до публикации см. регламент проверки candidate):

```sh
mkdir -p ~/Downloads/codex-dispatcher
cd ~/Downloads/codex-dispatcher
gh release download v2.5.2.post2 --repo heroicrealm/CodexAgent --pattern install-standalone.sh --pattern SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS
sh install-standalone.sh
```

Скрипт и manifest скачиваются из одного конкретного Release в пустой каталог. Проверка должна показать `install-standalone.sh: OK`; при ошибке не запускайте файл. Для перехода с 2.5.2 / **2.5.2.post1 один раз вручную скачайте новый установщик** этими командами. Старый установщик не обеспечивает новый контракт проверки. Не используйте скрипт из ветки main. Без авторизованного gh публичные артефакты можно скачать браузером со страницы этого Release.

При каждом запуске новый установщик синхронно проверяет свои реальные байты по `SHA256SUMS` последнего стабильного Release, включая GitHub digest manifest при наличии. Проверка выполняется также при первой установке и при уже актуальном пакете. Ошибка API/manifest/digest/checksum приводит к ненулевому коду до изменения установки. Даже добавленный комментарий меняет SHA. При несовпадении выводится ссылка конкретного Release: скачайте из него свежие `install-standalone.sh` и `SHA256SUMS` в новый пустой каталог, проверьте и запустите вручную. Автоматической перезаписи или запуска скачанного установщика нет. Assets опубликованного релиза должны оставаться неизменными.

Пакет устанавливается обычным wheel в отдельный venv внутри `~/codex-dispatcher`, а `~/codex-dispatcher/.venv` указывает на активную генерацию. Предыдущие генерации сохраняются до удаления программы. Повторный запуск той же версии не заменяет пакет; downgrade запрещен. Сбой загрузки, checksum или pip сохраняет прежний пакет. Чужую `.venv` или чужую короткую команду установщик не заменяет: разберите конфликт вручную, не удаляя рабочие данные.

Удалитель скачивается из того же Release, что wheel и шаблон, и проверяется по SHA-256 до установки. Он хранится в `~/codex-dispatcher/.venv-standalone-*/uninstall-standalone.sh` с правами 0755. Ссылка `~/.local/bin/codex-dispatcher-uninstall` указывает через `.venv` на активную генерацию. Обновление и откат переключают пакет и удалитель вместе; чужая команда удаления вызывает отказ. Установщик доставляется аналогично: `~/.local/bin/codex-dispatcher-install` → `~/codex-dispatcher/.venv/install-standalone.sh`. SHA проверяется до доставки; переключение и rollback включают обе команды. Чужие файлы/ссылки не заменяются. Повторный запуск восстанавливает отсутствующие управляемые ссылки только при подтвержденном ownership и пригодных скриптах.

Команда доступна через `~/.local/bin/codex-dispatcher` без активации venv. Если каталога нет в PATH, добавьте в `~/.profile`:

```sh
export PATH="$HOME/.local/bin:$PATH"
```

Откройте новый терминал. Проверьте:

```sh
codex-dispatcher --help
codex-dispatcher --version
command -v codex-dispatcher-install
codex-dispatcher --config-schema-version
~/codex-dispatcher/.venv/bin/python -m pip show codex-dispatcher-v2
```

## Конфигурация и первый запуск

Основной файл — `~/.config/codex-dispatcher/config.yaml`, либо `$XDG_CONFIG_HOME/codex-dispatcher/config.yaml`, если XDG_CONFIG_HOME — абсолютный путь. Параметр `--config /absolute/path` идет **до** подкоманды. Установщик обслуживает стандартный/XDG-файл; перед обновлением при нестандартном `--config` остановите все экземпляры и согласуйте его YAML вручную. Общая блокировка установленного пакета также запрещает обновление/удаление при активном runtime с нестандартным `--config`; установщик не редактирует такие YAML автоматически.

В шаблоне сохранены все настройки. `dispatcher.root_path` вложен в `dispatcher`, содержит абсолютный путь пользователя; литерал `~` не поддерживается. Пути workspace/database разрешаются относительно root. Добавьте тестовый проект в `projects`, например:

```yaml
dispatcher_version: "2.5.2.post2"
config_schema_version: 1
dispatcher:
  root_path: /home/alice/codex-dispatcher
projects:
  - id: sandbox
    repository: alice/dispatcher-sandbox
    base_branch: main
```

Для новой БД используйте явный bootstrap; существующие БД не инициализируйте заново:

```sh
codex-dispatcher db bootstrap
codex-dispatcher init-labels
codex-dispatcher run --once
codex-dispatcher run
```

`run` работает в foreground. Из другого терминала:

```sh
codex-dispatcher status
codex-dispatcher queue
codex-dispatcher stop
```

Штатная остановка ждет выполняющуюся работу; `stop --force` — принудительная остановка. Также поддерживается Ctrl+C в foreground. Пример другого файла: `codex-dispatcher --config /home/alice/test.yaml run --once`. Для подробных CLI/DB/recovery-команд смотрите README и `--help`.

Начиная с реализации V2.5.3, перед каждым `run` выполняется ограниченная тайм-аутом проверка последнего стабильного релиза. При сбое проверки выводится предупреждение, запуск продолжается без запроса подтверждения. `queue` и `status` эту сеть не используют. Для Ubuntu Server доступна [пользовательская служба](v2.5.3-ubuntu-service.md).

## Обновление и схема

Остановите runtime и дождитесь завершения, затем выполните `codex-dispatcher-install` без активации venv. Установщик проверяет штатные locks/control socket и удерживает runtime-блокировки во время переключения. При активном или неопределенном состоянии отказывает; PID сам по себе не является доказательством остановки.

При схеме 1 обновляется только `dispatcher_version`; проекты, пути и комментарии сохраняются. Для отсутствующей/неверной/новой схемы основной файл сохраняется, создается `config.new.yaml`. Существующий новый файл заменяется только после отдельного вопроса. Сравните оба файла, вручную перенесите свои настройки в новый шаблон, сохраните резервную копию старого, затем замените основной файл. Проверьте `dispatcher.root_path`, проекты, labels и схему. Старые конфиги автоматически совместимыми не считаются. Изменяющие команды блокируются до согласования; `--help`, остановка и диагностическое чтение доступны. При поврежденной структуре основного YAML установщик может отказать, поскольку не может доказать остановку runtime: сначала восстановите корректные пути вручную.

`codex-dispatcher --version` выводит `Codex Dispatcher 2.5.2.post2` из metadata пакета без YAML, SQLite, сети и runtime. При отсутствии metadata возвращается понятная ошибка. Версия пакета берется из metadata venv, а `dispatcher_version` — только метка YAML. После смены схемы они могут различаться. Повторная установка той же версии не выполняет миграцию: завершите ручное согласование уже созданного файла.

## Диагностика и удаление

При отказе проверьте PATH, Python, `gh auth status`, `codex login status`, доступ к API, путь XDG и `--config`, `config_schema_version`, `db check`, `status`. Не стирайте lock-файлы у работающего runtime. При ошибке установки успех не выводится; старая генерация и пользовательские данные сохраняются. Поврежденный YAML или неоднозначная принадлежность файлов требуют ручного разбора.

Для установки со службой V2.5.3 сначала выполните `codex-dispatcher service uninstall`. После штатной остановки:

```sh
codex-dispatcher-uninstall
```

Перед удалением выводится версия и предупреждение о сохранении данных, затем `Proceed with uninstall? [y/N]:`. Только `y` (регистр и окружающие пробелы не учитываются) разрешает удаление. `n`, Enter, EOF и Ctrl+C отменяют операцию с кодом 0. Без TTY — ненулевой код без ожидания; активный daemon вызывает отказ до вопроса. Флага обхода подтверждения нет.

Удаляются помеченные установщиком поколения venv, установленные скрипты установки/удаления, три ссылки команд и ownership-маркер. Пустой `.standalone-install.lock` сохраняется: удаление его inode создало бы гонку между параллельными установщиками. Конфигурация, SQLite, workspace/worktrees, репозитории и credentials сохраняются; весь `~/codex-dispatcher` не удаляется. Для запуска скриптов требуется Python и доступ к зависимостям bootstrap. Публикация описана в [регламенте](releasing.md).
