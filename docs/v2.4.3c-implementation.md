# V2.4.3.C — безопасный локальный purge

Destructive `project remove ID --purge` реализован. Ожидается ручная приёмка;
PR/merge не выполняются. Ветка `V2_4_3_CLI_MONITORING`.

Изменены `src/dispatcher/purge.py`, CLI-маршрут `__main__.py`, добавлены
`tests/test_purge.py`, актуализированы два прежних inventory-теста и документация.
Схема, обычные Recovery API, DB Guard, InstanceLock, Scheduler и Poll не менялись.
Коммит реализации и тестов: `76cfb9c`
(`Implement guarded local project purge with transactional Recovery cleanup`).
Документация зафиксирована следующим отдельным коммитом этой же ветки.

## Фактический алгоритм

Dry-run читает приватный main+WAL snapshot через существующий DB Guard inspection.
Проверяет schema/UUID/workspace/integrity/FK, точные определения Recovery triggers,
Recovery barrier, глобальные незавершённые executions, операции и quarantine.
Показывает rowid всех кандидатов, счётчики, изменения summary, пути/хеши файлов,
локальные refs/OID и worktree, причины отказа и состояние прошлых попыток.
Исходная SQLite и sidecars не открываются на запись. Git-команды только локальные
читающие; при отсутствии checkout subprocess вообще не нужен. Lockfiles, backup
и новые каталоги не создаются. Для локальных Git-команд задан
`GIT_OPTIONAL_LOCKS=0`, чтобы git status не переписывал index при dry-run.

Destructive запуск сначала выводит тот же план и требует полный project.id в TTY.
Неправильный ID, EOF и non-TTY не создают файлов. Затем получает штатный InstanceLock
(оба lock, наследуемые Executor), проверяет DB Guard execution admission и quiescent,
повторяет/сравнивает весь план, включая fingerprint содержимого рабочих таблиц.
Отдельный YAML edit lock защищает конфигурацию; её полная загруженная модель должна
совпасть. Проверяются пересечения managed roots с DB, workspace, backup и YAML.

Backup создаётся существующим SQLite Backup API, затем проверяется DB Guard и
привязка UUID. Файл имеет 0600, каталог `<root_path>/backups/purge/` — 0700.
Имя `<UTC timestamp>-<project ID>-<uuid>.sqlite`; журнал `<project ID>.json` — 0600.
Журнал заменяется атомарно с fsync файла/каталога, содержит исходный YAML,
instance UUID, полный план, backup path и фазу.

На выделенном writable соединении с `foreign_keys=ON` выполняется `BEGIN IMMEDIATE`.
Повторно проверяются metadata/admission, определения триггеров и fingerprint.
Только `recovery_events_no_update` и `recovery_events_no_delete` снимаются.
Общие summary обновляются; DELETE идут в порядке:

1. recovery_events, recovery_execution_archive, recovery_approval_reset;
2. recovery_quarantine, recovery_operations;
3. error_log, state_history, pull_requests, executions, debug_operations;
4. issue_relations (обе стороны), issues, recovery_sessions.

Каждая таблица удаляется одним SQL statement: это сохраняет корректность self-FK
внутри execution groups/corrections. `debug_operations.repository` учитывается
без issue_id. Recovery events выбираются по issue_id, operation_id и доказанной
принадлежности session/details. Смешанные identity блокируются.
Триггеры создаются точными исходными SQL из schema.sql. До COMMIT проверяются
FK, integrity_check, остаточные ссылки, все неизменяемые чужие строки и схема.
На любом исключении (включая KeyboardInterrupt) ROLLBACK возвращает данные и DDL.
После COMMIT повторяются schema/integrity/FK/trigger checks.

## Shared sessions и JSON

В текущем Recovery summary — массив `{issue_id,reasons,target}`; также поддержан
обогащённый формат с repository/issue_number. Общая сессия сохраняется: удаляются
только свои элементы, проверяются и пересчитываются checked/quarantined counters.
Неизвестные форматы, противоречащие identity и неустранимые ссылки дают конкретный
blocker. Чисто проектная сессия удаляется; её события без прямого issue/operation
допустимо удалить только при доказанной полностью проектной summary.

Поиск repository выполняется также в текстовых/JSON значениях чужих строк и
служебных metadata. Project ID считается ссылкой в ключах project/project_id,
а не при совпадении с обычным словом. Чужие строки с такими ссылками не удаляются:
они блокируют операцию. Глобальные metadata и schema_migrations сохраняются; текстовые ссылки в них
также проверяются и при неоднозначности блокируют операцию.
Runtime poll diagnostics JSONL очищаются построчно по authoritative context.repository;
остальные строки сохраняются байт-в-байт. Неоднозначная диагностика блокирует purge.

## Git, файлы и фазы

Managed checkout допускается только по стандартному пути workspace/repos/ID,
с ожидаемым origin, самостоятельным .git и чистым status, включая ignored files.
Проверяются все worktree и локальные ветки; посторонние объекты блокируют purge.
Worktree должен лежать непосредственно в workspace/worktrees/ID, иметь имя
`e-<execution ID>-<32 hex>` и соответствующую ветку
`refs/heads/dispatcher-v2/<execution ID>-<32 hex>`. Это позволяет найти также
сиротские managed worktree. Внутренние orphan refs допускаются только с той же
служебной грамматикой в доказанно изолированном checkout. Помимо внутренних веток
разрешена только base branch. Внешний checkout всегда сохраняется и блокирует purge.
Общие/пересекающиеся configured paths, symlinks и dirty worktree запрещены.

После SQL COMMIT выполняются локальные `git worktree remove` без force и
`git update-ref -d REF EXPECTED_OID`. Затем удаляются результаты актуальных и
архивных executions, очищаются diagnostics, пустая project worktree area и
изолированный managed checkout. Результаты проверяются по SHA256, HEAD/status
worktree проверяются повторно. Пользовательские remote refs не меняются:
нет fetch/push/ls-remote/clone или GitHub API. Базовая/remote история на сервере
сохраняется. Неидентифицируемый orphan result блокирует удаление вместо угадывания.

Фазы журнала: backup → database-intent → database-committed → files-removed →
yaml-intent → yaml-removed. При падении в database-intent нельзя полагаться только
на запись фазы: COMMIT мог уже завершиться. Выбран безопасный путь восстановления,
а не автоматическое продолжение с предположениями о внешнем состоянии.

После удаления файлов повторно проверяются SQLite, остаточные ссылки и артефакты.
Только затем атомарно удаляется project из YAML. После чтения итогового YAML и
DB Guard проверки temporary backup и журнал удаляются, каталог fsync.

```text
PASS purge: 15 database rows, 2 results, 1 worktrees; temporary backup removed
FAIL purge phase=database-committed; backup preserved: /root/backups/purge/...sqlite; journal: /root/backups/purge/p.json. ...
```

## Ошибки и безопасная повторная попытка

При ошибке команда сохраняет snapshot/журнал, сообщает фазу и оба пути.
Следующий dry-run/запуск показывает старые файлы и результаты проверки backup;
новый snapshot не создаётся. Даже если YAML уже удалён, журнал обнаруживается по ID.
Никакие старые failed backups не удаляются автоматически.

Остановить daemon. Проверить журнал, сопоставить plan с оставшимися файлами/refs.
Если YAML уже удалён/повреждён — восстановить его из journal.original_config.
Выполнить штатный `db restore BACKUP` для того же экземпляра, затем штатную Recovery
reconciliation. Она может потребовать пользовательского решения по исчезнувшим
worktree/results; SQLite backup не является файловым backup. Нельзя обходить
quarantine или обнулять barrier вручную. После успешной reconciliation явно
перенести файлы failed попытки в собственный архив вне backups/purge, сохранить
доступность исходного snapshot и повторить dry-run/purge. Этот архив — явный выбор
пользователя, автоматическая временная копия новой успешной попытки удаляется.

Если crash произошёл после создания backup, но до записи журнала, backup остаётся
видимым при повторном запуске; разрушение ещё не начиналось. Crash после удаления
backup может оставить один журнал: он тоже блокирует новые действия до проверки.
Файловая система/Git/SQLite не образуют общую транзакцию. Журнал нужен для
диагностики и восстановления, а не для обещания автоматического возврата файлов.

## Ручная приёмка

1. Использовать отдельный приватный root_path и тестовый конфиг. Создать два
   проекта Playground и Control, db bootstrap/check. Сохранить явный db backup
   и копию файлов вне managed roots. Не использовать production данные.
2. Подготовить историю обоих проектов с одинаковыми Issue numbers, завершёнными
   executions/PR, результатами и общими Recovery sessions. Сохранить строки Control,
   refs, файлы и контрольные хеши. Остановить daemon штатно, убедиться в STOPPED.
3. Выполнить `project remove Playground --purge --dry-run`. Сверить кандидатов,
   summary updates, counts, SHA256 и refs/OID. Сравнить DB/WAL/SHM и дерево файлов:
   dry-run не должен ничего создавать или менять. Устранить blockers штатно.
4. Проверить отказ из pipe, wrong ID и EOF: backup отсутствует, YAML/DB неизменны.
   Отдельно проверить работающий daemon и dirty worktree; после штатного stop и
   сохранения пользовательских изменений снова проверить план.
5. Запустить purge в TTY, ввести полный ID. Ожидать PASS и temporary backup removed.
   Проверить отсутствие project в YAML, project-scoped строк/summary/results/trees,
   temporary backup/journal. Выполнить db check, integrity_check/foreign_key_check
   read-only инструментом; убедиться в наличии обоих triggers.
6. Сверить Control: неизменность его строк, событий, файлов и refs, допустимое
   сокращение общей summary только на элементы Playground. GitHub Issue/PR/labels,
   comments и серверные branches должны быть неизменны.
7. На отдельном одноразовом экземпляре выполнить fault injection через
   `execute(..., checkpoint=...)`: drop/delete/create, database-committed,
   worktree/ref/result/diagnostic/files-removed/yaml-intent/yaml-removed. Для каждого
   сбоя проверить FAIL, backup 0600, журнал 0600, каталог 0700 и db check snapshot.
   SQL-инъекции должны вернуть триггеры/строки; поздние фазы могут оставить уже
   удалённые ресурсы, перечисленные исходным планом.
8. Повторить dry-run/команду после сбоя: ожидать показ backup, phase и блокировку
   без новой копии, в том числе после YAML commit. Выполнить описанное выше
   восстановление с штатной Recovery, явно архивировать failed attempt и повторить.
9. После успешного purge выполнить project add того же repository с прежним либо
   новым ID (эта отдельная команда делает обычные удалённые read-only проверки).
   Проверить отсутствие retained-history конфликта. Rediscovery открытых ready
   Issue проверять штатным Poll после осознанного запуска daemon.
10. Обычный project remove проверить отдельно: он удаляет только YAML, история
    и файлы сохраняются; retained-history admission снова запрещает add.
