## 3. Задача B — `db restore` при исторической незавершённой записи

Сегодня `src/dispatcher/db_guard.py` блокирует `restore` при **любой** текущей записи `executions.status IN ('reserved','preparing','executing','publishing')`, выдавая `Executor stop cannot be proven`, даже если процесс остановлен. SQLite отражает историческое состояние и не является прямым доказательством живого исполнителя.

**Требуемое изменение контракта:**
- При наличии действительно активного диспетчера, живого дочернего исполнителя или недоказанной остановки — `restore` обязан отказать.
- При полностью доказанной остановке, даже если SQLite ещё содержит `preparing/running` и активный технический execution status, `restore` разрешён, не требует прежде исправлять исторические строки и не удаляет местные рабочие артефакты.
- Обязательны существующие эксклюзивные lock-файлы, защита дочерним процессом наследуемых файловых блокировок, политика control socket, WAL/SHM, строгий UUID/DDL/integrity, проверенный `before-restore` backup и atomic replace. После восстановления — `recovery_required=1`.
- **Ключевой критерий безопасности:** не считать только `InstanceLock` доказательством отсутствия произвольного некооперирующегося процесса. Признать и документировать границы доказательства; если предусмотренные механизмы остановки не дают достоверного вывода, отказать с диагностикой, а не стирать БД.
- Не ослаблять отказ для текущей неверной/повреждённой SQLite; не разрешать неизвестный UUID или несовместимую схему. Не менять реальные worktree/ветки при restore.
- Сохранить все гарантии V2.4.1 для корректного backup, чужого backup, повреждённого backup, до/после restore snapshots.

### Случай артефактов, появившихся после восстанавливаемого backup

После установки старой БД могут остаться локальные worktree/refs от исполнений, отсутствующих в backup. Recovery обязан **не запускать Codex и не удалять такие артефакты**. Требуется согласованный fail-closed контракт: либо безопасно связать их с известным контекстом и изолировать без восстановления неизвестной истории, либо оставить глобальный recovery_required=1 и выдать диагностическую рекомендацию. Не разрешать общее снятие барьера, если локальная принадлежность и полнота наблюдений не доказаны. Не вводить «автоматическую очистку неизвестного».

Сначала установить, способен ли текущий `Recovery.collect` корректно обработать такой случай без регрессий; при необходимости минимальная корректировка с тестами. Не создавать новую бизнес-модель без согласования.

## 4. Задача C — воспроизводимые тесты

Автоматические тесты на отдельной временной SQLite/Git, без GitHub и настоящего Codex:
- 2 и 3 worktree, наличие локальных изменений, `--porcelain -z`, стабильное перечисление и отсутствие скрытых записей;
- несовпадающие path/branch/HEAD, чужой каталог, symlink, prunable/locked worktree → fail closed;
- положительный безопасный cleanup только при всех доказательствах принадлежности;
- stopped `preparing` и stopped `executing`/running запись в текущей БД → допускается `db restore` после проверенной остановки, `before-restore` сохранён и recovery_required=1;
- живой daemon/worker c inherited lock, конфликт lock, оставшийся control socket, WAL/SHM, неизвестный executor → отказ, текущая SQLite сохранена;
- corrupted/foreign backup → отказ, до/после состояние не повреждено;
- восстановление снимка, не содержащего более нового локального worktree → нет опасных побочных действий; `db recover` отказывает безопасно или изолирует только если доказательств хватает;
- повторный `db restore` и `db recover`, fault-injection до atomic replace;
- полная регрессия V2.4.1/V2.4.2.

## 6. Критерии приёмки

1. Два корректно зарегистрированных worktree не пропадают из адаптера по причине дефекта кода; при недоказанном состоянии очистка не выполняется.
2. `db restore` может восстановить зарегистрированный backup поверх остановленного диспетчера с историческим `preparing`, не требуя произвольной SQL-очистки.
3. Активные исполнители и неизвестные условия остановки по-прежнему блокируют restore.
4. После restore всегда стоит глобальный recovery barrier, неизвестные локальные результаты не затронуты.
5. Все тесты зелёные; пользовательская Issue #42 и её worktree оставлены нетронутыми агентом.
