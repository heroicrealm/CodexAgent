# V2.4.1 implementation

Исследование до изменений: V2.3, schema_migrations.version=1; таблицы
schema_migrations, issues, issue_relations, executions, pull_requests,
state_history, error_log, debug_operations; точный DDL в src/dispatcher/schema.sql.
Storage.__init__ создавал отсутствующую/пустую SQLite, каталоги и WAL.
Открытия: Runtime, worktree-cleanup, Cleanup.orphans, Storage.connection и
Storage._readonly. InstanceLock использует два flock (БД и workspace), дескрипторы
наследует Codex. Инициализация отдельной команды не имела.

Инварианты перехода: точное сравнение старого DDL, quick_check и FK до записи;
backup API до регистрации; исходные issue/execution не изменять. Metadata —
отдельная singleton-таблица с format_version, instance_id UUID, recovery_required.
Workspace содержит приватный маркер UUID, независимый от проектов и абсолютного
пути. Перенос допускается явным db bind после проверки UUID. Restore сохраняет
UUID и устанавливает recovery_required=1 до атомарной замены. Автоматического
снятия барьера нет: надёжная сверка GitHub/worktree/процессов — V2.4.2.

## Реализованные изменения

- `src/dispatcher/db_guard.py`: проверка приватной копии main+WAL (исходник
  не открывается SQLite), точный DDL, quick_check, FK, известные state, связи
  repository/group/PR/execution, уникальность нормализованного repository/number,
  UUID и metadata format_version=1. PASS/WARN/FAIL через CLI.
- `storage.py`: создание только через явный bootstrap с O_EXCL; обычное открытие
  требует существующий файл, 0600, без symlink. Соединение записи использует
  mode=rw и проверяет recovery barrier до изменений. Схема V2.3 не переписана.
- `__main__.py`: db bootstrap/register/bind/check/backup/restore. Stop доступен
  даже при повреждении SQLite, чтобы пользователь мог остановить службу.
- `runtime.py`, `services.py`, `execution.py`, `cleanup.py`: предварительная
  проверка до внешних действий, repository вместо project.id, исключение
  отключённых/удалённых проектов, успешный poll перед выбором новых задач.
- `config.py`, `github.py`: регистронезависимые owner/name, enabled boolean.
- `locking.py`, `tools/worktree_cleanup.py`: запрет symlink lock, повторная
  проверка допуска перед maintenance с изменениями.
- `README.md`: чистая установка, регистрация V2.3, перенос, backup, restore,
  аварийная файловая копия и матрица отказов.

Metadata создаётся в явной транзакции. Регистрация сначала резервирует V2.3;
никакие issues, executions, snapshots, lifecycle или project_id не переписываются.
Таблица schema_migrations сохраняет version=1; версия guard хранится отдельно.
Если запись маркера невозможна, транзакция metadata откатывается. Обрыв между
записью маркера и commit требует диагностики; выполнение при несовпадении блокируется.

Backup использует SQLite Connection.backup, O_EXCL destination, проверку результата,
0600 и fsync файла. Валидация backup не полагается на расширение файла.
Restore проверяет источник и текущую identity, удерживает обе flock, отказывает
при control socket, активных executions и исходных WAL/SHM; сохраняет archive,
использует каталог staging 0700 на той же FS, устанавливает recovery_required=1,
проверяет staging, делает os.replace и fsync каталога. Пустые sidecar, созданные
самим архивным read-only backup после доказанной остановки, удаляются до замены;
появление непустого WAL вызывает отказ. Ошибка до replace сохраняет основной файл.

## Открытые ограничения / блокеры

1. Restore поверх отсутствующей, повреждённой или логически неопределённой текущей
   БД не поддержан: невозможно доказать отсутствие связанных исполнителей по
   недоступному состоянию. Небезопасного force-обхода нет (раздел 11 ТЗ).
2. V2.4.1 не реализует внешний recovery-admission. После любого restore остаётся
   постоянный барьер до отдельной проверяемой процедуры V2.4.2. Нет команды resume,
   автоматического rebuild или ручного утверждения «всё сверено».
3. Check работает с временной копией. При конкурентном изменении main/WAL возможен
   отказ на несогласованном наборе; повторять после остановки. PASS не удостоверяет
   состояние GitHub, контейнеров или worktree и не гарантирует актуальность snapshot.
4. Кооперативные flock защищают daemon и наследующих дескрипторы исполнителей.
   Внешние инструменты не должны подменять/изменять файлы SQLite во время maintenance.
   Клонированный вместе с marker UUID не отличим от оригинального экземпляра.
5. Fault injection покрывает исключение до atomic replace. Настоящий power-loss,
   отказ диска/fsync и чужие detached-процессы не эмулируются; гарантий их полного
   восстановления нет. После replace ошибка fsync не выдаёт успех и archive остаётся.
6. Pre-registration archive намеренно содержит точную старую схему без UUID и не
   принимается db restore как зарегистрированный снимок. Он нужен для сохранения
   исходного V2.3 состояния и расследования перехода.
7. Поддержка V1, восстановление GitHub и миграция неизвестных схем не добавлены.
