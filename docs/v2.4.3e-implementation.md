# V2.4.3.E — заключительные исправления

Ветка `V2_4_3_CLI_MONITORING`. Реализованы BUG-03, UI-08, UI-09.
PR и merge не выполняются; после push ожидается ручная приёмка.

## Изменения и безопасность

`src/dispatcher/purge.py`: специализированные `control_admission()` и
`removal_quiescent()` используются только удалением проекта. Общая
`db_guard.quiescent()` не изменена: restore/upgrade продолжают отвергать любой
socket. Recovery admission, UUID/schema/FK/triggers, fingerprint, ownership,
транзакция SQL, backup, фазовый журнал и порядок SQLite → Git/files → YAML
сохранены. Scheduler/Poll/GitHub/lifecycle/схема не менялись.

План и execute применяют одну control admission. Проверяется штатный абсолютный
путь `.control.sock`, без symlink в любом компоненте. Существующая monitor
metadata должна быть читаемым JSON-объектом с положительным целым PID;
`kill(pid, 0)` должен доказать отсутствие PID. Живой PID, включая PID reuse
с другим starttime, и неопределённость блокируют операцию даже при свободных lock.
Отсутствие metadata допустимо: эксклюзивные lock исключают штатный dispatcher
и наследующих дескрипторы детей. Давность heartbeat не даёт разрешения.

Если socket существует, необходимы одновременно:

- Тип UNIX socket и UID текущего пользователя.
- Connect с ограниченным timeout возвращает именно ECONNREFUSED. ENOENT во время
  probe, timeout, permission errors и прочая неопределённость означают отказ.
- В читаемом Linux `/proc/net/unix` отсутствует bound socket с этим путём.
  Это исключает также живого владельца между bind и listen, когда connect уже
  возвращает ECONNREFUSED. Недоступность kernel evidence блокирует stale admission.
- До/после probe совпадают dev, inode, mode, uid, ctime_ns filesystem entry.
  Идентичность входит в точный план и повторно сверяется после подтверждения.

Dry-run не создаёт каталогов/lockfiles/backup, не изменяет socket/YAML/SQLite/Git.
После точного project.id в TTY execute получает **оба** штатных исключительных
InstanceLock, повторяет DB/admission/sidecar проверки и сверяет план. Lock
удерживаются до завершения. Занятый или унаследованный lock исключает удаление.
При повторном plan под собственными lock игнорируется только ожидаемый daemon
blocker; остальные проверки и точное сравнение сохранены.

**Socket не удаляется и не переименовывается вообще.** Поэтому нет unlink TOCTOU,
который мог бы удалить подменённый socket живого сервера. Новый штатный daemon не
может стартовать во время удаления из-за обоих lock. При обычном последующем run
действует существующий механизм работы с socket. Активный listener без lock тоже
блокирует admission; подмена socket во время probe или подтверждения отказывает
до backup. Сторонние процессы, игнорирующие InstanceLock, не входят в протокол
совместного доступа к БД; исключительного владения через один socket не заявляем.
WAL/SHM, незавершённые executions, Recovery/quarantine остаются блокерами.

`src/dispatcher/monitoring_output.py`: публикации в `show -v` — Yes/No/N/A,
включая отсутствующий ключ; exit code и другие числа не преобразуются.
JSON сохраняет исходные типы, значения и структуру.

Единый `render_removal_plan()` используется dry-run и destructive-командой
(`src/dispatcher/__main__.py`, `purge.py`). Это только представление, без изменения
точного плана. В stdout нет rowid, SQL, fingerprint, metadata, UUID и JSON.
Blockers показываются полностью, пользовательские строки — Rich Text literals.
Показываются счётчики, наличие managed checkout, Database/Recovery/Daemon и Ready.
Необязательный `remove --json` не добавлялся; подтверждение обойти нельзя.

## Пример human-плана

```text
PROJECT REMOVAL · cap
Repository: heroicrealm/codexagentplayground
Mode: DRY RUN
Daemon: STOPPED
Database: OK
Recovery: READY
Ready: YES

Local data to delete | Count
SQLite records      | 11
Codex results       | 1
Managed worktrees   | 0
Local branches      | 1
Managed checkout    | Yes
Diagnostic files    | 0
Blockers: none
Stale control socket: verified leftover; preserved under instance locks.
WARNING: This permanently deletes ALL local project data.
GitHub Issues, PRs and remote branches are not modified.
```

Для реального удаления Mode: PERMANENT REMOVAL и обязательный запрос
`Type full project.id (cap) to permanently purge local history:`.
Неверный ID, EOF, Ctrl+C, non-TTY отказывают без backup и удаления данных.
Успех сообщает количество SQLite rows/results/worktrees и
`temporary backup removed`. При позднем сбое сохранены точные пути backup/journal.

## Повторная ручная приёмка

1. В отдельном тестовом root подготовить проект cap и контрольный проект,
   сохранить явные backup и нужные файлы вне managed roots. Остановить daemon
   и убедиться в отсутствии Executor; использовать оставшийся после crash socket.
2. `status`: STOPPED; `stop`: control unavailable без traceback.
   `project remove cap --dry-run`: компактная карточка, правильные counts,
   Ready YES, stale socket preserved. Сверить неизменность YAML/DB/Git/socket,
   отсутствие новых backup/каталогов. Повторить на ширине 80/120 и с NO_COLOR/pipe.
3. `project remove cap`: сверить тот же план, ввести ровно `cap` в TTY.
   Ожидать PASS и temporary backup removed. Socket должен остаться.
   Проверить очищенные данные cap, неизменность контрольного проекта/GitHub.
4. `db check`: PASS; повторный `project add cap owner/repo` должен пройти
   штатные проверки. `show cap NUMBER -v`: публикации Yes/No, отсутствующие N/A,
   exit code 0 остаётся 0. JSON сохраняет 1/0/null и исходные timestamps.
5. До удаления также проверить безопасный отказ на неверный ID/EOF/pipe,
   живой daemon/Executor, Recovery barrier, WAL/SHM и unsafe Git ownership.
   Не обходить блокеры удалением lock/socket вручную. После поздней ошибки
   использовать прежнюю инструкцию восстановления из backup/journal V2.4.3.D.

Live GitHub/Codex и пользовательская ручная приёмка не выполнялись.
Stale admission зависит от Linux `/proc/net/unix`; при недоступности — отказ.
Как прежде, SQLite/Git/files/YAML не образуют общей атомарной транзакции;
после позднего сбоя требуется штатное восстановление. SQLite backup не
восстанавливает удалённые Git/files. PR и merge ожидают отдельного разрешения.
