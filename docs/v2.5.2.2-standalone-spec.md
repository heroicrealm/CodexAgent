# Техническое задание V2.5.2.2 — завершение поставки Standalone

**Репозиторий:** `heroicrealm/CodexAgent`  
**Основание:** `V2_5_2_1_WSL_DISTRIBUTION`  
**Рабочая ветка:** `V2_5_2_2_STANDALONE_IMPROVEMENTS`  
**Статус:** согласовано для реализации, до ручной приемки  
**Дата:** 2026-11-16

## 1. Назначение

Завершить улучшения Standalone (Ubuntu native и WSL2, без systemd): постоянная команда установки, проверка актуальности самого установщика по SHA-256 **без самоизменения и без автоматического запуска скачанного установщика**, команда просмотра версии диспетчера и подтверждение перед удалением.

Программа остается совместимой с пакетной поставкой `2.5.2.post1`, жизненный цикл Issue/PR, scheduler, SQLite и модель конфигурации не меняются.

## 2. Версии и границы

| Компонент | Значение |
|---|---|
| Этап | V2.5.2.2 |
| Версия дистрибутива `codex-dispatcher-v2` | `2.5.2.post2` |
| Release tag | `v2.5.2.post2` |
| `dispatcher_version` в шаблоне | `"2.5.2.post2"` |
| `config_schema_version` | `1` |
| Тип поставки | Standalone |

В `pyproject.toml`, шаблоне, smoke-тестах, названии wheel, release notes и регламенте публикации версии должны совпадать. Тег и стабильный Release агент **не публикует** без отдельного разрешения.

Не входят: самообновление/перезапуск установщика, сервис systemd (отдельная V2.5.3), Docker, миграция конфигурации, обработка сетевых сбоев во время работы, обновление самой программы без согласия пользователя.

## 3. Подтвержденная база реализации

В V2.5.2.1:
- Пакет `codex-dispatcher-v2` версии `2.5.2.post1`, CLI в `src/dispatcher/__main__.py`, глобальный `--config-schema-version`; `--version` пока нет.
- Общий исходник встроенных установочного и удаляющего скриптов: `scripts/standalone_distribution.py`, генератор `scripts/embed-standalone.py`; два итоговых скрипта `install-standalone.sh` и `uninstall-standalone.sh`.
- Установщик выбирает `/repos/heroicrealm/CodexAgent/releases/latest`, получает `SHA256SUMS` и assets, проверяет wheel, шаблон и удалитель, переключает поколения `venv`, поддерживает ownership-маркер и lock.
- `~/.local/bin/codex-dispatcher` и `~/.local/bin/codex-dispatcher-uninstall`; удалитель находится в активном принадлежащем поколении `venv`.
- Конфиг: `$XDG_CONFIG_HOME/codex-dispatcher/config.yaml` при абсолютном `XDG_CONFIG_HOME`, иначе `~/.config/codex-dispatcher/config.yaml`; внутри `dispatcher.root_path` абсолютный. Совместимое обновление меняет только `dispatcher_version`.
- Существующий удалитель блокирует удаление при работающем диспетчере, но не требует подтверждения; команда установки не размещается в `~/.local/bin`.

Доработки не должны ломать существующие ownership, locking, XDG, защиту пользовательских данных, поддержку WSL2/Ubuntu native.

## 4. Постоянная команда установки

После **первоначальной установки новой версии** и после **обновления** должна существовать:

```bash
codex-dispatcher-install
```

Ожидаемый путь: `~/.local/bin/codex-dispatcher-install`. Она использует фактически установленный и контролируемый установщиком скрипт, а не случайный файл из CWD. Рекомендуется хранить экземпляр скрипта в каждом собственном поколении `venv` и адресовать через активную `~/codex-dispatcher/.venv`, аналогично доставленному удалителю. Допускается другое решение с эквивалентной атомарностью и ownership-защитой.

Требования:
1. Installer script текущего Release должен скачиваться как отдельный asset из **того же релиза**, что и wheel, шаблон и удалитель; проверять SHA-256 до установки.
2. Исполняемая копия и короткая команда создаются только после успешной подготовки и в контролируемом installer namespace; обновляются вместе с переключением поколения.
3. Чужие файлы/символические ссылки с именем `codex-dispatcher-install` не заменяются.
4. При ошибке установка/обновление не должны оставлять битую или чужую ссылку; rollback возвращает прежний работающий установщик и пакет.
5. При удалении удалить только собственную ссылку и собственный установленный скрипт, сохранив данные пользователя; временные/общие lock-файлы не удалять небезопасно.
6. Если пакет уже актуален, повторный запуск не должен портить установку и должен по контракту восстанавливать недостающие собственные управляемые ссылки только после подтверждения их принадлежности.

### 4.1. Проверка актуальности самого установщика

При запуске `install-standalone.sh` или `codex-dispatcher-install`:
1. До изменения установленного пакета, YAML, поколения `venv`, ссылок и ownership-маркера получить метаданные последнего **стабильного** GitHub Release.
2. Получить опубликованный SHA-256 asset `install-standalone.sh` из релиза (из валидированного `SHA256SUMS`, с уже применяемым контролем GitHub asset digest при наличии). Проверить, что контрольная сумма присутствует и корректна.
3. Посчитать SHA-256 **реальных байтов выполняемого скрипта**. Если команда является symlink, разыменовать только подтвержденную собственную ссылку. Не путать SHA ссылки и SHA ее целевого файла.
4. При полном совпадении — продолжить обычную установку/обновление (с прежним подтверждением установки пакета).
5. При несовпадении — вывести понятное предупреждение, номер/ссылку релиза, инструкцию скачать свежий `install-standalone.sh`, проверить его SHA-256 и запустить заново. Завершить с ненулевым кодом **без изменения установленной программы и пользовательских данных**.
6. Если API, manifest, digest или checksum недоступны/ошибочны — отказать без изменения установки, не пропускать проверку.
7. Если установленная версия уже равна версии релиза, правило проверки SHA всё равно действует: нельзя завершиться по ранней проверке равенства версий до проверки самого установщика.

Не загружать/исполнять новый установщик вместо старого; не переписывать текущий выполняющийся файл. Допускается скачать manifest и проверить данные для сравнения, но никакой автоматической замены. Проверка должна применяться и при первой установке, и при повторной.

**Существенное уточнение:** SHA-256 сравнивает **байты**, а не формальную версию установщика. Изменение даже комментария в опубликованном скрипте будет требовать его обновления — это сознательно принятое правило. Все файлы релиза неизменны после публикации.

### 4.2. Первое включение механизма

В версиях 2.5.2 / 2.5.2.post1 ещё нет проверки SHA собственного файла и команды `codex-dispatcher-install`. Переход на V2.5.2.2 требует **одного ручного получения свежего `install-standalone.sh`**; новая поставка уже должна обеспечивать постоянную команду.

Требование проверки SHA нового скрипта на первом шаге не должно незаметно зависеть от версии старого установщика. В руководстве дать прямой способ скачать скрипт и `SHA256SUMS` из **одного конкретного Release** и проверить целостность до запуска.

## 5. Команда `codex-dispatcher --version`

Добавить глобальный аргумент:

```bash
codex-dispatcher --version
```

Пример результата:

```text
Codex Dispatcher 2.5.2.post2
```

Версия определяется из метаданных установленного дистрибутива `codex-dispatcher-v2` (`importlib.metadata.version`), а не из YAML. Аргумент должен завершаться кодом 0, работать без `config.yaml`, SQLite, GitHub и daemon, не запускать сетевые проверки и не изменять состояние. Формат должен быть стабильным; при отсутствии метаданных — понятная ошибка без ложной версии. Существующие `--help`, `--config-schema-version` и подкоманды остаются работоспособными.

## 6. Подтверждение удаления

При выполнении `codex-dispatcher-uninstall` или `sh uninstall-standalone.sh`:

1. Сохранить существующие проверки принадлежности, конкуренции, остановленного runtime и защиты пользовательских каталогов.
2. После доказательства допустимости удаления и **до первого необратимого удаления** вывести предупреждение с версией и явно указать, что сама программа будет удалена, а конфиг, SQLite, workspace/worktrees, репозитории, авторизация сохранятся.
3. Спросить: `Proceed with uninstall? [y/N]:`.
4. Только явный ответ `y` (без учета регистра после удаления пробелов) разрешает удаление.
5. `n`, пустой ответ, EOF, Ctrl+C → отмена без изменения; без TTY → отказ без ожидания ввода и без удаления.
6. При активном диспетчере отказать по действующим правилам без предложения удаления; не запускать автоматическую остановку.
7. Не добавлять `--yes`/`--force` для обхода подтверждения в V2.5.2.2.
8. Подтверждение должно сохранять ownership/installer lock на время операции, не создавать гонок между вопросом и удалением.

При отказе пользователя можно завершать с кодом 0 как сознательно отмененную операцию либо с заранее определенным ненулевым кодом; выбрать один контракт и зафиксировать его тестом и документацией. При отсутствии TTY — ненулевой код обязателен.

## 7. Автотесты

Добавить/обновить тесты без реального GitHub и без пользовательских credentials:
- `--version`: корректная версия, отсутствие конфигурации и SQLite, отсутствие сетевых обращений, независимость от `dispatcher_version`.
- SHA установленного и скачанного установщика: совпадает, различается, отсутствует в manifest, неверный digest, отказ API/сети, symlink, ранний выход при актуальной версии, несущественное изменение байтов.
- При SHA mismatch никакие данные/links/venv/SQLite/YAML/ownership не меняются; нет автоматической загрузки-исполнения нового скрипта.
- Первичная/повторная установка `codex-dispatcher-install`, переход 2.5.2.post1 → 2.5.2.post2, инварианты при rollback, конфликты с чужими путями.
- Удаление после подтверждения, отказ `n`/Enter/Ctrl+C/EOF/non-TTY, блокировка при runtime RUNNING, сохранение пользовательских файлов.
- Совместимость с существующими `codex-dispatcher`, `codex-dispatcher-uninstall`, `run`, XDG, config schema 1, `db check`, `queue`, `status`, тесты Issue/PR.

В `.github/workflows/standalone-release.yml` сохранить полноценные smoke-тесты wheel и установки, обновить имена/версии/asset bundle. При необходимости улучшить последовательность CI, но не расширять объем реализации за рамки задачи.

## 8. Документация и выпуск

Обновить `docs/standalone.md`, `docs/releasing.md`, README, release notes `docs/releases/v2.5.2.post2.md`; описать:

Создавать подготовительный wheel и Actions artifact можно. **Не создавать Git-тег, не публиковать стабильный Release, не создавать PR и не выполнять merge** до отдельной приемки владельцем.

## 9. Ручная приемка

Проверить в WSL2 на действующем тестовом окружении:
1. Проверить release bundle и контрольные суммы; установить 2.5.2.post2 со старой 2.5.2.post1, используя один раз свежий скрипт.
2. Проверить `codex-dispatcher --version` независимо от YAML, схему 1, `db check`, `queue`, `status`, сохранность настроек и Issue.
3. Проверить `command -v codex-dispatcher-install` и повторный запуск без активации venv.
4. Проверить SHA совпадение (штатный сценарий), искусственно испорченный **тестовый экземпляр** установщика (отказ без изменений) и отказ при недоступной проверке.
5. Проверить `codex-dispatcher-uninstall`: `n`/Enter сохраняют установку, при работающем daemon отказ, при STOPPED + `y` успешное удаление, после чего команды исчезают.
6. Проверить сохранность SQLite, конфигурации и workspace после удаления и повторной установки.
7. По возможности повторить основные сценарии Ubuntu native.

Отдельно зафиксировать результаты тестов и возможные отклонения. Изменения `Service` и `Docker` не допускаются.

## 10. Критерии завершения

V2.5.2.2 готов к приемке, если:
- версия пакета `2.5.2.post2`, схема конфигурации 1;
- команда `--version` читает metadata и не требует конфигурации;
- `codex-dispatcher-install` появляется после установки/обновления и защищена ownership-проверкой;
- SHA mismatch требует ручного скачивания актуального установщика и **ничего не изменяет** в установке;
- удалитель требует явного интерактивного согласия, не удаляет данные пользователя;
- CI и smoke tests проходят; реальный сценарий WSL2 подтвержден вручную;
- обработка Issue/PR остается неизменной.
