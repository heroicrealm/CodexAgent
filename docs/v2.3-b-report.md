## Поведение и решения

Регистрация по codex-ready создаёт собственную временную группу и не читает
INPUT. При approve загружаются актуальная Issue и все страницы комментариев.
Корректировка разрешается по номеру Issue своего репозитория. Назначение группы,
непосредственного источника, снимка, веток, состояния и истории выполняется
одной транзакцией. Источник может быть любой предыдущей Issue группы; ветки
берутся с корня. Наличие need-fix обязательно; старое разрешение не позволяет
обойти error/rejected новой попытки. Конкурентные approve оставляют только одну
активную Issue, проигравшая остаётся discovered без частичного снимка.
Прежние технические методы Storage A с correction_of сохранены для совместимости
с принятыми тестами A; пользовательский поток B их для ранней привязки не вызывает.

При отсутствии base_branch используется `projects[].base_branch`, по умолчанию
`main`; автоматического запроса default branch репозитория нет. Новая группа
не присваивает себе существующую удалённую рабочую ветку: коллизия приводит
к ошибке подготовки. Корректировки используют существующую ветку своей группы.

Поздние связи после preparing не записываются в учитываемый набор. Уже учтённые
связи остаются зафиксированными при дальнейшем исполнении. До preparing полный
успешный опрос может заменить набор связей по решению V2.2/T14. Рекурсивного
обхода нет. Конфликт цели merge ребёнка и снятие ready при открытом PR блокируют
родителя. Зарегистрированный реальный ребёнок с учитываемой связью блокирует
родителя до done/cancelled независимо от текущего наличия codex-ready. Саму метку
codex-ready диспетчер не восстанавливает. Никакие постоянные счётчики не введены.

SQLite остаётся источником состояний. Для preparing метки нет; running появляется
после готовности окружения, manual-running — только после push ручной ветки.
Используются эффективные метки проекта, чужие метки сохраняются.

Codex получает только утверждённую постановку и INPUT через stdin. Маркер начала
фиксируется до создания процесса, неопределённая попытка повторно не запускается.
Git/worktree, GitHub и Codex не вызываются внутри SQL-транзакций. Poll работает
во время исполнения Codex. Обычный stop ждёт worker, force останавливает группу
процессов с сохранением доступного результата. Ошибка не удаляет worktree
с неопубликованной копией.

Publisher ищет PR всех состояний с точным repository/head, учитывает время
текущего execution и исключает PR прежних попыток. Это позволяет обнаружить
ручной PR, уже слитый между опросами, и не использовать старый отклонённый PR
корректировки. Известные PR проверяются и при закрытой GitHub Issue.
Неопределённый ответ создания PR сверяется перед повторным POST.

OUTPUT содержит состояние, ветку, PR, времена, длительность, подтверждение push
и итоговый ответ агента (до 20 000 символов; полный stdout сохраняется отдельно
в workspace/results). Обновления выводятся из SQLite; INPUT/OUTPUT не перечитываются
для мониторинга. Подтверждённый OUTPUT хранится только после ответа GitHub.
Если штатное обновление получило 404 для известного OUTPUT, комментарий
не восстанавливается и дальнейшие попытки для этого ID подавляются на время
процесса. Ошибка фиксируется; публикация PR остаётся принятой. Повторный запуск
может сделать одну попытку штатного обновления отличающегося состояния.
Итоговый error report отправляется один раз после накопления ошибок;
флаг выставляется после подтверждения, удаление человеком не мониторится.

Все видимые REST-попытки проходят через адаптер и диагностируются с poll_id;
контекст Poll распространяется также на запросы его публикаций. Повторяются
только GET при 429/502/503/504, максимум две повторные попытки. Неопределённые
POST не повторяются вслепую. Диагностика не хранит payload, тексты Issues,
stdout/stderr или секреты. Базовый повторный Poll одной discovered Issue без
изменений проверен на бюджет **3 GET**: Issues, parent, Sub-issues; комментарии
не читаются. Скрытые внутренние запросы gh не объявляются отдельно учтёнными.

## Очистка и сохранность

Автоматическая очистка рассматривает только executions.worktree_path и ветки
терминальных групп. Worktree удаляется без force, только если он принадлежит
пространству имён V2, чист (включая игнорируемые файлы) и HEAD достижим из текущих
удалённых веток. При сомнении ресурс остаётся. В rejected/need-fix общая ветка
сохраняется. Ошибки очистки не меняют терминальные состояния.

Удаление удалённой ветки требует подтверждённого push и совпадения текущего tip
с известным result_commit группы. Неизвестные пользовательские коммиты защищены.
Для защиты гонки между проверкой и удалением применяется **условное удаление**
`git push --force-with-lease=refs/heads/BRANCH:EXPECTED --delete BRANCH`.
Это CAS удаления терминального ресурса; публикация результатов никогда не
использует force/lease, rebase или перезапись истории. Если tip изменился,
удаление отклоняется. Успешная очистка запоминается в процессе; после рестарта
состояние проверяется заново по существующим данным, без cleanup_pending.

Ручная утилита требует существующую совместимую SQLite, захватывает общую
блокировку, защищает все канонические пути из executions независимо от статуса,
исключает активные/неопубликованные/грязные/чужие worktree, symlink escape и
основной checkout. Отсутствие записи в SQLite само по себе не разрешает удаление.
Подтверждение владения: управляемый каталог проекта, имя e-ID-UUID и соответствующая
ветка dispatcher-v2/ID-UUID. Перед каждым удалением проверки повторяются.
Dry-run не меняет worktree/Git refs/записи SQLite; служебные lock-файлы могут
создаваться для исключения параллельной работы.

## Запуск

Скопировать config/config.example.yaml в отдельный конфигурационный файл V2.
Заполнить projects и base_branch; checkout должен быть отдельным checkout V2.
При отсутствии checkout Runtime клонирует проект в workspace/repos/PROJECT.
Настроить gh auth и Git SSH-доступ оператора; Codex CLI должен поддерживать
указанный argv (команда полностью настраивается).

```bash
codex-dispatcher --config /path/to/v2.yaml init-labels
codex-dispatcher --config /path/to/v2.yaml run
codex-dispatcher --config /path/to/v2.yaml stop
codex-dispatcher --config /path/to/v2.yaml stop --force
codex-dispatcher --config /path/to/v2.yaml status
codex-dispatcher --config /path/to/v2.yaml publish EXECUTION_ID
worktree-cleanup --config /path/to/v2.yaml --project PROJECT
worktree-cleanup --config /path/to/v2.yaml --project PROJECT --apply
```

Для INPUT используется один отдельный комментарий:

````markdown
<!-- codex-dispatcher:INPUT:v2 -->
```yaml
dispatcher:
  base_branch: main
  run_codex: true
```
````

OUTPUT: `<!-- codex-dispatcher:OUTPUT:v2 -->`;
сводный отчёт: `<!-- codex-dispatcher:ERROR:v2 -->`.
Текущая справка Codex CLI проверена локально; выбор exec, stdin и workspace-write
соответствует [официальному примеру OpenAI](https://developers.openai.com/cookbook/examples/codex/build_iterative_repair_loops_with_codex).
REST родителей/Sub-issues сверялся с [GitHub REST documentation](https://docs.github.com/en/rest/issues/sub-issues).

## Оставшиеся ограничения и граница приёмки

- Реальные GitHub/gh/Codex не испытаны; T41 и финальная приёмка C требуют
  отдельного задания и нового тестового репозитория.
- Runtime, supervisor, блокировки и управление используют POSIX/Linux
  (fcntl, Unix socket, process groups). Путь Unix socket должен помещаться
  в ограничение ОС. Windows не заявлен.
- Репозиторий принадлежит одному проекту конфигурации. Межрепозиторные
  Parent/Sub-issue требуют отдельного согласования отображения проектов;
  сейчас такой опрос отклоняется без частичного применения.
- Консервативная очистка сохраняет неизвестные, непроверенные, игнорируемые
  и изменённые пользователем ресурсы для ручной проверки. Автоматического
  prune, force remove и удаления локальных веток нет.
- Общепринятые риски неопределённого ответа создания OUTPUT/error report
  сохраняются: авария после GitHub, но до SQLite, может дать дубль.
- Формат маркеров и argv CLI конкретизированы в B. Базовая ветка main по
  умолчанию, отказ присвоения существующей ветки новой группе и условное
  удаление подтверждённого tip описаны выше для проверки при приёмке.

Защита путей V1 не зависит от расположения установленного wheel: любой путь
с компонентом V1/v1 отклоняется, в том числе после разрешения symlink.

Новых противоречий, требующих изменения SQLite или архитектуры, не обнаружено.
Поздние уточнения INPUT и варианта A очистки применены поверх принятого A.


## Исправление ready-child перед повторной приёмкой B

Основание: `docs/v2.3-b-ready-child-fix.md`.

Причина дефекта: `GroupService.evaluate_db` использовал наблюдаемый `is_ready`
как условие учёта незавершённого ребёнка. После удаления codex-ready из GitHub
Poll корректно записывал `is_ready=0`, но refresh ошибочно освобождал родителя.
Факт регистрации и сохранённая учитываемая связь должны иметь приоритет.

Изменённые файлы:

- `src/dispatcher/services.py`: выбираются только реальные дети `is_virtual=0`
  по issue_relations; любое состояние, кроме done/cancelled, блокирует родителя
  независимо от is_ready. NULL также не считается терминальным. Отдельная
  блокировка снятия ready при открытом PR и конфликт цели merge сохранены.
- `tests/test_services.py`: добавлено восемь регрессионных проверок с учётом
  параметризации и усилены две прежние проверки конфликтов и поздних связей.
- `docs/v2.3-b-report.md`: актуализированы поведение, результаты и этот раздел.

Проверены пути StateService.refresh_db/apply_observation, PollService и
GitHubAdapter.sync_labels. Изменять их код не потребовалось: зарегистрированные
Issues уже сохраняются без codex-ready, is_ready остаётся наблюдаемым флагом,
а статусная метка берётся из effective labels независимо от ready.

Регрессии покрывают awaiting-children с discovered-ребёнком без PR после снятия
ready; стандартную и проектную карту меток; отсутствие повторных запросов меток
и истории при неизменном Poll; восстановление отсутствующей статусной метки без
восстановления codex-ready; последующее approve и законное завершение ребёнка
в done/cancelled; удаление связи до preparing; игнорирование виртуального ребёнка
и защиту от трактовки NULL как терминального состояния. Прежние проверки теперь
также проходят через Poll при снятии ready с ребёнка с открытым PR и после
добавления позднего ребёнка. Конфликт merge в другую базовую ветку продолжает
блокировать родителя.

До исправления пять новых проверок воспроизвели преждевременный pending.
