## 2. BUG-03 — безопасная обработка stale control socket при полном удалении

### Наблюдаемое воспроизведение

После аварийного завершения системы (WSL2), при свободных daemon-lock и невозможности подключения к оставшемуся UNIX socket:
- `codex-dispatcher status` → `Daemon: STOPPED`.
- `codex-dispatcher stop` → `Daemon: STOPPED; control unavailable: [Errno 111] Connection refused`.
- `codex-dispatcher project remove cap`: первоначальный `plan` показывает `executable: true, blockers: []`; после ввода `cap` команда выдаёт **`FAIL Control socket exists; verify service shutdown`**.

Причина проверена по коду: `src/dispatcher/db_guard.py:quiescent()` отклоняет **любое** наличие `workspace/.control.sock`, не различая живой socket и мёртвый filesystem entry. Процедура `purge.execute()` вызывает `db_guard.quiescent(config)`, не согласованную с `monitoring.daemon(config)` и `purge.plan(config,name)`.

### Требуемое поведение

1. Если на момент удаления **достоверно установлено**, что daemon и Executor остановлены, lock получены эксклюзивно, нет живого слушателя, а `.control.sock` — именно устаревший сокет штатного расположения, он **не должен мешать** полному удалению.
2. Должны сохраняться безусловные отказы при работающем daemon, занятых/inherited lock, активном socket listener, противоречивой идентичности процесса, неопределённом состоянии, symlink/подменённом сокете, постороннем файле на месте сокета, опасных SQLite WAL/SHM, незавершённом Recovery или execution.
3. Не удалять и не переименовывать произвольные файлы, чужие socket или lock. При необходимости убирать только **проверенный** stale socket после исключительного захвата lock; выполнять повторную проверку типа и идентичности filesystem entry непосредственно перед unlink, включая защиту от races. Не допустить TOCTOU, который позволил бы удалить новый socket живого сервера.
4. Привести `plan` и `execute` к **одинаковой политике пригодности**, чтобы dry-run с `executable: true` не приводил к предсказуемому отказу сразу при подтверждении. Если устранение stale socket требует мутации, dry-run обязан оставаться строго read-only, а destructive path может безопасно очищать socket после подтверждения/lock. Выводить в плане факт обнаруженного stale socket и предполагаемое действие.
5. **Не ослаблять глобально `db_guard.quiescent()`** для `db restore` или других опасных операций ради исправления одного CLI-кейса. Предпочтительно небольшой специализированный helper/admission для удаления с теми же или более строгими гарантиями; если используется общий helper, явная проверка, что Recovery и restore не стали слабее.
6. `stop` после аварийного завершения по-прежнему без traceback; `status` по-прежнему STOPPED при доказанном отсутствии процесса и UNKNOWN при неопределённости.

### Проверки

- Stale UNIX socket + свободные locks + доказанный STOPPED → `remove --dry-run` без изменений, затем `remove` проходит с точным подтверждением ID.
- Активный listener с занятыми locks → отказ до backup и разрушительных действий, socket не удалён.
- Занятый lock при отсутствии socket / stale heartbeat / PID reuse / symlink или обычный файл вместо socket / racing socket replacement → безопасный отказ.
- Отсутствие socket → прежний успешный сценарий.
- Наличие WAL/SHM → прежняя защита без обхода.
- Проверить, что `db restore` и Recovery admission не получили новых обходных путей.
- В случае отказа YAML, SQLite, backup и Git-артефакты остаются неизменными.
- Тесты с реальными Unix-domain sockets и lock, без необходимости реально перезагружать компьютер.

## 3. UI-08 — человекочитаемые логические значения в show -v

В `Execution details` три поля:
- `Push publication` (`push_completed`)
- `PR publication` (`pr_published`)
- `Comment publication` (`comment_published`)

Показывать `Yes` для 1/true и `No` для 0/false **только в Rich human-readable режиме**. Для отсутствующего значения — `N/A`; не путать 0 с None. Не распространять преобразование на `exit_code`, `execution_id` и другие числовые поля. Сохранить исходные машинные значения и структуру `show ... --json`.

Тесты human Yes/No/N/A, JSON original, NO_COLOR и pipe.

## 4. UI-09 — Rich-оформление плана project remove и dry-run

Сейчас `purge.execute()` выводит `json.dumps(initial, indent=2)`, а `project remove ID --dry-run` в `__main__.py` помещает аналогичный JSON в Rich Panel. В обычном терминале это сотни строк внутреннего плана с rowid, sha256, UUID и metadata.

**Предлагаемый human-readable экран, общий для удаления и dry-run:**

```text
PROJECT REMOVAL · cap
Repository: heroicrealm/codexagentplayground
Mode: DRY RUN / PERMANENT REMOVAL

Local data to delete
  SQLite records      <total and/or concise counts by category>
  Codex results       1
  Managed worktrees   0
  Local branches      1
  Managed checkout    yes / no
  Diagnostic files    <count>

Daemon: STOPPED      Database: OK      Recovery: READY
Ready: YES           Blockers: none

WARNING: This permanently deletes ALL local project data.
GitHub Issues, PRs and remote branches are not modified.
Type full project.id (cap) to confirm:
```

Конкретное Rich-оформление выбирается агентом; использовать существующую визуальную систему и окрашивать только значимые значения/предупреждения. Требования:
1. Краткий **достоверный** план: project.id, owner/repo, количество строк SQLite (с понятной разбивкой по основным типам при необходимости), результатов, worktree, локальных веток, managed checkout, diagnostics, возможность удаления, blockers. При наличии отказа выводить причины полностью, без скрытия критических условий.
2. Не выводить огромные internal `rowids`, raw SQL, полный `database_fingerprint`, `metadata`, хеши путей, raw JSON и приватные сведения без отдельной необходимости. Не утверждать «готово к удалению», если blockers есть.
3. `--dry-run` использует **тот же** renderer с пометкой DRY RUN, без подтверждения, backup, создания каталогов/lockfiles, изменения SQLite/Git/YAML/socket. При stale socket можно указать его как проверенный leftover, но не удалять.
4. `project remove ID` показывает ту же сводку, затем **обязательно требует буквальный project.id** в настоящем TTY. Отказ/не-TTY/EOF/неверное имя — без изменения данных.
5. Не изменять расчёт или сверку fingerprint, ownership, список удаляемых объектов, backup, транзакцию Recovery audit, journal и идемпотентные защитные проверки. **Разделить представление плана и его точную машинную структуру**: renderer не должен менять объект `plan`, которым пользуется исполнение.
6. При ошибке — краткое `FAIL` с понятной причиной, блокером, а если уже создан backup — точный путь к сохранённой копии и журналу. При успехе — количество удалённых объектов и `temporary backup removed`.
7. Если для администрирования предусмотрен полный машинный вывод, разрешено добавить явный `--json` **для dry-run**, выдающий один полный JSON-объект без ANSI и Rich; это необязательно, но запрещено менять внутренний объект плана или требовать JSON по умолчанию. Не добавлять `--json` к destructive-команде так, чтобы была возможность обойти интерактивное подтверждение.
8. Ширина 80/120 столбцов, NO_COLOR, pipe, Unicode/длинные имена. Текст проекта и пути выводить как литералы, не интерпретировать Rich markup.

## 5. Совместимость и ограничения

- Пользователь уже вручную проверил весь базовый сценарий: создание проекта, poll, pending→running→review→done, закрытие GitHub Issue, Rich status/queue/show, stop после crash, полное локальное удаление `project remove cap`, backup cleanup, `db check`, пустой managed checkout и повторный add.
- После исправлений поведение этих команд не должно ухудшиться.
- Не добавлять обращения к GitHub/GitHub API при status/queue/show/удалении; никакого удаления remote branches/PR/Issues. Локальные Git-проверки в purge допустимы.
- `disable` сохраняет историю, `remove` полностью удаляет текущую локальную историю; `--purge` в CLI не возвращать.
- Не реализовывать systemd, автоматическое обновление конфигурации, миграцию старых тестовых данных.
- В файлах README/документации обновить только соответствующие разделы, включая понятные примеры Rich-плана и stale-socket безопасность.
