## 1. Предмет работы и принятое решение

Агент уже реализовал другие интерфейсы V2.4.3 и сознательно заблокировал destructive purge, обнаружив FK-связи append-only `recovery_events` и защитные триггеры `recovery_events_no_update` / `recovery_events_no_delete`. Блокировка была правильной.

**Теперь утверждена особая административная политика:** после успешного `codex-dispatcher project remove ID --purge` в текущих локальных данных диспетчера не должно остаться никаких упоминаний удалённого проекта/репозитория, включая Recovery audit, историю исполнений, диагностику, результаты Codex, управляемые worktree и принадлежащие только проекту локальные ветки. Пользователь намеренно удаляет всю его историю. GitHub НЕ трогать.

**Утверждён механизм:** удалять записи в *исходной* SQLite в транзакции с сохранением `PRAGMA foreign_keys=ON`. Допускается временно снять два защитных триггера `recovery_events` *внутри той же транзакции*, удалить только принадлежащие проекту записи с учётом FK, восстановить триггеры и проверить целостность **до COMMIT**. При любом сбое ROLLBACK обязан вернуть как данные, так и защитные триггеры. Не копировать всю БД в новую для удаления проекта, не использовать глобальный `PRAGMA foreign_keys=OFF`, не оставлять долговременное ослабление защиты, не менять обычную семантику Recovery. После COMMIT повторно проверить наличие триггеров и целостность.

**Тонкость:** в SQLite DDL DROP/CREATE TRIGGER может быть транзакционным, но агент обязан доказать этот сценарий тестами с принудительными исключениями между DROP, DELETE и CREATE. Выполнять только на выделенном writable соединении с проверенными lock/DB guard. Не применять этот приём к пользовательским операциям Recovery.

## 2. Границы изменения

Реализуй реальный `project remove ID --purge` и скорректируй `--dry-run`; дополни тесты/документацию и отчёт. Не перерабатывай status/queue/show, project add, Scheduler, Poll, публикацию GitHub или систему Recovery без прямой необходимости. Используй существующий `src/dispatcher/purge.py` как место реализации и включи его в `__main__.py`. Если существующие helper'ы не подходят, добавь небольшие изолированные модули.

Не выполнять GitHub API, `git push`, удаление remote refs, изменение GitHub Issue/PR/labels/comments. Не удалять внешний пользовательский `project.checkout`, чужой checkout или shared workspace. В рамках purge допустимы **только локальные** безопасные Git операции (worktree remove, ref delete) после доказательства ownership.

## 3. Полный план очистки

Переработать `plan()` из inventory кандидатов в полный достоверный план удаления. Включить:
- все строки `issues` для репозитория/проекта; `issue_relations` как по parent, так и child;
- `executions`, `pull_requests`, `state_history`, `error_log`, `debug_operations` (включая строки с `repository`, но без `issue_id`);
- `recovery_operations`, `recovery_events`, `recovery_quarantine`, `recovery_execution_archive`, `recovery_approval_reset` и прочие связанные таблицы;
- ссылки `recovery_events.operation_id`, `recovery_events.session_id`, `recovery_sessions.summary`: отдельно выявлять общие с другими проектами события/сессии и поля JSON, где упоминается удаляемый репозиторий. Не удалять общую сессию целиком, если есть данные другого проекта. Сохранить корректные FK и историю других проектов. При невозможности безопасно удалить только свои упоминания — блокировать purge с конкретной причиной, а не объявлять успех;
- meta/служебные таблицы и текстовые/JSON-поля с ссылками на удаляемый repository/project ID; не удалять общие глобальные metadata, нужные другим проектам. Различать идентификатор проекта, который может совпадать с обычным словом, и достоверную ссылку;
- результаты Codex, diagnostics, временные файлы и управлявшиеся диспетчером каталоги/worktree; отдельно учесть сиротские артефакты, не перечисленные напрямую в executions;
- локальные Git refs: только доказанно созданные и принадлежащие *этому* проекту; не затрагивать базовые или общие ветки и remote refs;
- внешние checkout и неоднозначные/shared пути считать сохраняемыми или блокирующими в соответствии с безопасностью.

Все найденные элементы плана и blockers показывать в `--dry-run`; без файловых/SQLite/Git мутаций, backup и GitHub. Отличать inventory от исполнимого плана (`executable` false при недоказанной принадлежности или нарушенных preconditions). Убедиться, что `--dry-run` не создаёт lockfiles/sidecars и не меняет DB/WAL/SHM.

## 4. Preconditions и подтверждение

Перед разрушением:
1. Зафиксировать исключительный доступ через действующий `InstanceLock` и проверить достоверную остановку daemon и отсутствие работающего Executor, не полагаться только на отсутствие socket.
2. Проверить DB Guard, привязку UUID/workspace, целостность, foreign keys и отсутствие глобального `recovery_required` и незавершённых Recovery-операций/карантина, запрещающих очистку.
3. Проверить отсутствие неожиданных shared references и посторонних Git/worktree объектов. Все пути нормализовать; запретить symlink traversal и удаление за пределами доказанного managed root.
4. Построить итоговый план повторно под lock и сравнить с предъявляемым пользователю.
5. Показать точный план и запросить ввод **полного project.id** в интерактивном терминале. При non-TTY, неправильном ID или отказе — без мутаций, exit !=0. Не добавлять `--force`.

Не ослаблять действующие блокировки, чтобы добиться успеха.

## 5. Автоматическая временная резервная копия

**Это утверждённая политика, отдельного CLI-флага сохранения backup НЕ требуется.**

До первого разрушительного действия автоматически создать проверенный SQLite backup стандартным существующим Backup API. Каталог:

`<root_path>/backups/purge/`

Имя должно быть уникальным и информативным (timestamp, project ID, случайный/уникальный suffix); защищённые права `0600` на файл, `0700` на каталог. Убедиться, что директория/backup не попадут под удаление вместе с проектными рабочими файлами. Проверять snapshot через существующие DB Guard/backup механизмы.

Политика:
- `--dry-run`: backup не создавать;
- **успешный purge**: после окончательной проверки SQLite, очищенных артефактов и удаления конфигурационной записи временный backup **автоматически удалять**, без накопления скрытых копий;
- **ошибка / прерывание**: backup сохранять, путь показывать пользователю вместе с состоянием операции и безопасной инструкцией для повторного выполнения/восстановления;
- при следующей попытке purge проверять и **явно показывать** оставшиеся backup/журналы неудачных предыдущих операций; не удалять их молча и не создавать бесконтрольно новые повторные копии. Для повторной попытки использовать безопасную проверку журнала и существующего backup либо явное решение о новом snapshot; сохранять доступность исходного восстановления.

`db backup` (явный пользовательский архив) не трогать; временная purge-копия не должна переживать успешное завершение.

Техническая особенность: автоматический SQLite backup может содержать проект до удаления. Поэтому гарантии полного удаления относятся к текущей системе **после успешного удаления автоматического backup**. При неудаче сохранённая копия допускается и явно раскрывается.

## 6. Безопасная транзакция SQLite

Использовать реально существующую схему `src/dispatcher/schema.sql`, а не предположения о FK. Составить явный dependency order и добавить тесты FK.

В одной транзакции:
1. Доказать штатное наличие и ожидаемое SQL-определение двух триггеров Recovery (из утверждённой схемы); любое расхождение — отказ.
2. `DROP TRIGGER` только двух известных триггеров, без отключения `foreign_keys`.
3. Удалить ровно project-scoped строки с надлежащим учётом `recovery_events` и иных FK.
4. Восстановить те же триггеры с точными исходными определениями из схемы.
5. Выполнить `PRAGMA foreign_key_check` и дополнительные проверки остаточных упоминаний, условий сохранности других проектов, наличия всех защитных triggers.
6. Только затем `COMMIT`.

Никаких отдельных commits между DROP и CREATE. Проверить отказ/ROLLBACK на каждом контрольном шаге; `PRAGMA foreign_keys=ON` действует на всём протяжении. Учитывать, что SQLite `PRAGMA integrity_check` и внешнее файловое состояние требуют дополнительных проверок после commit.

**Важно:** если есть общие `recovery_sessions` или их JSON summary с межпроектной информацией, не пытаться просто `DELETE` общую сессию; требуется сохранить данные чужих проектов, удалить только принадлежащие удаляемому проекту упоминания, сохраняя проверяемые форматы. Если корректная селективная очистка невозможна без изменения гарантий, зафиксировать конкретный блокер, вместо небезопасной операции.

## 7. Устойчивость к прерыванию и файлы/Git

SQLite-транзакция не атомарна с файловой системой и Git. Реализовать минимальный надёжный журнал фаз очистки вне удаляемой проектной директории (например в приватном локальном служебном каталоге root_path), с атомарной записью/fsync. Он должен позволять определить, завершена ли DB-фаза, что осталось очистить, и нужно ли продолжить либо восстановить из сохранённого backup. Не хранить после успеха постоянных упоминаний о проекте: служебный журнал успешной очистки удалить.

Продумать порядок фаз так, чтобы при падении между SQL COMMIT, удалением worktree/refs/results и удалением записи YAML:
- не удалялись чужие файлы;
- не оставались неконтролируемые dangling refs;
- команда при повторном запуске могла безопасно продолжить или предложить восстановление;
- backup до успешного завершения не уничтожался;
- YAML проекта не удалялся преждевременно.

Проверять symlinks, boundaries, ownership и shared resources. Worktree удалять через безопасные механизмы Git, локальную ветку — лишь при доказанной принадлежности. Обычная команда `project remove` без purge по-прежнему удаляет **только запись YAML**, сохраняя историю и артефакты.

## 8. Завершающие проверки

Перед признанием успеха:
- PRAGMA integrity_check, foreign_key_check, наличие Recovery triggers в исходной SQLite;
- ноль относящихся к проекту строк во всех рабочих таблицах, включая `recovery_events` и диагностический журнал;
- ноль project-scoped ссылок в допустимых структурированных метаданных, JSON и связях; сохранность данных контрольного проекта;
- отсутствие принадлежащих проекту управляемых worktree/refs/results/каталогов;
- исключённый project из YAML; тот же repository снова можно `project add` без конфликта retained history;
- отсутствие GitHub-вызовов и изменений remote.

После успешных проверок удалить временный backup и локальный служебный журнал; проинформировать пользователя `PASS` с количеством удалённых объектов и явным сообщением, что temporary backup removed. При любой ошибке — `FAIL`, сохранение backup и путь к нему.

## 9. Автоматические тесты

Добавить тесты как минимум:
- пустой проект; проект с Issue, PR, executions/results, debug и Recovery events;
- Recovery-events, связанные через issue_id и/или operation_id и session_id, смешанная общая Recovery-сессия;
- удаление только одного из двух проектов с идентичными Issue numbers; чужие ссылки/сессии сохраняются;
- SQL FK/triggers действуют до и после purge; инъекция ошибок сразу после DROP, DELETE и CREATE гарантирует ROLLBACK триггеров и строк;
- `--dry-run` без любого side effect;
- отказ без TTY, отказ при неправильном подтверждении, работающем daemon, recovery_required/quarantine, неизвестном ownership и внешнем checkout;
- проверенный backup до разрушения; успешное автоудаление временного backup; сохранение и вывод пути при ошибке; видимость старых failed backups и повторное выполнение;
- аварии на границах filesystem/Git/SQLite/YAML и повторное выполнение/восстановление;
- отсутствие изменений GitHub и любых удалённых веток, сохранность чужих файлов/веток;
- полный после purge `project add` того же repository под прежним либо новым ID (сетевые проверки add — mocks);
- полный регрессионный `python -m pytest -q`, исходно 435 passed из отчёта агента, `git diff --check`.

Не выдавать success только на основании пустого `issues`, если остались Recovery audit или файловые артефакты.
