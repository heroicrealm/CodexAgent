# V2.4.2 — Восстановление и сверка состояния после db restore

**Статус:** УТВЕРЖДЕНО заказчиком (2026-11-11)  
**Репозиторий:** heroicrealm/CodexAgent  
**База:** CODEXAGENT_V2, принятая V2.4.1  
**Цель:** безопасно снять recovery_required после внешней сверки, не допустить случайного повторного Codex.

## 1. Принятые решения

- **A:** консервативная сверка; не реконструировать автоматически неизвестные попытки Codex.
- **A2:** конфликтные Issue помещаются в индивидуальный карантин, а независимые безопасные могут выполняться.
- **A2.1:** снятие карантина только явным административным решением пользователя; poll/recover не снимают его автоматически.
- **R1:** все изменяющие recovery-команды исполняются только при остановленном диспетчере, под InstanceLock.
- **T2:** после retry необходим новый пользовательский approve через GitHub; старый approve не принимается.
- **RETRY:** при доказанном отсутствии опубликованного результата пользователь вправе отбросить неизвестную локальную работу, очистить принадлежащий заданию worktree, вернуть Issue в discovered.
- **AUDIT:** до удаления прежней строки executions обязательно архивировать исполнение и связанные диагностики. Записи state_history не удалять.

Приоритет: сохранность результатов и защита от дублирования > удобство. Не добавлять новое issues.state, не вводить общий механизм множественных запусков.

## 2. Границы и техническая база

V2.4.1 использует dispatcher_metadata(singleton,format_version=1,instance_id,recovery_required), строгую проверку точного DDL, schema_migrations с версией 1, InstanceLock на DB/workspace, executions.issue_id UNIQUE. Storage.connection() блокирует обычную запись при recovery_required=1. Runtime.run() вызывает Executor.recover(), затем cleanup; Scheduler, Publisher, PollService, Cleanup имеют самостоятельные пути действий. Новая защита должна покрыть ВСЕ эти пути.

Не входят: возобновление процесса Codex, force push, удаление remote branch, восстановление данных GitHub из SQLite, миграция V1, попытка восстановить неизвестные исполнения по косвенным признакам, тайное исправление правдоподобных конфликтов.

## 3. Глобальный recovery admission

После любого restore metadata.recovery_required=1; обычный run/publish/cleanup и изменяющий poll запрещены, включая восстановление исполнителя. db check/backup/status и безопасная диагностика остаются доступны согласно контракту.

`db recover --dry-run` — полный read-only анализ без изменений SQLite, GitHub, Git или файлов; может делать сетевые GET/read-only Git. `db recover`:
1. Получить оба InstanceLock и проверить отсутствие control socket, управляемых процессов и неизвестной активности, без опасной эвристики по PID.
2. Проверить UUID, точную совместимую схему, integrity/FK, recovery_required; запретить неясные SQLite WAL/SHM состояния.
3. Полностью собрать данные активных и сохранённых проектов, зарегистрированных Issue, PR, отношений, веток, worktree; не считать GitHub-список открытых Issue исчерпывающим для закрытых ранее отслеживаемых Issue.
4. Отнести каждую ситуацию к достоверной/карантинной/глобальной ошибке, построить детерминированный план.
5. Перепроверить критичные внешние предпосылки непосредственно перед фиксацией; внешние вызовы не проводить внутри долгой SQLite транзакции.
6. Одной административной транзакцией применить допустимые изменения, ДОБАВИТЬ обнаруженные причины карантина, записать session/events и снять recovery_required=0.
7. Если обязательная проверка неполна, GitHub недоступен, активный исполнитель возможен или локальная идентичность не доказана: fail closed, общий барьер остаётся, никаких частичных разрешений.

Существующие карантины из backup сохраняются; повторный recover и poll не имеют права удалять их. Для проекта, удалённого/отключённого в текущей конфигурации: не исполнять ничего; сохранять его прежние данные/запрет; отсутствие доступа к нему не должно бездумно приравниваться к успешной сверке. Определить политику отдельной изоляции отключённых репозиториев при отсутствии их проверки, не допуская автоматического исполнения при последующем включении без повторной верификации.

Отсутствие PR, push или worktree само по себе не доказывает отсутствие запуска Codex. Если невозможно доказать допустимость продолжения — карантин.

## 4. Классификация состояний

| Состояние backup | Внешнее наблюдение | Действие |
| --- | --- | --- |
| discovered | согласовано, нет признаков исполнения | оставить discovered |
| discovered | обнаружены признаки исполнения | карантин |
| pending | достаточно подтверждений безопасного ожидания, нет следов исполнения и устаревшего approve | оставить pending |
| pending | неизвестная попытка, ветка, PR, старое approve | карантин |
| awaiting-children | проверенные зависимости | штатный пересчёт GroupService |
| awaiting-children | карантин ребёнка | заблокировать запуск/автозавершение контейнера |
| preparing/running | результат неизвестен | карантин, никогда не запускать Codex заново |
| preparing/running | доказан PR и допустим переход | восстановить согласованное review/результат без фиктивной истории; иначе карантин |
| manual-running | PR нет | сохранить ожидание человека, не завершать автоматически |
| manual-running | PR доказан | review при допустимом переходе |
| review | PR open | review |
| review | PR merged | done по правилам группы |
| review | PR closed без merge | rejected |
| rejected/need-fix/error | внешнее состояние не противоречит | сохранить; при доказанном PR применить только разрешённый переход |
| done/cancelled | подтверждено или не требует исполнения | сохранить |
| любое | сомнение в идентичности/истории/результате | карантин |

Не менять модель State или ALLOWED повсеместно; специальные переходы recovery допустимы только через выделенный админ-интерфейс с журналом. Для PR в другую base branch сохраняются правила V2.3 (merge завершает Issue, контейнер может ожидать исправления конфликта целевой ветки). Вложенные контейнеры работают через непосредственные зависимости. Не помещать родителя в карантин только за карантин ребёнка, если нет собственной причины.

## 5. Состав сверки

- GitHub: repository casefold, глобальный issue_id и issue_number, open/closed, ready/approve/state-метки, тело/заголовок и утверждённый снимок, отслеживаемые subissues, PR по ID и ветке, статус, base/head, SHAs; нельзя считать одно лишь имя ветки достаточным доказательством принадлежности.
- Git: local/remote refs, рабочая ветка и её использование другими задачами, push и коммиты, worktree/dirty/untracked; не удалять ничего при непроверенной принадлежности.
- Если в backup не было новой Issue: обычное обнаружение без автоматического доверия старому approve и без запуска при подозрении на прежний результат.
- Не раздувать GitHub запросы: batch открытых Issue/PR, cache наблюдений, точечные GET; debug_operations режим V2.2 сохранять.

## 6. Карантин

Независим от issues.state, persistent по глобальному issue_id. Причины:
`execution-uncertain`, `branch-conflict`, `pr-conflict`, `local-worktree`, `approval-uncertain`, `group-dependency`, `state-conflict`.
Допускается несколько причин на Issue.

На всех путях Scheduler.reserve/next, Executor.recover/execute, Publisher.publish/phase_output, StateService, PollService, runtime и Cleanup/maintenance проверять применимые ограничения; диагностические read-only GET допустимы, автоматическое удаление/публикация/переходы конфликтной Issue — нет. Разрешение одной причины не удаляет другие. Дочерний карантин препятствует запуску и завершению зависимого контейнера, но не затрагивает независимые задания.

## 7. CLI

```bash
codex-dispatcher --config config/dispatcher.yaml db upgrade
codex-dispatcher --config config/dispatcher.yaml db recover --dry-run
codex-dispatcher --config config/dispatcher.yaml db recover
codex-dispatcher --config config/dispatcher.yaml db recovery status
codex-dispatcher --config config/dispatcher.yaml db recovery accept PROJECT ISSUE
codex-dispatcher --config config/dispatcher.yaml db recovery retry PROJECT ISSUE
codex-dispatcher --config config/dispatcher.yaml db recovery cancel PROJECT ISSUE
```

PROJECT разрешается в текущий repository, а не по историческому project_id; ISSUE — номер в этом репозитории, обязательно проверить глобальный issue_id и repository. `status` read-only, доступен при глобальном барьере. Все изменяющие команды требуют полного exclusive InstanceLock и отсутствия работающего диспетчера/исполнителей.

### 7.1 accept

Повторить чтение GitHub, установить доказанную связь PR/Issue и допустимый переход: открытый PR → review, слитый → done с правилами группы, закрытый без merge → rejected. Не запускать Codex, не создавать фиктивные executions, не обходить ограничения; недостоверный результат — отказ. Записать решение и снять только действительно разрешённые причины карантина.

### 7.2 cancel

Явно отказаться от продолжения; проверить состояние группы и прежние опубликованные результаты; архивировать диагностику по необходимости, выполнить только допустимый контролируемый переход cancelled, не удалять неизвестные Git артефакты; журнал и диагностический комментарий, где предусмотрен. Если нельзя завершить безопасно — оставить карантин.

### 7.3 retry — ОСНОВНОЙ УТВЕРЖДЁННЫЙ КОНТРАКТ

Условия: Issue в карантине; Codex и daemon остановлены; успешно проверены GitHub PR и все относящиеся remote refs; нет опубликованного результата и чужих/неизвестных удалённых коммитов; возможна доказуемо безопасная очистка worktree и допустимой локальной ветки; нет нарушений отношений группы. Если обнаружен PR, push, неопределённость GitHub или нет уверенности в принадлежности локальных файлов — НЕ выполнять опасный сброс, карантин оставить. Никаких force-push и удаления remote branch.

Успешный retry реализуется повторяемой state-machine:
1. Зарегистрировать уникальный `operation_id`/фазу, сохранять карантин до конца; надёжно сохранить исходную идентичность и предпосылки.
2. Сохранить **до первого разрушительного действия** долговечный архив старой executions, всех связанных error_log сведений, статуса, времени, веток/SHA/признаков публикации, исходного approve/hash и причины. Архив без секретов и без произвольных файлов worktree.
3. Нейтрализовать старую GitHub approve и проверить её отсутствие. Не принимать прежнюю метку после сбоя.
4. Удалить только доказанно принадлежащий Issue worktree штатным git worktree механизмом и допустимую исключительно локальную ветку; удалённые refs не трогать. Очистка повторного вызова безопасна.
5. Атомарно с учётом FK удалить старую строку executions (связанную диагностику перенести в архив/безопасно отвязать), освободить UNIQUE(issue_id); state_history сохраняется.
6. Сбросить прежний approval/approved_at и прочие активные поля, сохранив снимок в архиве; специальным recovery-переходом вернуть Issue в discovered.
7. Опубликовать GitHub diagnostic comment с уникальным operation_id; фиксировать comment_id; при неопределённом POST перед повтором проверять существование комментария по маркеру.
8. Только когда проверены результаты шагов и все причины разрешены, снять карантин и завершить operation. Если есть другие причины, оставить блокировку и сообщить.
9. После retry новый пользовательский dispatcher:approve ОБЯЗАТЕЛЕН; старое approve нельзя трактовать как новое. Отсутствие старой метки должно быть наблюдено и сохранено. Новый approve через обычный PollService приводит discovered→pending, затем штатное исполнение.

Сообщение GitHub: «Codex Dispatcher — Recovery retry. Предыдущее незавершённое исполнение сброшено после db restore; опубликованный результат не обнаружен; локальная работа удалена; диагностика сохранена; Issue возвращена в discovered. Для повторного выполнения проверьте постановку и заново установите dispatcher:approve». Указывать маркер operation_id для дедупликации.

Ошибки/прерывания между SQLite, Git и GitHub: не нарушать инварианты; сохранять фазу recovery_operations и карантин; повторная команда должна продолжить/идемпотентно завершить, не архивировать и не удалять повторно. Не оставлять состояние без quarantine при незавершённом retry.

## 8. SQLite, строгая схема, upgrade

V2.4.1: schema_migrations содержит version=1; dispatcher_metadata.format_version=1. V2.4.2: история schema_migrations сохраняет 1 и добавляет 2; format_version=2. Не пытаться интерпретировать обе версии одинаковым эталоном _validate; отдельные точные DDL и проверки с whitelist известных версий.

Новые логические таблицы (конкретный DDL/индексы агент уточняет с сохранением контрактов):

- `recovery_quarantine(issue_id FK, reason_code, details, created_at, updated_at, PRIMARY KEY(issue_id,reason_code))`;
- `recovery_events(id PK, issue_id FK, session_id, operation_id, action, reason_code, details, created_at)` — append-only;
- `recovery_sessions(session_id PK, started_at, completed_at, status, checked_issues, quarantined_issues, summary)` — успешно завершённые sessions; fail до commit вне БД в diagnostics;
- `recovery_execution_archive(archive_id PK, operation_id UNIQUE, issue_id FK, original_execution_id, execution_snapshot JSON TEXT, related_diagnostics JSON TEXT, reason, archived_at)`;
- `recovery_operations(operation_id PK, issue_id FK, action=accept/retry/cancel, phase, started_at, updated_at, github_comment_id, details)` — не более одной активной операции на Issue;
- `recovery_approval_reset(issue_id PK FK, operation_id, requested_at, old_approved_hash, approval_absent_observed boolean, completed_at)`.

Использовать CHECK, FK, необходимые индексы и строгую схему. Держать данные минимальными, не записывать секреты.

`db upgrade`: только под lock после точной проверки V2.4.1 и UUID; сначала атомарно/через SQLite Backup API создать отдельный проверенный backup 0600; затем транзакционно создать новые таблицы, обновить metadata и schema_migrations; verify integrity/FK/DDL; сохранить recovery_required неизменным. Повторный upgrade на V2.4.2 без destructive effect; чужой/неизвестный формат отклонить. Не выполнять upgrade автоматически на старте.

`db restore` в V2.4.2 принимает только проверенные зарегистрированные V2.4.1 или V2.4.2 того же UUID. Для V2.4.1 проверить исторический DDL и мигрировать staging до актуального DDL; для V2.4.2 сохранить уже имеющиеся карантин и аудит, назначить recovery_required=1. Применять существующую политику lock, WAL, atomic replace и before-restore snapshot. Fail closed при несогласованной БД/неизвестной схеме.

## 9. Консистентность

- SQLite транзакция атомарна только локально: GitHub POST, Git clean, SQLite должны быть согласованы через persistent intent/phase/outbox.
- Одна глобальная операция допуска снимает metadata barier исключительно в той транзакции, где фиксируются финальные результаты и карантин.
- Не удалять quarantine через обычный poll или при совпадении внешнего состояния.
- Ошибка GitHub и отсутствие доказательств — отказ, а не «успех с предупреждением».
- Runtime и maintenance должны отсекать любые побочные действия для quarantined Issue, включая наследуемые recovery-пути и очистку.
- Не блокировать весь диспетчер при локальных конфликтах после успешной полной сверки.

## 10. Тесты и приёмка

Автоматические тесты (Fake GitHub и локальный Git, временная SQLite, fault injection): migration 1→2, rollback, exact DDL/FK, safe restore v2.4.1/v2.4.2, повтор upgrade/recover, global fail closed при неполном API, pending/preparing/running/manual-running/review/done/cancelled, открытый/слитый/закрытый/ретаргетированный PR, worktree/remote branch, subissues и вложенные контейнеры, независимые Issue, блокировки Scheduler/Executor.recover/Publisher/Cleanup, accept/cancel/retry, сбой в каждой фазе retry, архив до удаления execution, связанные error_log FK, дедупликация комментария, T2 и старое approve, UUID/locks/symlinks, audit и ограничение количества API calls.

Ручная приёмка на CodexAgentPlayground:
1. backup+restore без конфликтов и успешный recover;
2. старый pending, но PR существует: нет повтора Codex;
3. preparing/running с локальным worktree, без push/PR: карантин;
4. retry очищает worktree, архивирует execution, переводит discovered, публикует комментарий;
5. прежний approve не срабатывает, новый approve переводит pending;
6. quarantined child блокирует контейнер, независимая Issue работает;
7. GitHub unavailable при recover сохраняет общий барьер;
8. прерывание retry и повтор команды не удаляют лишнего и не дублируют комментарии.

Критерий готовности: все тесты проходят, V2.4.1 контракты не регрессируют, PR и merge только после ручной приёмки. Отчёт реализации перечисляет изменения, команды тестов, остаточные ограничения и проверенные сценарии.
