# V2.5 — Общая спецификация поставки: WSL2, Ubuntu native и Docker

**Проект:** Codex Dispatcher V2  
**Репозиторий:** `heroicrealm/CodexAgent`  
**Базовая ветка:** `CODEXAGENT_V2`  
**Редакция:** консолидированная спецификация от 2026-11-16  
**Статус:** принятые архитектурные решения; реализация распределена по V2.5.1–V2.5.5.

## 1. Цель и границы

Эта спецификация фиксирует общие требования **всей V2.5**, а не единое задание агенту. Реализация и приемка разделены на этапы V2.5.1–V2.5.5. Текущее небольшое задание: [V2.5.1](v2.5.1-spec.md).

Подготовить существующую реализацию V2 к трем способам эксплуатации:

- **WSL2:** пользователь вручную запускает диспетчер, выполняет задачи и штатно останавливает его; запуск WSL при старте Windows не нужен.
- **Ubuntu native:** постоянная системная служба `systemd`, отдельный непривилегированный Linux-пользователь, работа без интерактивного терминала.
- **Docker:** единый образ для работы диспетчера, первоначальной настройки и административного CLI; изменяемые данные и авторизация — вне образа.

V2.5.1 охватывает только аудит существующего ядра, необходимые исправления процесса и единый HTTPS-транспорт. Установочные сценарии WSL2, systemd, Dockerfile/Compose, публикация образа и интеграционные проверки выполняются в последующих подэтапах.

**Не менять** логику GitHub Issues/PR, модель состояний, схему SQLite, политику Recovery и поведение очереди, кроме минимальных документированных исправлений, без которых инфраструктурная поставка невозможна. Совместимость с V1 и миграция V1 не требуются.

## 2. Исходные контракты V2 (не реализовывать заново)

Следующие механизмы уже существуют в ветке `CODEXAGENT_V2`:

1. Публичная foreground-команда `codex-dispatcher run` (в том числе `run --once`). Не планировать её как новую CLI-команду; проверить пригодность для systemd/Docker.
2. Разрешение конфигурации: явный `--config` приоритетен; иначе абсолютный `$XDG_CONFIG_HOME/codex-dispatcher/config.yaml` или `~/.config/codex-dispatcher/config.yaml`. CWD, дерево исходников и `/etc` автоматически не сканируются.
3. `dispatcher.root_path` — абсолютный корень установки; относительные `dispatcher.database`, `dispatcher.workspace` и `project.checkout` разрешаются относительно него. Пример текущего V2: `database: runtime/dispatcher.sqlite3`, `workspace: workspace`.
4. Идентичность установки: UUID/metadata SQLite и маркер `.dispatcher-instance` в workspace должны оставаться согласованными; текущие InstanceLock, control socket, проверки PID/start time и Recovery admission нельзя обходить.
5. Операции SQLite `db bootstrap`, `db check`, `db backup`, `db restore`, `db recover` и другие команды обслуживания имеют собственные существующие предусловия и блокировки.
6. CLI `status`, `queue`, `show` доступны для локального мониторинга, включая остановленный daemon (по текущему контракту мониторинга). `stop [--force]` использует существующий управляющий канал.

Перед правками агент обязан сверить все утверждения с актуальным кодом ветки V2 и зафиксировать обнаруженные расхождения. Не переносить поведение V1 из устаревших `docs/specification.md` или корневого README другой ветки.

## 3. Режимы процесса

### 3.1. Единый runtime

Один планировщик, один набор адаптеров и одна реализация управления дочерними процессами для всех вариантов. Выбор способа запуска не должен менять функциональность задач и публикации.

`run` работает в текущем процессе, не daemonize и не запускает вторую копию диспетчера. Код возврата должен однозначно различать штатное завершение и сбой. Ошибки до инициализации собственных логов должны попадать в stderr.

### 3.2. WSL2

Сохранить периодическое управление через CLI. Не требовать systemd, Windows Services, Планировщик заданий Windows или автозапуск WSL. Для штатной работы допустим foreground `run`; дополнительный менеджер фонового процесса не должен дублировать scheduler. Специальное введение команды `start` без отдельного утверждения не требуется: она не является текущим контрактом V2.

### 3.3. Ubuntu/systemd

Принята **системная**, а не пользовательская служба (`systemd --user` не требуется), с `User=` для выделенного непривилегированного пользователя. Systemd выполняет существующий `run` с явным абсолютным `--config /etc/codex-dispatcher/config.yaml`; значение является целевым соглашением установщика, не новым правилом поиска конфига.

- `WorkingDirectory`, сервисный Linux-пользователь, `HOME`, `PATH` и необходимые права записи должны быть заданы явно. Расположение, формат, хранение и управление credentials определяются самими `gh` и Codex CLI; инфраструктура лишь обеспечивает доступность их штатных пользовательских данных при одинаковом окружении.
- Для штатной остановки systemd передаёт SIGTERM и **не прерывает бесконечное ожидание активных задач таймаутом**. Целевое значение `TimeoutStopSec=infinity`; фактическое поведение проверить в systemd.
- Выбор `KillMode` (предварительно `mixed`) должен быть обоснован тестом с деревом дочерних процессов, чтобы systemd не уничтожил активный Codex при начале обычного stop.
- Автозапуск включается оператором в процессе установки; после неустранимой ошибки конфигурации или авторизации не допускается бесконечный restart-loop.
- Управление жизненным циклом службы — через `systemctl`. Внутренний CLI `stop` не должен противоречить `Restart=` и управлению systemd; безопасный контракт для операторов описать в документации.

### 3.4. Docker

Основной процесс — `run` в foreground, получает SIGTERM. Нет systemd и внутреннего supervisord, если его необходимость не доказана. Предусмотреть корректную передачу сигналов, при необходимости `init: true` для reap дочерних процессов.

Для штатной остановки без временного лимита нужен соответствующий способ остановки Docker/Compose (например, `docker stop --timeout=-1` при поддержке движком); обычный `docker stop` со стандартным конечным timeout **не выполняет** принятую политику A. Формально проверить параметры целевых версий Docker и Compose при реализации.

Внешние `docker kill`, остановка хоста, авария daemon Docker и принудительное удаление контейнера не гарантируют graceful shutdown.

## 4. Остановка, блокировки, восстановление

**Принятое правило A:** обычный stop запрещает новые задания, даёт уже активным заданиям закончить, завершает необходимые операции фиксации/публикации и освобождает ресурсы **без фиксированного предела ожидания**. Повторный SIGTERM не превращает остановку в force.

Принудительное завершение (`stop --force` или эквивалентный предусмотренный механизм) сохраняет алгоритм действующего Lifecycle: SIGTERM группам управляемых процессов, ограниченный grace period, затем SIGKILL оставшимся; при необходимости ожидать реального ухода потомков. Сигналы не должны попадать чужим PID/PGID.

Сохранить проверки двух блокировок, control socket, идентичности процессов и admission для SQLite. Состояние `running` в БД само по себе не доказывает живой процесс; устаревшие socket/PID не должны создавать ложное подтверждение активности. Не ослаблять fail-closed восстановление.

Запретить одновременные рабочие экземпляры на общих SQLite и workspace, включая разные контейнеры. Поддерживаемые volumes должны обеспечивать корректную межпроцессную работу `flock`; не заявлять защиту для произвольных внешних клиентов, обходящих протокол блокировок.

Операции обновления или пересоздания установки: сначала штатная остановка, потом изменение ПО. Обновление не удаляет SQLite, WAL/SHM, workspace, маркер UUID, результаты и журнал восстановления. Прерванные задачи не возобновляются автоматически вопреки существующему контракту Recovery.

## 5. Конфигурация и размещение данных

**Не менять текущий V2 resolver.** Не добавлять конкурирующую схему `paths.state`, не выполнять поиск конфига в `/etc` автоматически, не вводить молчаливую миграцию путей.

Требуемое разделение — на уровне размещения данных установки:

- YAML-конфигурация (XDG для пользователя, явный путь `/etc/codex-dispatcher/config.yaml` для системного unit).
- Постоянная SQLite и её сопутствующие файлы.
- Рабочие Git checkout, worktree, результаты и маркер экземпляра.
- Журналы и данные диагностики.
- Файлы авторизации `gh` и Codex — отдельно от образа и рабочих Git-репозиториев.

Это достигается существующими `root_path`, `database`, `workspace` и средствами установки; новые конфигурационные поля добавлять лишь при доказанной необходимости. Сохранить валидность текущих V2-конфигов.

Для системной установки предлагаются `/etc/codex-dispatcher/config.yaml` и выделенное приватное дерево в `/var/lib/codex-dispatcher`; конкретные пути SQLite/workspace задаются YAML. Для Docker конфигурация, база, workspace и credentials монтируются извне. Требуется стабильный UID/GID контейнерного пользователя и безопасные права 0600/0700, где применимо.

**Критически важно:** UUID-маркер workspace и SQLite переносить/сохранять согласованно. Нельзя автоматически создавать пустую БД вместо отсутствующей/недоступной существующей. `db bootstrap` применяется только к действительно новой установке и по явной процедуре, `db check` — к существующей.

## 6. Авторизация GitHub, Git и Codex

### 6.1. Разделение

- **GitHub API:** действующая долговременная авторизация GitHub CLI (`gh`).
- **Codex CLI:** действующая долговременная штатная авторизация Codex.
- **Git clone/fetch/push:** только HTTPS с Git credential helper GitHub CLI. Старый SSH-ключ с парольной фразой в WSL2 является историческим способом доступа и более не используется диспетчером после перевода служебных remote.

Не запрашивать у пользователя пароли аккаунтов средствами диспетчера. Не помещать токены в YAML, SQLite, логи, Git remote URL, Dockerfile, image layers или сборочные ARG/ENV.

### 6.2. Единый Git-транспорт HTTPS

Для **всех управляемых диспетчером Git-операций** в WSL2, Ubuntu native и Docker принят исключительно HTTPS. Канонический remote для GitHub: `https://github.com/OWNER/REPOSITORY.git` (без встроенных токенов, логинов или паролей). Git-авторизация выполняется через штатный credential helper `gh`, настраиваемый оператором командой `gh auth setup-git`. Все новые служебные clone должны получать HTTPS remote независимо от старого пользовательского значения `gh` git protocol; проверить фактическое поведение `gh repo clone` и выбрать безопасный способ принудительно использовать HTTPS.

`gh auth status` не является проверкой работы Git credential helper, а успешный GitHub API-запрос не гарантирует возможность Git push. Требуется безопасная неинтерактивная диагностика HTTPS Git с `GIT_TERMINAL_PROMPT=0` и проверкой фактических fetch/push URL. Не заявлять подтверждение права записи без соответствующей проверки.

**Существующие служебные SSH remote не переписывать молча.** При обнаружении SSH remote остановить соответствующую Git-операцию с диагностикой и предоставить отдельную явную, проверяемую процедуру перевода управляемого checkout на HTTPS. Перед изменением проверить принадлежность checkout, ожидаемый GitHub repository и фактические fetch/push URL; не изменять сторонние пользовательские checkout. Git worktree, ветки и коммиты должны сохраниться. Не допускается подмена удалённого репозитория или запись токена в remote URL.

После перевода SSH не является поддерживаемым способом Git-доступа диспетчера. Создание SSH-ключей, запуск `ssh-agent`, настройка SSH remote и автоматический fallback на SSH **не входят** в V2.5.

### 6.3. Ubuntu

Начальная авторизация `gh` и Codex выполняется от имени выделенного сервисного Linux-пользователя штатными средствами; дальнейшая работа — без терминала. `HOME` и необходимые параметры окружения должны совпадать у службы и административного CLI. Местоположение и формат credentials определяются штатными механизмами внешних CLI, не кодом диспетчера. Credentials не копируются из домашнего каталога администратора автоматически.

### 6.4. Docker

**Один универсальный образ**, без credentials. При первоначальной настройке на **целевой машине** пользователь запускает временный интерактивный контейнер с теми же постоянными mounts и выполняет вручную `gh auth login`, штатный вход Codex CLI и `gh auth setup-git` при необходимости. Контейнер не запускает логин автоматически, не знает пароли и не запрашивает их своим установщиком.

Авторизация сохраняется в специальных постоянных volume(s) и переживает пересоздание контейнера. Не монтировать весь пользовательский HOME без необходимости; обеспечить доступ только нужному UID/GID. В случае отсутствующей/неработоспособной авторизации рабочий dispatcher не запускается, причина выводится без утечки секретов. При повторной авторизации пользователь самостоятельно выполняет процедуру интерактивного входа.

Способ безопасной проверки авторизации Codex зависит от реально установленного CLI: проверять доступные read-only команды, не выполнять дорогое или изменяющее задание только ради диагностики; если достоверная проверка невозможна — диагностировать неопределённость, а не выдавать ложный PASS.

## 7. Docker: один образ, два канала поставки

Единый образ содержит Python, Git, GitHub CLI, Codex CLI и диспетчер. Из него создаются **разные контейнеры по назначению**, без отдельных образов:

- рабочий `dispatcher run`;
- временный интерактивный контейнер для настройки/повторной авторизации;
- одноразовый контейнер `db bootstrap`, `db check`, backup/recovery и других допустимых операций;
- одноразовый CLI-контейнер для чтения очереди/статуса при остановленной основной службе.

При работающем контейнере допустим `docker exec ... codex-dispatcher queue`. При остановленном — `docker compose run --rm ... codex-dispatcher queue` с теми же mounts. Никакой одноразовый CLI-контейнер не должен по умолчанию запускать основной loop. Для изменяющих операций сохраняются ограничения V2 и контроль блокировок.

**Способы поставки, реализуемые оба:**

A. **Локальная сборка:** исходники, Dockerfile, Compose, скрипты и инструкции в GitHub; сборка на целевой машине.

B. **Готовый образ:** после успешной приёмки Docker-этапа V2.5 собрать и протестировать тот же Dockerfile из фиксированного commit, опубликовать версионированный образ в Docker Hub, указать исходный commit SHA и процедуру установки. Должны быть предусмотрены воспроизводимые версии, а не обязательная опора на `latest`. Имя Docker Hub репозитория утверждается при подготовке публикации.

Оба пути используют **идентичную процедуру настройки на целевой машине**; исходники и образы не содержат авторизацию и данные конкретной установки. Повторная установка не стирает конфигурацию, SQLite, UUID-маркер, workspace, результаты и volumes. Скрипты установки/обновления должны быть идемпотентными и останавливаться при конфликте.

Публикация Docker Hub входит в завершающую поставку Docker V2.5, **не** в реализацию общего ядра V2.5.1.

## 8. Первоначальная подготовка Docker

Установочный сценарий (реализация — последующий Docker-подэтап):

1. Получить образ (локально собрать или загрузить).
2. Создать целевые постоянные volumes и конфигурацию для **новой** установки, не затирая существующие данные.
3. При необходимости запустить интерактивный одноразовый контейнер: пользователь вручную выполняет авторизацию `gh` и Codex.
4. Настроить HTTPS Git credential helper; проверить доступность GitHub API и безопасную неинтерактивную Git-операцию.
5. Для действительно новой установки — выполнить `db bootstrap`; для существующей — `db check`, не пересоздавать БД.
6. Проверить соответствие UUID SQLite и workspace, доступность/права томов, нужные prerequisites.
7. Только после успешной подготовки запустить рабочий контейнер.

Не пытаться хранить токены в build stage или «промонтировать volume во время docker build». Не запускать автоматически login при старте рабочего контейнера. Ошибки подготовки оставляют данные сохранными и имеют понятный диагностический вывод.

## 9. CLI администрирования

- **Ubuntu:** оператор пользуется своим аккаунтом. Для CLI, требующего доступ к файлам сервисного пользователя, предоставить документированную ограниченную sudo-обёртку, запускающую CLI с правильными `User`, `HOME`, `PATH` и `--config`, без интерактивного входа в сервисную сессию. `start/stop/restart` службы — через `systemctl`, чтение системного журнала — `journalctl`.
- **Docker:** при живом контейнере `docker exec`; при остановленном — одноразовый CLI-контейнер с идентичными volumes и путём конфигурации.
- **WSL2:** штатный пользовательский CLI V2.

Считать доступ к изменяющим CLI-командам привилегированным: не разрешать всем пользователям произвольные команды от сервисного UID. Обёртка не должна открывать возможность произвольного shell/подмены исполняемого файла через PATH. Для действий с подтверждением в TTY (например, `project remove`) обеспечить передачу интерактивного терминала и сохранение требований V2.

Управляющие команды не должны обходить guards для `db restore`, `project remove`, Recovery и других разрушительных операций. Просмотр состояния не должен требовать запуска daemon.

## 10. Диагностика и журналирование

Сохранить существующие безопасные диагностические команды и вывод мониторинга V2; новый `doctor` может быть добавлен только как обоснованное дополнение, с проверками без побочных эффектов:

- корректность конфига, разрешённых путей, наличия SQLite и согласованности identity;
- необходимых Linux-примитивов, прав каталогов и возможности неблокирующего чтения;
- программ `git`, `gh`, `codex`, `HOME/PATH`;
- авторизации `gh` и доступности Git credential helper для HTTPS;
- фактические HTTPS fetch/push remote всех управляемых checkout; SSH remote диагностируется как несовместимый с принятым транспортом и требует явного перехода;
- известного безопасного способа проверки Codex login;
- отсутствия конфликта с работающим экземпляром и противоречий в его идентичности.

Диагностика не должна создавать SQLite, выполнять `db bootstrap`, изменять GitHub, делать push или запускать Codex задание. При недостатке подтверждений — `WARN/UNKNOWN`, не ложный успех. Секреты, содержимое auth-файлов и свободный вывод внешних CLI не публиковать в логах.

Для systemd сообщения доступны в journald, для Docker — в `docker logs`; ошибки раннего запуска выводить в stderr. Сохранить журналы, необходимые существующему мониторингу и восстановлению, и не дублировать одно событие неконтролируемо.

## 11. Общие требования к тестированию V2.5

По мере выполнения соответствующих подэтапов должны быть реализованы автоматические тесты без реальных токенов и сетевых изменений:

1. Актуальный `run` запускается foreground с ожидаемой обработкой завершения и кодом возврата.
2. SIGTERM/INT => graceful без фиксированного timeout; второй SIGTERM не становится force; `stop --force` сохраняет действующий контракт.
3. Длительный ребёнок и потомки не получают SIGKILL при обычном stop; force очищает собственную группу, не чужую.
4. Одновременные экземпляры/попытка одноразового CLI на общей SQLite не обходят существующие locks/guards.
5. Неоднозначные stale PID/socket и UID/UUID mismatch приводят к безопасному отказу.
6. `--config`, XDG и `root_path` сохраняют **реально существующие** правила V2; нет обращения к CWD или автоматического перехода на другой SQLite.
7. Конфигурация системной службы использует явный путь, не предполагает пользовательский XDG root.
8. Без Git credentials тесты завершаются диагностикой, не интерактивным зависанием; HTTPS clone/fetch/push проверяются заглушками и локальными Git, существующий SSH remote отклоняется до явной миграции, автоматического fallback на SSH нет.
9. Отсутствующие Codex credentials не ведут к автоматическому login.
10. `db bootstrap` не выполняется автоматически при запуске и не перезаписывает существующую SQLite.
11. Мониторинг и административные команды сохраняют read-only контракты и режим stopped.
12. Тесты V2.4.x и проверка упаковки проходят без регрессий.

Ручные платформенные тесты в следующих этапах: systemd c активным долгим Codex; Docker stop без лимита; одноразовый контейнер для обслуживания; интерактивная авторизация в volume; обновление образа при сохранении SQLite/workspace/авторизации; HTTPS fetch/push при отключённом SSH agent; восстановление после kill.

## 12. Сводные критерии приёмки V2.5

Эти пункты относятся ко всей V2.5 и принимаются на соответствующих подэтапах, а не все в V2.5.1:

- [ ] Сверены текущие `run`, config resolver, paths, identity, locks и Recovery с `CODEXAGENT_V2`; устаревшие требования V1 исключены.
- [ ] Единый foreground/runtime пригоден для последующих systemd и Docker адаптеров.
- [ ] Обычная остановка ждёт активные задания без фиксированного ограничения; принудительная остановка безопасна.
- [ ] Нет дублей исполнителей при смешанных способах запуска.
- [ ] XDG resolver и `root_path` V2 сохранены; существующие установки не мигрируют и не переинициализируются молча.
- [ ] Подготовлен и проверен единый контракт неинтерактивной авторизации Git через HTTPS/`gh` во всех средах; новые remote создаются только в HTTPS, существующие SSH remote требуют безопасного явного перехода, SSH fallback отсутствует.
- [ ] Документированы `HOME`, права сервисного пользователя, административный CLI и безопасность секретов.
- [ ] Документированы контракты одного Docker image, persistent volumes, интерактивной настройки, offline CLI и двух каналов поставки.
- [ ] Проходят новые и существующие автоматические тесты.
- [ ] Обновлены документация и отчёт по выполненной работе; PR подготовлен только после ручной приёмки этапа.
