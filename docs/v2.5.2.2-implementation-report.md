Рабочая ветка: `V2_5_2_2_STANDALONE_IMPROVEMENTS`. Пакет: `2.5.2.post2`, схема: `1`.
Коммит реализации и тестов: `457b861` (`Implement standalone 2.5.2.post2 installer verification and lifecycle`). Документация и отчет зафиксированы следующим коммитом этой ветки.

Реализация подготовлена к ручной приемке. Реальный интерактивный сценарий WSL2 владельцем еще не подтвержден. PR, merge, push, тег и GitHub Release агентом не выполнялись.

## Измененные файлы

- `scripts/standalone_distribution.py`: read-only SHA preflight до создания namespace установки, раннего сравнения версий и prerequisite-команд; managed installer в поколении venv; ownership, доставка, переключение и rollback; подтверждение удаления под installer/runtime locks.
- `scripts/embed-standalone.py`, `install-standalone.sh`, `uninstall-standalone.sh`: передача фактического `$0` встроенному Python, регенерация из общего исходника.
- `src/dispatcher/__main__.py`: глобальный `--version` через `importlib.metadata.version("codex-dispatcher-v2")`; отсутствие metadata дает ненулевой код и понятную ошибку.
- `pyproject.toml`, `config/config.example.yaml`: версия post2, схема остается 1.
- `tests/test_distribution.py`: SHA match/mismatch, manifest/digest/API failure, отсутствие изменений HOME при preflight failure, равная версия, собственные/чужие symlink, доставка/repair/rollback CLI, отмена удаления и TTY, metadata, locks.
- `scripts/smoke-install.py`: реальные wheel/venv/pip, переход с legacy wheel, SQLite/YAML, db/queue/status, настоящий generated shell через установленный symlink с mock API, испорченная тестовая копия, non-TTY removal и подтверждение через PTY.
- `scripts/smoke-wheel.py`, `.github/workflows/standalone-release.yml`: версия и проверки CLI, bundle с post2 notes. Workflow не публикует Release.
- `README.md`, `docs/standalone.md`, `docs/releasing.md`, `docs/releases/v2.5.2.post2.md`, этот отчет: переход, SHA contract, команды и приемка.

Scheduler, GitHub adapters, Issue/PR, Service и Docker не изменены.

## Контракты отказа и ограничения

SHA mismatch возвращает ненулевой код, URL конкретного Release и инструкцию вручную скачать installer + SHA256SUMS, проверить и повторить запуск. Не создаются каталог установки, ownership, поколения и ссылки, не меняются YAML/SQLite. Новый installer payload не скачивается/не исполняется для автоматической замены. Ошибки API/manifest/digest/checksum также не пропускают проверку. Bootstrap создает временный venv и устанавливает зависимости до Python preflight, как и раньше; для запуска shell нужен доступ к Python dependencies (либо подготовленный pip cache/wheelhouse).

Собственная symlink-команда разрешена только при совпадении ownership, target и активного поколения. Произвольная symlink на скачанный installer отклоняется. При обычном файле проверяются его байты. Изменение комментария также требует ручного получения точного опубликованного файла.

Удаление: `n`, Enter, EOF, Ctrl+C отменяют операцию с кодом 0; non-TTY — ненулевой код. Только `y` после strip/lower выполняет удаление. При активном runtime отказ предшествует вопросу. Общий lock inode сохраняется, данные пользователя не удаляются.

До публикации post2 production latest содержит прежний installer: новый скрипт ожидаемо откажет по SHA. Для предварительной приемки используется локальный mock metadata, без ослабления production-кода. Проверка реальной GitHub-доставки возможна после отдельно разрешенной публикации. Результаты CI Python 3.11 и ручной WSL2/Ubuntu native приемки должен подтвердить владелец.

## Ручная приемка WSL2

Использовать отдельного тестового Linux-пользователя/дистрибутив WSL2 с установленной post1 и тестовым проектом. Остановить dispatcher, дождаться `STOPPED`. Не использовать рабочие credentials в mock-сценариях. Сохранить резервные копии YAML, SQLite, список Issue/queue и контрольные суммы пользовательских sentinel-файлов (workspace/worktrees, checkout, credentials); не копировать секреты в отчет.

### 1. Candidate до публикации

После push скачать artifact `standalone-release-candidate` успешного CI в пустой Linux-каталог. Checkout должен соответствовать тому же commit. Далее из корня checkout (пути заменить на свои):

```sh
export CANDIDATE_DIR="$HOME/Downloads/standalone-release-candidate"
(cd "$CANDIDATE_DIR" && sha256sum -c SHA256SUMS)
cmp install-standalone.sh "$CANDIDATE_DIR/install-standalone.sh"
cmp uninstall-standalone.sh "$CANDIDATE_DIR/uninstall-standalone.sh"
python3 -m venv /tmp/dispatcher-accept-tools
/tmp/dispatcher-accept-tools/bin/pip install PyYAML packaging
```

Для обновления именно тестовой post1 до публикации выполнить следующий harness из checkout. Он подменяет только ответы release API локальным проверенным bundle и вызывает тот же установщик с реальным интерактивным подтверждением и locks; HOME/XDG остаются тестового пользователя. Это инструмент ручной приемки, не способ обычного обновления:

```sh
cat > /tmp/dispatcher-candidate-accept.py <<'PY'
import hashlib, importlib.util, json, os
from pathlib import Path
root = Path(os.environ['CANDIDATE_DIR']).resolve()
spec = importlib.util.spec_from_file_location('distribution', 'scripts/standalone_distribution.py')
m = importlib.util.module_from_spec(spec)
spec.loader.exec_module(m)
names = ['SHA256SUMS', 'install-standalone.sh', 'uninstall-standalone.sh',
         'config.example.yaml', next(root.glob('*.whl')).name]
release = {'tag_name': 'v2.5.2.post2', 'assets': [
    {'name': name, 'browser_download_url': 'https://candidate.invalid/' + name,
     **({'digest': 'sha256:' + hashlib.sha256((root / name).read_bytes()).hexdigest()}
        if name == 'SHA256SUMS' else {})} for name in names]}
def fetch(url):
    if url == m.LATEST:
        return json.dumps(release).encode()
    assert url.startswith('https://candidate.invalid/')
    return (root / url.rsplit('/', 1)[1]).read_bytes()
m.fetch = fetch
script = Path(os.environ.get('ACCEPT_SCRIPT', str(root / 'install-standalone.sh')))
m.main(script_path=script)
PY
/tmp/dispatcher-accept-tools/bin/python /tmp/dispatcher-candidate-accept.py
```

Ответить `y` на установку. Проверить следующие команды без активации venv:

```sh
export PATH="$HOME/.local/bin:$PATH"
codex-dispatcher --version                    # Codex Dispatcher 2.5.2.post2
codex-dispatcher --config-schema-version      # 1
command -v codex-dispatcher-install
readlink "$HOME/.local/bin/codex-dispatcher-install"
codex-dispatcher db check
codex-dispatcher queue --json
codex-dispatcher status --json
```

Сравнить YAML с резервной копией: меняется только `dispatcher_version`; SQLite, Issue и пользовательские настройки сохраняются. Проверить `--version` с отсутствующим или поврежденным тестовым `--config`: версия должна выводиться без чтения YAML.

Повторить harness через установленный symlink:

```sh
ACCEPT_SCRIPT="$HOME/.local/bin/codex-dispatcher-install" /tmp/dispatcher-accept-tools/bin/python /tmp/dispatcher-candidate-accept.py
```

Ожидается `is current`, без создания поколения. Полный shell/PTY путь с mock HTTP можно независимо повторить в изолированном HOME автоматически (нужен wheelhouse под Python этой WSL):

```sh
/tmp/dispatcher-accept-tools/bin/pip download -d /tmp/dispatcher-accept-wheelhouse "$CANDIDATE_DIR"/*.whl
/tmp/dispatcher-accept-tools/bin/python scripts/smoke-install.py "$CANDIDATE_DIR"/*.whl /tmp/dispatcher-accept-wheelhouse
```

### 2. SHA и недоступность проверки

Снять SHA YAML/SQLite, содержимое ownership и `readlink ~/codex-dispatcher/.venv`. Испорченный файл должен быть отдельной копией:

```sh
cp "$CANDIDATE_DIR/install-standalone.sh" /tmp/dispatcher-altered.sh
printf '\n# acceptance byte change\n' >> /tmp/dispatcher-altered.sh
ACCEPT_SCRIPT=/tmp/dispatcher-altered.sh /tmp/dispatcher-accept-tools/bin/python /tmp/dispatcher-candidate-accept.py
```

Ожидается отказ и URL `.../releases/tag/v2.5.2.post2`, все снятые значения неизменны. Для проверки недоступности запустить обычную команду с заведомо недоступным proxy (bootstrap тоже может отказать раньше API — это допустимый отказ без изменения установки):

```sh
HTTPS_PROXY=http://127.0.0.1:9 HTTP_PROXY=http://127.0.0.1:9 ALL_PROXY=http://127.0.0.1:9 codex-dispatcher-install
```

Проверка именно отказов release API/manifest/digest без зависимости bootstrap: `python -m pytest tests/test_distribution.py -q` в окружении с test dependencies. Ожидается ненулевой код установщика, YAML/SQLite/venv/ownership неизменны.

### 3. Подтверждение удаления и locks

В STOPPED выполнить `codex-dispatcher-uninstall` отдельно с `n`, Enter, Ctrl+D и Ctrl+C на вопросе. Каждый раз установка сохраняется (отмена код 0). `printf 'y\n' | codex-dispatcher-uninstall` должен вернуть ненулевой код без удаления.

Запустить `codex-dispatcher run` с тестовым проектом в другом терминале; убедиться в RUNNING, выполнить удалитель: отказ до вопроса, без автоматической остановки. Затем выполнить `codex-dispatcher stop`, дождаться STOPPED и сверить сохранность Issue/queue.

При STOPPED выполнить удалитель и ответить `y`. Все три `~/.local/bin/codex-dispatcher*` управляемые команды и поколения удаляются. YAML, SQLite, workspace/worktrees, checkout и credentials сохраняются, lock inode остается. Выполнить `hash -r`, проверить отсутствие команд. Установить заново через candidate harness, проверить `db check`, `queue`, настройки и сохраненные sentinel-файлы без повторного bootstrap существующей БД.

По возможности повторить сценарий в Ubuntu native. Записать дату, WSL/Ubuntu/Python версии, commit, SHA bundle, результаты каждого пункта и отклонения; секреты в протокол не включать.

### 4. Действия владельца и реальная доставка

1. Выполнить `git push origin V2_5_2_2_STANDALONE_IMPROVEMENTS`.
2. Дождаться CI, скачать и проверить candidate, пройти приемку выше. Зафиксировать согласованный commit.
3. Только после подтверждения приемки и отдельного разрешения создать тег `v2.5.2.post2` и Release по `docs/releasing.md`. Не создавать PR/merge как часть этого задания.
4. После разрешенной публикации скачать installer и SHA256SUMS из одного конкретного Release в новый пустой каталог:

```sh
gh release download v2.5.2.post2 --repo heroicrealm/CodexAgent --pattern install-standalone.sh --pattern SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS
sh install-standalone.sh
codex-dispatcher-install
```

Подтвердить реальный latest/digest, первоначальное обновление с post1, повторную установку через постоянную команду и отказ измененной тестовой shell-копии. После появления следующего релиза несовпадение SHA установленного installer — ожидаемое требование ручного скачивания актуальных байтов, а не автоматическое обновление скрипта.
