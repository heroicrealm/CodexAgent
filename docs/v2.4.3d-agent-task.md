## 2. BUG-01: stale UNIX socket после нештатного завершения

**Воспроизведение:** завершение WSL2/компьютера без `codex-dispatcher stop`; после перезагрузки `status` показывает `Daemon: UNKNOWN`, а `stop` вызывает необработанный `ConnectionRefusedError: [Errno 111]`. Штатные `run`/`stop` исправны.

Исправить:
- `codex-dispatcher stop` не должен показывать traceback для ожидаемых `ENOENT`, `ECONNREFUSED`, timeout или stale socket; сообщать понятный результат/диагностику.
- Если отсутствие процесса **достоверно доказано** (проверка InstanceLock, отсутствия владеющего daemon, подтверждения PID+starttime/сокета), `status` должен отображать `STOPPED` даже при оставшемся устаревшем socket-файле.
- При неоднозначности сохранять `UNKNOWN`; не считать устаревший `.monitor.json` доказательством `RUNNING`.
- Не удалять сокет или lock-файлы потенциально работающего процесса; не нарушать конкурирующие блокировки; если вводится очистка stale socket, она допустима лишь при доказанной безопасности.
- Перезапуск после crash должен по-прежнему штатно восстанавливать рабочее управление.

Тесты: штатная работа/остановка; stale socket+освобождённые lock; реальные занятые lock; отсутствие socket; отказ подключения; изменившийся/повторно использованный PID; несовпадающие/старые heartbeat. Не допускать ложного STOPPED при потенциально активном daemon.

## 3. BUG-02: stale github_state='open' у закрытой диспетчером Issue

**Ручное воспроизведение:** Issue #58 переведена в `done` после merge PR #59, GitHub Issue закрыта самим диспетчером, но SQLite сохраняет `state='done', github_state='open'`. После закрытия ещё одной Issue `status` показывает `Open: 3` вместо фактически открытой на GitHub единственной Issue. `queue` исключает done независимо от этого поля, поэтому дефект заметен в `status`.

Требуется:
- Найти фактическую точку успешного закрытия Issue через GitHub API (Publisher / related services) и после **подтверждённого успеха** синхронизировать `issues.github_state='closed'` в SQLite для соответствующего глобального `issue_id`.
- **Не** подменять смысл поля: `done` сам по себе не означает `github_state=closed`; если GitHub закрыть не удалось, состояние должно оставаться достоверным.
- Обеспечить идемпотентное поведение при повторном закрытии / ответе «уже закрыто» и безопасную согласованность после crash между GitHub close и локальным commit. Использовать существующий путь reconciliation/наблюдения или минимальный адресный механизм; дополнительные запросы на каждом штатном poll запрещены.
- Проверить иные терминальные случаи, в которых **сам диспетчер** закрывает Issue, чтобы подобное расхождение не повторялось. Не менять политику ручного закрытия пользовательских Issue без необходимости.
- Если внешний GitHub API сообщает об ошибке, нельзя записывать фиктивное closed.
- `status Open` продолжает означать количество реально известных **открытых GitHub Issue**, а не просто недостигших done. `queue --all` сохраняет закрытые/терминальные записи.

Тесты: успешный close; API failure; «уже закрыта»; повтор после прерывания между операциями; последовательное завершение нескольких Issue; счётчики `Open` и `Disc.`; отсутствие дополнительных массовых GitHub API вызовов. Использовать mocks/stubs.

## 4. CHANGE-01: единственная семантика удаления проекта

**Утверждённая модель:**
- `codex-dispatcher project disable ID` — исключить из обслуживания, **сохранить всю историю**.
- `codex-dispatcher project enable ID` — вернуть в обслуживание.
- `codex-dispatcher project remove ID` — **необратимо удалить проект и ВСЕ его локальные данные**.
- `codex-dispatcher project remove ID --dry-run` — показать полный проверяемый план **без любых изменений**.
- УБРАТЬ `--purge` из CLI, подсказок и документации; не оставлять тихий режим обычного remove, сохраняющий историю. Попытка `--purge` должна быть отклонена как устаревший аргумент, а не незаметно вести себя иначе.
- Никаких `project restore-config`, `remove-orphaned` и иных одноразовых механизмов восстановления прежнего тестового окружения.

**Подтверждение как в GitHub:** после проверки условий и показа **реального** плана удаления CLI выводит `Project: ID`, `Repository: owner/repo`, число/типы удаляемых локальных объектов и явное предупреждение о необратимости. Требует, чтобы пользователь повторно набрал **точный project.id** (регистр и символы учитываются). Несовпадение, EOF, Ctrl+C, non-TTY — отказ БЕЗ создания backup или изменений. Дополнительный `--purge` не нужен и безопасности не добавляет. Защита подтверждением уже реализована в V2.4.3.C: переиспользовать, не писать второй механизм.

Перенести проверенный destructive path из `purge.execute` на `project remove` без ослабления мер безопасности: InstanceLock, остановленный daemon, проверка SQLite UUID/Recovery/FK/triggers, безопасная транзакция удаления Recovery audit, защита чужих проектов, проверка ownership local Git/worktrees/files, журнал фаз, безопасное повторное выполнение/восстановление после сбоя.

**Backup:** временная SQLite создаётся автоматически только после успешного ввода ID и всех предварительных проверок; путь `<root_path>/backups/purge/` допустимо **сохранить как внутренний путь**, хотя CLI-ключ `--purge` удаляется. На успешном завершении временный backup/журнал автоматически удаляются; при ошибке сохраняются и путь явно печатается. Старые неудачные попытки видны, не накапливаются незаметно. `--dry-run` не создаёт файлы, backup или GitHub запросы. Никаких внешних GitHub/remote изменений при remove.

После успешного удаления тот же репозиторий разрешено повторно зарегистрировать с прежним/новым project.id без retained-history конфликта. История исходной SQLite и GitHub остаются нетронутыми в иных отношениях; сам GitHub ни при каких обстоятельствах не очищается.

Обновить `project --help`, README, документацию и автоматические тесты: remove без флага осуществляет полный purge; dry-run; неверный ID; non-TTY; preconditions и backup; сохранность других проектов; recovery rollback и FK; повторный add. Устаревшие тесты обычного `remove` с сохранением history заменить. Не требовать миграции уже удалённой записи пользователя.

## 5. Rich/UI — семь согласованных замечаний

### UI-01. Цвета значений status/project list
**Подписи** Daemon, Database, Recovery, Executing, а также заголовки/рамки оставить нейтральными (белый/тема Rich). Окрашивать только сами значения:
- RUNNING, Database OK, Recovery READY, enabled — **зелёный**;
- STOPPED, BLOCKED, ошибки, disabled — **красный**;
- UNKNOWN — **жёлтый**;
- Executing с активной задачей — **голубой**;
- IDLE — **серый**.
Не окрашивать всю строку, фон, заголовки и числовые показатели.

### UI-02. Локальное время
В human-readable `status`, `show`, `show -v` преобразовывать ISO timestamps из SQLite/daemon в локальный часовой пояс **машины, запускающей CLI** (Python `datetime.fromisoformat(...).astimezone()` при aware datetime), формат `YYYY-MM-DD HH:MM:SS`; без дробных секунд и отображения `+00:00`. Поля: Last/Next poll, Started, Finished, Approved, Timeline, execution details и другие видимые даты. При отсутствии `N/A`. В **`--json` исходные ISO 8601 и машинные значения не менять**. Тестировать разные TZ (включая UTC и ненулевой offset) и корректный переход через сутки, не брать время из GitHub.

### UI-03. Branches
В `show` заменить `Branches: {'base_branch': ..., 'work_branch': ...}` на строки `Base branch: ...` и `Work branch: ...`. При отсутствии `N/A`. В JSON структура сохраняется.

### UI-04. Цвета состояний queue/show
Одна палитра значений State, только текст статуса:
- discovered, cancelled — серый;
- pending, awaiting-children, preparing — жёлтый;
- running, manual-running — голубой;
- review, done — зелёный;
- rejected, error — красный;
- need-fix — оранжевый.
Отличать pending (жёлтый) от running (голубой), не превращать всё в синий. В `show` окрашивать оба места отображения State, в `queue` только текст колонки. NO_COLOR и pipe корректно отключают ANSI; JSON без Rich.

### UI-05. Timeline в show -v
Заменить дамп JSON внутри панели Rich **хронологической таблицей**:
`Time | Type | Event / Transition | Details`.
Для state: `old_state → new_state` и reason. Для execution: событие started/finished/codex-start/codex-finish и execution ID. Для PR: merged/updated, номер и статус. Для Recovery: имеющиеся реальные события. Упорядочить по достоверным timestamps, даты локальные (UI-02). Не выводить целые словари JSON в human mode. Исходные полные поля сохранить в --json.

### UI-06. Execution details в show -v
Заменить сырой массив JSON компактной таблицей `Parameter | Value` (execution ID, status, branch, start/finish, Codex times, exit code, error, commits, push/pr/comment publication, worktree path). Нулевые/отсутствующие значения `N/A`, длинные пути/хеши перенести или адекватно отображать, не теряя значимых данных. Без повторяющихся бессмысленных полей в человеческом представлении, исходная информация доступна через JSON.

### UI-07. Diagnostics в show -v
Если пусты error_log и recovery_quarantine — краткий текст `No errors or recovery quarantine records.` (или локализованный аналог), а не `{"error_log":[],...}`. Если записи есть: Rich таблица ошибок `Time | Stage | Code | Message`, карантин отдельной таблицей Reason/Details (с датой при наличии). Не скрывать реальные ошибки; пользовательский текст трактовать как литерал, а не Rich markup.

**Глобальные требования UI:** читабельность при ширине 80 и 120, NO_COLOR, pipe, экранирование пользовательского текста, никакого ANSI в --json; существующие машинные JSON-контракты не изменять из-за косметических работ.
