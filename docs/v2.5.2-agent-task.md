# Задание агенту Codex — реализация V2.5.2 (WSL2)

**Репозиторий:** `heroicrealm/CodexAgent`  
**Рабочая ветка:** `V2_5_2_WSL_DISTRIBUTION`  
**Обязательное ТЗ:** [docs/v2.5.2-wsl-distribution-spec.md](v2.5.2-wsl-distribution-spec.md)

## Цель

Реализовать поставку диспетчера для WSL2: версионированный Python-пакет, install/uninstall скрипты, проверка схемы YAML, установка/обновление через GitHub Releases, информирование о новой версии и вопрос при недоступности GitHub перед `run`, документация и тесты. Выполнять **в соответствии с ТЗ**, без самостоятельного расширения архитектуры.

## Перед изменениями — обязательный аудит

Прочитай в текущей ветке `pyproject.toml`, `src/dispatcher/__main__.py`, `src/dispatcher/config.py`, `config/config.example.yaml`, существующие тесты/CI/workflows, архитектуру `Runtime`, локальные lock/monitor механизмы остановки. Зафиксируй реальные точки интеграции; не переноси код из старой `main` без проверки. Существующая команда запуска — **`run`**, не `start`; версия пакета сейчас `2.3.0a0`, distribution `codex-dispatcher-v2`. Существующий YAML имеет `dispatcher.root_path`. `--config` и `XDG_CONFIG_HOME` уже поддерживаются.

## План работ

### A. Версия и схема конфигурации

1. Подготовь пакет для релизной версии `2.5.2` (при необходимости учти принятый процесс подготовки релиза).
2. Введи единый кодовый идентификатор поддерживаемого формата конфигурации: `1` для первой версии этой схемы.
3. Добавь верхнеуровневые `dispatcher_version` и `config_schema_version` в пример конфигурации, **не изменяя вложенность остальных полей**.
4. Валидация несовпадения схемы: отказ до runtime/побочных эффектов для команды `run` и других изменяющих команд; не блокировать справку, безопасную остановку. Придумай минимальный безопасный интерфейс для получения версии схемы установщиком из будущего релизного шаблона/пакета.
5. Старые файлы без версии не считаются автоматически совместимыми; нужен `config.new.yaml`, не править старый файл.

### B. Установщик

1. Добавь `install-wsl.sh`: проверка prerequisite, обнаружение фактической версии установленного Python-пакета из выбранного `venv`, запрос стабильного GitHub Release, сравнение PEP 440, запрос подтверждения, загрузка wheel/артефактов релиза, проверка SHA-256, установка.
2. Для новой установки создай `venv` (не editable), основной YAML по актуальному шаблону; `dispatcher.root_path` записывай абсолютным путём текущего пользователя (не литералом `~`).
3. При совпадении схемы обновляй **только** метку `dispatcher_version` без потери остальных значений/комментариев. При несовпадении оставляй старый YAML, создавай `config.new.yaml`, информируй о необходимости переноса настроек. Не перезаписывай существующий `config.new.yaml` молча.
4. Создай `~/.local/bin/codex-dispatcher` (ссылка или обёртка на entrypoint venv). Проверяй PATH, конфликт с чужим файлом. Повторная установка безопасна.
5. Перед обновлением проверяй, что runtime остановлен, штатным надёжным способом. Не делать обновление при активной работе. Не удалять SQLite, workspace или пользовательские worktrees.
6. После установки проверяй версию пакета. При ошибке установки не заявляй успех, старайся сохранить/восстановить прежний рабочий пакет; избегай повреждения действующей установки.

### C. GitHub Release / CI

1. Добавь регламент публикации релизов и workflow сборки/тестов wheel, без ухудшения существующего CI.
2. Публикуемый стабильный релиз включает wheel, `install-wsl.sh`, актуальный шаблон YAML, контрольные суммы и release notes.
3. Не публикуй реальный стабильный релиз и не создавай тег без отдельной приёмки/подтверждения пользователя. Подготовь инструкции и workflow, позволяющие сделать это после приёмки.
4. Обеспечь установку из релизных артефактов без `git clone`, без PyPI.

### D. Проверка перед запуском

1. Встрой синхронную проверку в обработку **`codex-dispatcher run`**, также с `--once`, до существующей логики `Runtime.run`.
2. Запроси доступность основного GitHub API, затем последнего стабильного релиза; сравни пакетную версию. Если релиз новее, выведи номер и ссылку, продолжи.
3. Если основной API недоступен, выведи вопрос `Start dispatcher anyway? [y/N]:`: `y` — вызвать прежнюю логику без дополнительных ограничений; `n`, Enter, Ctrl+C — выход без запуска. При отсутствии TTY — отказ без подвисания.
4. Если основной API доступен, а releases нет, выведи предупреждение о невозможности проверить обновления и продолжи.
5. Тайм-аут порядка 3 секунд. Никаких новых повторных опросов, фоновых задач, сетевых guards для pending и push, модификации scheduler.

### E. Удаление и документация

1. Создай `uninstall-wsl.sh`, сохраняющий пользовательские конфигурацию, БД, workspace и credentials. Удалять только собственные компоненты.
2. Подготовь русскоязычное руководство WSL2: подготовка, установка, авторизация gh/Codex, CLI `run`/`stop`/`queue`/`status`, конфиг, обновление, ручное согласование схемы, диагностика, удаление.
3. Обнови README точечными ссылками на новое руководство и на правила публикации.

## Тесты

Добавь автономные тесты сетевой проверки, сравнения версий, повторной установки и обновления, инвариантов пользовательской конфигурации и удаления. Тесты должны быть без реальных запросов GitHub и без настоящих токенов. Проверь `pytest`, сборку wheel, запуск установленного wheel в чистом `venv`, `codex-dispatcher --help`, `codex-dispatcher run --once` в контролируемом тесте, а также существующие регрессионные тесты.

Особенно важны:
- отсутствие подмены `dispatcher.root_path` на неверный верхнеуровневый `root_path`;
- сохранение комментариев YAML при совместимом обновлении;
- расхождение фактически установленного пакета и `dispatcher_version` при изменении схемы;
- сохранность данных при неудачном/повторном обновлении;
- терминал / нет терминала, ответы y/n/Enter при недоступности GitHub;
- отсутствие работы с GitHub при запуске только команд `queue`/`status`, поскольку проверка обновлений относится к `run`;
- запрет обновления при активном runtime;
- сохранение текущих контрактов SQLite, recovery, sub-issues и PR.

## Результат агента

В одном или нескольких коммитах в `V2_5_2_WSL_DISTRIBUTION` предоставь:
- реализацию и тесты;
- документацию и release workflow;
- краткий отчёт: перечень файлов, результаты тестов, обнаруженные ограничения, точные инструкции ручной приёмки WSL2;
- отдельно перечисли пункты, которые требуют действий пользователя (например, публикация первого реального GitHub Release после приёмки).

**Не создавать PR и не сливать ветку автоматически.** После завершения реализации остановиться и передать результат на ревизию и ручные испытания. Не расширять V2.5.2 на исправление неудачного push при потере связи во время работы.
