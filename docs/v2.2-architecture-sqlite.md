# Codex Task Dispatcher — ТЗ V2.2

**Наименование:** архитектура компонентов и модель SQLite V2  
**Репозиторий:** `heroicrealm/CodexAgent`  
**Версия документа:** 1.1, 2026-11-07  
**Статус:** утверждено пользователем (V2.2).  
**Основание:** согласованная в проекте модель V2.1. При расхождении деталей переходов приоритет имеет утверждённая спецификация V2.1, а не старые реализации V1.

## 1. Цель и ограничения

Создать простую архитектуру локального диспетчера задач на Python с SQLite, GitHub и Codex CLI. Внутренние сервисы работают в одном процессе и используют общую БД. Никаких брокеров, распределённых блокировок, универсальных журналов событий и постоянных счётчиков дочерних Issues.

Нормативные инварианты:

1. Issue с `codex-ready` регистрируется как управляемая задача. Issue без этой метки не регистрируется, **кроме виртуальных родителей** уже зарегистрированных дочерних задач.
2. Каждая Issue концептуально является контейнером с нулём или более непосредственно связанными отслеживаемыми детьми; поле `issue_type` не требуется.
3. Отсутствующий в БД родитель представлен виртуальной строкой `issues` с GitHub ID, репозиторием, номером и, по возможности, заголовком. При получении `codex-ready` виртуальная запись материализуется **на месте** с сохранением ID и связей.
4. При подтверждении Issue с незавершёнными учитываемыми детьми состояние — `awaiting_children`; иначе — `pending`. Когда дети терминальны (`done`/`cancelled`) и нет блокирующих конфликтов, `awaiting_children → pending`.
5. Счётчики детей не хранятся. Решение вычисляется по `issue_relations` и `issues` в момент проверки. Проверка срабатывает при подтверждении родителя, завершении ребёнка, изменении связей и в плановом проходе Scheduler.
6. Дети без `codex-ready` не блокируют контейнер только фактом существования; ранее согласованные особые конфликтные случаи, в том числе снятие метки при открытом PR, обрабатываются по V2.1.
7. Для одной Issue допускается **не более одного фактического запуска Codex CLI**; новая корректировка — новая Issue. Подготовку разрешено продолжить в той же записи `executions` только если достоверно известно, что Codex ещё не запускался. При неопределённости повторный запуск запрещён.
8. Публикация (push, PR, комментарии) может повторяться без повторного исполнения Codex; публикация ошибок выполняется одним сводным комментарием по завершении обработки с ошибкой, без мониторинга или восстановления комментария после действий пользователя.
9. GitHub — источник внешних фактов, SQLite — источник локального состояния и памяти о совершённых действиях. Внешнее закрытие Issue не эквивалентно внутреннему `done`/`cancelled`.
10. Отладочная диагностика имеет режимы `off`, `api`, `verbose` и по умолчанию отключена.
11. V2 запускается с новой пустой SQLite и на отдельном новом тестовом GitHub-репозитории. Перенос данных из V1 и совместимость с V1 не предусматриваются; прежние БД, workspace и Issues не используются.

## 2. Логические компоненты и контракты

| Компонент | Обязанности | Запрещено |
|---|---|---|
| `Runtime` | жизненный цикл процесса; расписание poll/scheduler; конфигурация | прямое изменение состояния задач |
| `GitHubAdapter` | единая точка вызовов `gh`/GitHub API; нормализация Issue, Sub-issue, PR; API-диагностика | трактовать внешний факт как внутренний переход |
| `PollService` | чтение открытых Issues/меток, связей и отслеживаемых PR; сбор полных наблюдений | запуск Codex, изменение SQLite в обход StateService |
| `StateService` | проверка переходов V2.1, атомарная запись Issue/связей/истории | сетевые обращения внутри SQL-транзакций |
| `GroupService` | готовность по непосредственным детям, причины блокировок | рекурсивно управлять жизненным циклом детей |
| `Scheduler` | выбор `pending`, проверка готовности/слотов, резервирование | повторное резервирование Issue |
| `Executor` | Git/worktree, подготовка, единичный Codex CLI, результат | произвольные переходы `issues.state` |
| `Publisher` | push, PR, итоговый error report, метки | повторный запуск Codex; мониторинг опубликованного комментария |
| `Storage` | SQLite, миграции, транзакции, запросы | внешние вызовы GitHub/Git/Codex под транзакцией |
| `DiagnosticLogger` | best-effort временная отладочная запись | ломать основной процесс при ошибке записи диагностики |

Контракт вызовов (предлагаемая сигнатура; API Python в V2.3 может быть уточнён при сохранении семантики):

```python
PollService.poll_project(project) -> PollResult
StateService.apply_observation(project, issues, relations, prs) -> SyncResult
StateService.approve(issue_id, approved_snapshot) -> str
StateService.transition(issue_id, expected_state, target_state, reason) -> bool
GroupService.evaluate(issue_id) -> Eligibility
Scheduler.reserve(issue_id) -> Execution | None
Executor.prepare(execution_id) -> Execution
Executor.run_once(execution_id) -> ExecutionResult
Publisher.publish(execution_id) -> PublishResult
Publisher.send_final_error_report(issue_id) -> bool
DiagnosticLogger.record(level, component, operation, context, result) -> None
```

### 2.1. Контракт GitHub/Poll

- Сначала закончить чтение всех страниц/необходимых данных проекта; только затем применять синхронизацию. Ошибка неполного опроса не является доказательством отсутствия Issue, связей или PR.
- Отслеживаемые PR проверяются и при закрытых GitHub Issues. Повторный poll не должен создавать повторных переходов, executions или PR.
- При нахождении отслеживаемой дочерней Issue с отсутствующим родителем сначала создаётся виртуальная запись родителя (при необходимости получить стабильный GitHub ID), затем связь.
- При появлении `codex-ready` у виртуального родителя обновляется существующая строка; `issue_id` и все связи сохраняются.
- Изменения состава детей требуют перепроверки готовности родителя. Вложенные контейнеры рассматриваются как непосредственные дети; рекурсивный обход не нужен.

### 2.2. Контракт состояний

- `discovered` — зарегистрирована, ещё не подтверждена;
- `awaiting_children` — подтверждена, но есть незавершённые учитываемые дети;
- `pending` — подтверждена и готова к исполнению;
- `running` — исполнение зарезервировано/в работе;
- `review` — результат опубликован и ожидает действия пользователя;
- `done`/`cancelled` — терминальные состояния, учитываемые при проверке детей.

Остальные переходы, в том числе отклонения, ошибки, снятие `codex-ready`, закрытие PR без merge и конфликты перенаправления merge, регулируются V2.1. Реализация не должна выводить из данного краткого списка разрешение на новые переходы.

Готовность утверждённого родителя: **нет учитываемого непосредственного ребёнка, который не терминален, и нет блокирующего конфликта**. Виртуальный родитель не получает `pending`. После `done` ребёнка в другой base branch ребёнок может быть `done`, но ранее согласованный конфликт направления merge должен блокировать родителя до разрешения связей.

## 3. SQLite — нормативный DDL

SQLite V2 создаётся с нуля, независимо от V1; поддержка формата БД V1 не предусматривается. `PRAGMA foreign_keys=ON`, `journal_mode=WAL`, `busy_timeout=5000` устанавливаются соединением. UTC-времена пишутся в ISO 8601. GitHub ID хранится `INTEGER`, а номер Issue используется только в рамках пары `(repository, issue_number)`.

```sql
CREATE TABLE schema_migrations (
    version INTEGER PRIMARY KEY,
    applied_at TEXT NOT NULL
);

CREATE TABLE issues (
    issue_id INTEGER PRIMARY KEY,
    repository TEXT NOT NULL,
    issue_number INTEGER NOT NULL CHECK(issue_number > 0),
    project_id TEXT NOT NULL,

    is_virtual INTEGER NOT NULL DEFAULT 0 CHECK(is_virtual IN (0, 1)),
    state TEXT,
    github_state TEXT CHECK(github_state IN ('open', 'closed')),
    is_ready INTEGER NOT NULL DEFAULT 0 CHECK(is_ready IN (0, 1)),
    is_approved INTEGER NOT NULL DEFAULT 0 CHECK(is_approved IN (0, 1)),

    title TEXT,
    approved_title TEXT,
    approved_body TEXT,
    parameters_yaml TEXT,
    approved_hash TEXT,
    approved_at TEXT,

    base_branch TEXT,
    work_branch TEXT,
    error_report_sent INTEGER NOT NULL DEFAULT 0
        CHECK(error_report_sent IN (0, 1)),

    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    last_seen_at TEXT,

    UNIQUE(repository, issue_number),
    CHECK (
        (is_virtual = 1 AND state IS NULL AND is_ready = 0)
        OR (is_virtual = 0 AND state IS NOT NULL AND title IS NOT NULL)
    )
);

CREATE TABLE issue_relations (
    parent_issue_id INTEGER NOT NULL REFERENCES issues(issue_id),
    child_issue_id INTEGER NOT NULL REFERENCES issues(issue_id),
    PRIMARY KEY(parent_issue_id, child_issue_id),
    CHECK(parent_issue_id <> child_issue_id)
);

CREATE TABLE executions (
    execution_id INTEGER PRIMARY KEY AUTOINCREMENT,
    issue_id INTEGER NOT NULL UNIQUE REFERENCES issues(issue_id),
    status TEXT NOT NULL CHECK(status IN
        ('reserved','preparing','executing','publishing','completed','failed','interrupted')),
    branch_name TEXT,
    worktree_path TEXT,
    started_at TEXT NOT NULL,
    finished_at TEXT,
    codex_started_at TEXT,
    codex_finished_at TEXT,
    exit_code INTEGER,
    error_code TEXT,
    error_message TEXT,
    initial_commit TEXT,
    result_commit TEXT,
    push_completed INTEGER NOT NULL DEFAULT 0 CHECK(push_completed IN (0,1)),
    pr_published INTEGER NOT NULL DEFAULT 0 CHECK(pr_published IN (0,1)),
    comment_published INTEGER NOT NULL DEFAULT 0 CHECK(comment_published IN (0,1))
);

CREATE TABLE pull_requests (
    pr_id INTEGER PRIMARY KEY,
    issue_id INTEGER NOT NULL REFERENCES issues(issue_id),
    repository TEXT NOT NULL,
    pr_number INTEGER NOT NULL CHECK(pr_number > 0),
    head_branch TEXT NOT NULL,
    base_branch TEXT NOT NULL,
    status TEXT NOT NULL CHECK(status IN ('open','closed','merged')),
    merged_at TEXT,
    updated_at TEXT NOT NULL,
    UNIQUE(repository, pr_number)
);

CREATE TABLE state_history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    issue_id INTEGER NOT NULL REFERENCES issues(issue_id),
    old_state TEXT,
    new_state TEXT NOT NULL,
    reason TEXT NOT NULL,
    created_at TEXT NOT NULL
);

CREATE TABLE error_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    issue_id INTEGER NOT NULL REFERENCES issues(issue_id),
    execution_id INTEGER REFERENCES executions(execution_id),
    error_code TEXT NOT NULL,
    error_stage TEXT NOT NULL,
    error_message TEXT NOT NULL,
    created_at TEXT NOT NULL
);

CREATE TABLE debug_operations (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at TEXT NOT NULL,
    level TEXT NOT NULL CHECK(level IN ('api', 'verbose')),
    component TEXT NOT NULL,
    operation TEXT NOT NULL,
    repository TEXT,
    issue_id INTEGER,
    poll_id TEXT,
    method TEXT,
    endpoint TEXT,
    duration_ms INTEGER CHECK(duration_ms IS NULL OR duration_ms >= 0),
    result TEXT NOT NULL,
    http_status INTEGER,
    error_message TEXT
);

CREATE INDEX idx_issues_state ON issues(state);
CREATE INDEX idx_issues_project_state ON issues(project_id, state);
CREATE INDEX idx_relations_child ON issue_relations(child_issue_id);
CREATE INDEX idx_pr_status ON pull_requests(status);
CREATE INDEX idx_pr_issue ON pull_requests(issue_id);
CREATE INDEX idx_history_issue ON state_history(issue_id, id);
CREATE INDEX idx_error_issue ON error_log(issue_id, id);
CREATE INDEX idx_debug_created ON debug_operations(created_at);
CREATE INDEX idx_debug_poll ON debug_operations(poll_id);
CREATE INDEX idx_debug_operation ON debug_operations(operation);
```

Внешний ключ `issue_relations.parent_issue_id` допустим благодаря виртуальной строке родителя. Если у ребёнка нет `codex-ready` и он нигде не выступает необходимым виртуальным родителем, запись о таком ребёнке не создаётся. Историческая запись об уже зарегистрированной Issue не стирается при снятии метки; её дальнейшая обработка определяется V2.1.

### 3.1. Семантика полей `issues`

- `is_virtual=1` — технический родитель, без `state` и выполнения. Заголовок допустим; `approved_*` и `parameters_yaml` для него не используются. `is_virtual=0` — управляемая Issue.
- `is_ready` и `is_approved` — **наблюдаемые**, а не командные флаги. После использования approve метка может быть удалена, сохранившаяся утверждённая постановка остаётся авторитетной.
- `approved_title`, `approved_body`, `parameters_yaml`, `approved_hash`, `approved_at` — неизменяемый снимок утверждения. YAML хранится исходным текстом, проверяется парсером и схемой допустимых параметров; без YAML используется конфигурация проекта. Снимок не меняется при обычном poll.
- `base_branch` — зафиксированная ожидаемая цель; `pull_requests.base_branch` — фактическая цель PR. Это разные данные.
- `error_report_sent=1` — GitHub подтвердил отправку сводного комментария. Удаление/редактирование пользователем не отслеживается. Сбой после отправки, но до фиксации этого флага может дать дубль — риск осознанно принят.
- `github_state` не определяет самостоятельно `state`.

### 3.2. Семантика `executions`

- `UNIQUE(issue_id)` — максимум одна запись исполнения для Issue.
- Сохранённое `codex_started_at` является консервативным *маркером допуска к однократному запуску*, который записывается и фиксируется **перед созданием процесса**. Если процесс упал между записью маркера и фактическим стартом, попытка считается потенциально использованной; автоматический повтор запрещён.
- Если `codex_started_at IS NULL` и достоверно установлено, что процесс не стартовал, можно продолжить `reserved`/`preparing` на **той же** записи `executions`.
- После завершения Codex можно повторять публикацию, не меняя маркер начала. `push_completed`, `pr_published`, `comment_published` указывают лишь на подтверждённые результаты; сверка с GitHub перед созданием PR позволяет не плодить дубликаты.
- Ошибки до регистрации execution допускают `error_log.execution_id = NULL`. Для ошибки во время исполнения используется связь с существующей записью.

### 3.3. Проверка готовности родителей

Базовый критерий готовности по зарегистрированным детям (без рассмотрения специальных конфликтов):

```sql
SELECT NOT EXISTS (
  SELECT 1
  FROM issue_relations r
  JOIN issues child ON child.issue_id = r.child_issue_id
  WHERE r.parent_issue_id = :parent_issue_id
    AND child.is_virtual = 0
    AND child.is_ready = 1
    AND (child.state IS NULL OR child.state NOT IN ('done', 'cancelled'))
) AS tracked_children_finished;
```

Этот запрос **не является всей логикой V2.1**: StateService/GroupService также должны проверять особые блокировки (например, конфликт направления merge или снятие `codex-ready` с дочерней Issue с открытым PR). Предотвращаем ситуацию, когда `NULL` ошибочно считается терминальным состоянием. Для Issue без детей запрос возвращает истину; это обычная задача, которая после approve направляется в `pending`.

## 4. Транзакции и интеграция

- Все изменения `issues.state` и соответствующие строки `state_history` фиксируются одной транзакцией через StateService. Переход выполняется с проверкой ожидаемого исходного состояния (CAS/условный `UPDATE`).
- Резервирование `pending → running` и вставка единственной строки `executions` — одна транзакция `BEGIN IMMEDIATE`. Повторная операция не должна создавать второй execution.
- Создание виртуального родителя и связи — одна транзакция; материализация родителя изменяет исходную строку, а не создаёт новую.
- При успешном полном получении Sub-issues обновляется набор соответствующих непосредственных связей и пересчитывается готовность затронутого родителя. При ошибке GitHub состояние связей не уничтожается.
- Обновление сведений о PR и разрешённого перехода Issue выполняется в одной транзакции после получения данных GitHub.
- Запись ошибки в `error_log` не является разрешением на произвольный переход состояния. Исход обработки определяется V2.1.
- Git/GitHub/Codex операции выполняются **вне** транзакций SQLite. Долгие транзакции запрещены.

## 5. Отчёт об ошибках

Все значимые ошибки, относящиеся к Issue, пишутся в `error_log` с кодом, стадией, безопасным сообщением и временем. При завершении обработки с ошибкой формируется **один сводный комментарий** в исходной Issue, объединяющий накопленные записи. После успешной публикации `issues.error_report_sent=1`. Если отправка не подтверждена, допускается повторная попытка; случайный дубль при аварийном разрыве между GitHub и SQLite допускается без специальных защит. Состояние комментария никогда не мониторится, его удаление/редактирование пользователем не исправляется. Секреты и необработанные выводы команд в отчёт не записываются.

## 6. Диагностика API и операций

Конфигурация:

```yaml
dispatcher:
  debug:
    mode: off             # off | api | verbose
    retention_days: 7
```

- `off`: нет новых записей `debug_operations`.
- `api`: каждое **наблюдаемое** фактическое обращение к GitHub через централизованный GitHubAdapter, включая отдельные retry, метод, endpoint без чувствительных параметров, длительность, результат и HTTP-код (если доступен).
- `verbose`: всё из `api` + существенные внутренние действия Poll/StateService/Scheduler/Executor/Publisher/GroupService.
- Все наблюдаемые обращения одного цикла Poll содержат общий `poll_id`. Учитываются вызовы, непосредственно видимые приложению; внутренние HTTP-запросы, скрытые внутри одного вызова `gh`, не гарантированно доступны.
- Полные URL с токенами, bodies Issue, токены, секреты и полный stdout/stderr внешних процессов запрещены.
- Ошибка записи диагностики не меняет результат рабочей операции. Удаление старых записей — при старте и не чаще одного раза в сутки. Retention по умолчанию 7 дней.

Для сравнения API-нагрузки:

```sql
SELECT poll_id, COUNT(*) AS calls
FROM debug_operations
WHERE level = 'api' AND poll_id IS NOT NULL
GROUP BY poll_id
ORDER BY calls DESC;
```

## 7. Чистый запуск V2 без миграции с V1

**Миграция БД и совместимость с V1 исключены из объёма работ.** В старой БД находятся только тестовые данные, поэтому их перенос не нужен. Диспетчер V2 не читает, не преобразует и не модифицирует таблицы и записи V1. Код совместимости, конвертеры старых состояний, переносы history/attempts/PR и тесты этих переносов не разрабатываются.

### 7.1. Изоляция и инициализация

1. Остановить экземпляр V1, если он использует общие ресурсы. Для V2 задать **отдельные** конфигурацию, каталог workspace, SQLite и служебные файлы; пути не должны пересекаться с V1.
2. Для ручных интеграционных испытаний создать **новый пустой тестовый GitHub-репозиторий**, указав его через конфигурацию проекта. Имена и адреса тестового репозитория не хардкодить в коде либо тестах.
3. На первом запуске V2 создать пустую SQLite из нормативного DDL раздела 3; зафиксировать начальную версию схемы V2 `schema_migrations.version=1`.
4. При повторном запуске проверить совместимость версии и структуры **V2**; при обнаружении неизвестной/несовместимой схемы прекратить запуск с понятной диагностикой, **без** попыток преобразовать V1.
5. Выполнить первый Poll по новому тестовому репозиторию. Старые Issues и метки тестовых репозиториев V1 не участвуют в опросе и не требуют очистки.

Старая БД V1 остаётся в своей рабочей области нетронутой. По желанию пользователя её можно архивировать вручную, однако архивирование V1 **не является условием запуска или приёмки V2** и не входит в обязательный код диспетчера.

### 7.2. Будущие миграции V2

`schema_migrations` остаётся в схеме только для **последующих изменений формата V2**. Возможность обновления `V2 schema 1 → V2 schema 2` не подразумевает поддержки либо конвертации V1. Для несовместимых баз действует отказ от запуска вместо автоматической модификации.

### 7.3. Разделение тестирования

- Модульные и интеграционные тесты с подменённым GitHub используют временную чистую SQLite V2.
- Ручная проверка GitHub выполняется только в новом отдельном репозитории, созданном для V2.
- Тестовые сценарии не полагаются на состояние, ID, PR, метки или историю репозиториев V1.
- Конфигурация V2 не должна случайно указывать на старые пути V1; при обнаружении несовместимой базы V2 сообщает об ошибке, а не исправляет её автоматически.

## 8. Проверки и приёмка

### 8.1. Базовые задачи и YAML

- T01: новая Issue с `codex-ready` → `discovered`.
- T02: повторный poll без изменений → нет новых переходов.
- T03: approve при нуле детей → `pending`, снимок текста и YAML сохранён.
- T04: approve при незавершённых детях → `awaiting_children`.
- T05: изменение текста/YAML после approve не меняет утверждённый снимок.
- T06: некорректный YAML → диагностируемая ошибка, Codex не стартует.
- T07: YAML отсутствует → конфигурация проекта.

### 8.2. Контейнеры и виртуальные родители

- T08: дочерняя задача обнаружена раньше родителя → создан виртуальный родитель и корректная связь.
- T09: повторное обнаружение → нет дублированных строк.
- T10: виртуальный родитель получил `codex-ready` → материализуется без изменения ID и связей.
- T11: виртуальный родитель без метки не исполняется.
- T12: ребёнок без метки игнорируется для готовности; обычная Issue с нулём детей после approve получает `pending`.
- T13: последнее завершение ребёнка `done`/`cancelled` → `awaiting_children → pending`.
- T14: удаление незавершённого ребёнка из связей → повторная оценка родителя.
- T15: вложенный контейнер рассматривается родителем как одна дочерняя Issue; обход не рекурсивен.
- T16: слияние ребёнка в другую base branch → дочерняя Issue `done`, но родитель блокируется по V2.1 до разрешения конфликта.
- T17: снятие `codex-ready` с ребёнка при открытом PR → особый блокирующий сценарий V2.1.
- T18: частичная ошибка получения Sub-issues не стирает связи.

### 8.3. Однократное исполнение и PR

- T19: два параллельных резервирования создают один execution.
- T20: падение до установки маркера и доказанное отсутствие процесса → подготовка возобновляется на той же записи.
- T21: падение после фиксации маркера старта → Codex автоматически повторно не запускается, даже если фактический старт неизвестен.
- T22: успешный Codex и ошибка push/PR → повторяется лишь публикация.
- T23: PR уже создан на GitHub, но не отражён в SQLite → не создавать новый PR, зарегистрировать обнаруженный.
- T24: PR merged → допустимый переход в `done`; закрытый без merge не признаётся успешным.
- T25: закрытая GitHub Issue с отслеживаемым PR продолжает мониториться.

### 8.4. Отчёты и диагностика

- T26: несколько ошибок одной Issue → один сводный комментарий.
- T27: ошибка отправки отчёта → `error_report_sent=0`, повторная отправка допустима.
- T28: удаление/изменение комментария человеком не приводит к запросам на проверку или восстановление.
- T29: `off` → нет диагностических записей.
- T30: `api` → видимые вызовы и retry фиксируются с `poll_id`.
- T31: `verbose` → дополнительно фиксируются внутренние операции.
- T32: сбой debug logger не прерывает рабочую операцию.
- T33: retention удаляет старые записи.
- T34: записи не содержат секретов и полного текста заданий.
- T35: лог позволяет посчитать API-вызовы по циклам Poll.

### 8.5. Чистая инициализация и изоляция V2

- T36: на чистом workspace создаётся SQLite V2 с ровно восемью таблицами, индексами и `schema_migrations.version=1`.
- T37: при повторном запуске корректная SQLite V2 открывается без пересоздания таблиц или потери данных.
- T38: при указании несовместимой/старой SQLite диспетчер выводит диагностическую ошибку и не изменяет базу; конвертация V1 не производится.
- T39: тестовый запуск V2 использует отдельные конфигурацию, workspace, SQLite и новый GitHub-репозиторий; ресурсы V1 остаются нетронутыми.
- T40: несколько репозиториев с одинаковыми `issue_number` различаются; FK-инварианты соблюдены.
- T41: ручной сценарий на новом тестовом GitHub-репозитории проходит регистрацию, approve, запуск, публикацию PR и merge без зависимости от данных V1.

## 9. Критерий завершения V2.2

Выпущено и принято настоящее архитектурное ТЗ с исполнимой SQL-схемой, явными контрактами компонентов, описанием восстановления, чистой инициализации V2 и программой проверок. **Этап V2.2 — проектирование**, а не реализация: выполнение тестов в реальном GitHub, написание модулей и переход на новую БД относятся к V2.3 и следующим этапам. Отступления от согласованной V2.1 требуют отдельного решения, а не неявного изменения архитектуры.

## 10. Изменения редакции 1.1 относительно 1.0

- Удалены требования к резервному копированию V1 как обязательному шагу и к миграции данных/состояний V1 → V2.

- Уточнено назначение `schema_migrations`: только будущие изменения внутри V2.
- Вместо тестов миграции добавлены проверки чистой инициализации, отказа от несовместимой БД, изоляции и интеграционного цикла на новом репозитории.
