# V2.3 — реализация архитектуры компонентов и SQLite

**Статус:** задание агенту; реализация и приёмка ещё не выполнены.  
**Базовая ветка:** `CODEXAGENT_V2`. **Рабочая ветка:** `V2_3_IMPLEMENTATION`.  
**Нормативные документы:** `docs/specification_v2.md` (V2.1), `docs/v2.2-architecture-sqlite.md` (V2.2, редакция 1.1).

## 1. Цель

Заложить новую реализацию V2 на Python с нуля: SQLite, транзакционные сервисы, контракты компонентов и автоматизированные тесты. Каталог `V1/` не менять, не импортировать и не использовать как базу данных. Миграция и совместимость с V1 исключены. Изменения фиксировать в новой ветке, не сливать без приёмки.

### Этап B — прикладные сервисы
1. `GitHubAdapter` — единая точка GitHub-вызовов с учётом видимых попыток/retry; secrets и текст Issues в debug не писать. Все GitHub-метки — через эффективную карту `dispatcher.labels` + `projects[].labels`, никогда не через захардкоженные имена. Различать метки `running` (`dispatcher:running`) и `manual-running` (`dispatcher:manual-running`): первая означает работу Codex, вторая — готовность ветки к ручной работе. Для `preparing` не задавать и не выставлять статусную метку GitHub; `dispatcher:running` устанавливать только при `preparing → running`, а `dispatcher:manual-running` — только при `preparing → manual-running` после публикации ветки. Не выводить состояние SQLite только по метке GitHub.
2. `PollService` читает все необходимые страницы **до** применения изменений; ошибка частичного чтения не удаляет старые связи и не интерпретируется как удаление Issue/PR. Отслеживаемые PR продолжают проверяться при закрытой Issue.
3. `StateService` реализует переходы V2.1, снимок утверждённой постановки/INPUT/YAML, идемпотентность, CAS и однократную историю; GitHub-операции вне SQL-транзакций.
4. `GroupService` вычисляет готовность по непосредственным детям; не хранить постоянные счётчики и не делать рекурсивный обход. Учесть блокирующие конфликты V2.1.
5. `Scheduler` резервирует `pending` ровно один раз и проверяет допуск повторно перед запуском.
6. `Executor` фиксирует `codex_started_at` **до** создания Codex-процесса. Не повторять Codex после неопределённого старта; разрешить повторную публикацию без повторного исполнения.
7. `Publisher` реализует push/PR, подтверждённую фиксацию OUTPUT ID/текста, проверку уже существующего PR, итоговый сводный error report; не мониторит комментарии после их отправки.
8. `Runtime` связывает сервисы и обеспечивает отдельную конфигурацию, workspace и SQLite для V2.

## 3. Обнаруженные вопросы согласованности нормативных документов

**Уточнение V2.3 — утверждено пользователем:** `issues.correction_of_issue_id` и `issues.execution_group_id` хранятся непосредственно в `issues`. Каждая Issue входит ровно в одну группу, и корректирующая Issue ссылается не более чем на одну непосредственную Issue. Несколько корректировок вправе ссылаться на одну Issue (ветвление); `UNIQUE(correction_of_issue_id)` **не вводить**. Группа остаётся общей, не допускает более одной одновременно активной Issue и использует общую рабочую ветку. Минимальное расширение DDL и инварианты описаны в `docs/v2.3-schema-clarification.md`; это согласованное уточнение к V2.2. Для Stage A применять расширенный DDL, не создавать отдельную таблицу групп.

**Номенклатура состояний:** V2.1 использует `awaiting-children`, `manual-running`, `need-fix` и промежуточное `preparing`; V2.2 местами использует `awaiting_children` и описывает резервирование как `pending → running`. Зафиксировать канонические имена и отображение фаз **до** жёсткого кодирования переходов. До решения не вводить разноимённые варианты состояний.

Любые другие обнаруженные противоречия фиксировать в отчёте; не менять утверждённую семантику без решения пользователя.

## 4. Запреты

- Не изменять `V1/`, старые конфигурации, workspace и SQLite.
- Не вводить миграцию V1 → V2, долговременные блокировки, event sourcing, брокеры или постоянные счётчики детей.

- Не запускать Codex более одного раза на Issue.
- Не считать зелёные mock-тесты доказательством успешной проверки на реальном GitHub.
