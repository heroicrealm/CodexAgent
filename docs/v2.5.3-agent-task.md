## 0. Обязательная подготовка

1. Убедись, что находишься на ветке `V2_5_3_UBUNTU_SERVICE`; проверь актуальность относительно `CODEXAGENT_V2` и отсутствие чужих незакоммиченных изменений.
2. Прочитай полностью [ТЗ V2.5.3](v2.5.3-spec.md), [общую спецификацию V2.5](v2.5-spec.md), [аудит V2.5.1](v2.5.1-report.md), README и относящиеся к установке/выпускам документы.
3. Сверь реальный код: `src/dispatcher/__main__.py`, `runtime.py`, `releases.py`, `config.py`, `locking.py`, `monitoring.py`, `execution.py`, `install-standalone.sh`, `uninstall-standalone.sh`, `scripts/embed-standalone.py`, тесты и CI.
4. Зафиксируй короткий **предварительный аудит** в `docs/v2.5.3-implementation.md`: подтверждённые контракты, обнаруженные расхождения, план минимальных правок. Не копируй реализацию V1.

Не создавай новую SQLite-схему, supervisor, альтернативный scheduler или отдельный daemon.

## 1. Фаза A — управление systemd user service

Реализуй `codex-dispatcher service install|start|stop|restart|status|logs|uninstall`. Предпочтительно вынеси логику в отдельный компактный модуль (например `src/dispatcher/service.py`); `__main__.py` оставь тонким CLI.

Требования:
- user unit: `~/.config/systemd/user/codex-dispatcher.service`, управление **только** `systemctl --user` / `journalctl --user`;
- `Type=exec`, `ExecStart=<абсолютный стабильный CLI> run`, `Restart=on-failure`, `RestartSec=10s`, `TimeoutStopSec=infinity`, `KillMode=mixed`, `WantedBy=default.target`, `StandardOutput/Error=journal`, `StartLimitIntervalSec=300`, `StartLimitBurst=5`;
- никаких `User=` и `/etc` в user unit; стабильный CLI из standalone installation; HOME/PATH/WorkingDirectory без зависимости от login shell;
- idempotent install, проверка владения и отказ от перезаписи чужого unit; учёт симлинков/прав/атомарной записи; только собственный unit удаляется при uninstall;
- install включает `enable`, но **не стартует**; никогда не выполняет sudo, `loginctl enable-linger`, db bootstrap, auth login;
- `service status` и `service logs` не должны требовать существующей/исправной SQLite;
- `service restart` не может запускать процесс до окончания штатного stop; никакого собственного kill/таймаута graceful drain;
- диагностируй недоступный systemd user manager, D-Bus, неверный путь CLI и отсутствующий конфиг.

Проверь корректный парсинг `--config` в существующей CLI и сохранение XDG. Не добавляй новую «поисковую» схему конфигурации.

## 2. Фаза B — безтерминальный запуск

Устрани выявленный блокер `src/dispatcher/releases.py:before_run`: если проверка релиза недоступна/истекла, предупреждай, **но не требуй stdin и не блокируй запуск по причине одной этой проверки**. Не отменяй важные ошибки конфигурации, DB, Recovery, Git auth и рабочего процесса. Не добавляй автообновление.

Проверь, что SIGTERM main процесса вызывает graceful shutdown, завершение `future` дочитывается, а дочерние процессы не получают преждевременного сигнала от systemd. Не ломай `stop --force` и блокировки. При неподтверждённой ошибке `KillMode=mixed` зафиксируй диагностируемый риск, не объявляй проверку завершённой.

Устойчивые ошибки старта не должны приводить к бесконечному restart-loop: unit start-limit обязателен, изменения exit codes / `RestartPreventExitStatus` — только если необходимы и покрыты тестами.

## 3. Фаза C — standalone installer

Проверь совместимость с поколениями standalone-venv и путём `~/.local/bin/codex-dispatcher`. Не фиксируй путь конкретного поколения в unit.

Обновление: **сначала service stop**, затем подтверждённая остановка runtime, запуск существующего `codex-dispatcher-install`, проверка версии и отдельный ручной `service start`. Никакой автоматической перезагрузки и уничтожения активной Issue.

Согласуй поведение `codex-dispatcher-uninstall` при зарегистрированном unit: fail-closed предупреждение и требование предварительного `service uninstall` либо эквивалентная доказуемо безопасная последовательность. Не удаляй данные или чужие файлы. Если затрагиваешь release scripts, соблюдай workflow `scripts/embed-standalone.py --check` и соответствующие smoke tests.

## 4. Фаза D — автоматические проверки

Добавь набор автоматических тестов **без реального systemd, внешней сети и настоящего Codex/GitHub auth**:
- генерация и корректность unit/путей;
- shell-free вызовы `systemctl --user`/`journalctl --user`;
- idempotence, отказы при чужих файлах, ошибки daemon-reload/enable;
- stop/restart/uninstall и сохранение workspace/SQLite/конфига;
- статус и логирование при повреждённой SQLite;
- вызов `run` без TTY при offline release check;
- fake Codex subprocess без PTY, SIGTERM graceful, отсутствие второго runtime;
- регрессии WSL2 lifecycle и standalone updater;
- соответствие ограничениям Retry/Recovery.

Выполни полный `python -m pytest -q`, `python -m compileall -q src tests`, `git diff --check`, `sh -n install-standalone.sh uninstall-standalone.sh`, `python scripts/embed-standalone.py --check`, сборку wheel/smoke при доступности зависимостей и зафиксируй фактические результаты. Если проверки невыполнимы, напиши почему; не заявляй PASS без запуска.

**Не подменяй Ubuntu acceptance автоматическими тестами.**

## 6. Сценарии ручной приёмки

Подготовь исполняемую человеком инструкцию S01–S19 из [ТЗ](v2.5.3-spec.md). **Не отмечай её успешной до фактического прогона на Ubuntu Server.**

Критический сценарий **S19**:
1. Установить и запустить `systemd --user` службу с linger на Ubuntu.
2. Отключить все SSH-сессии пользователя.
3. Поставить новую тестовую Issue и разрешить её выполнение.
4. Убедиться, что **настоящий** `codex exec` работает без TTY/PTY, `tmux`, `screen` и интерактивного stdin.
5. Подтвердить успешные GitHub push/PR, отсутствие зависших процессов.
6. Перезагрузить Ubuntu, повторить задание и проверку.

Если есть сбои, анализировать stdin/stdout/stderr, параметры запуска, HOME/XDG/PATH и состояние авторизации Codex. Не добавлять tmux «на всякий случай».

Дополнительно особенно внимательно проверить S08/S09/S18 (stop с живыми Codex процессами): `TimeoutStopSec=infinity` и `KillMode=mixed` проверяются **на реальной системе**.

## 7. Формат отчёта и стоп-условия

В завершение выведи:
1. перечень изменённых файлов и ключевые решения;
2. результаты запуска всех автотестов (число passed/failed/skipped);
3. результаты проверки wheel/installer/shell/CI readiness;
4. неснятые риски, включая реальные Ubuntu/systemd/credentials ограничения;
5. точные команды и сценарий ручной приёмки;
6. commit SHA ветки.

**Не создавать PR, не выполнять merge, не выпускать новую release/tag и не объявлять V2.5.3 принятым** до отдельной команды пользователя. Не пытаться провести настоящий S19 в WSL2 или CI и записать его как Ubuntu PASS. После реализации передать пользователю на ручную приёмку.
