# V2.4.2 — задание Codex-агенту: анализ и исправление WAL/SHM после backup/restore

**Репозиторий:** `heroicrealm/CodexAgent`  
**Ветка:** `V2_4_2_RECOVERY_RECONCILIATION`  
**Контекст:** завершающая корректировка по ручному тестированию V2.4.2. Не менять согласованную логику recovery/recover/accept/retry.

## 1. Подтверждённые наблюдения

В WSL2 на новой тестовой установке, при остановленном диспетчере и отсутствии обращений других процессов:

1. До `db backup` в каталоге рабочей БД нет файлов `-wal` и `-shm`.
2. `db backup` возвращает `PASS backup verified`, но создаёт рядом с исходной SQLite `-wal` (наблюдался размер 0) и `-shm` (32 768 байт); файлы остаются после завершения CLI.
3. `db restore` отказывается выполняться, когда эти sidecar-файлы присутствуют: `FAIL Working WAL/SHM present; checkpoint after shutdown`.
4. После ручного checkpoint при полной остановке диспетчера восстановление возможно.
5. `db restore` также оставляет новые `-wal` и `-shm` рядом с **файлом резервной копии**.
6. После нормального завершения `run/stop` без `backup` sidecar-файлы не обнаружены.
7. Положительные ручные сценарии V2.4.2: auto-recover merged PR, quarantine + `accept`, `retry`. Несинхронизированные GitHub-метки после `recover` разрешаются следующим штатным запуском и в эту задачу не входят.

**Гипотеза, не доказанный факт:** чтение WAL-mode SQLite через `mode=ro` внутри SQLite Backup API провоцирует sidecar-файлы; текущий контекстный менеджер `connection()` явно вызывает `db.close()`, поэтому нельзя заранее объявлять ошибкой незакрытое Python-соединение.

## 2. Цель и ограничения

Установить воспроизводимую причину появления/сохранения sidecar-файлов и сделать так, чтобы штатные `db backup` и `db restore` в остановленной системе не оставляли **новых** WAL/SHM около исходной БД или неизменяемого backup-файла.

- **Сохранность данных и fail-closed важнее удобства.** Не удалять sidecar-файлы «вслепую», не использовать `unlink` как универсальную очистку и не обходить `quiescent()` / InstanceLock.
- `db backup` должен сохранить возможность делать консистентный backup при работающем диспетчере. Не checkpoint-ить и не удалять файлы, которыми пользуются другие подключения; при конкурентной работе допускается наличие WAL/SHM.
- `db restore` — только при доказанной остановке; исходный backup и его каталог должны оставаться неизменными, включая отсутствие новых sidecar-файлов. Приватная временная копия допускается при доказанной безопасности.
- Сохранить проверки SQLite integrity, exact schema/identity, права/симлинки, recovery barrier, сохранение предыдущей БД, атомарность и защиту от непроверенных исполнителей.
- Не изменять состояние задач, жизненный цикл PR, метки GitHub, модель карантина и другие части V2.4.2.

## 3. Этап A — анализ и воспроизведение

1. Исследовать `src/dispatcher/db_guard.py` (особенно `connection`, `backup`, `maintain`, `restore`, `quiescent`) и вызывающие участки. Проверить фактический порядок закрытия source/destination connections, состояние SQLite WAL, URI `mode=ro`, поведение Python `sqlite3.Connection.backup()`, проверок через `inspection()` и промежуточного backup `before-restore-*`.
2. Добавить минимальные **автоматические воспроизводящие тесты** на временном WAL-mode SQLite: sidecar отсутствуют до команды; backup создаёт проверяемую копию; файлы после; restore не модифицирует backup; запуски команды отдельными процессами, если нужно для точного воспроизведения.
3. Разделить понятия «завершённое соединение» и «оставшиеся sidecar-файлы»; объяснить доказанную причину в отчёте. Не объявлять причину установленной только по наличию WAL/SHM.
4. Проверить влияние обращения к резервной копии в `check(config, path=argument)` и `backup(argument, staging)` на её собственные sidecar-файлы.

## 4. Этап B — минимальное безопасное исправление

1. Предпочесть корректное закрытие SQLite и безопасный механизм SQLite для освобождения sidecar при **доказанном эксклюзивном доступе**, а не ручное удаление.
2. Разделить поведение online backup и offline backup. Не предполагать отсутствие внешних подключений только на основании PID или отсутствия управляющего сокета.
3. Для чтения резервной копии при restore обеспечить её неизменяемость без записей в каталог (при необходимости использовать validated temporary/private copy). Не использовать `immutable=1` без доказательства безопасности для WAL-состояний.
4. После успешной offline-операции гарантировать отсутствие **новых** служебных файлов от этой команды либо явно документировать доказанное исключение. Не скрывать ошибки cleanup/checkpoint. При ошибках восстановление должно оставаться fail-closed, с сохранением данных.
5. Проверить, что обрабатываются оба источника sidecar: рабочая БД и резервная копия, а также промежуточный архив `before-restore-*`.
6. Не переписывать рабочий протокол restore без необходимости.

## 5. Регрессионные тесты и критерии приёмки

**Офлайн backup:** `-wal/-shm` отсутствуют до операции, `db backup` PASS, копия целостна, новые sidecar-файлы рядом с исходной БД не остаются.

**Restore:** backup из предыдущего сценария восстанавливается при остановленном диспетчере; хеш/байты backup до и после одинаковы; новых `<backup>-wal/-shm` не остаётся; не остаётся новых sidecar у текущей БД после завершения restore; `recovery_required=1`.

**Online backup:** при действующих соединениях/незакоммиченных или неcheckpoint-нутых WAL-данных копия консистентна, текущие подключения не повреждаются; sidecar-файлы не удаляются и не checkpoint-ятся небезопасно.

**Отказы:** повреждённый или чужой backup, symlink, неподтверждённая остановка, существующий рабочий WAL/SHM, сбой до/после создания staging — без потерь, без ослабления проверок.

**Повтор:** последовательность `stop → backup → restore` без ручного `sqlite3 PRAGMA wal_checkpoint` должна работать при отсутствии сторонних подключений.

Запустить профильные тесты, затем весь `pytest`; зафиксировать количество и результат. Если ручное воспроизведение в WSL2 не удалось, честно указать различия среды и достаточные доказательства поведения.
