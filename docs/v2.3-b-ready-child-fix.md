# V2.3.B — исправление учёта зарегистрированного ребёнка после снятия codex-ready

**Статус:** задание агенту на исправление перед приёмкой V2.3.B.  
**Репозиторий:** `heroicrealm/CodexAgent`. **Ветка:** `V2_3_IMPLEMENTATION`.  
**Нормативная основа:** V2.1, V2.2 и согласованные уточнения V2.3; принцип `codex-ready` как однократной метки регистрации сохраняется.

## Дефект

В `src/dispatcher/services.py`, `GroupService.evaluate_db()` незавершённый ребёнок блокирует родителя только при `child['is_ready']`. Однако `is_ready` отражает текущее наблюдаемое наличие метки `codex-ready`, а не факт первоначальной регистрации и учёта ребёнка. Снятие метки у уже зарегистрированной дочерней Issue без открытого PR приводит к преждевременной готовности родителя.

## Требуемое исправление

1. В готовности родителя использовать **зарегистрированную учитываемую связь** `issue_relations` с реальной (`is_virtual=0`) дочерней Issue. Если у такого ребёнка нет терминального состояния `done` или `cancelled`, он продолжает блокировать родителя независимо от текущего `is_ready`. Не считать `NULL` терминальным.
2. Наличие или отсутствие `codex-ready` у зарегистрированной Issue не меняет её принадлежности к диспетчеру, утверждение, готовность как ребёнка и жизненный цикл. Не восстанавливать `codex-ready` автоматически; поле `is_ready` остаётся наблюдаемым флагом GitHub.
3. Особый конфликт **снятия codex-ready у ребёнка с открытым PR** из V2.1 сохраняется. Он не должен исчезать при исправлении обычного учёта; конфликт merge в другую base branch тоже сохраняется.
4. В GitHub для зарегистрированной открытой Issue должна сохраняться **соответствующая статусу метка**, например `dispatcher:discovered` или её переопределение проекта, даже если `codex-ready` отсутствует. Повторный poll не должен восстанавливать `codex-ready` или отправлять лишние API-запросы при неизменной статусной метке. Метки GitHub брать только из effective labels проекта.
5. После `preparing` набор учитываемых детей заморожен: новые связи не блокируют уже запущенного родителя. До `preparing` удаление связи при полном успешном чтении GitHub влияет на готовность согласно уточнению V2.2. Не вводить постоянные счётчики, дополнительные таблицы или миграции.
6. Проверить пути `StateService.refresh_db`, `PollService.apply_observation`, `GroupService.evaluate_db` и `GitHubAdapter.sync_labels`: реальная регистрация `is_virtual=0` и учтённая связь должны быть устойчивы к снятию метки `codex-ready`.

## Автоматизированные тесты

- Родитель `awaiting-children`, учтённый ребёнок `discovered`, PR отсутствует; снять у ребёнка `codex-ready`, выполнить poll: родитель остаётся `awaiting-children`.
- Ребёнок без `codex-ready` по-прежнему видим через корректную статусную метку GitHub и не получает автоматически `codex-ready`.
- У ребёнка с удалённой меткой `codex-ready` после законного перехода в `done`/`cancelled` родитель может стать `pending`, если нет других причин блокировки.
- Если связь удалена до `preparing` родителя, его готовность пересчитывается; если новый ребёнок добавлен после `preparing`, он не блокирует исполняемого родителя.
- Снятие `codex-ready` при открытом PR сохраняет особую блокировку; конфликт merge в другую base branch тоже блокирует согласно V2.1.
- Повторные poll не добавляют лишних изменений/вызовов меток и не дублируют историю переходов.
- Все ранее существовавшие тесты A/B проходят.

## Объём и сдача

Исправить только данный дефект и непосредственно связанные тесты/документацию. Не менять утверждённую семантику V2.3, не делать реальных GitHub-испытаний, не создавать PR, не начинать V2.3.C.

По завершении обновить `docs/v2.3-b-report.md`: причина дефекта, изменённые файлы, результаты тестов и оставшиеся ограничения. Остановиться для повторного аудита и приёмки B.
