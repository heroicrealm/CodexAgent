# ТЗ V2.4.1 — защита SQLite и конфигурации, резервное копирование и восстановление

Статус: утверждённые принципы, рабочее ТЗ для реализации.
Базовая ветка: `CODEXAGENT_V2`. Изменения ограничиваются этапом V2.4.1.

## 1. Цель
Отказ от исполнения при неправильной, отсутствующей, повреждённой или несовместимой SQLite, при ошибочном пути/конфигурации; диагностика без побочных эффектов; безопасная резервная копия и восстановление из неё. Не допускать повторного исполнения заданий из-за восстановления состояния.

## 2. Границы
Входит: проверка схемы, целостности и идентичности БД; отдельный безопасный bootstrap новой БД; CLI диагностики и резервирования/восстановления; запрет запуска до проверки восстановленного состояния; тестирование и документация.
Не входит: восстановление по GitHub, полное восстановление локальных попыток/PR/контейнеров по GitHub, автоматическое исправление логических конфликтов; это V2.4.2. Не выполнять миграцию из V1.

## 3. Источники истины и совместимость
Изучить фактические код и схему V2.3 в базовой ветке, существующую инициализацию и команды; не переносить механизмы V1 и не вводить схему «по памяти».
Существующие действительные базы V2.3 не должны неожиданно перестать открываться: предусмотреть явную, проверяемую, недеструктивную регистрацию идентичности/metadata, с резервированием исходной базы до изменений. Не считать любую произвольную SQLite допустимой старой V2.3: требовать проверяемые признаки точной совместимой схемы.
Никакого `CREATE TABLE IF NOT EXISTS` / автоматической миграции в обычном read-only осмотре и до установления допустимости базы.

## 4. Идентичность и проекты
Идентичность экземпляра диспетчера хранится отдельно от перечня проектов. Смена списка проектов, enabled, локального project.id и иных обычных настроек допускается. Для стабильной связи задач использовать нормализованный `owner/name`, независимо от project.id. Подмена `repository` у прежнего `project.id` трактуется как другой проект, без переноса старых задач и без смешивания данных.
Удаление проекта из YAML не удаляет его записи и не переводит их в терминальное состояние. При возвращении проекта сохранять данные и сначала выполнять синхронизацию перед любым новым исполнением.
Проверка пути workspace/идентичности должна ловить ошибочное подключение чужой базы. Один только fingerprint YAML, зависящий от списка проектов, не подходит.
Не использовать absolute path как единственный критерий идентичности, иначе корректное перемещение рабочего окружения станет необратимой ошибкой; предусмотреть диагностируемое явное переназначение при переносе с защитой данных.

## 5. Fail closed
Обычный запуск, poll и любая команда, читающая/изменяющая рабочее состояние, не должны молча создавать пустую SQLite при ошибочном пути. Отсутствие БД, повреждение, чужой формат/идентичность, неподдерживаемая версия или критическое нарушение схемы — понятная ошибка и ненулевой exit code.
Сначала проверки, затем побочные эффекты. В частности не изменять метки/Issues, не запускать Codex, не создавать новые попытки и не удалять worktree до разрешения проблем. Не изменять исходную базу при неудачной проверке.
Явная первичная инициализация базы должна оставаться доступной для нового пользователя, не перетирать существующий файл.

## 6. Диагностика
Предусмотреть `codex-dispatcher db check`: не создаёт SQLite, каталоги, служебные файлы, WAL и журнал; по возможности использовать строго read-only подключение, проверять SQLite header/структуру/версию/идентичность, `quick_check` или `integrity_check`, обязательные таблицы/индексы, важные FK и внутренние инварианты. Отличать физическую порчу от логических несоответствий и неопределённости внешних состояний.
Выводить PASS/WARN/FAIL и действия пользователя; не выводить секреты, приватные тела issue и SQL dump. Проверка консистентности с GitHub без мутаций может быть отдельной процедурой после восстановления.

## 7. Backup
Предусмотреть явную `codex-dispatcher db backup <destination>`. Для корректно открываемой SQLite использовать SQLite backup API, чтобы получить согласованный снимок в WAL. Не перезаписывать существующий destination, проверять итог и сохранять безопасные права 0600. Не копировать только основной .sqlite3 при активном WAL.
Для повреждённой/неоткрываемой базы у пользователя должна быть документированная процедура аварийного сохранения набора исходных файлов `db`, `db-wal`, `db-shm` при остановленном демоне. Не утверждать, что аварийная файловая копия уже является валидной SQLite backup.

## 8. Restore
Предусмотреть `codex-dispatcher db restore <backup-file>`. Отказ, если служба или связанные исполнительные процессы ещё работают или состояние остановки не может быть надёжно проверено. Проверить источник/схему/версию/идентичность до замены; резервировать старую рабочую базу, не уничтожать её даже при ошибке. Работать через приватный staging на той же файловой системе, проверять целостность и завершать атомарной заменой лишь в безопасном режиме, с корректной обработкой WAL/SHM (не оставлять WAL от старой базы).
Перед разрешением исполнения выполнить восстановительную проверку: зафиксировать необходимость повторной синхронизации и сверки локальных попыток, worktree и GitHub. Ни `pending`, ни `approve` из восстановленного снимка не дают права автоматически перезапустить Codex до успешной процедуры допуска. Fail closed на неоднозначных состояниях; не изменять произвольно жизненный цикл задачи.
Восстановление не должно автоматически разрешать/сливать PR, менять метки или запускать Codex.
Все потенциально разрушительные операции — явное действие пользователя; без тихого reset/rebuild.

## 9. Безопасность и эксплуатация
Не утекать токенами, телами задач или содержимым БД в логах. Безопасная обработка symlink, неправильных прав и некорректных путей. Не нарушать существующие команды CLI и формат журнала. Разделить диагностику (read-only) и операции, требующие блокировки и записи.
Документировать порядок: остановка → check → аварийная копия → backup/restore → check → сверка с GitHub → явное возобновление.
В частности явно описать ограничения восстановимости незафиксированных транзакций и состояния внешних процессов.

## 10. Автоматические проверки и критерии приёмки
Сценарии: пустой/неверный workspace, файл не SQLite, повреждённый файл, незнакомая версия, неверная структура, чужая идентичность, сохранение данных при смене состава проектов/id, WAL с незачекпойнченными данными, наличие destination, неверный backup, отказ restore при работающей службе, аварийное прекращение restore без потери исходного файла, безопасное обновление metadata на совместимой V2.3, запрет повторного исполнения pending/running после restore, отсутствие сетевых и файловых побочных эффектов от db check.
CI: действующие тесты V2.3 + новые тесты на временных базах; ни одной операции с реальными GitHub проектами в автоматических тестах.
Приёмка ручная, PR готовить только после тестов и проверки пользователем; без автоматического merge.

## 11. Вопросы реализации
Агент должен сначала представить фактическую схему V2.3 и предлагаемую точную форму metadata/guard и recovery-admission. Если опасный шаг не допускает надёжной реализации, запрещён небезопасный обход — отразить блокер и ограничить функциональность.
