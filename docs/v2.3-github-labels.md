# V2.3 — отображение внутренних состояний и команд на метки GitHub

**Статус:** утверждён принцип двухуровневой конфигурации и соответствия пользователя от 2026-11-07.  
**Основание:** `docs/specification_v2.md` (V2.1), `docs/v2.2-architecture-sqlite.md`.

## 1. Правило

Внутренние коды состояний/команд являются стабильными ключами программной модели; конкретные имена меток GitHub задаются конфигурацией. Сначала применяется общая карта `dispatcher.labels`, затем необязательное переопределение **отдельных ключей** `projects[].labels`. Проект наследует все не переопределённые значения. Имена меток не захардкожены в бизнес-логике. Разные проекты могут назначать разные метки одним и тем же ключам.

Пример конфигурации (структуру проектов согласовать с фактической схемой V2, семантику сохранить):

```yaml
dispatcher:
  labels:
    codex-ready: "dispatcher:codex-ready"
    discovered: "dispatcher:discovered"
    approve: "dispatcher:approve"
    awaiting-children: "dispatcher:awaiting-children"
    pending: "dispatcher:pending"
    preparing: "dispatcher:running"
    running: "dispatcher:running"
    manual-running: "dispatcher:manual-running"
    review: "dispatcher:review"
    rejected: "dispatcher:rejected"
    done: "dispatcher:done"
    cancelled: "dispatcher:cancelled"
    error: "dispatcher:error"
    need-fix: "dispatcher:need-fix"

projects:
  - id: example-project
    repository: owner/example-repository
    labels:
      codex-ready: "my-custom-ready"
      review: "my-custom-review"
```

Метки `running` и `manual-running` **различаются намеренно**: `dispatcher:running` означает, что работает Codex; `dispatcher:manual-running` означает, что подготовленная и опубликованная рабочая ветка ожидает работы человека (можно выполнить fetch). `preparing` отображается как `dispatcher:running` — это техническая фаза до готовности ветки для человека. Не использовать обратное преобразование `GitHub label → internal state` как универсальный источник состояния: источник внутреннего состояния — SQLite. В написании пользовательского примера `mannual-running` исправлена опечатка на `manual-running`.

## 2. Команды и статусные метки

- `codex-ready`, `approve`, `need-fix`, `cancelled` и пользовательский `done` — возможные входные команды согласно V2.1. Их разбор по **конфигурационным ключам**, а не по строкам меток.
- Остальные метки отражают состояния. Наличие `dispatcher:running` само по себе **не доказывает**, что внутри SQLite `running` или `preparing`; `dispatcher:manual-running` отличает готовую к ручной работе задачу.
- При переходе удалять устаревшие управляемые статусные метки и устанавливать целевую метку при необходимости; если старая/новая фаза сопоставляются одной строке, лишние операции удаления/установки не выполнять.
- Не удалять пользовательские метки, не входящие в итоговую конфигурацию меток диспетчера.
- Не считать отсутствие GitHub-метки основанием переписать состояние SQLite.
- При одинаковых строках **разных входных команд** или при конфликтном пересечении команды со статусом (кроме намеренно объединённых фаз исполнения) предусмотреть валидацию конфигурации и понятное сообщение вместо неоднозначной интерпретации.
- Учитывать, что `done` в состоянии `error` может служить пользовательской командой, а после завершения группы — статусной меткой. Разрешение зависит от состояния SQLite и V2.1.
- Названия `discovered`, `rejected` нормализованы; опечатки `dispatcher::discovered`, `rejecte`, `dispathcer` из сообщения пользователя трактуются как опечатки, не как отдельные канонические ключи.

## 3. Инициализация и проверка

- Режим инициализации проекта проверяет/создаёт **разрешённые** итоговые GitHub-метки проекта (уникальный набор фактических имён). Обработка коллизий с существующими GitHub-метками должна быть безопасной: не переименовывать и не удалять чужие метки автоматически.
- При загрузке конфигурации проверять поддерживаемые ключи, непустые значения, невозможные или неоднозначные совпадения.
- Для операций GitHub применять только `effective_labels(project)`.
- Тестировать наследование, переопределение одного ключа, независимость проектов, различие `running`/`manual-running` и переход между ними, совпадение `preparing`/`running`, отсутствие обратного вывода состояния по метке, ошибки конфигурации и точечные изменения управляемых меток.
- Не добавлять конфигурацию меток в SQLite: это настройка адаптера GitHub.

## 4. Отдельное уточнение

В V2.1 `preparing` — самостоятельное внутреннее техническое состояние; пользователь не указал отдельную метку для него. Здесь предложено отразить его той же GitHub-меткой, что `running`. Это не меняет переходов V2.1 и не требует дополнительной метки. При желании значение `preparing` можно отдельно переопределить в конфигурации.
