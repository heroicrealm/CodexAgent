# V2.5.1 — Аудит ядра, управление процессами и HTTPS Git

**Проект:** Codex Dispatcher V2  
**Базовая ветка:** `CODEXAGENT_V2`  
**Рабочая ветка:** `V2_5_1_INFRASTRUCTURE`  
**Статус:** согласованное техническое задание, реализация не начата  
**Общие решения:** [Спецификация V2.5](v2.5-spec.md)

## 1. Цель

Устранить только те препятствия общего ядра V2, которые мешают будущей поставке для WSL2, Ubuntu native/systemd и Docker. Не реализовывать установщики и платформенные адаптеры заранее.

Два функциональных результата: (а) проверенный существующий foreground runtime с корректной остановкой; (б) единый **HTTPS-only** Git transport через GitHub CLI без зависимости от `ssh-agent`.

## 2. Исходное состояние и обязательный аудит

Работать с актуальным кодом ветки `CODEXAGENT_V2`; старые V1 документы не являются контрактом V2. До изменений агент составляет короткий аудит реальных точек входа:

- `codex-dispatcher run` и `run --once` уже существуют; проверить обработчики SIGTERM/SIGINT, `stop --force`, дочерние процессы и процесс завершения.
- Разрешение конфигурации `--config` → XDG, `dispatcher.root_path`, `database`, `workspace`, `project.checkout` уже реализованы. Не создавать новый resolver и `paths.state`.
- SQLite связана с workspace UUID-маркером `.dispatcher-instance`; есть InstanceLock, control socket, Recovery guards и read-only monitoring.
- Обнаружить все точки формирования Git remote, `gh repo clone`, `git fetch/push/ls-remote`, проверки origin/fetch URL/push URL и способы запуска Git.
- Проверить, какие функции требуют интерактивной сессии, `HOME`, `PATH` или SSH credentials.

**Выход аудита:** перечень затрагиваемых файлов и минимальных изменений, без переписывания готовых механизмов.

## 3. Объём реализации

### 3.1. Процессы

1. Сохранить `run` как единственный foreground-вход для будущих systemd и Docker. Не создавать вторую копию scheduler, систему daemonization или новый `start` без отдельного основания.
2. SIGTERM/SIGINT запускают штатную остановку: новые задачи не допускаются, активные завершаются, итоговое состояние и публикации сохраняются; **фиксированного лимита ожидания нет** (утверждённая политика A).
3. Повторный SIGTERM не усиливает остановку до принудительной. `stop --force` оставляет действующий безопасный алгоритм отмены управляемых групп и не сигналит чужие процессы.
4. Проанализировать готовность к остановке внешним менеджером процессов, обработку сигналов во время долгой работы и exit codes; при необходимости исправить только ядро. Не создавать unit или Docker-образ.
5. Сохранить защиту от двух работающих экземпляров, идентичность PID/процесса, SQLite и workspace, все блокировки и Recovery admission. Исключить обход через другой способ запуска.
6. Ошибка перед настройкой штатного логирования видна в stderr и приводит к ненулевому exit code. Не раскрывать секреты.

### 3.2. Git через HTTPS

1. Для **всех управляемых диспетчером удалённых Git-операций** использовать HTTPS GitHub URL вида `https://github.com/OWNER/REPO.git` без встроенных credentials.
2. Новые служебные clone должны использовать HTTPS независимо от ранее настроенного `gh git_protocol=ssh`. Не полагаться на автоопределение `gh repo clone`, если оно может выбрать SSH. Сохранить проверки identity/origin и защиту от перенаправления push в чужой репозиторий.
3. Git credentials предоставляет `gh` через штатный credential helper после настройки пользователем `gh auth setup-git`. Диспетчер не запрашивает пароли, не пишет токены и не управляет файлами внутреннего хранилища `gh`.
4. Выполнение Git не должно блокироваться ожиданием ввода: `GIT_TERMINAL_PROMPT=0` и эквивалентные безопасные ограничения. `gh auth status` сам по себе не доказывает успешный Git push.
5. Для существующих **управляемых** SSH remote предусмотреть **fail-closed** диагностирование и отдельную явную проверяемую процедуру перевода на HTTPS; не переписывать их молча. Проверять принадлежность checkout, identity репозитория и фактические fetch/push URL; не менять сторонние пользовательские checkout. Сохранить worktree/ветки/коммиты.
6. Не поддерживать SSH fallback, автоматический запуск `ssh-agent`, создание ключей или SSH как альтернативный штатный способ транспорта в V2.5.
7. Web-ссылки GitHub Issues/PR не менять без фактического дефекта: они не являются Git remote.

### 3.3. Сохранение существующей конфигурации и данных

- Приоритет `--config`/XDG, `root_path` и порядок разрешения путей **не менять**.
- Не переносить и не создавать заново SQLite, не вводить автоматический `db bootstrap` при `run`.
- Не менять схему SQLite, состояния заданий, публикацию, UUID-маркер, процедуры backup/restore/recovery, журналы и блокировки без документированного дефекта, напрямую препятствующего этому этапу.
- Авторизация Codex и GitHub остаётся ответственностью их CLI; ядро лишь запускает их в корректном окружении и сообщает безопасную ошибку при невозможности работы. Реализация сервисных окружений — позднее.

## 4. За рамками V2.5.1

- WSL2: установочные скрипты и пользовательская процедура установки (V2.5.2).
- Ubuntu: системный unit, сервисный Linux-пользователь, sudo-обёртка, `journalctl` и установка (V2.5.3).
- Docker: Dockerfile, Compose, volumes, временные контейнеры, интерактивная авторизация, bootstrap/install-script, локальная сборка, Docker Hub (V2.5.4).
- Платформенная интеграционная приёмка, установка/обновление образов, сквозное восстановление (V2.5.5).
- Новый XDG resolver, собственное хранилище токенов, автоматические login/ssh-agent, миграция БД V1.

Решения по этим вопросам уже записаны в [общей спецификации](v2.5-spec.md), но **не являются задачами реализации V2.5.1**.

## 5. Проверки

Автоматически, без реальных credentials и доступа к GitHub:

1. `run` выполняется в текущем процессе, корректно завершается и сообщает exit code.
2. Штатная остановка при длительном активном задании не прерывает его и не имеет предельного времени; повторный SIGTERM не меняет режим.
3. Force-stop завершает только собственные управляемые группы согласно действующему алгоритму.
4. Второй экземпляр не запускается с общей SQLite/workspace; не ослаблены InstanceLock, socket и Recovery.
5. Новые Git remote — HTTPS независимо от `gh` SSH preference; fetch/push используют ожидаемый HTTPS origin.
6. Старый SSH remote даёт явную безопасную диагностику и не заменяется без явного действия; переход на HTTPS не теряет worktree/ветки.
7. Недоступная HTTPS авторизация завершает Git операцию без ожидания пароля; токены не оказываются в логах и URL.
8. `--config`/XDG/`root_path`, UUID и monitor/DB recovery сохраняют действующие контракты V2.
9. Проходит весь существующий набор тестов V2; нет незаявленных изменений схемы и состояний.

Ручная проверка V2.5.1: `run` с реальным stop/force, контроль долгого задания и HTTPS Git на тестовом проекте без запущенного `ssh-agent`; проверка безопасной реакции на старый SSH remote. Полноценные systemd/Docker тесты — позже.
