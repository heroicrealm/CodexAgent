## 3. Реализуемые компоненты

### 3.1. GitHubAdapter

Реализовать единую точку обращения к GitHub.

Обязанности:

- Получение открытых Issues и меток.
- Получение непосредственных Sub-issues и родительских связей.
- Получение INPUT-комментариев.
- Получение состояния отслеживаемых PR.
- Создание и обновление OUTPUT.
- Создание PR, управление метками и закрытием Issues.
- Работа с несколькими проектами.
- Использование конфигурации меток с наследованием и переопределением на уровне проекта.

Все обращения к GitHub должны проходить через адаптер.

Поддержать диагностическое журналирование фактических обращений с `poll_id`, включая наблюдаемые повторные попытки.

Избегать ненужных запросов к GitHub. Опыт V1 показал, что избыточная API-нагрузка является существенной проблемой.

### 3.2. PollService

Реализовать периодический опрос GitHub.

Порядок работы:

1. Получить полный набор необходимых данных.
2. Зарегистрировать новые Issues с `codex-ready`.
3. Обновить непосредственные родительские связи.
4. Обработать пользовательские команды.
5. Проверить состояния отслеживаемых PR.
6. Передать наблюдения StateService.

При `codex-ready` только регистрировать Issue.

**INPUT не анализировать до approve.**

Закрытые на GitHub Issues не участвуют в обычном опросе меток, однако связанные с ними PR продолжают отслеживаться.

Не уничтожать ранее сохранённые связи при неполном получении данных GitHub.

### 3.3. StateService

Реализовать модель переходов V2.1.

Особое внимание:

- `discovered → pending / awaiting-children`;
- `pending → preparing`;
- `preparing → running / manual-running`;
- `running → review / error`;
- `manual-running → review`;
- `review → done / rejected`;
- `rejected / error → need-fix`;
- терминальное завершение группы.

Все переходы должны проверяться на допустимость.

Изменение состояния и запись в `state_history` выполняются атомарно.

Состояние SQLite является авторитетным. Метки GitHub отражают его, но не заменяют.

Для `preparing` отдельная метка GitHub не устанавливается.

### 3.4. INPUT и утверждение Issue

Формат INPUT:

```yaml
dispatcher:
  base_branch: main
  branch: my_task01
  correction_for: 23
  run_codex: true
```

Все параметры необязательны.

При `approve`:

1. Прочитать актуальную постановку Issue и INPUT.
2. Проверить синтаксис и допустимые значения YAML.
3. Определить параметры выполнения.
4. При наличии `correction_for` разрешить номер Issue в глобальный GitHub ID данного репозитория.
5. Проверить разрешение `need-fix` и групповые ограничения.
6. Атомарно сохранить утверждённый снимок, INPUT и окончательную принадлежность к группе.
7. Перевести Issue в соответствующее состояние.

До `approve` пользователь вправе свободно редактировать Issue и INPUT.

Корректирующая Issue наследует базовую и рабочую ветки группы. Переопределять их в корректировке нельзя.

При ошибке утверждения Issue остаётся в `discovered`.

### 3.5. GroupService

Реализовать управление группами и непосредственными дочерними зависимостями.

Требования:

- `execution_group_id` — глобальный GitHub ID исходной Issue.
- Одна Issue принадлежит одной группе.
- Одна корректирующая Issue ссылается не более чем на одну Issue.
- Допускается ветвление истории корректировок.
- В группе не более одной активной Issue.
- Рабочая ветка общая для группы.

Готовность родителя вычислять из SQLite без постоянных счётчиков.

Новые связи, появившиеся после перехода родителя в `preparing`, не учитывать при его дальнейшем исполнении.

Учесть специальные блокирующие конфликты, предусмотренные V2.1.

Рекурсивное управление вложенными контейнерами не реализовывать.

### 3.6. Scheduler

Реализовать выбор готовых задач из `pending`.

Перед резервированием проверять:

- наличие утверждённой постановки;
- готовность непосредственных детей;
- отсутствие блокирующих конфликтов;
- отсутствие другой активной Issue группы;
- наличие свободного слота исполнения.

Резервирование должно быть атомарным и не создавать повторную запись `executions`.

На первом этапе достаточно одного одновременно работающего процесса Codex.

### 3.7. Executor

Реализовать подготовку и выполнение задач.

Для `run_codex: true`:

1. Подготовить рабочую ветку группы.
2. Создать Git worktree.
3. Зафиксировать разрешение на однократный запуск Codex в SQLite.
4. Запустить Codex CLI с утверждённой постановкой.
5. Сохранить результат.
6. Передать данные Publisher.

Не запускать Codex повторно, если ранее зафиксирован `codex_started_at`.

Для `run_codex: false`:

1. Подготовить рабочую ветку.
2. Опубликовать её на GitHub.
3. Перевести Issue в `manual-running`.
4. Установить метку `dispatcher:manual-running` либо её настроенный аналог.

Ручная задача не запускает Codex и ожидает создания PR пользователем.

### 3.8. Publisher

Реализовать публикацию результатов:

- Commit и push.
- Создание или обнаружение существующего PR.
- Публикация и обновление OUTPUT.
- Перевод Issue в `review`.
- Публикация сводного отчёта об ошибках.
- Синхронизация меток и закрытия Issues.

ID и текст OUTPUT сохранять в SQLite только после подтверждённой публикации.

Не мониторить изменения или удаление OUTPUT пользователем.

Повторная публикация не должна вызывать повторное выполнение Codex.

### 3.9. Runtime

Реализовать управляющий цикл диспетчера:

- Запуск и остановка.
- Периодический Poll.
- Вызов Scheduler.
- Исполнение задач отдельным процессом.
- Восстановление после аварийного завершения.
- Корректное завершение при штатном `stop`.
- Обработку `stop --force`.

Poll не должен блокироваться на время работы Codex.

### 3.10. Очистка ресурсов

Реализовать утверждённый вариант A.

При запуске диспетчер восстанавливает незавершённую очистку по существующим данным SQLite.

Дополнительно разработать ручную сервисную утилиту для поиска осиротевших Git worktree.

Предусмотреть:

- Dry-run по умолчанию.
- Удаление только по явному `--apply`.
- Проверку отсутствия worktree в SQLite.
- Проверку отсутствия активного исполнения.
- Проверку сохранности неопубликованных изменений.
- Запрет удаления пользовательских worktree и ресурсов V1.

Не применять принудительное удаление при неопределённом состоянии.

## 4. Тестирование

Реализовать модульные и интеграционные тесты с временной SQLite и подменённым GitHub.

Обязательно проверить:

- Регистрацию и approve.
- INPUT и корректировки.
- Виртуальных родителей.
- Зависимости Sub-issues.
- Группы исполнения.
- Однократность запуска Codex.
- Ручные задачи.
- Создание и обработку PR.
- Повторный poll.
- Восстановление после сбоя.
- Диагностическое журналирование и количество вызовов GitHub.
- Очистку worktree.
- Многопроектную конфигурацию.

Все существующие тесты V2.3.A должны продолжать проходить.

Реальные интеграционные испытания GitHub относятся к V2.3.C. Не выполнять их без отдельного задания.

## 5. Ограничения

Запрещается:

- Изменять каталог V1 или использовать его SQLite.
- Вводить миграцию V1 → V2.
- Добавлять постоянные счётчики дочерних Issue.
- Вводить дополнительные блокировки или механизмы синхронизации без необходимости.
- Выполнять GitHub/Git/Codex внутри SQLite-транзакций.
- Повторно запускать Codex для одной Issue.
- Удалять неопубликованные результаты.
- Самостоятельно менять согласованную модель состояний.

Если обнаружено противоречие, требующее изменения архитектуры или схемы SQLite, зафиксировать его и представить минимальный вариант решения. Не вводить архитектурные изменения молча.
