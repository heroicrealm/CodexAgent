Они не являются выявленными остатками дерева исполнения Issue #67/#70. По дереву процессов и времени запуска источник фонового app-server строго не доказан; на приёмку dispatcher это не повлияло.

**Уточнение по SSH:** успешный HTTPS origin и реальный push подтверждены. Утверждение, что весь сценарий выполнялся при полностью выключенном `ssh-agent`, вручную не проверялось: `ssh-agent` присутствовал по независимой причине. HTTPS-only/отказ от SSH fallback покрыт автоматическими тестами по отчёту агента.

**Уточнение по timeout:** наблюдаемая штатная остановка подтверждает ожидание длинной задачи до публикации; формально «бесконечность» нельзя измерить конечным тестом. Отсутствие заданного фиксированного лимита проверено анализом реализации и автоматическими тестами агента.

## 4. Ограничения, не блокирующие подготовку PR

1. Ручная миграция уже существующего служебного SSH checkout в HTTPS не выполнялась на проекте `cap`: checkout был создан новым HTTPS способом; автоматизированная проверка процедуры миграции заявлена агентом.
2. Отрицательные сценарии Git credentials, URL rewrite, multiple fetch/push URLs и чужого push URL проверены агентом автоматически, но не воспроизводились вручную с реальным GitHub.
3. Полная приёмка systemd/Ubuntu, Docker, установщиков, обновления и Docker Hub относится к V2.5.3–V2.5.5, а не к V2.5.1.
4. После принудительного прерывания Issue #70 остаётся в `error`, что соответствует наблюдавшемуся сценарию; автоматическое повторное выполнение не требовалось.
5. CI по данному PR ещё не выполнен; его прохождение обязательно до слияния.
