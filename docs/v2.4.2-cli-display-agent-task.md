# Задание Codex-агенту — V2.4.2: читаемый CLI recovery

**Репозиторий:** heroicrealm/CodexAgent  
**Ветка:** V2_4_2_RECOVERY_RECONCILIATION  
**Базовая спецификация:** docs/v2.4.2-spec.md  
**Приоритет:** до завершения ручной приёмки V2.4.2  
**Область:** только представление CLI, без изменения бизнес-логики или структуры SQLite.

## Контекст

При ручном тестировании `db recovery status` и `db recover --dry-run` диспетчер выводит большие однострочные JSON. В них отображаются только глобальные `issue_id`, по которым оператору трудно идентифицировать Issue в GitHub. Например, успешный `retry` Issue #41 имеет `issue_id=6370045834`, однако табличного представления нет.

Принято решение: по умолчанию выводить читаемые таблицы с рамкой, выравниванием и уместной подсветкой; оставить JSON доступным через `--json`.

## Цель

Реализовать единообразное человекочитаемое форматирование recovery CLI, в котором оператор видит repository и issue_number, причины карантина, статус операции и общий admission. Сохранить машинный интерфейс через явный флаг.

## Требования

### 1. Команды и форматы

Обеспечить два режима:

- По умолчанию, если не указан `--json`, показывать Rich-таблицы/панели (включая неинтерактивный stdout: без красок при перенаправлении; текст остаётся читаемым).
- При `--json` выводить **один корректный JSON-документ** с прежними полями и типами; допускаются только аддитивные поля идентификации. JSON без цветовых управляющих кодов и служебной разметки.

Поддержать:
```bash
codex-dispatcher --config config/config.yaml db recover --dry-run
codex-dispatcher --config config/config.yaml db recover
codex-dispatcher --config config/config.yaml db recovery status
codex-dispatcher --config config/config.yaml db recovery accept PROJECT ISSUE
codex-dispatcher --config config/config.yaml db recovery retry PROJECT ISSUE
codex-dispatcher --config config/config.yaml db recovery cancel PROJECT ISSUE
```

Для **каждой** из команд допускается суффикс `--json` в стандартном месте argparse. Флаг не должен влиять на исполнение или side effects.

### 2. Идентификация Issue

В публичные структуры результатов для каждой Issue добавить:

- `issue_id` — существующий глобальный GitHub ID (сохранить);
- `repository` — нормализованный `owner/repo`;
- `issue_number` — обычный номер Issue внутри репозитория.

Применить к:
- строкам `db recover --dry-run` и `db recover`;
- элементам `quarantine` и `operations` в `db recovery status`;
- результатам `accept/retry/cancel`, включая сведения о целевой Issue.

Для новой Issue, найденной после backup, идентификатор берётся из наблюдения GitHub, для существующей — из SQLite. Для операции retry в статусе номер Issue восстанавливается через JOIN по `issue_id`, без запросов GitHub. Сохранять консистентность repository и номера, не принимать `issue_number` за глобальный идентификатор. Не нужно менять таблицы SQLite.

### 3. Макет консоли

Использовать библиотеку `rich` (обновить `pyproject.toml`, при необходимости lock/инструкции установки). Вынести оформление в отдельный модуль (например, `src/dispatcher/recovery_output.py`), чтобы recovery.py и __main__.py не содержали цветовых кодов и большого объёма форматирования.

`db recovery status`:

- Рамка заголовка **CODEX DISPATCHER · RECOVERY**.
- Сводка: **Database version**, **Recovery required: YES/NO**, количество **Quarantined issues** (число уникальных Issue, не количество причин), количество незавершённых операций.
- Таблица **QUARANTINED ISSUES**: `Repository`, `Issue` (например `#41`), `Reason(s)`, при необходимости компактная заметка; **одна строка на Issue**, несколько причин объединены/перенесены внутри ячейки.
- Таблица **RECOVERY OPERATIONS**: `Repository`, `Issue`, `Action`, `Phase`; идентификатор операции, comment ID, полный timestamp — только в подробном или JSON-выводе, чтобы обычный вывод не был перегружен.
- При пустом карантине явно писать «No quarantined issues»; при отсутствии операций — «No recovery operations».
- Сортировка стабильная (repository, issue_number, reason_code или дата для операций). Широкий и узкий терминалы должны оставаться читаемыми; длинные значения переносить, не обрезать критичную информацию без возможности просмотра.

`db recover` и `--dry-run`:

- Таблица `Repository`, `Issue`, `Current/Target` (если исходное состояние доступно без новых запросов), `Reason(s)`.
- Ясно отличать **DRY RUN / NO CHANGES** от фактического применения и показывать факт глобального допуска после него без ложной гарантии отсутствия карантина.
- Не показывать «PASS» для отказавшей recovery операции.

`accept/retry/cancel`:

- Компактная сводка с номером и repository Issue, `action`, `operation_id` (можно сокращённый в человекочитаемой форме с полной копией в `--json`), `phase`, `recovery_required`, остаточными причинами карантина, относящимися к целевой Issue.
- После успешного retry отображать, что новое GitHub approve обязательно.

### 4. Цвет и TTY

- Зелёный: completed, done, global admission ready/NO.
- Жёлтый: quarantined, pending, warning.
- Красный: error, conflict, FAIL, global recovery_required=YES.
- Голубой: running, review, информационные действия.
- Цвет используется только для акцента, смысл должен быть понятен без цвета.
- `rich.Console` должен корректно отключать ANSI при выводе в файл/pipe и при `NO_COLOR`; не принуждать `force_terminal=True`.
- Не записывать JSON/таблицы в error diagnostics; ошибки остаются в stderr с существующими кодами выхода. Исключения не превращать в «успешный» отчёт.
- UTF-8 box drawing разрешён, но должен быть читаемый текстовый fallback для сред без цвета; не требовать настоящего интерактивного TTY.

### 5. Совместимость

- **Никаких** изменений в алгоритмах `Recovery.plan`, `retry`, `accept`, `cancel`, карантина, миграции, GitHub POST/GET, Scheduler, SQL.
- Не изменять статус/фазы и не нарушать идемпотентность операций.
- `db check`, `db backup`, `db restore`, `db upgrade` и основной `queue/status` — оставить как есть, если не требуется минимальная корректировка общего CLI.
- В отчёте явно отметить смену default output с JSON на таблицу; для машинных потребителей документировать обязательный `--json`.

## Автоматические тесты

Добавить изолированные тесты отображения без обращения к реальному GitHub и без Codex:
1. JSON-режим парсится через json.loads, имеет исходные ключи и новые repository/issue_number, не содержит ANSI.
2. Default-режим рисует структуру и нужные значения для 0, 1 и нескольких Issue; 2+ причины одной Issue выводятся одной строкой/группой.
3. Номер Issue не путается с issue_id для двух репозиториев с одинаковым номером.
4. В пустом карантине отображается понятное сообщение.
5. Идентичность Issue и операция retry показываются корректно; несколько operations (completed/in-progress).
6. В non-TTY/pipe и при NO_COLOR нет ANSI; для TTY цветов достаточно, но без зависимости от конкретных escape кодов в тестах.
7. Тесты всего CLI (argparse) для --json на каждой соответствующей команде и ошибок/exit code.
8. Регрессия существующих tests/test_recovery.py; весь pytest suite.
