# V2.3.C — доработка публичного OUTPUT

Дата: 2026-11-07. Ветка: `V2_3_IMPLEMENTATION`.
Основание: `docs/v2.3-c-output-improvements.md`.

## Изменения

- `execution.py`: OUTPUT содержит отдельную кликабельную ссылку `Result commit`
  из SQLite только при подтверждённом push и полном валидном SHA. PR также
  представлен явной ссылкой; состояние показано отдельно.
- `services.py`: наблюдение PR больше не перезаписывает уже подтверждённый
  результат публикации. Последующий успешный push обновляет его штатным путём;
  неудачная повторная публикация сохраняет предыдущий подтверждённый SHA.
- `output.py`: публичное представление локальных Markdown-ссылок проверяет
  принадлежность именно worktree текущего execution, включая `resolve()`.
  Подтверждённые файлы получают blob-ссылки с URL-кодированием пути, остальные
  ссылки заменяются подписью. Поддержаны angle destinations, пробелы, Unicode,
  специальные символы, скобки и суффиксы `:line:column`. Внешние URL и
  относительные ссылки сохраняются. Для голых путей в типичных локальных
  каталогах (`/home`, `/Users`, `/root`, `/tmp`, `/var`, `/workspace`, `/mnt`)
  остаётся имя файла. Это минимальная обработка путей, не универсальный фильтр
  секретов или произвольного текста.
- `git.py`: наличие обычного файла проверяется через локальный `git ls-tree`
  строго в дереве сохранённого коммита, с literal pathspec. Каталоги и symlink
  не считаются подтверждёнными файлами. После удаления worktree используется
  существующий checkout; клонирования, fetch и GitHub GET для проверки нет.
- `tests/test_output.py`: восемь регрессионных проверок, включая параметризацию.

Оригинальный stdout в `workspace/results` не изменяется. Схема SQLite,
канонические состояния, фоновые GitHub-запросы и V1 не менялись. Формирование
OUTPUT не запускает Codex и не создаёт PR; подтверждённое неизменное тело
не публикуется повторно. Ручное исполнение корректно показывает подтверждённый
коммит опубликованной ветки без вызова Codex.

### Хранение оригинала и безопасная публикация

Новый `error_diagnostics.py` сериализует исходное исключение в JSON внутри
существующего `error_log.error_message`: тип, исходный `str(exc)`, traceback
с причинной цепочкой, операция, доступные stdout/stderr/returncode каждого
исключения цепочки. Секреты и пути здесь не маскируются, искусственного лимита
длины нет. Старые текстовые записи остаются читаемыми. DDL, восемь таблиц
и версия схемы v1 не изменены.

`GitError` сохраняет вывод и код завершения Git, включая clone; при таймауте
сохраняются реально полученные частичные потоки и исходное исключение.
`GitHubError` сохраняет статус HTTP и локальные потоки gh, включая ошибки
запуска, таймауты и некорректный JSON ответа. Retry-правила GitHubAdapter
не менялись. INPUT/OUTPUT payload не копируется в публичную диагностику.

Executor передаёт само исключение и текущий этап в Publisher. Первичная
ошибка записывается **до** salvage commit/push; сбой salvage получает отдельную
запись с этапом `salvage`. Аналогично сохраняются ошибки публикации,
синхронизации OUTPUT и recovery. Одноразовая отметка запуска Codex остаётся
прежней; ошибка подготовки не запускает Codex или PR. Именование веток
по issue_number не менялось, включая #11 → `codex/task-0011` при другом issue_id.

ERROR строится только из разрешённых кодов и шаблонов причин, проверенных
этапов, числового execution_id, repository и валидированной base branch.
Произвольное содержимое `error_message` вообще не читается для публикации.
Неизвестная ошибка получает безопасный шаблон; traceback/stderr/текст
исключения не публикуются. Дополнительные поля допускаются по узкой грамматике;
известные префиксы токенов и чувствительные имена скрываются. URL userinfo,
Authorization, private key и абсолютный путь не проходят эту грамматику.
Размер ERROR ограничен 4000 символами; вторичные сбои отмечаются отдельно.

stdout Codex по-прежнему сохраняется оригиналом в `workspace/results/<id>.txt`.
Для failed execution он не добавляется к публичному OUTPUT: аварийный stdout
может содержать те же приватные данные, что stderr. Успешный OUTPUT сохраняет
существующую обработку результата и ссылок. Это не универсальный фильтр
секретов в произвольном успешном ответе модели. stderr/traceback туда не
подмешиваются. `status/queue` показывают только error_code/error_stage;
`debug_operations` сохраняет прежний набор безопасных полей, независимо от
режима debug. Отказы approve сохраняют исходное исключение локально,
на GitHub передаётся контролируемая сводка.

### stderr и права доступа

stderr Codex направлен в безымянный TemporaryFile на диске с правами 0600.
Это устраняет блокировку на заполненном stderr pipe и не накапливает stderr
в RAM во время работы. После ненулевого завершения/прерывания полный
захваченный текст считывается для SQLite; на этом этапе сериализация требует
RAM пропорционально объёму. stdout и stdin обслуживаются через communicate,
включая таймауты ожидания и SIGTERM/SIGKILL при остановке. Отдельный служебный
дескриптор supervisor сообщает о невозможности запустить сам Codex, чтобы
выдать `codex_start_failed`, не анализируя непроверенный stderr. Нового общего
лимита времени Codex не вводилось.

Отсутствующий поток обозначается null; пустой захваченный поток — пустой
строкой. Текст stderr декодируется как UTF-8 с replacement для некорректных
байтов (это текстовая диагностика, не архив бинарного потока). При падении
самого координатора безымянный временный stderr не является долговечным
архивом; recovery честно фиксирует прерванное исполнение без выдуманного вывода.
Сохранение диагностики предполагает доступный диск и работоспособную SQLite.

Новые каталоги диагностики/результатов/БД создаются с 0700; БД, results,
временные файлы stderr и SQLite WAL/SHM защищены 0600. Существующая управляемая
БД и sidecars ужесточаются до 0600. Существующие родительские каталоги не
переименовываются и не chmod-ятся; если родитель БД доступен другим
пользователям, выводится локальное предупреждение без диагностических данных.
Оператор отвечает за права уже существующих каталогов и резервных копий.

Схема v1 требует непустой issue_id у error_log. Поэтому poll-ошибка без
достоверной связанной зарегистрированной Issue сохраняется в защищённый
`workspace/diagnostics/poll-errors.jsonl` с проектом, repository, операцией
и оригиналом ошибки. Фиктивная Issue/ERROR-задача не создаётся; Runtime
выводит только безопасную фразу о неуспешном poll. Это решение сохраняет
совместимость без непринятой миграции. Такие локальные файлы, как и БД,
могут содержать секреты и не предназначены для Git/PR.

### Идемпотентность ERROR

Подтверждённый ERROR POST устанавливает `error_report_sent` только после ответа
GitHub; повторные обращения и recovery его не дублируют. Сериализация вызовов
в Publisher защищает от параллельной публикации. Перед POST в error_log
фиксируется `error_report_attempt`. При подтверждённом HTTP отказе появляется
`error_report_rejected`, позволяющий штатную повторную публикацию.
При ответе без достоверного HTTP статуса, иной неопределённой ошибке или
падении между попыткой и подтверждением автоматический повтор блокируется
устойчивой записью попытки/`error_report_uncertain`. Это выбирает минимальный
риск дубля без дополнительных опросных GET и без повторного Codex.
В таком случае ERROR может отсутствовать: оператор проверяет Issue на GitHub
и SQLite вручную. Автоматического определения доставки по комментариям нет.
Для подтверждённого успешного ответа остаётся прежний `error_report_sent`.

### Осознанный локальный просмотр

Следующая команда предназначена только для доверенного локального терминала:
она **может вывести секреты**. Путь необходимо взять из database в конфигурации.
Она не выполняет GitHub-запросов и открывает БД только для чтения:

```bash
.venv/bin/python - /absolute/path/to/state.sqlite <<'PY'
import json
import sqlite3
import sys
from pathlib import Path
with sqlite3.connect(Path(sys.argv[1]).resolve().as_uri() + '?mode=ro', uri=True) as db:
    for row in db.execute('SELECT id,issue_id,execution_id,error_stage,error_code,error_message '
                          'FROM error_log ORDER BY id'):
        print('Record / issue / execution / stage / code:', *row[:5])
        try:
            diagnostic = json.loads(row[5])
        except ValueError:
            print(row[5])  # совместимость со старыми текстовыми записями
        else:
            print('Operation:', diagnostic.get('operation'))
            print(diagnostic.get('traceback', ''))
            for error in diagnostic.get('exceptions', []):
                print(error['type'], error['message'])
                print('Return code:', error.get('returncode'))
                print('stdout:', error.get('stdout'))
                print('stderr:', error.get('stderr'))
PY
```

## Исправление ложного сокрытия ветки в OUTPUT

Доработка по `docs/v2.3-c-public-field-fix.md`, 2026-11-08.
Причина: неограниченный поиск `sk-` в `public_field()` совпадал с окончанием
`task-` и скрывал обычные `codex/task-0013` и `manual/task-0013`.
Теперь короткий префикс OpenAI проверяется в начале строки либо после символа,
не являющегося ASCII-буквой или цифрой. Разделители `/`, `_`, `.`, `-`
считаются границами токена; обычная граница `\b` здесь не подходит из-за `_`.
Проверки GitHub-префиксов и token/password/secret/authorization сохранены.
Узкая грамматика структурированных полей и проверка `branch_name()` сохранены:
валидность Git-ветки сама по себе не разрешает публикацию секретоподобного имени.

Добавлены 33 регрессионных случая: автоматические, ручные и пользовательские
имена; синтетические legacy/project/service-account OpenAI и GitHub PAT
форматы; токены внутри составных имён; чувствительные имена, локальные пути

## Файловая работа Codex и отсутствие diff

Доработка по `docs/v2.3-c-codex-file-work-and-no-diff.md`, 2026-11-08.
Ветка `V2_3_IMPLEMENTATION`; **V2.3.C остаётся открытым**.

В каждый новый вызов Codex добавлена постоянная инструкция работать с файлами
подготовленного worktree для задач изменения репозитория и кратко описывать
результат. Явные указания пользователя о предмете работы имеют приоритет:
инструкция запрещает произвольный выбор имени/языка при неоднозначности и
создание файлов для явно текстовых задач. Commit/push/branch/PR остаются
ответственностью диспетчера. Approved snapshot и GitHub INPUT не меняются,
права, sandbox и конфигурация Codex не расширяются. Manual mode не запускает
Codex; потреблённый execution повторно не исполняется.

`Publisher.publish()` до push получает актуальные Git refs и сравнивает
подготовленное дерево результата с merge-base и деревом целевой базы.
Это исключает ложный diff из-за одних лишь новых изменений в базе.
`git add --all` учитывает staged/unstaged/untracked файлы и удаления; индекс
может измениться при проверке, но файлы не удаляются и не перезаписываются.
Унаследованный diff корректирующей группы учитывается. Сравнение не требует
GitHub GET. Ненулевые коды Git кроме штатного diff=1 дают `git_diff_failed`,
а не ложное отсутствие изменений. Как и при обычной публикации, fetch и push
не являются атомарными относительно параллельного изменения удалённой базы.

Пустой результат даёт `OperationError`: `no_changes_for_pr`, этап
`publication`, операция `git.diff`. ERROR содержит разрешённую причину
«Codex completed successfully but made no file changes. PR was not created.»
без сырого stdout. Исходное исключение и путь `results/<execution_id>.txt`
записаны в локальном JSON `error_log.error_message`; stdout сохранён отдельно
в прежнем файле. Нет push новой пустой ветки, PR, ложного `Result commit` или
`Push confirmed: True`. Состояние обычного исполнения остаётся `error`.

`Publisher.fail()` пропускает salvage для `no_changes_for_pr`. Для остальных
ошибок сохранение выполняется только при реальных изменениях индекса либо
HEAD, отличающемся от последнего подтверждённого результата (или initial SHA
до первой публикации). Поэтому чистый исходный HEAD больше не публикуется
аварийно как результат. Незакоммиченные правки и локальные неопубликованные
коммиты сохраняются штатно; первичная и вторичная ошибки записываются отдельно.
Ранее подтверждённый результат не стирается при сбое. Повторная публикация
подтверждённого результата при уже совпадающей базе сверяет существующий PR
без лишнего push; новый PR при доказанном пустом diff не создаётся.

Добавлены 16 регрессионных случаев в `tests/test_file_work_no_diff.py`:
состав промпта и неизменность snapshot; только stdout; создание и удаление
файла, в том числе staged; staged/unstaged/untracked/committed результат;
база, догнавшая результат до первой публикации и после подтверждения;
ошибки Git diff; чистый HEAD и неопубликованный коммит при salvage;
унаследованный diff корректирующей группы при успехе и сбое. Проверяются
сохранность локального stdout, отсутствие его секретоподобного содержимого
в публичных комментариях, отсутствие GitHub-запросов при пустом сравнении,
идемпотентность ERROR/OUTPUT/recovery и запрет повторного запуска Codex.
Прежние тесты manual mode, salvage с незакоммиченными файлами, retry,
маскирования, веток `codex/task-00NN` и жизненного цикла сохранены.
