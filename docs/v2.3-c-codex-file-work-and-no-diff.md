# V2.3.C — файловый результат Codex по умолчанию и диагностика отсутствия изменений

**Статус:** задание агенту. **Ветка:** `V2_3_IMPLEMENTATION`. **Репозиторий:** `heroicrealm/CodexAgent`.

## Основание: реальные интеграционные проверки

В `heroicrealm/CodexAgentPlayground`:
- Issue [#15](https://github.com/heroicrealm/CodexAgentPlayground/issues/15), запрос `write helloworld in java`: Codex завершился с exit 0, но ответил только программой в stdout (`workspace-v2/results/1.txt`); файлового diff нет.
- Issue [#16](https://github.com/heroicrealm/CodexAgentPlayground/issues/16), `write hello world in java`: то же самое (`results/2.txt`); диспетчер запушил ветку с исходным SHA `d81d1f0235e9b8e0f25ef23bd3ed4c7c2a4422ce`, совпадающим с `main`. В OUTPUT появилось `Result commit` и `Push confirmed: True`, затем состояние `error` с общим `execution_failed`, PR не создан.
- Issue [#17](https://github.com/heroicrealm/CodexAgentPlayground/issues/17), `write hello world in java Into file hello.java`: Codex создал `hello.java`, появился PR [#18](https://github.com/heroicrealm/CodexAgentPlayground/pull/18), Issue перешла в `review`. Это подтверждает, что Codex исполнял буквально поставленную задачу, но диспетчер ожидает изменённый файловый результат.

**Цель:** дать Codex предсказуемую установку работать с файлами и не выдавать исходный HEAD за новый результат при нулевом diff.

## A. Постоянная инструкция Codex на работу в подготовленном worktree

1. Передавая задание в `ProcessRunner.run()`, добавлять к approved title/body/INPUT **короткую постоянную инструкцию диспетчера**, независимую от текста Issue, без изменения сохранённого approved snapshot и Github INPUT.
2. Смысл инструкции: «Работай непосредственно в предоставленном рабочем каталоге проекта; при задаче, подразумевающей реализацию или изменение кода, создавай/изменяй соответствующие файлы. Не ограничивайся выводом исходного кода в финальном сообщении. Кратко сообщи, что изменил. Не выполняй git commit/push/branch/PR — ими управляет диспетчер».
3. **Явное намерение пользователя имеет приоритет по предмету работы**: не придумывать произвольное имя файла или язык при неоднозначной постановке; не создавать файлы, если задача явно требует только объяснение, анализ или вывод текста без изменений. Для задач на изменение репозитория предполагать редактирование реальных файлов, даже если пользователь не написал «into file».
4. Инструкция должна действовать при повторном запуске на новом execution, включая корректирующие Issue; никогда не переисполнять существующий execution. Не расширять права/sandbox Codex и не изменять его конфигурацию.
5. Добавить тесты, проверяющие состав промпта (утверждённая постановка не потеряна, системное наставление есть), режим `run_codex:false` и отсутствие новых GitHub-запросов.

## B. Отсутствие изменений для PR — отдельная диагностируемая ошибка

1. После успешного Codex (exit 0) **до публикации новой ветки без изменений** определить, есть ли реальный файловый diff, достаточный для PR, относительно актуальной целевой базовой ветки. Учитывать staged, unstaged, untracked (включая необходимые новые файлы) и уже опубликованные изменения корректирующей группы. Для новых Issue без изменений не выполнять бессмысленный push; не создавать PR. Проверку проводить без GitHub GET; обычные Git-операции допустимы. Не проводить опасную очистку или перезапись файлов.
2. Для нулевого diff использовать структурированную `OperationError` с кодом **`no_changes_for_pr`**, этап `publication`, операция `git.diff` или `publisher.publish` (выбрать один стабильный вариант), понятная безопасная причина: `Codex completed successfully but made no file changes. PR was not created.` Привести `REASONS` и отображение операции в `public_error()` в соответствие.
3. В локальном `error_log.error_message` оставлять оригинал исключения и контекст, в том числе доступный stdout/ссылку на локальный файл `workspace-v2/results/{execution_id}.txt`. Не копировать сырой Codex stdout в публичный ERROR и не обходить маскирование секретов. Оригинальный stdout результата сохраняется в прежнем файле.
4. **Не показывать `Result commit` при отсутствии нового опубликованного результата**; не подменять его `initial_commit` / SHA базовой ветки и не утверждать `Push confirmed: True` только из-за попытки аварийного salvage. Если уже был ранее подтверждённый опубликованный результат той же группы, не терять его при неуспешной последующей попытке; соблюдать существующий контракт подтверждённых SHA и ручных задач.
5. Проверить совместимость с `Publisher.fail()`: сейчас salvage `commit_push()` на ошибке может автоматически запушить старый HEAD и снова поставить `result_commit`/`push_completed=1`. Для `no_changes_for_pr` **не выполнять бессмысленный salvage**, но оставить необходимое безопасное сохранение реальных незапушенных изменений при других ошибках. Не терять первичную причину и отдельные вторичные ошибки.
6. Не менять модель состояний: отсутствие результата остаётся `error`, не `review` и не `done`. Один слот Codex, запрет повтора после потребления попытки, идемпотентность ERROR/OUTPUT сохраняются.
7. Учесть крайние случаи: создан и затем удалён файл (нет итогового diff), изменённый файл, untracked файл, только stdout, изменённый файл без коммита, существующий результат корректирующей группы, пустой diff относительно обновившейся базы, ошибки Git при сравнении (не должны ошибочно классифицироваться как `no_changes_for_pr`).
8. Избегать изменения поведения `manual-running` (`run_codex:false`) и успешного publish/retry, в котором уже подтверждён результат. Никаких изменений SQLite DDL, V1, или лишних GitHub запросов.

## Критерии приёмки и тесты

- `write hello world in java` (без явного «into file») формирует промпт, мотивирующий Codex создать файл; интеграционно проверить новой Issue в Playground после выполнения задачи агентом. Не рассчитывать, что текстовая инструкция гарантирует действия LLM: отсутствие diff всё равно обрабатывается как ошибка.
- Смоделировать Codex exit 0 с чистым worktree: `no_changes_for_pr`, безопасный ERROR, нет PR, **нет push исходной ветки**, нет `Result commit`, `Push confirmed: False`; stdout сохранён локально; повторный запуск Codex не происходит.
- Смоделировать реальные изменения файлов: новый коммит, push и PR, переход в `review`, корректный URL/result SHA.
- Тесты regressions для корректировок, manual mode, salvage/retry, ERROR idempotence, последующего poll/recovery, безопасного маскирования, состояний, существующих имен веток `codex/task-00NN`.
- Полный набор тестов V2; `compileall` и `git diff --check`. Обновить `docs/v2.3-c-report.md`, указать проверки, ограничения и число тестов.

Работать в `V2_3_IMPLEMENTATION`; **не создавать PR и не закрывать этап V2.3.C**. После реализации пользователь отдельно проверит сценарий на реальной Issue.
