# Задание Codex-агенту — реализация V2.4.2

**Репозиторий:** heroicrealm/CodexAgent
**Рабочая ветка:** V2_4_2_RECOVERY_RECONCILIATION
**База:** CODEXAGENT_V2 (V2.4.1 уже принята)
**Нормативное ТЗ:** [docs/v2.4.2-spec.md](v2.4.2-spec.md)

## Цель

Реализовать безопасную внешнюю reconciliation после db restore: глобальный recovery_required снимается только после полной сверки, конфликтные Issue остаются в индивидуальном карантине, его снятие только админ-командами. Особое внимание — управляемый retry: архивирование прежней попытки, отказ от локальной работы, discovered и новое GitHub approve.

## Важные правила работы

1. Перед изменением кода изучи V2.4.1: db_guard.py, storage.py, schema.sql, __main__.py, models.py, services.py, execution.py, runtime.py, github.py, git.py, cleanup.py, locking.py и tests/test_db_guard.py. Не используй код V1 из default branch.
2. Работай только в указанной ветке, не делай PR/merge и не переходи на другую ветку без указания пользователя.
3. Соблюдай ВСЕ инварианты утверждённого ТЗ, не упрощай безопасность ради зелёных тестов. Если обнаружена принципиальная неоднозначность, задокументируй выбранное консервативное поведение и блокируй действие, а не додумывай результат.
4. Не изменяй GitHub тестового/боевого репозитория во время автоматических тестов; использовать fake gh и локальные Git remotes.
5. Не запускать настоящие Codex exec при автоматическом тестировании.

## План реализации

### Этап I — SQL и admission
- Версионируй строгую проверку DDL для V2.4.1 и V2.4.2; добавь version=2 и metadata.format_version=2.
- Реализуй явный db upgrade с защитой InstanceLock, before-upgrade backup, откатом на сбое.
- Реализуй новые recovery_quarantine, recovery_events, recovery_sessions, recovery_execution_archive, recovery_operations, recovery_approval_reset с FK/индексами.
- Обнови bootstrap актуальной схемой; restore поддерживает проверенные зарегистрированные backup схем 1/2 и мигрирует только staging.
- Выдели минимальный административный Storage API, которым можно менять данные при recovery_required=1, не ослабляя обычный Storage.connection.

### Этап II — полная сверка
- Создай отдельный recovery.py; read-only сбор GitHub/Git и классификацию, без долгих SQL транзакций.
- Реализуй db recover --dry-run и db recover. Любой неполный обязательный сбор — глобальный отказ с сохранением recovery_required.
- Не путай существование PR/branch с доказательством авторства/принадлежности. Проверяй также закрытые Issues, удалённые/disabled проекты; не разрешай автоматическое выполнение после включения непроверенного проекта.
- Пересчитывай зависимости контейнеров по действующим правилам. Действующие карантины нельзя удалять автоматически.
- Применяй план и снимай барьер в одной SQL транзакции.

### Этап III — тотальная защита
- Проверь все способы выполнения и публикации: Scheduler, Executor.recover/execute, Publisher.publish/phase_output, PollService, Runtime, Cleanup, standalone CLI.
- Quarantine — независимый запрет на side effects, без нового issues.state. Quarantined child блокирует зависимый контейнер без дублирования записи карантина родителю.
- Допусти нормальную работу независимых безопасных заданий.

### Этап IV — ручные команды
- db recovery status read-only.
- accept: только достоверно установленный внешний PR и допустимый переход; без фиктивных executions.
- cancel: только безопасная отмена с аудитом.
- retry: реализуй *persistent resumable state machine*, до удаления worktree обязательно записать диагностический архив и намерение. Нейтрализовать старое approve и наблюдать его отсутствие. Очистить только принадлежащие Issue локальные артефакты без remote изменений. Сохранить диагностику и FK при удалении executions. Перевести в discovered. Опубликовать диагностический комментарий с operation_id, защита от повторов по маркеру/ID. Снять карантин в самом конце. Новое approve через GitHub обязательно.
- Падение на любой фазе должно оставлять запись об операции и запрет запуска; повтор команды продолжает безопасно, без удаления чужой работы и двойного POST.

### Этап V — качество, отчёт
- Unit и интеграционные тесты с fault injection, в т.ч. таблицы уникальности, FK, обрывы между публикацией комментария и commit, stale approve.
- Проверить обратную совместимость с V2.4.1; прогнать полный pytest, compileall, git diff --check.
- Обновить README (upgrade, recover, status, accept/retry/cancel, безопастное восстановление), docs; записать отчёт в docs/v2.4.2-implementation.md.
- В ответе перечисли изменённые файлы, командные строки тестов и результаты, риски и ограничения, и отдельно список сценариев для ручного тестирования.

## Критерии приёмки

- После restore запуск заблокирован, пока нет полной сверки.
- Локальный конфликт не мешает независимым Issue после успешного recover.
- Quarantine снимается только пользователем и сохраняется при рестартах.
- Retry безопасно архивирует прежнее исполнение ДО разрушительных действий, удаляет его из активного учёта, очищает только локальные артефакты, возвращает discovered, публикует дедуплицированный комментарий, требует новое approve.
- Нельзя обойти карантин через Executor.recover, publish, cleanup, специальные CLI или контейнеры.
- Схема мигрируется явно и строго; ошибочный или чужой backup отклоняется.
- Автотесты зелёные. PR создавать только после ручной приёмки пользователем.

**Важно:** спецификация нормативна; при расхождении этого плана с ТЗ приоритет имеет docs/v2.4.2-spec.md.
