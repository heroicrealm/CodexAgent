# Codex Task Dispatcher

Этапы 1–2: локальная инфраструктура диспетчера на Python 3.12+ для Ubuntu и WSL2,
конфигурация нескольких независимых проектов и чтение GitHub Issues с сохранением
очереди в SQLite. Реализованы однократный опрос `poll` и отдельный цикл `poll --watch`.
Подтверждение заданий, запуск Codex, worktree, публикация отчётов и PR пока не реализованы.
Команда `start` запускает инфраструктурный процесс, но не включает polling автоматически.

## Установка

Работайте в Linux filesystem, например `~/projects`, а не `/mnt/c`.
Установите Python 3.12+ и соответствующий пакет `python3-venv` средствами Ubuntu.
Установите Git, GitHub CLI и Codex CLI, добавьте их в PATH и выполните `gh auth login`.

```bash
python3 --version
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
cp config/config.example.yaml config/config.yaml
codex-dispatcher --config config/config.yaml doctor
codex-dispatcher --config config/config.yaml start
codex-dispatcher --config config/config.yaml status
codex-dispatcher --config config/config.yaml stop
codex-dispatcher --config config/config.yaml start
codex-dispatcher --config config/config.yaml stop --force
```

`--config` указывается перед командой. По умолчанию используется `config/config.yaml`
относительно текущего каталога. Ошибки возвращают exit code 1; успешные операции и
`status` (как running, так и stopped) — 0. Doctor выводит PASS/WARN/FAIL и возвращает
1 при наличии FAIL. Он проверяет Python, запуск `git --version`, `gh --version`, `codex --version`, `gh auth status` и доступ на
запись в каталоги. Doctor может создавать локальные каталоги и временный файл;
запускает Codex только с `--version`, не выполняет задания и не изменяет внешние
репозитории. Команды имеют таймаут 15 секунд; ошибки запуска, таймауты и ненулевые
коды возврата дают FAIL. Вывод внешних CLI и тексты исключений не сохраняются.

SSH Agent проверяется отдельно от API-аутентификации `gh`: наличие `SSH_AUTH_SOCK`,
доступность агента и загруженного ключа через `ssh-add -l` (таймаут 15 секунд).
При SSH remote отсутствие рабочего агента/ключа даёт FAIL с инструкцией запустить
`ssh-agent` и выполнить `ssh-add` локально. Парольную фразу dispatcher не запрашивает
и не сохраняет. При известных HTTPS/local remote отсутствие агента даёт PASS;
неисправный настроенный агент — WARN. Ключ в агенте не гарантирует доступ к репозиторию.

Протокол определяется read-only командой `git -C <workspace>/<project.id> remote -v`
для существующих клонов включённых проектов; проверяются fetch и push URL.
Если клона/remote ещё нет или команда не удалась, протокол неизвестен (WARN),
а отсутствие агента не считается FAIL. Поле `owner/name` протокол не задаёт.
SSH config, Git `insteadOf`/`pushInsteadOf`, remote helpers и будущий способ клонирования
могут менять фактический транспорт и не разрешаются этой проверкой. Пользователь
должен сверить эти настройки самостоятельно. Текущий remote самого диспетчера
не определяет транспорт целевых проектов.

## Конфигурация

Полный пример: [config/config.example.yaml](config/config.example.yaml).
`projects` — обязательный непустой массив; для каждого проекта обязательны `id`,
`enabled` (boolean), `repository` (`owner/name`), `base_branch`, `task_label`.
Идентификаторы уникальны и содержат буквы, цифры, `_`, `-`; первый символ — буква
или цифра. Отключённые проекты сохраняют независимые настройки.

Значения по умолчанию: интервал 30 секунд, параллелизм 1, политика `wait`, grace timeout 5 секунд, авторизация
`gh`, executable `codex`, каталоги `~/codex-dispatcher/workspace` и
`~/codex-dispatcher/logs`. Интервал, параллелизм и `dispatcher.force_grace_timeout_seconds` — положительные целые числа.
Другие shutdown policy и auth method отклоняются. Интервал применяется к `poll --watch`; команда `start` пока не запускает polling.

Относительные workspace/logs разрешаются относительно каталога YAML; `~` раскрывается
для текущего пользователя, затем путь канонизируется. Переменные окружения в YAML
не подставляются. Пути внутри `/mnt` отклоняются, включая ссылки в `/mnt/c`.
`codex.executable` — имя в PATH либо путь к бинарнику, без shell-аргументов.
Не помещайте токены в YAML: используется существующая авторизация `gh`.

## Жизненный цикл и данные

Один диспетчер на workspace: постоянный файл `.runtime/lock` защищён `flock`, поэтому
одновременные start не создают дубликаты. Идентичность процесса проверяется по PID и
времени старта из `/proc`, совместно с блокировкой; сигнал отправляется через Linux
pidfd для защиты от повторного использования PID. Требуется Linux с поддержкой pidfd.
Разные workspace позволяют запускать независимые диспетчеры; для одного workspace
используйте один конфиг. Start ждёт готовность до 5 секунд.

`stop`, SIGTERM и SIGINT запрещают новые операции и ждут завершения активных.
Ожидание намеренно не ограничено таймаутом. Параллельно можно выполнить `stop --force`:
SIGUSR1 переключает остановку в принудительный режим, посылает SIGTERM группам
дочерних процессов, ждёт до `dispatcher.force_grace_timeout_seconds` (по умолчанию 5),
затем посылает SIGKILL оставшимся группам и ждёт исчезновения всех живых членов.
Если группа завершилась после SIGTERM, SIGKILL не отправляется. Проверяется вся
группа через `/proc`, включая потомков уже завершившегося родителя; zombie не
считаются активными процессами (их освобождает родитель или системный reaper).
Операции контракта Lifecycle запускаются в отдельных process groups; будущие
интеграции должны сохранять эту принадлежность, не демонизировать дочерние команды.
Lifecycle удерживает непосредственного ребёнка, включая zombie, до завершения группы,
чтобы PID/PGID не мог быть переиспользован. Затем ребёнок освобождается, группа
удаляется из учёта; повторная отмена не посылает сигналы старым PGID. Только Lifecycle
должен вызывать wait/poll/waitpid для возвращённого Popen; внешнее освобождение
лидера прерывает отмену с ошибкой до отправки сигналов. Методы submit/drain/cancel
вызываются последовательно одним scheduler, request_stop меняет только флаги.
Самовольные setsid/setpgid и демонизация выходят за гарантии: Lifecycle не разыскивает
и не сигналит такие процессы по сохранённым PID из-за риска PID reuse. Для произвольных
демонов потребуется отдельная cgroup. Процессы в непрерываемом kernel sleep могут
задержать завершение даже после SIGKILL; состояние не очищается преждевременно.
На этапе 1 daemon не принимает реальных заданий. Контракт с активными процессами
проверяется тестами отдельно от daemon.

При обычном завершении состояние удаляется. После SIGKILL/сбоя ядро освобождает lock,
а stale state не считается работающим процессом и заменяется при следующем start.
SIGKILL невозможно обработать; он не является поддерживаемым способом остановки
будущих активных заданий. Используйте `stop --force`, чтобы очистить дочерние процессы.

Каталоги workspace, logs и `.runtime` получают права 0700, runtime-файлы и журнал
создаются с правами 0600. Структура проектов: `workspace/<id>/tasks/`; это граница
для будущих каталогов отдельных задач. JSONL журнал `logs/dispatcher.jsonl` содержит
UTC timestamp, level, event и опциональные project/task. Логируются только события
жизненного цикла, без YAML, переменных окружения и вывода внешних CLI. Ротация пока
не реализована. Используйте выделенные приватные каталоги, принадлежащие пользователю.
Локальный конфиг, workspace, runtime, логи и `.env` исключены из Git; произвольные
абсолютные пути вне репозитория также не следует добавлять в Git.

## Проверки и архитектура

```bash
python -m pip install -e '.[test]'
bash scripts/test.sh
python -m pip wheel --no-deps . -w /tmp/dispatcher-wheels
```

`bash scripts/test.sh` запускает pytest и `compileall` для `src` и `tests`.

Тесты используют временные каталоги, stub/mock внешних CLI и безвредные локальные
процессы. Проверяются YAML и несколько проектов, doctor и ошибки авторизации/прав,
одновременный start, stale PID, restart, graceful drain, force и дочерние процессы.
Реальная авторизация GitHub и реальные задания для тестов не нужны.

`config` отвечает за immutable настройки, `runtime` — за блокировки и Lifecycle,
`logging` — за JSONL, `github` — за чтение и нормализацию Issues, `storage` — за SQLite,
`github.sync` — за синхронизацию проектов, `codex` — граница будущего
адаптера, `cli` объединяет команды. `Lifecycle.submit()` ограничивает параллелизм и
отклоняет новые операции после запроса остановки; scheduler следующих этапов должен вызывать
его только для разрешённых конфигурацией проектов. Планировщик запуска заданий здесь отсутствует.

### Этап 2: опрос GitHub Issues

Авторизуйте CLI: `gh auth login`, затем проверьте `gh auth status`.
В конфигурации каждого проекта задайте `labels.ready` и
`security.allowed_authors` (список GitHub login). Пустой список запрещает все
Issues. Старые `task_label` и `base_branch` поддерживаются; предпочтительны
`labels.ready` и `default_branch`. Путь CLI задаётся `executables.github`.
Комментарии не служат командами. Необязательная целевая ветка указывается в
теле Issue отдельной строкой `Target branch: feature/name` (также принимается
`Целевая ветка: feature/name`); иначе используется default/base branch проекта.
Повторные поля и недопустимые имена веток приводят к ошибке опроса проекта.

```bash
codex-dispatcher --config config/config.yaml poll
```

Команда только читает GitHub и сохраняет SQLite в
`paths.workspace/.runtime/tasks.sqlite3`; JSON содержит `discovered`, `updated`,
`unchanged`, `revoked`, `skipped_untrusted`, `errors`. При ошибках код выхода 1.
Для проверки двух проектов добавьте второй enabled-проект со своими repository,
labels и allowlist, выполните команду дважды: повторный опрос не создаёт записей.
Опрос читает все открытые Issues постранично, чтобы замечать снятие ready-метки;
PR исключаются. Проекты применяются отдельными атомарными транзакциями только
после полного успешного обхода. Ошибка проекта не отзывает его очередь.

`tasks.snapshot` — текущий согласуемый снимок, `observed` — последнее наблюдение,
`history` — журнал изменений. Значимые поля: GitHub id, title, body, author,
target branch. Метки и updated_at не изменяют версию. Подтверждение хранится в
`approved_version`; изменение содержимого или отзыв готовности сбрасывает его
для незапущенной задачи. `Store.reset_confirmation(repo, number, expected_version)`
предоставляет атомарную операцию для этапа 3. Для running/review и терминальных
состояний снимок и состояние сохраняются, новые данные попадают в observed.
Возврат ready не запускает такие задачи повторно.

`SyncService.run(threading.Event)` предоставляет останавливаемый цикл с интервалом
`dispatcher.poll_interval_seconds`; Event прерывает ожидание между опросами.
Один запрос ограничен 30 секундами, максимум три попытки; backoff и серверные
Retry-After/reset ограничены 60 секундами. Служба этапа 1 пока не запускает этот
цикл автоматически. Нет исполнения Codex, записи GitHub или команд одобрения.

Проверка всех этапов: `pip install -e '.[test]'`, затем `bash scripts/test.sh`.
Тесты используют подменённый gh и временную SQLite, без GitHub-токенов.

Для непрерывной ручной проверки: `codex-dispatcher --config config/config.yaml poll --watch`.
SIGINT/SIGTERM прекращают цикл; текущий ограниченный сетевой запрос и его
повторы завершаются перед выходом, ожидание интервала прерывается сразу.
Один repository допускается только в одном проекте во избежание конфликта политик.
