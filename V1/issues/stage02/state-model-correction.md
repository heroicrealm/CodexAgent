# Исправление модели состояний — этап 2

Репозиторий: `heroicrealm/CodexAgent`. Рабочая ветка: **`STAGE_02`** (не создавать `STAGE_04`, не изменять `main`). Основание: утверждённое пользователем уточнение модели состояний от 24.10.2026, корректирующее прежнюю формулировку `docs/stages/stage02.md`.

## Утверждённая модель
- `discovered`: подходящий Issue получен с GitHub, ожидает ручного подтверждения.
- `pending`: пользователь подтвердил актуальную версию Issue; задание ожидает запуска Codex CLI.
- `running`: исполнение начато.
- `review`: агент завершил работу, ожидается ручная приёмка.
- `done`: результат принят.
- `revoked`: Issue утратил готовность (закрыт, снята ready-метка, автор больше не доверен) до начала исполнения; подтверждение аннулировано.
- `rejected`, `failed`, `cancelled`, `interrupted`: сохранить в соответствии с общим ТЗ, без автоматического повторного запуска терминальных попыток.
- **Не использовать `approved`**: подтверждение выражается переходом `discovered → pending`. Не трактовать `pending` как неподтверждённое.

## Переходы при polling
1. Новый подходящий Issue → `discovered`, `available=1`; повторный опрос не создаёт дубль.
2. Значимое изменение Issue в `discovered` → обновить снимок/версию, остаться в `discovered`.
3. Значимое изменение Issue в `pending` до запуска → обновить снимок/версию, **сбросить подтверждение и вернуть в `discovered`**. Только updated_at, метки без утраты ready, комментарии и другие незначимые метаданные не сбрасывают подтверждение.
4. Потеря готовности в `discovered` или `pending` → `revoked`, `available=0`, подтверждение сброшено; восстановление ready → `discovered` (без автоматического подтверждения), одна существующая запись.
5. `running`, `review`, `done` и прочие состояния начатых/терминальных попыток: не переписывать исполнительный snapshot, не менять состояние при polling, наблюдаемые изменения хранить отдельно; не перезапускать автоматически.
6. Подтверждение пользователем (`discovered → pending`) относится к этапу 3; на этапе 2 предоставить согласованный атомарный контракт/метод для будущего подтверждения и проверки версии, **не добавляя CLI approve**. При переходе в `pending` должен быть фиксирован подтверждённый номер версии (например, `approved_version`); не создавать противоречия между состоянием и версией.
7. Обеспечить безопасную миграцию уже существующей SQLite: ранее созданные `pending` без подтверждения → `discovered`; прежние `approved` с валидным подтверждением → `pending`; прежние `revoked` сохранить, при возвращении готовности переводить в `discovered`. Не потерять историю, версии, снимки и терминальные состояния. Учесть существующие записи `pending` с `approved_version` и без него.
