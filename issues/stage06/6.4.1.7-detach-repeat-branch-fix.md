# 6.4.1.7 — исправление повторного запуска после Detach (Issue #41/#42)

## Контекст и подтверждённый дефект
Ветка разработки: `STAGE_06_04_01_07`; целевая интеграция: `STAGE_06_04_01`. Ручная проверка на CodexAgentPlayground: после снятия `codex-ready` во время исполнения Codex завершается естественно, worktree удаляется и отсутствует в `git worktree list`, каталог `tasks/issue-42` пуст. При повторном добавлении `codex-ready` Issue #41 и #42 получают `failed/git_operation_failed`, Codex не запускается. Команда `git branch --list 'codex/issue-42'` подтверждает оставшуюся локальную ветку. В `src/dispatcher/workspace.py::prepare` обычный путь выполняет `git worktree add -b <branch> ...`, что конфликтует с существующим ref. Это сильная гипотеза; агент обязан воспроизвести и подтвердить точную ошибку Git, не считать гипотезу доказательством.

## Утверждённая политика
Повторное утверждение после **завершённого Detach** создаёт новую итерацию с актуальной базовой ветки проекта (`origin/<base_branch>`, после fetch), **без наследования незакоммиченных или закоммиченных результатов отменённой попытки**. Старую историю локальной ветки сохранять в архивном ref с уникальным именем, привязанным к предыдущему attempt/iteration. Никакого `reset --hard`, удаления ветки или переписывания чужих refs. Сохранение старой ветки не означает автоматическое использование её HEAD для нового запуска.

## Требования к реализации
1. Найти и воспроизвести первопричину на сценарии `running → ready removed → natural exit → detached → ready added/approved → pending → prepare`; включить полезную, безопасную диагностику Git stderr/операции без утечки секретов.
2. Различать новый запуск после Detach, повторную доработку отклонённого PR (`rejected → pending`, `repeat_branch`) и обычную первую попытку. **Не менять семантику** существующего PR retry: после rejected сохраняется предусмотренная ветка и история. Не полагаться только на наличие `work_branch` или локального ref для классификации; использовать durable state/stop_requests/attempt/iteration с проверкой идентичности.
3. Для новой итерации после Detach: проверить завершённость Detach, безопасность cleanup и отсутствие активного worktree/процессов; подтвердить принадлежность локальной ветки данной задаче, соответствие ожидаемому имени, репозиторию и предыдущей попытке. Если ref существует и подтверждён — безопасно переименовать его в уникальный архивный ref (предусмотреть уже существующий архив и повторный запуск после частичного сбоя). Если ref отсутствует — не создавать искусственный архив. При неоднозначности или чужом ref — fail closed с отдельным понятным кодом причины и без изменений чужих данных.
4. Выполнить fetch актуального `origin/<base_branch>`, проверить наличие и корректность base, создать worktree с рабочей веткой от актуального base. Проверить отсутствие конфликтов с удалённой веткой и ранее опубликованными результатами; не перезаписывать remote branch. Если старый remote branch существует, определить безопасную политику с учётом branch ownership и запрета на force push: при невозможности безопасного продолжения — явная ошибка, а не поздний push failure. Учитывать пользовательские `base_branch`/`branch_name` и многопроектность.
5. Сохранить атомарность насколько возможно: повторный `poll`, crash/restart между архивированием ref и `worktree add`, повторная попытка после ошибки не должны терять refs, создавать дубликаты архивов или обходить проверки. Не очищать архивы автоматически вместе с worktree.
6. Убедиться, что после успешного повторного запуска штатно выполняются Codex, публикация и весь жизненный цикл; при новой отмене снова работает natural drain/cleanup. Не менять контракт timeout, emergency, `stop`/`stop --force`.
7. Добавить автоматические регрессионные тесты на реальном временном Git repo: подтверждённый сценарий #42, отсутствие локального ref, наличие старого ref, уже существующий архив, конфликт/чужая ветка, частичный сбой и restart, remote branch conflict, PR rejected retry, кастомные имена веток, повторный Detach, изоляция проектов. Проверять что новый HEAD равен свежему base и отменённые изменения не наследуются.
8. Обновить ТЗ/implementation report этапа 6.4.1.7 и описание ручной проверки. Выполнить `scripts/test.sh`, `git diff --check`, сообщить реальные результаты и ограничения.

## Критерии приёмки
- После удаления worktree и сохранения локальной ветки повторное `codex-ready` запускает Codex без `git_operation_failed`.
- Новый worktree основан на актуальной базовой ветке; прежняя история доступна в архивном ref; отсутствуют destructive операции над чужими ветками.
- Ошибки владения, remote conflicts и неопределённость дают понятный отказ до запуска Codex.
- Не сломаны PR retry, Detach, timeout, emergency и force-stop; тесты проходят.
