**Репозиторий:** heroicrealm/CodexAgent

**Основание:** утверждённая пользователем схема состояний; Issue #4 и docs/stages/stage02.md.

## Утверждённая модель

- `discovered` — допустимый Issue обнаружен, ожидает ручного подтверждения.
- `pending` — пользователь подтвердил актуальную версию, задача ждёт запуска Codex CLI.
- `running` — исполнение агентом.
- `review` — результат ожидает ручной приёмки.
- `done` — результат принят.
- `revoked` — готовность утрачена до запуска (закрыт Issue, снята ready-метка, автор не соответствует allowlist).
- `rejected`, `failed`, `cancelled`, `interrupted` — сохраняются с прежним смыслом.

**Состояние `approved` исключить:** оно дублирует `pending`. Не использовать его ни в новых записях, ни в переходах, ни в тестовых сценариях.

## Обязательные переходы

1. Новый подходящий Issue: создать одну запись со статусом `discovered`, `available=1`, без подтверждения.
2. Подтверждение (реализация команды approve относится к этапу 3): `discovered → pending` с фиксацией подтверждённой версии; не выполнять автоматическое подтверждение при polling.
3. Значимое изменение title/body/target_branch/других согласованных полей до подтверждения: обновить снимок, увеличить версию, оставить `discovered`.
4. Значимое изменение в `pending` до запуска: аннулировать подтверждение и вернуть в `discovered`. Изменения только метаданных/комментариев не должны сбрасывать подтверждение.
5. Потеря готовности в `discovered` или `pending`: `revoked`, `available=0`, подтверждение сбросить. Повторная готовность: `revoked → discovered` без дублирования записи, даже если содержимое изменилось.
6. `running`, `review` и терминальные состояния не менять из-за polling; исполняемый снимок неизменен, новое наблюдение сохранять отдельно. Не запускать завершённые задачи повторно.
7. `pending → running → review → done` — целевой контракт будущих этапов; на этапе 2 не реализовывать запуск Codex или приёмку.
8. Сохранить атомарность SQLite, идемпотентность, историю и безопасное поведение при неполном опросе.
