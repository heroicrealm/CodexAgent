# Замечания к реализации STAGE_03 — исправление после первичной проверки

**Репозиторий:** heroicrealm/CodexAgent  
**Ветка:** STAGE_03 (не main)  
**Основное задание:** #8  
**Спецификация:** docs/stages/stage03.md

## 1. Надёжная привязка GitHub-команд к версии Issue (приоритет: высокий)
В src/dispatcher/queue.py проверка времени события GitHub относительно локального history.created_at чувствительна к рассинхронизации часов и задержкам polling. Разработать и реализовать проверяемый механизм привязки approve/reject к актуальной версии Issue без доверия к локальному времени как единственному доказательству. Сохранять проверку actor и allowed_authors, first-writer-wins, защиту от edit/revert, ready remove/restore, повторной доставки событий и fail-closed при невозможности доказать актуальность. Не допускать принятия старой команды после новой версии. Описать алгоритм и его границы в документации. Добавить тесты на clock skew, одинаковые секунды, задержку polling, смену версии и повторную доставку.

## 2. Диагностика отклонённых GitHub-команд (приоритет: высокий)
В src/dispatcher/github/sync.py и queue.py команда может оказаться неподтверждаемой после Store.apply. Обеспечить понятный результат оператору: причину отклонения (недоверенный actor, устаревшая версия, отсутствие доказательства и т.п.), запись в лог без секретов и безопасный способ повторить команду для актуальной версии. Не оставлять управляющие метки в состоянии, создающем бесконечные повторные попытки или случайное подтверждение при следующем polling. Не стирать чужие метки и не менять SQLite решение при сбое GitHub. Добавить тесты.

## 3. init_message (приоритет: средний)
В src/dispatcher/initialization.py сохранять в init_message конкретную безопасную причину ошибки, если она доступна (например, 403, отсутствие доступа к репозиторию, ошибка создания метки, ошибка сохранения конфигурации). Не записывать токены, персональные пути с секретами или сырой вывод gh. Успех очищает сообщение; ошибка одного проекта не блокирует остальные. Если сохранение YAML невозможно, корректно отразить ошибку в CLI/логах, не утверждать, что она сохранена. Добавить тесты.

## 4. doctor: точность сообщения о правах (приоритет: низкий)
Проверка doctor остаётся строго read-only. Разделить «репозиторий доступен», «GitHub сообщает push/maintain/admin» и «возможность создавать/изменять метки подтверждена». Не выдавать PASS, который можно ошибочно трактовать как доказательство права управления метками без записи. Отобразить WARN при непроверяемых правах и подсказать init. Добавить тесты вывода.
