# Задание Codex-агенту — V2.4.1

База: `CODEXAGENT_V2`. Рабочая ветка: `V2_4_1_SQLITE_GUARD_RECOVERY`.
Основной контракт: [docs/v2.4.1-spec.md](../docs/v2.4.1-spec.md).

## Порядок работы
1. Сверить текущую реализацию V2.3 и состояние схемы SQLite, команд CLI, инициализации, открытия Store, фонового daemon и тестов. Убедиться, что работа выполняется в указанной ветке. Не использовать устаревший код `main` как архитектурный образец.
2. Кратко зафиксировать исследование в `docs/v2.4.1-implementation.md`: текущая схема и версия, все места открытия БД, возможные неявные создания, существующая блокировка и инициализация. Перед необратимыми изменениями определить инварианты и порядок перехода существующей V2.3 SQLite.
3. Реализовать предзапускную проверку существующей SQLite. Обычный запуск не должен создавать базу при опечатке в workspace. Явный bootstrap оставить для первого запуска, не ломая текущий сценарий чистой установки.
4. Реализовать независимую идентичность экземпляра и проверку совместимости без связывания с фиксированным списком проектов: добавление, удаление и возвращение проектов, а также смена project.id при неизменном repository разрешены. Не путать данные разных repositories.
5. Реализовать `db check` строго read-only, `db backup <destination>` через SQLite Backup API и безопасный `db restore <backup-file>` с проверкой остановки процессов, staging, backup старого состояния, проверкой WAL и предотвращением повторного исполнения из старого snapshot. Не объявлять restore успешным до всех проверок.
6. Дополнить README эксплуатационной инструкцией и матрицей восстановления, не включая rebuild из GitHub (V2.4.2).
7. Добавить unit/integration тесты для всех критериев раздела 10 ТЗ, запустить весь существующий тестовый набор, compileall и git diff --check. Сохранить детальный отчёт о результатах.
8. Сделать коммиты в рабочую ветку, предоставить перечень файлов, тестов, открытых рисков. Не создавать PR до отдельного запроса после ручной приёмки, не объединять ветки.

## Обязательные условия
- При любой ошибке проверки — отказ от исполнения и отсутствие изменения исходной БД.
- Состояния issue/PR/контейнеров не угадывать; при сомнении блокировать повторный запуск.
- Ни одна диагностическая операция не создаёт новую SQLite и не отправляет команды GitHub.
- Данные исключённых из конфига проектов не удалять.
- Для существующей V2.3 базы обязательна документированная недеструктивная регистрация metadata перед включением строгой проверки.
- Не утверждать гарантий восстановления, которые невозможно подтвердить тестами.
- Не использовать реальные токены, репозитории и пользовательские данные в автоматических тестах.
